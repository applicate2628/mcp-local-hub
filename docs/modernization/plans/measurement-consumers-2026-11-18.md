## 3. CMake trace: от инструмента до ограниченного ответа

### 3.1. Производитель и потребитель

**Таблица 3. Фактический путь R12.**

| Граница | Реализованное действие | Источник |
|---|---|---|
| Hub → сервер vcpkg | Manifest задаёт `stdio-bridge`, команду `mcphub vcpkg`, daemon default:9138 и клиентский `/mcp`. Скрытая команда запускает MCP-сервер через стандартные потоки | [2](#ref-2) |
| Регистрация → вызов | `vcpkg_cmake_trace`: схема аргументов разрешается один раз; каждый запрос проходит JSON → map → строгую проверку, затем повторное декодирование в `Args` | [3](#ref-3) |
| Прямой потребитель | Единственный найденный производственный вызов `cmaketrace.Trace(ctx,args,DefaultDeps())` находится в handler этого инструмента | [3](#ref-3) |
| Файл → записи | Проверяются отмена, наличие абсолютного пути и обычный файл. Поток читается через ограничения байтов/строк и декодируется в `[]Record`. Внешний CMake здесь не запускается | [4](#ref-4) |
| Записи → индексы → выборка | Сначала по всему принятому префиксу строятся include-chain и индексы файлов/строк. Затем `file` / `command` сужают Records на месте и применяется `max_records` | [4](#ref-4) |
| Result → клиент | Владелец проверяет размер до полного кодирования; возвращается полный JSON либо минимальная проекция. JSON преобразуется в строку MCP `TextContent`; `StructuredContent` здесь не устанавливается | [5](#ref-5) |

MCP — Model Context Protocol, протокол контекста модели; JSON — JavaScript Object Notation, текстовый формат данных; stdio — стандартные потоки процесса. Индексы намеренно относятся ко всему принятому входу: маленький `max_records` или узкий фильтр не уменьшают начальные чтение, декодирование и индексирование. Кеша трасс, индексов или готовых ответов в прослеженном пути нет. Прогретый файловый кеш измерительной серии не является кешем результата приложения. Реальная частота повторных запросов одного файла неизвестна.

### 3.2. Три разных ограничения

**Таблица 4. Пределы входа, результата и публикации.**

| Участок | Значение | Смысл |
|---|---:|---|
| Входные байты | 256 МиБ | Допускаемый объём; один дополнительный байт различает точный предел и превышение |
| Одна строка JSON Lines | 4 МиБ | Ограничение записи при потоковом чтении |
| Материализованные записи | 2 000 000 | Независимый предел количества |

МиБ и КиБ — двоичные мебибайты и кибибайты; значения заданы константами, а не получены измерением [4](#ref-4), [5](#ref-5). Абсолютный regular-file вход не является закреплённым за каталогом интерфейсом #627 и не получает автоматически его гарантий идентичности или запрета перехода по ссылкам.

### 3.3. Что в действительности означает сохранённая серия

В repeated/50k создаются 50 000 синтетических записей одного файла с последовательными номерами строк. Внутренний Result содержит 1 000 Records и один объект `FileLines` с 50 000 номерами; `input_incomplete=false`, `truncated=true`. Проектор целиком исключает `include_chain`, `records`, `executed_lines`, `files_in_trace`. Счётчики исключений соответственно **0 / 1000 / 1 / 1**, а `result_projection.complete=false`. Счётчик `executed_lines` относится к объектам `FileLines`, не к отдельным номерам строк. Это вывод из точного проектора и существующего контрактного случая, без нового запуска [5](#ref-5), [6](#ref-6).

Поэтому историческая медиана **0,245 мс** — цена проверки допуска и публикации минимальной проекции уже подготовленного Result. Она не измеряет передачу клиенту даже 1 000 Records. Медианы остальных независимых серий: разбор **84,260 мс**, файл + Trace + индексы **99,811 мс**, файл → Trace → ограниченный JSON **100,140 мс**, по десять образцов; Windows/amd64, Go 1.27.4, прогретый файловый кеш, последовательная нагрузка, `GOMAXPROCS=4`. У всей матрицы есть только пробный однократный запуск, а не десять образцов каждого случая [6](#ref-6).

Не измерены проверка аргументов, внешняя оболочка MCP, транспорт, клиент, конкуренция запросов, реальные трассы и пик памяти. Независимые медианы нельзя вычитать как точную стоимость индексов. `B/op` — суммарные выделенные байты на операцию, а не одновременно удерживаемая память.

Шесть производственных Git-объектов файлов совпадают между #624 и master: `cmaketrace.go`, `parse.go`, `projection.go`, `open_regular_posix.go`, `open_regular_windows.go`, `publicresult.go`. От измеренного `87bf2fe` до `251fb4f` изменялся только каталог доказательств. Это подтверждает соответствие выбранного исходного пути; исторический запуск не объявляется проверкой всего master.

### 3.4. Следующий вопрос

Сначала определить, нужны ли пользователю выбранные записи и раскрытые аргументы большой трассы, когда глобальный индекс заставляет исключить все коллекции. Нынешнее поведение документировано; без продуктового требования это не новый дефект. Если такие данные нужны, решение относится к приоритетам ограниченного ответа у существующего владельца: ускорение parser само по себе их не вернёт [7](#ref-7).

Для отдельно подтверждённой проблемы удержания памяти есть минимальный Go-кандидат: после индексов, фильтра и ограничения результата очищать неэкспортируемый хвост исходного массива Records. Сейчас сужение среза и фильтр на месте оставляют массив и ссылки за новой длиной. Это свойство владения данными, а не измеренный выигрыш. Очистка добавляет проход, не освобождает сам массив и не убирает пик во время разбора/индексирования; сравнение должно отдельно учитывать удерживаемую память после сборки мусора, пик и полную задержку [4](#ref-4), [8](#ref-8). Изменение не выполнено.

## 4. Relay: конфигурация, процесс и нагрузка

### 4.1. Кто действительно создаёт Relay

В реестре шесть адаптеров с `relayStdio: true`: **Antigravity, Zed, Aider, Pi, Pochi, Zencoder**. Все включаются по выбору; установочные адаптеры по умолчанию — Claude Code и Codex CLI — используют обычный HTTP-маршрут без Relay. Это число классов адаптеров, не число установленных клиентов или процессов. Фактические конфигурации пользователя и работающие клиенты в этом аудите не наблюдались [9](#ref-9).

Все шесть записывают допущенный абсолютный `RelayExePath`. Zed использует `relay --url`; остальные поддерживают также `relay --server S --daemon D`. Установочный запрос, маршрутизаторы LSP — Language Server Protocol, протокола языкового сервера — и Serena передают данные тем же адаптерам. Путь фиксируется до записи конфигурации. Отдельный агрегат `mcphub-hub` предназначен для HTTP-клиентов и исключает Relay-адаптеры; он не является уже реализованной заменой всех их подключений [10](#ref-10).

Codex shared-stdio replay умеет формировать `command="mcphub"` без абсолютного пути. Однако поиск по производственным Go-исходникам не нашёл вызывающих мест для `RelocateSharedStdioEntry` / `writeAdoptSharedStdioSnapshot`; обнаружены определения, интерфейс и подготовка данных воспроизведения. Этот код не посчитан седьмым действующим производителем. Если его подключат, разрешение команды через PATH потребует отдельной проверки [11](#ref-11).

### 4.2. Два разных маршрута Windows

**Таблица 5. Стоимость запуска зависит от фактической точки входа.**

| Маршрут | Последовательность | Учитываемые процессы и проверки |
|---|---|---|
| Обычная сгенерированная конфигурация | `RuntimeMcphubExecutable` выбирает текущий Product либо аутентифицированный образ supervisor; проверяется роль, затем путь передаётся адаптеру | При обычном установленном наборе запускается непосредственно `mcphub-product/mcphub.exe`; загрузчик автоматически не добавляется |
| Явный `mcphub.exe relay` из корня выдачи | Корневой launcher проверяет набор и ограничение обновления, создаёт Product приостановленным, проверяет исходный процесс, разрешает выполнение и ждёт завершения | Живут launcher и Product; измерять нужно оба. Его допуск до выполнения — отдельный контракт |
| Измерительный опыт #626 | `exec.CommandContext` запускает явно указанный обычный Go executable с `relay --url` | Измеряется этот файл; поиск установленного Product и корневой launcher автоматически не выполняются |

Роль Product требует графическую подсистему Windows **2** и соответствующую идентичность VERSIONINFO. Корневой launcher имеет консольную подсистему **3** и не проходит как Product. Проверки выбора пути выполняются при составлении конфигурации; ветка CLI — интерфейса командной строки — `relay --url` их заново не вызывает. Поэтому нельзя начислять обнаружение исполняемого файла каждому RPC — удалённому вызову процедуры — или приписывать прямому запуску проверку корневого launcher перед возобновлением процесса [12](#ref-12).

### 4.3. Время жизни и очереди

Один запуск команды создаёт один экземпляр Relay для одного адреса; в нём удерживается один идентификатор сессии. Процесс обслуживает соединение клиента, а не создаётся на каждый `tools/call`. Число окон/проектов, активных записей конфигурации, перезапусков и длительность сессий исходниками не установлены.

В master до получения идентификатора сессии POST выполняется синхронно. После этого допускается до **64** конкурентных обработчиков POST. Строка читается до ожидания допуска, поэтому в памяти может быть также прочитанный ожидающий запрос и входной буфер. Максимальная входная строка — **1 МиБ**. Это предел числа обработчиков, не общий предел памяти очередей [13](#ref-13).

Отдельный GET получает SSE — Server-Sent Events, события сервера через HTTP; он и POST-ответы разделяют сериализованную запись stdout. Медленный получатель, ожидание допуска, HTTP-соединения, серверная очередь и материализация ответа образуют разные участки задержки. JSON-ветка читает ответ через `io.ReadAll`; общий предел события legacy SSE не задан параметром в этом пути. Предел входа 1 МиБ не следует выдавать за общий предел ответов [13](#ref-13).

При штатном EOF — конце ввода — master ждёт POST, отменяет GET, ждёт слушателя и делает попытку DELETE с отдельным двухсекундным контекстом. Статус DELETE игнорируется: одно завершение Relay не доказывает принятие удаления сессии сервером. Стандартный HTTP-клиент имеет тайм-аут 60 секунд. Это факты кода, не результаты нового опыта [13](#ref-13).

**#629 остаётся отдельным исправленным контрактом.** Он сохраняет ошибки вывода, объединяет независимые ошибки и получает право прервать stdin от его владельца через main/CLI. Минимальный control #626 вызывает только `HTTPToStdioRelay.Run` с `os.Stdin` и не содержит этой композиции. Его нельзя считать готовой заменой исправленного входа #629. Три производственных файла `relay.go`, CLI `relay.go`, `main.go` различаются между #629 и master/#626; семь проверенных файлов производственного пути #626 и master совпали. Равенство этих файлов не переносит старую серию на #629 или установленный Product [14](#ref-14).

### 4.4. Что измеряет #626

Процессный опыт использует **1/8/32** child-процесса, каждый с **16 последовательными запросами по 1 КиБ**; параллельность возникает между процессами. Запуск каждого измеряется до правильного initialize, затем получаются снимки памяти после готовности и после нагрузки. Это замкнутый цикл: следующий запрос следует за ответом. Он не устанавливает задержку при независимом потоке поступлений, насыщение 64 обработчиков или p99 под перегрузкой [15](#ref-15).

Локальный benchmark — иной опыт: 32 вызова на жизненный цикл, размеры 1/64 КиБ, JSON/POST-SSE и общий прогретый transport. Его аллокации включают тестовые сервер и генератор нагрузки. Fixture отвечает **405 на GET**, поэтому не измеряет живой длительный канал уведомлений GET-SSE и его повторное подключение. Исправленные положительный и три отрицательных контроля от 18 ноября проверяют правильность измерительной проверки, а не дают новую серию производительности [15](#ref-15), [16](#ref-16).

|---|---|---|
| Размер executable | Байты конкретного файла сборки | Не память процесса и не размер всего установленного набора |
| Working set | Текущие резидентные страницы процесса | Сумма процессов может повторно учитывать общие страницы; снимок не является пиком |
| Private working set | Текущая частная резидентная память | Не вся резидентная память и не private commit |
| Private commit / `PrivateUsage` | Частная память, под которую ОС приняла обязательство предоставить обеспечение | Не число страниц, находящихся в физической памяти |
| Время CPU за жизнь child | Процессорное время child в пользовательском режиме и ядре | Не скорость потребления CPU в простое; сервер и генератор сюда не включены |
| `B/op` | Выделенные байты Go на операцию benchmark | Не удерживаемая или пиковая память установленного процесса |

Определения Windows закреплены первичной документацией Microsoft [17](#ref-17). Observer #626 использует `PROCESS_MEMORY_COUNTERS_EX2` только по явному включению, проверяет доступность и раздельно выдаёт частный рабочий набор и commit. Наличие этого наблюдателя не превращает историческую сумму рабочих наборов в измерение частной памяти [16](#ref-16).

Следующий сравниваемый Go-вариант должен сохранять выбор адреса/manifest, точные аргументы, распознавание клиентской записи, идентичность и правила поставки/обновления, stdio-режим Windows, сессию, ошибки, отмену и завершение. Нынешний маленький control поддерживает только `--url` и не является готовым устанавливаемым Product. Нельзя глобально подменить `RuntimeMcphubExecutable`, поскольку он обслуживает и другие запуски Hub [12](#ref-12), [14](#ref-14), [18](#ref-18).

## 5. Наблюдение процессов: поля, частоты и полномочия

PID — идентификатор процесса; PPID — идентификатор его родителя; RSS — Resident Set Size, здесь размер рабочего набора памяти; IPC — межпроцессное взаимодействие. WMI — Windows Management Instrumentation, инфраструктура управления Windows; WMIC — её командная утилита; CIM — Common Information Model, общая информационная модель; COM — Component Object Model, компонентная модель объектов.

### 5.1. Измеренные функции и реальные вызовы

Приобретение последнего исключено из таймера. Это чтение диагностических данных, не создание нового полномочия управлять процессом [19](#ref-19).

### 5.4. Конкретный следующий контракт `lookupProcess`

**Пять из шести мест вызова** используют только PID/признак результата. Общая Windows-функция после netstat всё равно вызывает WMIC ради RAM и uptime. Но шестое место — fallback status — читает все поля. Удалять вторую часть общего контракта без решения о fallback нельзя [25](#ref-25).

**Таблица 10. Все шесть мест вызова: два места в kill-пути показаны одной строкой.**

| Функция | Что читает | Как сейчас трактуется `!ok` |
|---|---|---|
| `portHeldByOurDaemonForPortArm` | PID + ok | Отказ подтвердить владение; далее существуют отдельные image/parent/scheduler проверки |
| `supervisorOwnedPortPIDOutcome` | PID + ok | При существующей функции — unknown; структурно отсутствующая функция — surface unavailable |
| `killDaemonByPortOutcome`, начальный запрос и опрос после kill | Сначала PID + ok, затем только ok | В начале — no listener; после taskkill — released/killed |
| `waitPortReleasedAfterPIDKill` | PID + ok после уже успешного доверенного PID/tree kill | `!ok` возвращает успех ожидания; структурно отсутствующая функция на POSIX даёт отдельное предупреждение |
| `enrichStatusWithRegistry`, fallback | **PID, RAM, uptime, ok** | Нет обогащения; используется при отсутствующем batch-результате |

**Условие и конкретное последствие потери информации:** ошибка/тайм-аут netstat и успешное отсутствие подходящей строки возвращают одинаковый `false`. Ownership-пути трактуют его консервативно, но два пути ожидания освобождения могут отобразить неудачное наблюдение как отсутствие слушателя/освобождение порта. У `waitPortReleasedAfterPIDKill` ранее успешный kill остаётся отдельным фактом; ошибка наблюдения не опровергает его и не доказывает освобождение порта. Ошибка только WMIC, напротив, оставляет `PID,0,0,true`. Это установленные исходниками ветви, без заявления нативного воспроизведения или одинаковой опасности каждого caller. Код существовал до #628 и им не введён [25](#ref-25), [26](#ref-26).

Опрос имеет паузу **200 мс после завершившегося запроса**, а не гарантированную частоту 5 Гц. В legacy-пути каждый subprocess ограничен 45 с и `WaitDelay=2 с`; две последовательные команды не разделяют один общий scalar-дедлайн.

Публичный владелец `LoopbackPortOwnerPIDContext` / snapshot уже существует, но прямое переподключение меняет контракт: он различает найденный PID, отсутствие и ошибку, проверяет диапазон порта, получает контекст; Windows пока использует netstat, Linux — `/proc`, прочие платформы unsupported. Delegate с `context.Background()` сам не добавляет legacy-ограничения 45 с/`WaitDelay`. Более того, `TestMain` специально обнуляет старые hooks, чтобы тесты не обращались к действующим процессам и службам. Обход этих hooks обошёл бы изоляцию [27](#ref-27).

Поэтому минимальная правка должна совместно сохранить: PID-only получение без лишних метрик; RAM/uptime для status; явные found/absent/unknown; сроки и завершение subprocess; платформенный смысл отсутствующей возможности; тестовые seams — точки подстановки безопасных реализаций. Проверки затрагивают ownership/preflight, timeout≠absence, batch/fallback/self-PID, Windows sentinel и POSIX success-with-warning, а также `TestMain`. В этом этапе реализация и проверки не выполнялись.

### 5.5. Уже существующие владельцы и вывод для status

`HeldPIDObservation` удерживает query/synchronize-дескриптор и предоставляет identity, SID — идентификатор безопасности пользователя Windows, ожидание и закрытие. `HeldPIDJobObservation` наблюдает принадлежность Job — объекту группы процессов Windows. `HeldPIDGeneration` отдельно имеет право terminate. Оригинальные владельцы создания удерживают process/thread и данные рождения; синхронное заимствование запрещает сохранить или закрыть чужой дескриптор и прекращается при освобождении владельца [28](#ref-28).

Наличие таких объектов не означает, что любая строка status уже располагает подходящим исходным дескриптором. Возможный минимальный дизайн — одно наблюдение текущей строки в пределах операции: обязательные liveness/image/creation на одном query/synchronize handle, RAM — отдельно необязательное поле. Подходящий уже удерживаемый handle можно заимствовать только по правилам его владельца. Это архитектурный вывод, не готовая безопасная правка и не измеренное ускорение. Новый общий PID-реестр и новый владелец lifecycle из этой карты не следуют.

## 6. Конкретные следующие действия

1. **R16: контракт выбранного PID-only потребителя.** Сохранить получение метрик там, где их читают, и перестать запрашивать их только для PID там, где они не нужны. Совместно решить found/absent/error, пределы subprocess, платформенные различия и тестовую изоляцию. Изменение принимается у существующего владельца; новый глобальный реестр не требуется.
2. **R12: полезность ответа и один измерительный вопрос.** Зафиксировать требуемые данные большой трассы, разрешённый представительный вход и один критерий — задержку, удерживаемую память либо повторное чтение. Только затем сравнить текущий и минимально улучшенный Go. Сохранённый repeated/50k не повторять без этого вопроса.
3. **R09: договор о нагрузке и маршруте запуска.** Задать число одновременно работающих процессов и запросов на процесс, срок соединений, уведомления/reconnect, распределение payload и требуемую задержку. Сравнивать целиком допущенные исполняемые варианты на одном маршруте, с раздельным учётом driver/server и метрик памяти.
4. **Rust-пилот — условный следующий шаг.** Он нужен, если оставшийся дефицит подтверждён полным сценарием и минимальное Go-изменение недостаточно. Учитывать FFI — Foreign Function Interface, интерфейс вызовов другого языка, копирование, материализацию, запуск, идентичность, отмену и освобождение ресурсов. Сравнение маленькой функции или обёртки с новым child не доказывает выигрыш замены.
5. **Остальные направления не закрыты этой картой.** R10 сохраняет зависимости от WP-11E, R13 — собственный граф/журналы, R14 — согласованный снимок реестра, R15 — события; R17 — операции планировщика. Продуктовое Rust-подключение продолжается в своей параллельной работе после сверки фактически опубликованного/предоставленного исходника.

Это конкретный остаток после завершённого чтения, а не разрешение установок, платных запусков, ручной CI — непрерывной интеграции — либо объединения веток. Действующие требования к тестам и приёмке не ослабляются.
