# Конкретный план независимых работ MCPHub → Rust

**Дата:** 12 ноября 2026 года. **Статус:** proposed execution plan; ни Rust-пилот, ни переключение рабочего Хаба этим документом не объявляются выполненными.

**Цель:** пока основная ветка завершает исправления, получить воспроизводимые измерения, проверенный изолированный Rust-владелец процесса и подготовленные независимые изменения без конфликтов с текущими владельцами.

**Архитектура:** web и предметное Go-ядро сохраняются. Измерительные тесты работают на закреплённых снимках; Rust-прототипы — вне рабочего дерева и установки. Интеграция является отдельным решением после сверки обновлённых контрактов.

**Стек:** существующие Go-тесты, стандартные профилировщики, Rust и системные API; без нового COM, переписывания vendor SDK и обязательного Python для стендов. Новые зависимости/установки требуют отдельного разрешения.

**Спецификация:** [кроссплатформенный план](rust-cross-platform-plan-2026-11-12.md), [его схема](rust-cross-platform-boundaries.svg), [WP-11B–E](wp-11a-to-11f.md), [governance](../governance.md). Настоящий документ — детализация RX-пакетов, не второй roadmap и не новый реестр текущих статусов.

Для исполнителя: читать спецификацию и соответствующий блок ниже вместе. При выполнении применять `executing-plans` и проверку перед заявлениями о завершении; запуск внешних агентов, ботов и платных сервисов из этого плана не следует.

### Общие ограничения исполнения

- Не редактировать #616, активные локальные деревья, чужие PR, реальные конфигурации, задачи автозапуска и серверы. Наш #624 меняется только в его собственной ветке.
- Для каждого опыта — отдельный полный снимок исходников с его зависимостями либо изолированная копия; исходный снимок не изменяется. Не вырезать случайную часть Go-модуля с потерянными `replace`-зависимостями.
- Без установки toolchain/зависимостей: Go — локальный toolchain и имеющийся cache; Rust — закреплённый lockfile и offline-режим. Отсутствующую зависимость не скачивать молча; продолжать независимую доступную часть.
- Только собственные тестовые дети, временные каталоги и локальный HTTP-сервер. Не запускать поставщиков, модели, чужие проекты или скрытые фоновые задачи. Не открывать GUI-окна.
- Нагрузочные измерения на одном физическом хосте выполняются последовательно. Предлагаемый предел незавершённой разработки — два независимых результата, не 24 одновременно.
- Нет автоматического push/merge, переключения установки или вызова бота со стороны исполнителя. Публикация конкретных изменений сохраняет действующее разрешение и repo-gates; планирование не выдаёт новых полномочий.
- Подтверждённо ненужные собственные временные копии — в trash после сохранения единственных полезных исходников/результатов вне trash. Корзину не очищать.

### Основные риски для проверки

Потеря ответа не должна повторять операцию; поздняя ошибка не стирает полученный результат; чужой stdin/handle нельзя закрыть; unsupported нельзя превратить в успешный более слабый режим; изменение основной ветки обнуляет зависимые выводы, но не требует повторять несвязанные исследования.

- [ ] После каждой доступной нативной ОС выдать отдельный verdict: что исполнилось, что unsupported, что не проверено. Недоступный Mac не блокирует Windows-исследование, но блокирует заявление о macOS-ready.

**Готово:** исходники опыта, сравнение контрактов, native evidence и список конкретных правил владения, проверяемых Rust. В Хаб ничего ещё не подключено. Стабильность может обосновать перенос без ускорения, но не без проверки поведения.

### RX-04/read. Параллельный файловый пилот, сначала без записи

**Читайте:** `internal/api/state_read_beneath_root_windows.go`, его POSIX/платформенные реализации и существующие tests. **Интерфейс:** `ReadStateFileBeneathRootNoFollow(ctx context.Context, root string, relativeComponents []string, expectedSHA256 string) ([]byte, error)`. При последующей интеграции сверить изменения этой границы.

- [ ] Работать только в owned fixture root. Воспроизвести bounded read, удержание фактической identity, запрет перехода по запрещённым ссылкам, проверку hash и безопасную ошибку закрытия.
- [ ] Проверить замену компонента пути между шагами, symlink/reparse, недоступность прав, слишком большой файл, не-ASCII путь и отмену. Не читать секреты рабочего Хаба.
- [ ] Сравнить Go и минимальную Rust-реализацию `<scratch>/rx-file-read/` на этих сценариях и на памяти/системных вызовах. Никакого общего «filesystem framework».
- [ ] Протокол записи/rename/fsync/rollback оставить отдельной части RX-04/write (кандидат R05) после сверки фактически принимаемых WP-11D/0.4.60. Исследовать его можно заранее, но готовый writer не обещать по тестам reader.

**Готово:** один квалифицированный read-сценарий либо решение сохранить Go. Не меняются state schema, vault, установка и транзакционный owner.

### RX-05b/contract. Подготовка отказа от COM, без мутаций задач ОС

**Читайте:** `internal/scheduler/scheduler_windows.go`, `scheduler_com_windows.go`, `internal/autostart/`.

- [ ] По каждому вызову заполнить: требуемое поле/действие, текущая гарантия, документированный системный CLI, typed outcome, gap. Разделить definition и live state.
- [ ] На сохранённых безопасных XML/выходных фикстурах проверить UTF-16/UTF-8, локали, absent/denied/unavailable, неправильного владельца и изменившееся определение.
- [ ] Не объявлять query-then-run атомарным; не обходить gaps через новый Rust COM/WMI-binding, Registry Run или TaskCache.
- [ ] Подготовить отдельные маленькие изменения для чтения, запуска и разрушительных действий. Реальные create/delete/stop и смена autostart — только в последующей разрешённой приёмке у текущего владельца.

**Готово сейчас:** однозначная карта замен с проверяемыми gaps. **Не требуется Rust:** убрать COM можно у существующего Go-adapter.

### RX-07. Готовый native Grafana вместо Python-launcher

**Читайте:** `marketplace/v2/catalog.json` и будущую принимаемую схему каталога. Не публиковать изменение устаревшего v2, если текущий владелец уже мигрирует строку на v3.

- [ ] Зафиксировать тот же upstream release, exact assets/hash и сохранение CLI/stdio/tools/auth. Наличие архива — не испытание бинарника.
- [ ] Подготовить изменяемую проекцию только строки Grafana и соответствующий тест поставки; использовать существующего установщика, без нового downloader/framework.
- [ ] Раздельно проверить archive inspection и запуск. Скачивание/установка/внешний Grafana и токен этим планом не разрешаются. До разрешённой квалификации результат — готовый patch и список непроверенных условий.
- [ ] Перед PR свериться с owner каталога и подготовленными операциями; при конфликте оставить материал для него, не делать параллельную установку.

**Готово:** отдельная поставка того же upstream сервера без Python-оболочки после необходимых проверок, без rewrite сервера. Это независимое сокращение зависимости, не результат Rust.

### RX-08, RX-06 и RX-09. Когда открываем оставшиеся реализации

**RX-08a/relay и RX-08b/parser:** открывать только после соответствующего RX-01. Сравнивать одинаковые входы, лимиты, session/error/cancel outcomes и одинаковый объём работы; сначала проверить минимальное улучшение Go. Rust-relay заменяет существующий standalone-процесс, не добавляет постоянно живущего посредника. Большой parser переносится вместе с нужным представлением данных; не миллионы мелких FFI-вызовов.

**RX-06/Python native:** после нужных RX-02/03/04 переносить только наши нативные обязанности `cst_saved_field_containment_windows.py`/`cst_saved_field_transfer.py` и затронутых consumers. SDK CST/HFSS, NumPy, FastMCP и чужие серверы не переписываются. Не дублировать job/provenance/session state. Pre-main C-bootstrap получает отдельную квалификацию.

**RX-09/integration:** отдельный PR на один принимаемый путь. Перед первым изменением production — свежий delta-review основной ветки, применимых WP-11B–E/selected/0.4.60 и всех вызывающих сторон. Сохранять public API, формат состояния, OFF, выбранный набор, межпроектную изоляцию и результаты уже выполненных операций. На новое время жизни — один owner; неизвестный исход не запускается повторно другим backend.

Сравнение всего supervisor остаётся возможным после результатов пилотов, но не является обязательным расширением. R01–R24 не исчезают: полная карта остаётся в спецификации; этот документ определяет ближайшее исполнение и gates поздних кандидатов.

## 4. Единые правила измерений и приёмки

**Таблица 3. Артефакт и решение после каждого законченного опыта.**

| Артефакт | Минимальное содержимое |
|---|---|
| Воспроизведение | Source/base/test hashes, toolchain, native ОС/архитектура, команда, вход и seed/hash |
| Корректность | Функциональный результат, негативные случаи, public/typed errors, непроверенные ветви |
| Ресурсы | CPU, wall time, allocation traffic, RSS/peak RSS, дескрипторы/потоки; недоступное явно |
| Сравнение | Текущий вариант → минимально улучшенный без смены языка → Rust; одинаковые лимиты и семантика |
| Итог | `оставить Go`, `улучшить Go`, `Rust-пилот полезен`, `интеграция допущена`, `нужны данные` — с доказательствами |

Эти поля — требования к evidence, не новый инструмент или production schema. Большие сырые данные, приватные пути и секреты не коммитить.

Минимум 10 повторов/предложенные размеры служат начальной настройкой опытов, не магическими критериями. Нет заранее придуманного обязательного «x2» или процента выигрыша. Значимость определяется целевой нагрузкой и разбросом; по стабильности назвать конкретно исключённую ошибку владения. Компиляция и unit tests не доказывают гарантии ОС.

Пакетные tests, `-race` для исполняемых concurrent Go-путей, native lifecycle и FFI tests выполняются по затронутой области. Before merge действуют полные repo-gates из governance; исходные failures не превращаются в PASS и не обходятся автоматически. План не запускает CI, review bots или независимого агента. Для обязательного независимого lifecycle/security review отсутствие разрешённого review оставляет интеграцию незавершённой, но не блокирует независимые профили.

## 5. Что пока не подключаем

Не меняем рабочий supervisor, scheduler/autostart, install/recovery, секреты, каталоги пользователей и маршрутизацию. Не переносим web на Qt/GPUI, не вводим C++, новые COM-клиенты, общий platform-daemon, новый protocol SDK или production Cargo workspace заранее.

**Завершённый стенд не равен разрешённой интеграции.** Обновление upstream требует повторить только затронутые контракты. Независимый parser не ждёт всей научной приёмки; новый process-owner не включается только потому, что parser быстрее.

NablaMesh MCP и постепенная передача mesh IO остаются в отдельном [PR NablaMesh #183](https://github.com/applicate2628/NablaMesh/pull/183), не дополнительным Rust-проектом Хаба.
