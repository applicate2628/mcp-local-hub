<a id="context"></a>
## 1. Контекст

В production-файлах накопились комментарии, описывающие номера Pull Request, раунды бота, временные расследования и последовательность исправлений. Такие записи быстро устаревают, скрывают текущий инвариант и создают ложное впечатление, что старый контекст всё ещё нормативен. Одновременно простое удаление истории может уничтожить rationale безопасности, совместимости или жизненного цикла.

<a id="decision"></a>
## 2. Решение

Production-комментарий отвечает только на вопросы:

1. какой инвариант действует сейчас;
2. почему он необходим для корректности, безопасности или совместимости;
3. какие локальные условия нельзя нарушать при изменении кода.

История выбора, отвергнутые альтернативы, номера Pull Request, результаты экспериментов, migration waves и trade-offs хранятся в ADR либо hash-bound evidence artifact. Ссылка из кода на ADR допустима, когда без неё rationale нельзя кратко и точно выразить рядом с инвариантом.

<a id="boundary"></a>
## 3. Граница между комментарием и историей

| Остаётся в коде | Переносится в ADR/evidence |
|---|---|
| текущий safety invariant | хронология PR и раундов review |
| причина fail-closed поведения | список всех ранее найденных вариантов дефекта |
| формат persisted state | migration history и временные facades |
| требование owner/cancel/join | обсуждение альтернативных ownership-моделей |
| ссылка на protocol requirement | длинные выдержки из исследования и внешних обсуждений |

Нельзя заменять точный invariant общей фразой «см. ADR»: код должен оставаться понятным без чтения всей истории.

<a id="consequences"></a>
## 4. Последствия

- `history_comment` в `archcheck` становится ratchet-сигналом, а не запретом полезных комментариев.
- Cleanup исторических комментариев выполняется только после сохранения существенного rationale.
- Тесты и файлы не называются по номеру review-раунда как конечная структура; regression coverage группируется по устойчивому контракту.
- Изменение принятого rationale требует amendment к ADR, а не переписывания истории задним числом.

<a id="migration"></a>
## 5. Миграция

1. Инвентаризировать исторические комментарии через `archcheck`.
2. Классифицировать каждый комментарий как invariant, rationale, история либо мусор.
3. Для значимого rationale создать ADR/amendment.
4. Сократить production-комментарий до текущего инварианта.
5. Выполнить link/anchor checks и regression tests.
6. Удалить соответствующий baseline fingerprint в том же PR.

<a id="alternatives"></a>
## 6. Альтернативы

- **Хранить всю историю рядом с кодом.** Отклонено из-за дрейфа и шума.
- **Удалять все исторические комментарии без переноса rationale.** Отклонено как риск потери security/compatibility context.
- **Хранить историю только в Git.** Недостаточно: rationale трудно обнаружить и связать с нормативным решением.
