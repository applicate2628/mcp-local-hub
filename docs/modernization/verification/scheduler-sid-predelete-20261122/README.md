# Scheduler: SID владельца и повторная проверка перед удалением

Дата квалификации: **22 ноября 2026 года**.

**В ограниченной композиции Windows подтверждены два изменения: определение владельца по SID и отказ от удаления задачи после обнаруженного изменения её XML.** Отрицательные контроли различают прежнее и исправленное поведение. В этой же композиции успешно выполнены выбранные проверки восстановления и `BackendRunHold`, полная сборка и `go vet`.

Это результат для сохранённого исходного дерева `858812988833a84368c60fba1540ae601155fa71` с **39 заменами файлов Go через overlay**. Самостоятельное дерево текущего PR #660 не исполнялось. Нативные операции Windows Task Scheduler и приёмка всего жизненного цикла остаются открытыми.

## 2. Изменённые контракты

### 2.1. Владелец определяется по идентичности учётной записи

Короткое имя вроде `alice` не различает `DOMAIN_A\alice` и `DOMAIN_B\alice`. Исправленный код сохраняет SID текущего пользователя при построении планировщика и владельца миграции. COM-проекция списка и состояния задачи переводит владельца в SID через общий преобразователь, который также используется проверкой `RunOwned`.

Если владелец пуст или его нельзя разрешить, список и состояние возвращают ошибку недоступности без частично успешных данных. Экспорт XML сохраняет исходное представление владельца: чтение восстановительного определения не требует преобразовывать его в полномочия на запуск.

Проверка порта в API сравнивает полученный SID с текущим SID, а не с коротким именем. Отдельные проверки подтверждают отказ для одинакового короткого имени в другом домене, пустого владельца и неразрешённого имени. Сравнение полностью указанных имён больше не отбрасывает доменную часть.

### 2.2. Сохранённый снимок не заменяет проверку текущей задачи

Перед удалением существующей задачи производственный код уже сохранял её исходное определение. Однако другой участник мог заменить задачу после получения этого определения. Новая приватная функция `verifyInstallTaskDefinitionBeforeDelete` проверяет текущий XML после сохранения снимка и непосредственно перед двумя прямыми местами удаления: заменой запланированной задачи и удалением устаревшей задачи.

Удаление допускается, когда повторный экспорт вернул **непустые байты, точно совпадающие с сохранёнными, и не вернул ошибку**. Совпадающие байты вместе с ошибкой также означают отказ. Изменённое определение, исчезновение, пустой ответ и ошибка чтения не дают полномочий на удаление.

Для обязательной замены отказ запускает существующий откат ранее выполненных действий. Текущая неподтверждённая задача не получает новой компенсации, поскольку её ещё не изменяли. Для необязательного удаления устаревшей задачи сохраняется предупреждение с путём снимка; эта задача пропускается. Последующая ошибка установки не должна приводить к компенсации пропущенной задачи.

Проверка остаётся наблюдением. Между последним чтением и удалением по имени сохраняется окно гонки; одинаковый XML не доказывает идентичность поколения задачи, её дескриптора безопасности или учётных данных.

Сверены имена событий, а не только их количество.

Контроль SID сохранил три успешных случая: уже записанный SID в списке, уже записанный SID в состоянии и экспорт исходного владельца без разрешения имени. Прежний код не прошёл проверку сохранения текущего SID и шесть случаев проекции владельца; вместе с итогом корня проекции это восемь тестовых FAIL. В журнале присутствуют ожидаемые причины отказа, заданные манифестом.

Оба отрицательных контроля — подготовленные композиции со специально возвращёнными прежними производственными файлами и теми же фикстурами. Они не являются запуском неизменённого исторического дерева. `completed=true` у контрольной фазы означает, что запуск завершился и получил **ожидаемую ошибку проверки**, а не что старое поведение прошло тесты.

Единственный пропуск — `TestExecuteInstallToRollbackBackendCompatibility/unsupported_platform`. В исходнике эта ветвь предназначена для Linux и macOS; на Windows она выполняет `t.Skip("native backend is supported on this platform")` до сброса тестового режима планировщика. Этот пропуск не является проверкой нативного планировщика Windows.

Все шесть непосредственных процессов завершились; тайм-аутов и ошибок завершения в квитанциях нет. Вывод ошибок `stderr` пуст. Сборка заняла 19,472142 секунды, `vet` — 23,800557 секунды. Это длительности конкретного запуска, не производительные нормативы.

## 4. Изоляция тестовых ресурсов

Проверки COM действительно запускают установленный PowerShell, но предварительно заменяют единственное подключение к `Schedule.Service` объектами в памяти. В проверках SID также заменяется разрешение доменной учётной записи. Фикстура `Run` записывает диагностическую метку; её `Stop` и `Delete` возвращают исключение. Публичные вызовы списка, состояния и экспорта используют `withCOMRunner`. Производственные преобразование ответа, сериализация и обработка ошибки при этом остаются действующими.

Проверки миграции получают `newEntrypointTaskBackendFake` и собственный файл блокировки в `t.TempDir`. В API функция `installRecoveryPlan` подставляет планировщик в памяти и регистрирует восстановление подмены через `t.Cleanup`. Проверки владения портом подменяют наблюдения процесса, образа и состояния задачи. Снимки, манифесты и защищённые каталоги принадлежат тестам.

Проверка adopt может кратковременно открыть собственный TCP-listener на `127.0.0.1`, чтобы выбрать свободный порт; `nextBindableAdoptPortForTest` закрывает его перед возвратом. Это не обращение к внешнему сервису. Её callback установки возвращается к планировщику в памяти.

Канонический API TestMain перенаправляет конфигурации клиентов и состояние в тестовые каталоги, проверяет границы путей и подменяет обращения к действующему supervisor, автозапуску, таблице процессов и завершению процессов. Среда фиксирует `MCPHUB_E2E_SCHEDULER=none`; временные каталоги, профили и кэши находятся на диске D. Новые зависимости не загружаются.

Из рассмотренных корней не вызываются регистрация или изменение нативных задач Windows Task Scheduler. Реальное исполнение PowerShell с объектными фикстурами не заменяет нативную проверку `Run`, `RunOwned`, `Stop` и `Delete`.

## 5. BackendRunHold и сохранённая граница восстановления

В квалифицированном `internal/api/install_parsed_manifest.go` одновременно присутствуют обе необходимые части:

- Поведение master: копирование `prior.BackendRunHold` при слиянии intent и очистка hold только в копии для временной проверки записи.
- Поведение #660: условие `len(installSchedulerRecoveryTasks(err)) == 0` перед созданием доказательства завершённого отката провайдерной установки.

**Таблица 3. Точное сравнение одного производственного файла.**

| Версия | Байты | SHA-256 | Отличие |
|---|---:|---|---|
| #660 `0bdb725e…` | 143 165 | `8f04d1117f44afd7e57743b78414e76f7e7f1a10d1439ed4857bb627c5540a0b` | Guard восстановления присутствует; двух Hold-ханков нет |
| master `75dbc640…` | 143 411 | `1cca59a45b0d4eb7ddb37c5e9e98598790e29fc2e927e0d6aa3317bb0a5e605a` | Два Hold-ханка присутствуют; guard #660 отсутствует |
| Квалифицированный overlay | 143 465 | `e3b66f71a690d2be7006f5cd65e6ef38365fee01aa297ee332cdfe93de05b561` | Обе части присутствуют |

Прямой diff **#660 → overlay содержит ровно два Hold-ханка**. Прямой diff **master → overlay содержит ровно добавление guard**. Обратное удаление guard видно только при сравнении #660 с master; в проверенном входе guard не удалялся.

Эта граница нужна после ошибки `a.installPlan`: при новой провайдерной установке без попытки записи intent незавершённое восстановление Scheduler не должно превращаться в `providerInstallUnpublishedRollbackError`. Следующий владелец в `install.go` принимает такой тип ошибки как положительное доказательство и вызывает `markProviderUnpublishedRollbackSettled`. Потеря guard могла бы ошибочно пометить неразрешённые эффекты Scheduler как завершённый откат. В текущем входе guard сохранён. Его отдельный провайдерный тест не включён в рассматриваемые селекторы; повторный PASS именно этого теста не заявляется.

**Переносить только два Hold-ханка в самостоятельную ветку #660 нельзя.** В дереве `0bdb725e…` ещё нет `SupervisorBackendRunHold`, поля `SupervisorIntentFile.BackendRunHold`, требуемых методов и тестовых фикстур master. Такая частичная правка создаст ссылки на отсутствующую модель. Полная замена файла квалифицированным overlay имеет ту же проблему.

Граница публикации этого инкремента — изменения SID и проверки перед удалением на текущей базе #660. Hold-ханки и их два теста сохраняются в воспроизводимых входах квалификации. При полноценной интеграции с master требуется сохранить оба Hold-поведения вместе с guard восстановления. Здесь не выполнялись синхронизация дерева, merge, rebase или перенос зависимостей модели hold.

## 7. Границы результата

Полные тестовые наборы Go не запускались. Успешные `go build ./...` и `go vet ./...` относятся к объявленной композиции с overlay. Успешный `-race` означает отсутствие выявленных гонок в выбранном запуске и не доказывает отсутствие гонок во всей программе.

Открыты реальные `Run`/`RunOwned`/`Stop`/`Delete`, разрешение владельцев в настоящих доменах, права и учётные данные, внешняя нативная замена, отмена и срок жизни дерева процессов. Квитанции непосредственных дочерних процессов не доказывают завершение всех потомков. Проверка полного установленного продукта и независимые обязательства #628/#659 этим результатом не закрываются.

Собственное ревью исходников и фактических свидетельств выполнено. Внешнее ревью точного опубликованного коммита остаётся отдельным условием. Публикация, обратное чтение опубликованных байтов и последующая уборка рабочих копий не заявляются как результат трёх описанных фаз.


**Публичные транспортные записи.** В двух обёртках экспорта частное имя Windows-профиля заменено на `<user>`; все 36 первичных файлов Go сохранены без изменения. Архив содержит `publication/redactions.json` с контрольными суммами исходных и опубликованных вариантов. Неотредактированные обёртки сохранены отдельно вне trash; их исходные хеши в отчёте обозначают первичные варианты.
