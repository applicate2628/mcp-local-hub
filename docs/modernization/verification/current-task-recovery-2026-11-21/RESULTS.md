## 1. Исправленная граница

В исходной версии установщик сначала удалял существующую задачу, затем создавал новую. Обработчик отката для текущей задачи добавлялся только после успешного создания. Поэтому успешный `Delete` и последующий отказ `Create` оставляли прежнее определение только в памяти; откат его не восстанавливал.

Исправление относится к ветви `executeInstallToWithSymlinkConsents`, которая действительно выполняет `SchedulerTasks`. Оно не означает, что каждый современный глобальный сценарий командной строки проходит эту ветвь: обычный глобальный путь через `selectGlobalInstallExecutionPhase` использует `SkipSchedulerTasks=true`.

Теперь последовательность следующая:

1. До получения Планировщика проверяются повторяющиеся имена в плане: точные совпадения, различия регистра и необязательный начальный обратный слеш. Иначе ранее добавленный откат мог снова затронуть текущую задачу.
2. Существующий допуск `ExportXML` сохраняется: ошибка, пустой успешный ответ и противоречивое отсутствие останавливают замену.
3. Для существующей задачи требуется дополнительная возможность `XMLCreator`; её отсутствие останавливает работу до удаления.
4. До `Delete` сохраняется новый защищённый файл восстановления и проверяются прочитанные из него байты.
5. После отказа `Create` выполняется ровно один `CreateXMLIfAbsent` с прежним определением. Эта ветвь не удаляет текущую задачу и не вызывает принудительный `ImportXML`.
6. Ошибка установки возвращается и при успешной регистрации прежнего определения. При отказе восстановления возвращаются обе причины и путь к сохранённому снимку.

**Таблица 1 — поведение после ошибки создания.**

| Наблюдаемое состояние | Действие | Сохраняемый результат |
| --- | --- | --- |
| Имя свободно, регистрация старого определения подтверждена | Один вызов создания из XML | Прежнее определение зарегистрировано; исходная ошибка установки и снимок сохранены |
| Имя занято внешней задачей | Получить нативный конфликт | Присутствующая задача не обновляется; обе причины и снимок сохранены |
| Создание новой задачи применилось, но ответ потерян | Попытка восстановления получает конфликт | Присутствующая задача сохраняется; совпадение имени или байтов не считается доказательством владения |
| Восстановление отказало до применения | Вернуть обе ошибки | Снимок остаётся доступен после завершения процесса |
| Восстановление могло примениться до потери ответа | Вернуть неопределённый исход | Повторного удаления, принудительного импорта и автоматического повтора нет |

Платформенная операция использует COM — объектный интерфейс Windows — `RegisterTask` с `TASK_CREATE | TASK_IGNORE_REGISTRATION_TRIGGERS`, числовое значение 34. Флаг обновления не передаётся. Гарантия отказа при занятом имени берётся из договора самого сервиса, а не из предварительной проверки отсутствия [1, 2].

<a id="snapshot"></a>
## 2. Сохранённый снимок

Снимок — новый файл `scheduler-recovery-<случайное-имя>.json` в каталоге состояния пользователя. JSON — текстовый формат структурированных данных. В нём записаны версия формата, точное имя задачи, время получения в UTC, исходные байты XML и их SHA-256 — контрольная сумма длиной 256 бит. XML хранится как Base64, поэтому сохраняется исходная кодировка; Base64 не является шифрованием.

Запись использует существующий механизм защищённого создания с проверкой прав родительского каталога. Уже существующий файл не заменяется. Значение `created=false` не принимается за сохранение новых байтов. После записи выполняется ограниченное чтение без следования по ссылкам с проверкой контрольной суммы. Размер полного JSON, включая Base64, ограничен одним мебибайтом — 1 048 576 байт.

Файлы сохраняются при всех исходах, включая успешную замену: последующие шаги установки ещё могут завершиться ошибкой. Наличие файла само по себе не означает завершённое или неудачное восстановление. Автоматическое удаление и политика хранения по возрасту в этот срез не входят. Используемый механизм синхронизирует файл; испытаний отключения питания и доказательства долговечности записи каталога нет.

XML не содержит отдельно сохранённого пароля и не заменяет самостоятельный снимок дескриптора безопасности задачи. Новый метод не обещает восстановить эти данные и не меняет исходного пользователя запуска на текущего пользователя принудительно.

`-race` включает обнаружение гонок данных в Go. Это не доказательство отсутствия всех гонок между независимыми процессами или внешними участниками Планировщика. Использованы установленный Go 1.27.4, существующие кэши и отключённая загрузка модулей. Общий набор тестов не запускался; прежние общие FAIL и ограничения продуктовых входов не снимаются.

В тестах Windows-моста исполняется PowerShell-код с полностью подменённым участком подключения к COM. Проверяются реальная передача JSON/Base64, Unicode, флаги регистрации, вложенные коды HRESULT и отсутствие повторной попытки. Эти тесты не обращаются к реальному Планировщику; отдельная нативная проверка описана ниже.

Ожидание непосредственного дочернего процесса в новом запускающем скрипте ограничено. При превышении срока скрипт работает с сохранённым дескриптором именно этого процесса и отмечает состояние потомков как неопределённое. Срок и завершение всего дерева процессов не подтверждены.

## 4. Первоначальный неуспешный запуск

Первый контроль исходной версии также воспроизвёл 15 ожидаемых FAIL. Первый кандидат дал 26 PASS и 16 FAIL тестов, плюс FAIL пакета. Все 12 сообщений об ошибках утверждений относились к двум проверкам представления Windows-пути: продукт печатал путь через `%q`, а тест искал неэкранированную строку.

Исправлены только импорт `strconv` и два сравнения с `strconv.Quote(path)`. Проверки состояния задач, исходных байтов, обеих причин ошибки, количества операций и отсутствия ложного успеха не ослаблены. Продуктовый патч сохранён побайтно. После этой правки заново выполнены контроль и кандидат; первоначальные журналы, манифест, патчи и квитанция изменения сохранены отдельно в `diagnostics/initial` и включены в публичные свидетельства с обезличиванием путей.

## 5. Нативная проверка

Исправленный нативный проход завершён 21 ноября в 02:37:05 МСК. Два свежих определения — UTF-8 и UTF-16LE с BOM, отметкой порядка байтов — зарегистрированы через новый метод. Обе задачи отключены, скрыты, не имеют триггеров, не допускают запуска по требованию; действие указывает на заведомо отсутствующий файл. Действия задач не запускались.

Получены два отказа на повреждённые входные байты и четыре конфликта: для точного имени и варианта регистра каждой задачи. Во всех четырёх случаях полный повторный экспорт совпал с исходным побайтно. Проверены исходный SID пользователя, способ входа, смысл уровня привилегий, действие, все 109 байтов аргументов, рабочий каталог и настройки. После повторной проверки полного определения и владельца обе задачи удалены; отсутствие наблюдалось отдельно. 23 записи сохранённого журнала совпали с выводом процесса, отдельный итог подтвердил `created_tasks=2`, `deleted_tasks=2`.

Первоначальный реальный проход сохраняет FAIL: первая задача создалась, но проверка ожидала буквальный узел `RunLevel=LeastPrivilege`. Независимый наблюдатель и последующий разбор сохранённых 1702 байтов установили отсутствие этого узла. По MS-TSCH отсутствие означает LeastPrivilege [1]; остальные 17 сравнений полей прошли. Стенд исправлен только для документированного значения по умолчанию: отсутствующий узел принимается, явно пустой и иной уровень отвергаются. Имя владельца из Status разрешается в SID; строка имени не сравнивается с SID напрямую. Продуктовый патч не менялся.

Первая задача была сохранена до завершения разбора. Отдельная очистка связала пять файлов происхождения с подтверждённым первоначальным созданием, заново сверила весь экспорт, SID и отключённое состояние, выполнила один Delete и получила ErrTaskNotFound в 02:40:44 МСК. Всего в двух реальных проходах созданы три задачи и для каждой отдельно подтверждено отсутствие после очистки. Исходная задача UTF-16 первой попытки не создавалась. Проверка перед удалением предполагает отсутствие сторонних записей в эти случайные имена; атомарной проверки и удаления нет.

Ранее первая попытка подготовки остановилась до сборки и запуска стенда из-за отсутствующего переданного файла. Её отдельная квитанция сохраняет `commands=[]`, `native_task_operations=false`. Неуспешный запуск PowerShell-файла для чтения был заблокирован действующей политикой выполнения; политика не менялась. Для наблюдения использована отдельная Go-программа с существующими ExportXML и Status. [Подробная диагностика](NATIVE-DIAGNOSIS.md) и [независимое чтение исправления](NATIVE-FAILURE-REVIEW.md) разделяют подготовку, исходный FAIL, наблюдение, повтор и очистку.

Три сырых XML-файла остаются частными. Архив содержит их размеры и контрольные суммы, обезличенные квитанции и журналы; упаковщик проверяет эти байты и конфиденциальность, а вывод о нативном поведении сделан по прочитанным событиям и исходникам стенда.

Нативный стенд использует два синтетических определения. Этот опыт не является повторной регистрацией неизменённого результата `ExportXML`. Он отдельно проверяет регистрацию XML, кодировки, пользователя запуска и отказ при конфликте. Модельная проверка установщика и нативная проверка платформенной операции не объявляются полной установкой продукта с искусственно вызванным нативным отказом `Create`.

## 6. Границы выводов

Не закрыты внешняя подмена между `ExportXML` и исходным `Delete`, неопределённый результат самого `Delete`, старые обработчики отката других задач, их принудительный импорт и ошибки компенсаций. Полная атомарность установки не заявляется. Отказ при совпадении имён проверен для указанного точного имени, обычного изменения регистра и корневого префикса; все правила Unicode-эквивалентности имён Windows не квалифицированы.

Восстановление паролей, точных исходных прав объекта, других пользователей и всех способов входа требует отдельных контрактов. Подавление регистрационных триггеров не исключает срабатывания временных триггеров у произвольной включённой задачи [2]. Выполнение действий, `Run`, `RunOwned`, `Stop`, отмена и сроки всего дерева процессов остаются отдельными проверками.

Накопление файлов восстановления и удобный интерфейс их последующего разбора остаются вопросами жизненного цикла. Существующее CLI — интерфейс командной строки — при собственной ошибке вывода может заменить исходную ошибку установки; сохранённый файл не доказывает доставку всех типизированных причин по каждому внешнему каналу.
