## 2. Подтверждённое поведение

В `executeInstallToWithSymlinkConsents` перед заменой задачи теперь различаются три результата `ExportXML`: подтверждённое отсутствие, успешный непустой снимок и отказ либо противоречивый ответ. XML — расширяемый язык разметки, здесь формат сохранённого определения задачи. [2]

При ошибке экспорта, пустом успешном снимке либо непустом ответе одновременно с ошибкой текущая замена прекращается до `Delete` и `Create`. Причина передаётся через существующий `failAfterRollback`; для ошибок сохраняется проверяемая связь через `errors.Is`. Если получено прямое или обёрнутое `ErrTaskNotFound` и нет байтов определения, выполняется `Create` без предварительного `Delete`. При успешном непустом снимке ошибка `Delete` прекращает текущую замену до `Create`. [2], [4], [5], [8]

В подставном планировщике проверены сохранность исходных байтов и наличия заблокированной задачи, отсутствие запрещённых вызовов и отсутствие сообщений успеха. Для модели «снимок показал отсутствие, затем `Create` столкнулся с внешней задачей» проверено, что внешнее определение не удаляется и не перезаписывается. Для отказа на следующей задаче подтверждено выполнение существующей компенсации ранее завершённого шага. Эти результаты относятся к модели; ограничения её переноса на настоящий Планировщик Windows перечислены в [разделе 7](#limits). [2], [4], [5], [8], [10]

Соседняя выборка сохранила разделение проходов установки: при `startTasks=false` второй проход запуска пропускается; при `startTasks=true` запускаются только задачи входа пользователя; отказ `Run` второго прохода не откатывает успешно созданные задачи. Здесь также использован подставной планировщик. [6]

Реальный контроль удовлетворил этим условиям. Поэтому его ошибка не отнесена к произвольному сбою сборки или окружения. ## 5. Задержка завершения контрольной команды

Последнее пакетное JSON-событие отрицательного контроля записано в `2026-11-21T00:42:33.1938714+03:00`, что соответствует **`2026-11-20T21:42:33.1938714Z`**; поле пакетного `Elapsed` равно **0.036 с**. Командная квитанция фиксирует завершение Go в **`2026-11-20T21:45:49.506383+00:00`** с кодом 1. Между этими отметками прошло **196.3125116 с**, то есть примерно **196.31 с**. Общая монотонная длительность команды — 228.14654029998928 с. Причина задержки **не установлена**. [4]

В промежутке, в `2026-11-20T21:45:07.350897+00:00`, выполнен один снимок процессов только для чтения. Он содержит `go.exe` с идентификатором процесса 1148 — тем же, что в контрольной квитанции, — временем создания FILETIME `134396845213616806` и значением `GetExitCodeProcess` 259. Это наблюдение присутствия процесса после финального тестового события и до записанного завершения команды. Оно не определяет причину задержки и не удостоверяет завершение полного исторического дерева потомков. Принудительное завершение и повтор отрицательного контроля не выполнялись. [4], [9]

Пара `observe_control.py` / `control-process-observation.json` связывается сохранёнными контрольными суммами файлов. В исходном JSON наблюдения нет поля `runner_sha256`; задним числом оно не добавлялось, и самоудостоверение наблюдателя этим файлом не заявляется. Перечисление процессов и чтение их свойств имеют собственные границы: возможны изменения дерева во время наблюдения, а один снимок не доказывает полноту жизненного цикла. [9]

Параметр `-timeout=180s` относится к тестовому исполнению Go и не задаёт общий жёсткий предел для сборки, всей команды или её потомков. Runner ожидает прямой дочерний процесс без собственного предельного срока; квитанции прямо содержат `direct_child_wait_bounded=false` и `whole_process_tree_deadline_enforced=false`. Отметка `started_utc` фиксируется до получения метаданных исходников, а монотонный таймер команды запускается позже, поэтому её арифметическое отличие от `finished_utc` не обязано совпадать с `seconds`. [4], [11]

## 6. Изоляция исполнения

Использован отдельный клон той же ветки из уже существующей локальной квалификационной копии: `--single-branch --local --no-hardlinks --no-checkout`, затем точная база. На этапе контроля и кандидата сетевое получение исходников не выполнялось; отдельное получение точного опубликованного коммита отражено в таблице 4. Все назначенные рабочие каталоги, профили, временные каталоги, состояние и используемые кэши находятся в разрешённой рабочей области на диске D:. Применялись уже установленные инструменты. [4]–[8], [11]

Команда `go version` записала **`go1.27.4 windows/amd64`**. В окружении установлены `GOENV=off`, `GOTOOLCHAIN=local`, `GOPROXY=off`, `GOSUMDB=off`, `GOVCS=*:off`, `GOWORK=off`, `GOFLAGS=-mod=readonly`, `GOTELEMETRY=off`, `GOMAXPROCS=4`, `CGO_ENABLED=1`. Загрузка модулей и другого набора инструментов отключена. Для тестов заданы `MCPHUB_NO_AUTO_GUI=1`, `MCPHUB_E2E_SCHEDULER=none` и тег `test_state_path_env`. Последний выбирает тестовое перенаправление состояния. [4]–[8], [11]

Новые тесты используют `schedulerFactoryFn` с восстановлением через `t.Cleanup`, подставной планировщик и `t.TempDir`; параллельное выполнение через `t.Parallel` не включается. Поле `installRelayExePath` направлено на временный путь, который эти новые сценарии не исполняют. В соседнем тесте существующая подготовка создаёт пустой подставной канонический файл под `t.TempDir` и использует предусмотренное переопределение пути. Это не проверка запуска установленного продукта. [2], [6], [10]

Изоляция не означает отсутствия любых файловых записей: тестовый `TestMain` создаёт собственные state/audit-файлы — состояние и журнал аудита — и использует разрешения временной области. Записывать или изменять чужие разрешения и системную политику эта серия не требовала. Реальные задачи Планировщика Windows не создавались, не изменялись, не запускались, не останавливались и не удалялись. Установки, ручной запуск CI — непрерывной интеграции — и платные внешние запуски не выполнялись. Снимок процессов из раздела 5 был отдельной операцией чтения и не обращался к задачам Планировщика. [4]–[11]

| Общая приёмка ветки № 658 | NOT_RUN | Данная серия относится к точной базе и продолжению № 660; результаты между ветками не переносятся |
| Объединение веток № 658 и № 660 | NOT_RUN | Объединение веток, включая локальное, не разрешено и не выполнялось |
| Реальный жизненный цикл задач и установленных потребителей | NOT_RUN | Выбраны адресные сценарии с подставным планировщиком, а не нативные операции |

Прежние отказы полных наборов этим адресным PASS не отменяются. Сборка всего дерева и `go vet ./...` из таблицы 3 не заменяют исполнение полных наборов. Ограничения заранее зафиксированы в `ACCEPTANCE.md`; новые положительные результаты распространяются только на указанные команды и состояния исходников. [10]

Сохраняются следующие существенные границы реализации:

1. **Успешный `Delete`, затем неуспешный `Create`.** Контракт восстановления текущей задачи ещё не реализован: её существующая компенсация по-прежнему регистрируется после успешного `Create`. Подтверждён откат ранее завершённого шага, а не восстановление текущего после удаления. [2], [10]
2. **Неопределённый нативный исход `Delete`.** Подставной отказ происходит до применения удаления. Его PASS не доказывает, что настоящая задача сохранилась после ошибки платформенного вызова. [2], [10]
3. **Конкурирующая замена.** Снимок и последующее удаление не атомарны. Проверенная модель конфликта `Create` после отсутствия не закрывает гонку между `ExportXML` и `Delete` либо гонку при восстановлении. [2], [10]
4. **Принудительный импорт.** `ImportXML` продолжает использовать `/F`, разрешающий замену. Условное восстановление с проверкой владения и защита внешнего определения от перезаписи не добавлены. Слепой перенос прежней компенсации перед `Create` может затронуть внешнюю задачу. [10]
5. **Нативный экспорт.** Новая проверка требует непустые байты без ошибки; она не вводит семантическую проверку XML. Переход между COM — компонентной объектной моделью Windows — и CIM — общей информационной моделью управления, имена задач, скрытые задачи, ошибки доступа, поведение провайдера и передача текста потребителям этой серией не квалифицированы. [2], [10]
6. **Нативный запуск, отмена и дерево процессов.** Реальные `Run`, `RunOwned`, `Stop`, `Delete`, владение запущенными экземплярами, общий предельный срок и завершение всех потомков не проверялись. Наблюдение из раздела 5 эти критерии не закрывает. [9]–[11]

Работа не меняет отдельные направления R16, оставшуюся квалификацию экспорта R17 и параллельный Rust-контракт `mh_wait1`/`WaitForExit`, `mh_close1`/`CloseExited`. Полная готовность PR и внешний одобряющий отзыв из приведённых тестовых результатов не следуют.

**Сокращения.** API — программный интерфейс; CLI — интерфейс командной строки; PR — запрос на включение изменений; CI — непрерывная интеграция; JSON — текстовый формат структурированных данных; XML — расширяемый язык разметки; SHA-256 — алгоритм контрольной суммы; UTC — всемирное координированное время; FILETIME — формат Windows для временных отметок в интервалах по 100 нс от начала 1601 года UTC. `stdout`/`stderr` — стандартные потоки вывода и ошибок.
