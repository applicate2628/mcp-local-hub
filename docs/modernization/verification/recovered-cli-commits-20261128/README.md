## 3. Воспроизведение

В отдельной восстановительной repository получите публичную основу `5ad374eb…` и её объекты. В новом временном index последовательно примените два сохранённых full-index patches; после каждого `write-tree` сравните tree с таблицей 1. Затем импортируйте соответствующий исходный commit object командой `git hash-object -w -t commit --stdin`. Результат обязан совпасть с commit в таблице 1. Новый обычный `git commit` для воспроизведения исходного идентификатора не подходит.

## 4. Границы результата

Ранее опубликованные наблюдения «GitHub 422 / объект не найден в проверенной repository» остаются достоверными для своих мест и времени. Новое успешное чтение другой сохранённой repository уточняет доступность; оно не переписывает прежние FAIL/UNKNOWN.

Восстановленные семь путей не пересекаются с пятью путями fallback-патча `f39a10a395675c93068ff8f19a98de1ce856b616de3fc911e28d6b4a2e88ef89` для Source4 `4ac73379…`. Это сравнение множеств путей, а не утверждение о равенстве композиционных исходников или о возможности переносить приёмку между ними.

Исторический Source `727d66753814dc218e26d699e57402db2d13190a`, его отдельная интеграционная tree из 3509 файлов, Product `3ebe335…`, Source4 и новые A–D составы имеют разные области доказательств. Данный пакет восстанавливает только два CLI commits из таблицы 1. Исторические 717 CLI roots по-прежнему означают 712 PASS + 5 SKIP разных запусков/ревизий; они не превращаются в один полный PASS.

Обе обязательные Go-команды, текущие Product/private-input привязки, безопасная передача закрытого cache, оставшийся expected-failure control и публикация точного code head требуют собственных результатов. Полная готовность #666 или всей композиции здесь не заявляется.
