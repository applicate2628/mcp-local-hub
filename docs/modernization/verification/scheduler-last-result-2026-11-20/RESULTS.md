**20 ноября 2026 года, московское время.** Исправлена потеря результата задачи в COM-мосте Windows. Изменение продолжает существующий Draft PR #660; это отдельный ограниченный шаг внутри R17. Полная системная приёмка и остальные пункты R17 открыты.

**Код:** `9721681633440d3593d37ffb8f580e5d98440da2`, единственный родитель `1b870e04f58bbf60fde2d2339fcd4ae9b50b24c3`; дерево `016c9faa5aaedb3ed7db2e6b23066913824a4f09`. Пять изменённых Go-файлов, **+360/−13 строк**. Два производственных файла — +30/−10, включая комментарий и форматирование; три тестовых файла — +330/−3. Из других веток изменения не переносились.

## 1. Причина и контракт

На исходном `1b870e04` поле `TaskStatus.LastResult` существовало, но PowerShell не читал `IRegisteredTask.LastTaskResult`, внутренний JSON-ответ не содержал результата, а Go-преобразование не присваивало публичное поле. Поэтому успешные запросы выдавали **нулевую инициализацию Go**, независимо от настоящего результата задачи. Это существовавший ранее дефект, а не регрессия исправления hidden-поиска [1–2].

Microsoft определяет значение свойства как `LONG`: знаковое 32-разрядное целое. Результат задачи отличается от `HRESULT` самого COM-вызова; возвращённый код нельзя выводить из текущего состояния `Running`, `Ready`, `Queued` или `Disabled` [3–4]. Исправление сохраняет исходное число без нормализации.

**Таблица 1 — выбранный контракт.**

| Вход | Результат Status/List |
|---|---|
| Явный `0` | Сохранить `0`; это не самостоятельное доказательство готовности приложения |
| Положительный прикладной код, например `87` | Сохранить исходный код |
| Информационные коды Планировщика, включая `267011` (`0x41303`) | Сохранить число, не преобразовывать в `-1` |
| Отрицательное число и обе границы `int32` | Сохранить знак и все 32 бита значения |
| Отсутствующее JSON-поле или `null` | Вернуть `ErrUnavailable`, не создавать ложный успех |
| Неверный JSON-тип, дробь или выход за диапазон | Отклонить сообщение как нарушение протокола |
| Сбой или отсутствие свойства PowerShell | Вернуть ошибку без частичного списка |
| Экспорт XML | Не читать `LastTaskResult`; статистика выполнения не нужна для экспорта определения |

`0x41303` обозначен в документации среди кодов Планировщика, но из этого не следует, что каждое состояние обязано давать именно этот `LastTaskResult` [5]. Неизменённый публичный классификатор уже считает `-1` условным отсутствием статистики; настоящий native-код `-1` остаётся неоднозначным для этого потребителя. Новый nullable-тип публичного API и новая политика классификации в эту правку не входят [6].

## 2. Реализация и потребители

В `scheduler_com_windows.go` добавлен один PowerShell-helper: чтение свойства → проверка `$null` → преобразование в `[int]`. Проверка необходима **до** числового преобразования. PowerShell может подавлять исключения при доступе к свойствам; дополнительная проверка отсутствия исключает превращение такого исхода в ноль [7]. В `list` и `status` передаётся `last_result`; ветка `export` этого чтения не получает.

Внутренняя Go-структура использует `*int32`, чтобы различать отсутствующее значение и настоящий ноль. `taskStatusFromCOM` отвергает `nil`, затем присваивает `int(*task.LastResult)`. Публичный `TaskStatus.LastResult` остаётся `int`; поля и JSON-ключи публичного API сохранены. Проверки числового состояния, видимости и защищённого запуска не меняются.

Два прежних положительных тестовых объекта теперь содержат явный `LastTaskResult=0`, а старый тест преобразования состояния — указатель на `int32(0)`. Новый файл содержит пять групп проверок, **32 подтеста**. В десяти сценариях PowerShell исполняется полный производственный текст с заменой только подключения к службе на искусственные объекты. Маркер чтения свойства обнаруживает дефект даже для ожидаемого нуля. Экспорт требует и точных XML-байтов, и отсутствия этого маркера.

Достижимый потребитель результата: `Scheduler.List` → `API.StatusWithOptsDetailed` → `DaemonStatus.LastResult`; этот маршрут используется специальными вариантами CLI-статуса. **Обычный `API.Status()` и GUI-poller получают данные через supervisor IPC**, поэтому результат исправления не переносится автоматически на обычный графический интерфейс [8]. Независимое [ревью области и потребителей](INDEPENDENT-REVIEW.md) содержит точные исходные ссылки.

Перепроверены изменённые файлы всех **31 открытого Draft PR**: только #660 владеет `internal/scheduler/*`. Поэтому область #660 явно дополнена корректностью данных `Status`/`List`; новый дублирующий PR не создан. #623 сохраняет доказательства, #658 — действующий остаток плана.

Проверки выполнены на Windows/amd64 (версия ядра 10.0.22631), существующим Go 1.27.4. Загрузка зависимостей отключена; кеши уже существовали. Рабочая копия, временные каталоги и тестовое состояние изолированы. Настоящий lifecycle-тест Планировщика не включался; для общих тестов установлен предусмотренный репозиторием `MCPHUB_E2E_SCHEDULER=none`.

## 4. Полные проверки и ограничения

Обычный полный прогон дал **FAIL, код 1, 400,641 с**. Не прошли шесть пакетов; это свежий результат проверяемого дерева, а не перенесённый вердикт прежнего коммита.

**Таблица 3 — наблюдаемые отказы обычного прогона.**

| Пакет | Наблюдение и предел вывода |
|---|---|
| `cmd/mcphub` | Пять тестов командного входа: координатор запуска не вызван, маршрутизация bare/debug-входа не совпала с ожиданием |
| `internal/api/lsp_routing` | 10 диагностик строгой проверки разрешений родительского каталога: DACL содержит `S-1-5-11` с маской `0x0001013f`; подготовка данных отвергнута |
| `internal/api/serena_routing` | 19 диагностик той же проверки разрешений; свойства маршрутизации в этих случаях не подтверждены |
| `internal/api` | Общий лимит пакета 5 минут, 300,131 с. В момент остановки `TestRestore_OneClientOccupiedPort_ApplySelectedOnly` имел округлённые 0 с; его текущий стек не устанавливает причину расходования лимита |
| `internal/cli` | Нет квалифицированного тестового Product и абсолютного `MCPHUB_CANONICAL_ENTRY_FIXTURE` для RunV5; затем общий лимит 5 минут, 300,080 с. Активный rollback-тест имел 1 с, а не установленное пятиминутное зависание |
| `internal/process` | Два сценария Windows Job отклонены из-за отсутствующей qualified entry configuration; их native-свойства не подтверждены |

`internal/scheduler` прошёл весь пакет — 27,538 с. `internal/gui` в этом прогоне также прошёл — 247,112 с, тогда как в прежнем отчёте он был седьмым неуспешным пакетом. Причина прежнего `Malformed`/пустого pidport не установлена; единичный текущий PASS не объявлен её исправлением. В общих тайм-аутах теперь активны другие тесты; подписей отказа недостаточно для доказательства причинной независимости от текущей правки.

Тегированный полный прогон `internal/api/` и `internal/cli/` дал **FAIL, код 1, 322,436 с**. В API отсутствуют требуемый принимающий бинарник и его ожидаемый хеш; затем исчерпан общий пятиминутный бюджет, при остановке `TestDaemonIntent_ConcurrentWrite` имел 12 с. В CLI повторился отсутствующий вход RunV5; сценарии Serena отвергнуты по `SERENA_BUILD_SOURCE_INVALID` либо `E_WINDOWS_PE_SUBSYSTEM` (ожидалось 2, получено 3). Затем исчерпан общий бюджет, при остановке `TestCLISecretsDelete_FailedWriteEmitsNoAuditEvent` имел 0 с. Требуемые свойства принимающего пути и миграции этими отказами не квалифицированы. Подсказки тестовых журналов об установке Product не исполнялись.

Обе полные команды выполнены один раз на окончательном кодовом дереве перед публикацией. Адресный повтор после публикации имеет отдельные квитанции и не заменяет эти отрицательные общие результаты.

Успех объектных PowerShell-фикстур подтверждает передачу и обработку контролируемых значений, но **не квалифицирует чтение результата настоящего COM-объекта**. Предыдущие разрешённые нативные серии остаются привязанными к `1b870e04`; их допуски и RunId не использовались повторно. Этот шаг не создавал, не запускал и не удалял задачи Планировщика, не менял системные политики.

Не проверены новой серией: настоящий ненулевой результат запуска, весь набор native-ошибок/прав, происхождение отрицательных кодов на реальной задаче, действительная отмена уже начатого COM-запроса и срок жизни всего дерева процессов. Командная обвязка ожидает непосредственных детей через сохранённые объекты `Popen`, но не заявляет отдельного доказанного ограничения всего дерева.

После общих проверок и после повтора точного коммита выполнены отдельные read-only наблюдения процессов по уникальному маркеру рабочей папки в пути исполняемого файла или командной строке. В обоих снимках оставшихся совпадений нет; собственные процессы наблюдателя исключены явно. Это подтверждает отсутствие совпадений в моменты чтения, но не доказывает отсутствие потомков без такого маркера и не устанавливает общий срок дерева. Все непосредственные команды в квитанциях имеют `settled=true`.

Выполнен собственный просмотр всех пяти изменённых файлов после форматирования: требования, корректность, обработка ошибок, совместимость, безопасность и сложность. Дополнительно выполнено независимое статическое ревью. Новых подтверждённых дефектов в ограниченной дельте не найдено. Проверенные решения: нет интерполяции пользовательских имён в код PowerShell; отсутствие не принимается за ноль; полное число сохраняется; список не выдаёт частичный успех; экспорт не приобретает зависимости от статистики; фильтры hidden/List и проверки `RunOwned` сохранены.
