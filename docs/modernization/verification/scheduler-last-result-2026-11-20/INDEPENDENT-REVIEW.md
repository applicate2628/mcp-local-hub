## 3. Контракт и потребители

На базе поле `TaskStatus.LastResult` существует, но отсутствует и в PowerShell-ответе, и в `schedulerCOMTask`, и в инициализаторе `taskStatusFromCOM`. Поэтому успешные `Status`/`List` возвращают не наблюдённый успех, а нулевую инициализацию Go [1–3]. Это исходный дефект, не регрессия hidden-lookup изменения.

Microsoft определяет результат `IRegisteredTask::get_LastTaskResult` через `LONG*` [8]. Кандидат сохраняет знаковое 32-разрядное значение, включая `0x41303` и `-1`, без нормализации. XML-перечисление уже использует `-1` для неизвестной статистики; совместимость с этим источником сохраняется. Неоднозначность настоящего результата `0xffffffff` и старого условного значения `-1` остаётся существующим ограничением; новый nullable-контракт публичного API здесь не вводится.

Прямая цепочка потребления: `sch.List` → `StatusWithOptsDetailed` → `DaemonStatus.LastResult` через `int32(t.LastResult)` [4]. CLI использует её для `--health`, `--force-materialize`, `--workspace-scoped`; JSON-вывод сериализует возвращённые строки [5]. Публичные типы и ключ `last_result` не меняются [6].

**Обычный `API.Status()` и GUI-poller получают статус через supervisor IPC.** При недоступном supervisor этот путь возвращает ошибку, а не подменяет данные scheduler-списком [4]. Поэтому исправление планировщика не доказывает изменение обычного GUI-пути. Классификатор `IsRealFailure` и потребители `DaemonStatus` действительно учитывают результат, но их достижимость необходимо отличать от существования поля [7].

## 4. Производственная правка и тесты

В прочитанном `scheduler_com_windows.go` проверены следующие границы:

- Строки 50–53: значение читается один раз; `$null` отвергается **до** `[int]`, поэтому отсутствие не превращается в ноль.
- Строки 34, 188–194: `*int32` различает отсутствующее/null JSON-поле и настоящий ноль; отсутствие даёт `ErrUnavailable`, значение расширяется до `int` без потери знака.
- Строки 118–120: результат читается только для `status`; `ExportXML` не получает новой зависимости от статистики запуска.
- Строка 100: успешный список сериализуется после построения всех строк. Ошибка уходит в общий обработчик; публичный Go-список также не возвращает накопленные строки при ошибке преобразования [3].

Это существенно для PowerShell: документация предупреждает о подавлении исключений при доступе к свойствам [9]. Кандидат не полагается только на внешний `catch`: отсутствие результата вызывает собственный `throw`. Новый тест использует `ScriptProperty` с исключением и маркером чтения; отсутствие, null и отказ проверяются также после корректной первой строки списка.

Новый набор тестов проверяет числовые классы и границы `int32`, неверные JSON-типы, публичные `Status`/`List`, производственный PowerShell-сценарий с подменённым подключением и независимость экспорта. При экспорте проверяются и точные XML-байты, и отсутствие обращения к getter. Тестовый объект не обращается к службе Task Scheduler. Декодирование не ссылается на новое частное поле напрямую, поэтому конструкция допускает отрицательный контроль на старом коде; его результат здесь не утверждается.

## 5. Граница непроверенного

Автор этого ревью не запускал сборку, Go-тесты, PowerShell, службы, удалённые команды или записи GitHub. Выполнены только чтение исходников, сравнение файлов и метаданных. Результаты выполняемых другим участником проверок в этот документ не перенесены.

Остаются непроверенными этим проходом: компиляция кандидата, фактическая семантика объектных фикстур в целевой Windows PowerShell, получение результата настоящего COM-объекта, обязательные полные проверки репозитория и окончательная опубликованная вершина. Предыдущий ограниченный успех hidden-фикстуры не переносится на новый код. Наличие теста и отсутствие найденного дефекта не заменяют исполнение. `NextRun`, фильтр принципала, отмена, сроки, автозапуск и удаление COM не оценивались как исправленные.
