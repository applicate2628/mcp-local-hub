## 1. Проблема и последствия

Действующий Go reader `ReadStateFileBeneathRootNoFollow` и вариант для резервных копий `ReadClientConfigBackupBeneathRootNoFollow` обходят путь относительно открытого корневого каталога, проверяют объект и закрывают принадлежащие вызову ресурсы. В Windows и POSIX — семействе систем с интерфейсами Portable Operating System Interface — найдены связанные нарушения завершения этой операции. Точные исходники и принадлежность изменений сохранены в `reader/source-manifest.json` и `reader/ownership.json`.

**Таблица 1. Причины и последствия дефекта.**

| Условие | Поведение исходного кода | Последствие |
|---|---|---|
| После открытия следующего каталога закрытие прежнего родителя возвращает ошибку | `current` ещё содержит прежний числовой дескриптор; ветка закрывает следующий ресурс, а отложенное завершение повторяет закрытие прежнего | Повторная попытка закрытия уже потреблённой числовой идентичности; операционная система могла переиспользовать её |
| Ошибка чтения, проверки, открытия или отмены уже установлена; закрытие тоже возвращает ошибку | Условие `closeErr != nil && retErr == nil` отбрасывает дополнительную причину | Вызывающий код не получает полный результат завершения операции; при нескольких ошибках закрытия причины также теряются |
| Данные прочитаны, но их завершающее закрытие ошибочно | В отдельных путях результат содержит одновременно байты и ошибку закрытия | Вызывающий код получает данные операции, завершение которой не подтверждено |
| Ошибка отсутствия файла объединяется с ошибкой закрытия | Два непосредственных потребителя принимают `errors.Is(err, os.ErrNotExist)` за чистое отсутствие | Подготовка компенсации может создать обратную запись после неполного чтения; проверка потребителей может заменить исходный отказ общей диагностикой ожидающего потребителя |

Последняя строка таблицы 1 важна при исправлении сохранения ошибок: `errors.Is` правильно продолжает находить отсутствие среди объединённых причин, но это ещё не основание действовать так, словно вся операция успешно установила отсутствие файла. Разбор исходных ветвей и вызывающих функций сохранён в `reader/REVIEW.md`.

## 2. Минимальное исправление

После успешного открытия следующего каталога reader сохраняет прежний ресурс, передаёт `current` следующему ресурсу и только затем закрывает прежний. Если это закрытие ошибочно, единственное отложенное завершение уже владеет следующим ресурсом. Прежний числовой дескриптор повторно не закрывается. Такой порядок применён в обеих платформенных ветвях.

Общий `completeStateReadClose` сохраняет первоначальную ошибку первой и присоединяет типизированную ошибку закрытия через `errors.Join`. Если закрытие ошибочно, имеющийся буфер результата очищается существующей `zeroStateSecretBytes`, а вызывающему коду возвращается `nil` вместо данных. На Windows ошибки проверки корневого или следующего объекта также сохраняются вместе с ошибкой его закрытия.

Новые глобальные тестовые переключатели, публичный интерфейс, зависимости и отдельная система классификации ошибок не вводятся. Полная правка: `reader/overlays.patch`, точные восемь файлов: `reader/overlays-manifest.json`.

## 3. Совместимость и строгое отсутствие

Существующий тип `StateFileReadError` сохранён. Обычные `errors.Is` находят исходные и добавленные причины; порядок объединения сохраняет первоначальную типизированную ошибку первой для `errors.As`. Общая проекция `errors.Is(joined, os.ErrNotExist)` намеренно остаётся диагностической и может быть истинной при дополнительном отказе закрытия.

Только два непосредственных потребителя используют частный `stateReadBeneathRootAbsent`. Он принимает прямой `*StateFileReadError` категории `StateFileReadErrorUnsafeObjectOrIO`, возникший на `open-root`, `open-component` или `open-final`, с непосредственной native причиной отсутствия. Обёрнутая ошибка, `errors.Join`, вложенная составная `Cause`, нетипизированный `os.ErrNotExist` и отсутствие, возникшее на операции закрытия, не дают разрешения продолжать ветку «файла нет». Предикат вызывается до оборачивания ошибки потребителем; обход произвольного графа ошибок ему не нужен.

Есть небольшой нюанс прямого вызова метода: на POSIX `StateFileReadError.Is(os.ErrNotExist)` теперь возвращает `true` для исходного native open-missing, как на Windows. Раньше обычный `errors.Is` находил эту причину через `Unwrap`, но прямой вызов метода `Is` её не признавал. Обычные вызовы `errors.Is` и `errors.As` сохраняют поведение; прямых производственных вызовов этого метода в проверенной области не найдено. Native причина проверяется непосредственно как `syscall.Errno == unix.ENOENT`, поэтому составная `Cause` не принимается за чистое отсутствие.

Вариант чтения резервной копии сохраняет первоначальный захват без заранее известной SHA-256 — контрольной суммы алгоритма Secure Hash Algorithm 256 — и чтение с заданной суммой. Лимит остаётся **16 MiB, то есть 16 777 216 байт**; общий state reader сохраняет лимит **1 MiB, то есть 1 048 576 байт**. Поведение отмены контекста сохранено. Затронутый существующий тест резервных копий повторён вместе с новыми тестами, включая точный лимит, превышение на один байт, несовпадение контрольной суммы, отмену и отказ для объекта, не являющегося обычным файлом.

## 4. Почему отдельный PR

Производственный владелец дефекта — существующий Go reader в `master` на `75dbc6406123e22468f168b861d5e0622c9d5769`. Три `state_read_beneath_root_*` файла побайтно совпадают с их версиями в проверенных точных головах #627 (`6615d239fe066eaa5fa78c22a5272d6602528274`) и #643 (`daaa04c14bc3944babd4efbc3a125eaf495e6534`). Эти reader-файлы отсутствуют в текущих дельтах #627, #643 и сохранённого #652; перечни путей и Git-объектов находятся в `reader/ownership.json`.

#627 содержит эксперимент Rust reader и его доказательства; #643 сохраняет композицию владения Serena. Внесение независимого производственного исправления Go в одну из этих веток смешало бы разные обязанности. Отдельный небольшой PR исправляет конкретную обнаруженную причину и не дублирует изменения существующих веток. Он не заявляет завершение Rust reader, Serena или общей программы R24/R25.

Тестовые функции подстановки выполняют реальные open/stat/read/close на собственных временных файлах, затем внедряют нужный результат ошибки. ## 7. Ревью и пределы доказательства

Собственное ревью проверило требования, порядок владения, причины ошибок, совместимость, границы побочных эффектов и отсутствие лишних слоёв. Ревью root обнаружило первоначально слишком широкую проверку вложенной `Cause`; она исправлена на непосредственный native predicate и закреплена отдельным отрицательным случаем. После исправления независимое ревью исходников обязательных замечаний не оставило: `reader/REVIEW.md`, `reader/independent-review.json`. Runner и форматирующий helper также прошли отдельное чтение: `qualification/reader-runner-independent-review.json`, `qualification/reader-format-stage-independent-review.json`.

Границы результатов остаются следующими:

- Native файловые ресурсы использованы реально, но ошибки stat и close внедрены тестом после успешных операций. Фактическое получение таких отказов от операционной системы не квалифицировано.
- Windows-пути совмещённого отказа проверки корневого/следующего объекта и его close исправлены и прочитаны при ревью; отдельное внедрение ошибок этих проверок узкими тестами не выполнено.
- Для Linux подтверждена компиляция. Исполнение POSIX-тестов, другие POSIX-платформы и Linux race-проверка не выполнялись.
- Полная сборка и vet не означают полный запуск всех тестов. Общие и специальные наборы с build tags, нативный Scheduler, установленный продукт, Rust #627 и интеграция Serena этим пакетом не проверялись.
- Runner ограничивает ожидание прямого дочернего процесса и сохраняет его исходный `Popen`. Квитанции не заявляют отдельного доказательства завершения всего дерева потомков.
- Требование внешнего ревью точного опубликованного коммита остаётся открытым. До его выполнения PR сохраняет статус Draft.
