## 3. Три попытки и границы доказательства

**Таблица 2. Сохранённые результаты попыток.**

| Попытка | Результат | Что сохранено |
|---|---|---|

| V2 | Импорт master blobs превысил 60 секунд; launcher остановлен, дочерний worker продолжил работу | Неизменная failed-квитанция с `process_tree_unresolved=true`, оба наблюдения процессов, поздний stdout и точный исходный префикс |

В V3 срок только точного base import увеличен до 300 секунд; свежие
рабочие пути и версия runner отделяют попытки. Остальные проверки и
пределы сохранены. Импорт реально занял 195,75 секунды, подготовка Source —
188,23 секунды при её пределе 600. Все 27 команд завершились без timeout:
24 с кодом 0, три `git config --get` — с ожидаемым кодом 1 для отсутствующих
`core.hooksPath`, `commit.gpgSign` и `init.templateDir`.

У V2 stdout вырос после timeout с 36 864 до 134 070 байт. Исходный префикс
сверен по записанной контрольной сумме и сохранён отдельно. Последующее
самостоятельное окончание worker не меняет исходный отказ и не снимает
`process_tree_unresolved=true` с прежней квитанции.

Внешний Python runner ограничивал ожидание своего прямого дочернего
процесса. Его результаты не заявляют общий предел времени для всего
дерева потомков. Source helper использует существующего владельца Windows
Job для собственных Git-вызовов; это отдельная граница ответственности.
Успешный Source подтверждён реальными квитанциями и повторным чтением,
а не утверждением о несуществующем универсальном ограничении процессов.

Собран только служебный `./tools/windows-product-validate`; выполнены его
ветви `--prepare-source` и `--source-snapshot`. Product, Serena publisher,
runtime, тесты проекта, установщики и планировщик не запускались.
Исторические `NOT_RUN` в первоначальных планах и manifest сохранены;
текущий Source PASS опирается на отдельные фактические результаты V3.

## 4. Независимый аудит и воспроизведение

[replay.py](replay.py) — неизменённый независимый проверяющий скрипт.
Он выполняет операции над данными без запуска Git, Go, кода проекта или
native программ. [audit.json](audit.json) фиксирует реально выполненный
аудит исходной рабочей области: повторно проверены все **3323 физических
файла**, оригинальный evidence ZIP, 198 распакованных членов, все 121
входа исполнения, 109 дельт, оба дерева, raw-коммит, snapshot, команды и
семантика прежних отказов. Подробности — в [audit-report.md](audit-report.md).

Отдельно выполнен переносимый аудит распакованного комплекта. Он проверил
121 физический вход и 198 зафиксированных raw-членов, полные таблицы,
snapshot, дельты, дерево, коммит и результаты команд. Его фактический
отчёт включён в архив как `independent-native-audit/bundle-audit.json`.

При наличии только компактного комплекта повторное чтение отсутствующих
полных исходников и оригинального evidence ZIP явно получает `NOT_RUN`.
Это не изменяет записанный успешный аудит рабочей области и не позволяет
приписать переносимому запуску чтение отсутствующих файлов.

Для переносимого повторения сначала распаковать [bundle.zip](bundle.zip)
в новый каталог. Восстановить исходный payload и control V2 в новые файлы
вне комплекта:

```text
python <unpacked>/pack_execution.py --output <fresh-outside>/transfer.b64
python <unpacked>/pack_execution.py --v2-control --output <fresh-outside>/v2-control.b64
python replay.py --root <unpacked> --layout bundle --payload <fresh-outside>/transfer.b64 --v2-control <fresh-outside>/v2-control.b64
```

Обе передачи воспроизводятся с проверкой точных исходных SHA-256;
небольшой control V3 уже находится в `next-step/v3-control.b64`.
Для дополнительных физических проверок у replay существуют параметры
`--source-root <restored-full-source>` и
`--evidence-zip <retained-original-evidence.zip>`. Полный source root
восстанавливается описанным внутри архива `restore_source.py`, а
оригинальный evidence ZIP сохраняется отдельно: 963 852 байта, SHA-256
`f4154b8e666f1cab452fc35d1083444c884413dee86dcdcb140b8d73e50a455b`.
Все его 198 членов уже включены в компактный архив побайтно.

**Таблица 3. Три различных контракта следующей работы; все `NOT_RUN`.**

| Ветка | Существующий вход и роль | Ограничения |
|---|---|---|
| Обычный Product | `build.ps1`, роль `product`; при `-SourceSnapshotPath` используется выданный epoch | Корень определяет `$PSScriptRoot`; output вне Source; полная тройка release metadata; дата будущей сборки ещё не присвоена |
| Serena qualification publisher | `tools/test-serena-publisher`, роль `serena-qualification`, два tags `test_state_path_env,serena_qualification` | Native Windows/amd64; новый отдельный work root; builder сам повторно подготавливает Source из clean checkout |
| Test-state Product из #657 | `build.ps1 -TestStateIsolatedProduct`; роль `product`; в command-test fixture `source_epoch=""` | Canonical switch требует test-state switch; release metadata и SourceSnapshotPath отвергаются; output под `.scratch` отдельной рабочей копии |

У обычного `build.ps1` отсутствует параметр `SourceRoot`. Для export без
Git metadata закреплён реальный `ReleaseCommit` из таблицы 1. Будущая
`ReleaseBuildDate` должна быть фактической датой новой сборки, а не датой
подготовки Source. Даже `PrintPlanJson` расположен после Git/Go preflight;
сейчас этот скрипт не исполнялся. A5 не проверяет PowerShell executable
и полный кэш ресурсообразователя `goversioninfo@v1.5.0`.

Существующие flags Serena publisher: `--checkout`, `--expected-commit`,
`--go`, `--go-root`, `--module-cache`, `--work-root`, `--timeout`.
Flags для передачи готового `--source-epoch`, `--source-snapshot` или
`--source-root` отсутствуют. `--timeout` задаёт общий рабочий context
длительностью не более 10 минут; очистка процессов и потоков может
использовать дополнительные 15 секунд до `deadline + 15s`. Это не
универсальный wall-clock предел всех синхронных файловых операций.

В его будущих proofs форма `source_input` различается:
`proof/source-preparation.json` содержит `schema` и три поля данных,
а `proof/publisher.json` — только `source_snapshot_sha256`, `source_epoch`
и `file_count`. В JSON сохранены две отдельные ожидаемые формы по точным
путям и указателю `/source_input`, чтобы не создавать ложный отказ при
сравнении. Publisher также требует отказ обычного Product admission для
образа с ролью `serena-qualification`; такой образ не заменяет Product
или test-state fixture из #657.
