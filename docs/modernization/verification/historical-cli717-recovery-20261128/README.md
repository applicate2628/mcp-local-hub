## 2. Прежние отказы и последующие наблюдения

В `cli717-fixed-v3` получены 451 PASS и 4 SKIP. Запущенный `TestUpgradeCurrentAutorunOffSettlesBeforeOuterFenceRelease` не имеет итогового события корня: Go завершился по своему сроку 5 минут во время под-теста `rollback_retains_operation_and_policy_failures`. В журнале нет терминального события пакета. Исходный test command и parent вернули exit 1; первоначальная оценка остаётся FAIL.

В `remaining261-v1` получены 259 PASS, 1 SKIP и 1 FAIL. Провалившийся корень — `TestWorkspaceRegisterSerena_NativePreparationProducerToTerminalFrame`. Все 261 корня имеют терминальное событие; пакет завершился FAIL. Этот результат также сохранён.

Позднее `compact-profile-v1` на другой ревизии получил:

- `TestUpgradeCurrentAutorunOffSettlesBeforeOuterFenceRelease` — PASS, **73.87 с** по событию корня.
- `TestWindowsProductPreflightOriginalEntrySet` — повторный PASS, **51.73 с**.

Затем `marked-workspace-replay-v2` получил `TestWorkspaceRegisterSerena_NativePreparationProducerToTerminalFrame` — PASS, **142.69 с**, на третьей ревизии. Его журнал содержит терминальное событие пакета PASS. [1–2]

Итоговый выбор использует последний доступный исход каждого имени в явно заданном порядке четырёх запусков. Прежние наблюдения остаются в массиве `observations` соответствующей строки и отдельно перечислены в `original_failure_observations` внутри evidence. Поэтому 712 PASS + 5 SKIP описывает историческую сводку, а не изменение статуса первых двух запусков.

Пять SKIP сохранены именно как пропуски:

- `TestProductionSpawnFn_ReapsExitedChildProcess` — `cli717-fixed-v3`.

- терминальный exit исходного parent и закрытие обоих его capture-файлов;
- `commands_quiescent=true` у parent и execution;
- для каждой исходной команды: полученный direct exit, пустой Job, закрытые native handles и пустой список native issues;

## 4. Как читать полный ledger

[ledger.jsonl](ledger.jsonl) содержит **717 строк JSON**, по одной на имя из точного ожидаемого списка и в том же порядке. Каждая строка включает:

| Поле | Смысл |
|---|---|
| `test` | Полное ожидаемое имя корня |
| `selected_outcome` | Последний исторический PASS или SKIP этого имени |
| `selected_run` | Запуск, предоставивший выбранное наблюдение |
| `selected_source_commit` | Точная ревизия этого запуска |
| `selected_duration_seconds` | Исходный `Elapsed` выбранного корня, в секундах |
| `observations` | Все полученные наблюдения имени в порядке четырёх запусков, включая FAIL и UNTERMINATED |

Каждое наблюдение сохраняет имя запуска, полный Source commit, исход, длительность и наличие терминального события. Число начатых корней проверялось отдельно от числа терминальных исходов. Дублированные старты и терминальные события среди этих корней не обнаружены.

## 5. Воспроизведение по исходным данным

[verify_history.py](verify_history.py) — отдельный проверяющий скрипт для данных. Он читает только явно переданные JSON/text-файлы, сверяет размеры и SHA-256, проверяет исходные признаки завершения и заново строит все 717 строк. Он не импортирует controller, не запускает процессы или модели, не обращается к сети и не пишет файлы.

Оператор отдельно задаёт приватный JSON с полями `expected_roots` и `runs`. Первое содержит путь к исходному списку. `runs` содержит ровно четыре ключа из таблицы 1; для каждого нужны явные пути `parent`, `execution`, `stdout`, `stderr`. Машинные значения этих путей, примеры с исходными путями и их закодированные копии здесь не публикуются.

Пример вызова использует только имена ролей:

```text
python -I -S -B verify_history.py --paths ORIGINAL_PATHS_JSON --capsule CAPSULE_DIRECTORY
```

Для выдачи побайтно восстановленного ledger в stdout добавляется `--emit-ledger`. Без этого параметра скрипт выводит краткий JSON, в котором `historical_aggregate_verified=true`, но `single_full_run_pass=false` и `mandatory_gate_qualification=false`.

При подготовке пакета результат был вычислен напрямую как данные из полученных исходных файлов: хеши, JSON-разбор, сопоставление корней и полный ledger. Предоставленный Python-скрипт **не исполнялся**; его возможный будущий DATA-прогон нельзя приписывать этой публикации. Контрольная опись [artifact-manifest.json](artifact-manifest.json) связывает все публичные файлы, кроме самой описи. [4]

Полные private captures не публикуются. Поэтому читатель без исходных файлов может проверить внутреннюю согласованность публичной проекции и её Git-байты, но не пересчитать хеши отсутствующих private captures. Хеш сам по себе не заменяет получение исходного файла.

## 6. Границы результата и оставшаяся приёмка

Исходный `cli717-fixed-v1` остаётся отдельным FAIL/UNKNOWN в замороженной execution-квитанции; отдельный поздний physical-closure документ не переоценивает его qualification. Его capture в эту сводку не включался.

Старый `literal-full-v1` / full-v8 изолирован: доступные управляющие записи содержат превышение срока и `terminal_exit_received=false`. Его capture и кэши не читались и не использовались.

Отдельный full-v9, согласно восстановленному continuation checkpoint, имеет физическое CLOSED при сохранённом FAIL/UNKNOWN; Source/cache postclosure finalization там помечена NOT_RUN. Этот пакет не предоставляет разрешения использовать эти ресурсы и не подменяет предусмотренную приёмку после завершения.

История 717 относится к выбранному ранее набору. Она не утверждает прохождение текущего полного CLI/API inventory, 14 migration + 2 canonical controls в обоих режимах, оставшегося expected-refusal control либо двух обязательных команд:

```text
go build ./... && go vet ./... && go test -count=1 -timeout 5m ./...
go test -tags=test_state_path_env -count=1 -timeout 5m ./internal/api/ ./internal/cli/
```

Новые тесты, изменения Source и кэшей, слияния или публикация из этого скрипта восстановления не выполнялись. Root review и штатный publication gate остаются отдельными действиями владельца PR.
