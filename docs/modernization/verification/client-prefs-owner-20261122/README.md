## 1. Производственный инвариант и границы изменения

В `internal/gui/client_install_prefs.go` удалены две изменяемые пакетные
переменные `clientInstallPrefsViewFn` и `clientInstallPrefsSetFn`, а также
два помощника, которые при отсутствии подмен создавали новый API на каждом
обращении. Вместо них объявлен узкий интерфейс `clientInstallPrefsAPI`
из двух существующих методов: `ClientInstallToggleView` и
`SetDefaultInstallClientNames`. [1]

`Server` хранит этот интерфейс в поле `clientInstallPrefs`.
`NewServer` выполняет `s.clientInstallPrefs = s.api`, используя уже созданный
API этого экземпляра. Дополнительного API или нового владельца хранилища
не появляется. GET читает через это поле; POST сначала сохраняет набор
через то же поле, затем читает обновлённый снимок через ту же зависимость.
Настройка конкретного тестового сервера больше не заменяет функцию
обратного вызова всего пакета. [1]

Прежний HTTP-контракт сохранён: маршрут `/api/client-install-prefs`,
защита `requireSameOrigin`, методы GET/POST, ограниченный разбор тела,
ответы 400 для неизвестного клиента и пустого набора, 405 для другого
метода, 403 для запрещённого источника и повторное чтение после успешной
записи. Производственный слой API по-прежнему отвечает за проверку имён,
сохранение предпочтений и вычисление действующего набора. [1]

Это изменение владения **зависимостью**, а не создание отдельного
постоянного хранилища для каждого сервера. Два производственных API могут
обращаться к одному пользовательскому файлу предпочтений. Проверка двух
серверов ниже использует отдельные подставные состояния и доказывает
отсутствие общего перенаправления вызовов; из неё нельзя выводить изоляцию
реальных файлов или долговременное сохранение на диске. [1, 2]

Просмотрены фактические пути регистрации и вызова: производственная
регистрация выполняется из `NewServer` после связывания зависимости;
затронутые тесты используют `newEphemeralServer`, который вызывает этот
конструктор. Минимальные литералы `Server` из других тестов данный
обработчик не вызывают. Обходной `nil`-путь, который снова создавал бы API
из обработчика, не добавлен. Это результат просмотра текущих исходников,
а не заявленная поддержка вызова этого маршрута на нулевом `Server`. [1, 3]

## 3. Проверки маршрута и отрицательный контроль

Кандидат запускает ровно восемь корней:

- `TestClientInstallPrefs_UsesServerAPI`;
- `TestClientInstallPrefs_ServersKeepIndependentDependencies`;
- `TestClientInstallPrefs_GetDefault`;
- `TestClientInstallPrefs_PostPersistsAndReturnsSnapshot`;
- `TestClientInstallPrefs_PostUnknownClientIs400`;
- `TestClientInstallPrefs_PostEmptySetIs400`;
- `TestClientInstallPrefs_MethodNotAllowed`;
- `TestClientInstallPrefs_CrossOriginRejected`.

Первый проверяет тождественность зависимости `s.clientInstallPrefs` и
существующего `s.api` после конструктора. Второй создаёт два сервера,
устанавливает обоим отдельные подставные зависимости и только затем
чередует чтения и записи. Оба POST обязаны вернуть снимок после своей
записи; чтение другого сервера должно сохранить его прежний выбор.
Проверяются HTTP 200, активное переопределение, ровно четыре строки клиентов
и единственный ожидаемый выбранный клиент. [1]

Отрицательный контроль — **семантическая мутация общего владения**.
Конструктор сохраняет последний созданный `Server` в одной пакетной
переменной; все три вызова предпочтений используют зависимость этого
последнего сервера. Интерфейс, конструктор, подставные хранилища и все
утверждения теста остаются совместимыми и неизменными. Контроль не является
восстановлением целиком исторической головы: такое восстановление при
новой фикстуре перестало бы использовать подставные зависимости и не
проверяло бы именно межсерверное перенаправление. [1–3]

**Таблица 3. Шесть чередуемых шагов и наблюдённый контроль.**

| Шаг | Ожидание фикстуры | Результат общего перенаправления |
|---|---|---|
| Первое чтение первого сервера | `cursor` | FAIL: `vscode` |
| Первое чтение второго сервера | `vscode` | PASS |
| POST первого сервера | `claude-code` в ответе | PASS; фактически изменено подставное состояние второго |
| Чтение второго после первого POST | `vscode` | FAIL: `claude-code` |

Контроль выбирает только двухсерверный корень. Сырые события дают
**3 PASS / 5 FAIL**, включая FAIL родителя и пакета. Каждый из трёх
конечных отказов содержит точное несоответствие выбранного клиента из
таблицы 3; отказа на количестве строк, HTTP-статусе, гонке или отсутствии
подставного хранилища нет. Кандидат даёт **15 PASS / 0 FAIL**: восемь
корней, шесть подтестов и пакет, то есть 14 именованных событий и
13 конечных случаев. В обеих командах **SKIP=0**. [1, 2]

Все тесты используют реальную регистрацию маршрута и его HTTP-обработчики,
но заменяют только предпочтения конкретного сервера подставным API.
`TestClientInstallPrefs_PostPersistsAndReturnsSnapshot` в этой выборке
проверяет передачу записи и последующее чтение подставного состояния;
его название не доказывает запись реального файла. `newEphemeralServer`
сохраняет маршруты, отключает несвязанную запись журнала событий и
регистрирует завершение фоновых работников `Broadcaster`. Сетевой
слушатель для этих обращений не запускается; запросы проходят через
зарегистрированный mux с `httptest`. [1]

и новый baseline; полное дерево подтверждает, что дополнительных изменений

## 6. Неуспешная подготовка и исправление checker

### Исходный отказ проверки метаданных ZIP

Первый `source.py` скачал неизменяемый codeload-архив по конкретному
commit. Архив: **22469879 байт**, SHA-256
`e4c4b4fe80673eb5cf93d0f752159564266514b14d03049bbf823fd935b2c089`.
Затем подготовка остановилась с `Unadmitted archive directory`:
ожидание Unix-режимов не соответствовало фактическому представлению
метаданных ZIP. Это отказ подготовки источника, а не ошибка разбора Go
или провал проектного теста. Он произошёл до создания обеих исходных
копий и до проектного исполнения. [1]

Сохранённая диагностика показывает **192 записи каталогов** с
`create_system=0`, `external_attr=0x10`, верхним Unix-режимом 0;
у **3283 файлов** — `create_system=0`, `external_attr=0x0`, Unix-режим 0.
Все каталоги в точности совпадают с родительскими путями независимого
Git-инвентаря, включая корень архива. Исходные скрипт, план, квитанция и
диагностика сохранены. Квитанция отказа имеет 849 байт и SHA-256
`aadb195e39fcb3bfb3baba9ca87d85a9b75c5552198abf659675fcf6c2ab5aa1`.
[1, 2]

`source_v2.py` использовал только тот же сохранённый архив, без повторной
загрузки, с новым планом и новым каталогом результатов. Допуск расширен
ровно до наблюдённого сочетания DOS-метаданных. Требуются точные пути,
нулевые размеры каталогов, отсутствие неожиданных атрибутов, полный набор
файлов и каталогов, заявленный независимым Git-инвентарём режим `100644`,
размер и SHA-256 каждого файла, идентификаторы blob и восстановленный
Git-корень. Все эти проверки выполняются до создания исходных копий;
после записи читается полный материализованный состав. [1, 2]

DOS-метаданные этого ZIP не содержат Unix-бит исполняемости. Режим Git
в v2 берётся из независимо прочитанного неизменяемого дерева, а не
приписывается отсутствующим Unix-битам архива. Подготовка v2 не запускает
подпроцессы, Go, Product или установку. Прежний архив и квитанция отказа
сверены повторно и сохранены; результат v2 имеет `completed:true`. [1]

Полный 22-мегабайтный архив источника остался в удалённой разрешённой
области и не дублируется в [raw-evidence.zip](raw-evidence.zip).
Локальный аудит проверяет его закреплённую идентичность, диагностику,
квитанции и полные инвентари, а также независимо читает все исходные
Git-байты. Повторного локального хеширования самого загруженного ZIP-архива
этот отчёт не заявляет. [1–3]

### Ошибка v2 при проверке представления абсолютного пути

После успешных проектных сканирований локальный
`check_evidence_v2.py` отклонил их поле `root`: он ожидал обратные косые
черты из `str(PureWindowsPath)`, тогда как производственный
`internal/archguard/scan.go` применяет `filepath.ToSlash`.
Фактический путь `D:/dev/ChatGPT/...` обозначал тот же точный абсолютный
корень, но не совпадал с ожидаемым текстом. [1, 2]

В `check_evidence_v3.py` изменена ровно одна строка:
`str(...)` заменено на `(...).as_posix()` при построении ожидаемого
`root`. Буквальные argv/cwd команд, хеши полных отчётов, содержимое
исходников и все счётчики проверяются с прежней строгостью.
Исходный v2 сохранён; его отказ воспроизведён локально с кодом 1 и
`RuntimeError: Scan used a different physical root`. На тех же сырых
данных v3 завершился с кодом 0. Оба потока и квитанция повторения лежат
в `a3-local-checks/`; нового Go-запуска для этого исправления не было.
[1, 2]

Воспроизведённый вывод v3 относится к стадии до удаления baseline и
честно содержит `architecture_gate:"FAILED"`,
`baseline_edit_performed:false` и `build_vet:"NOT_CHECKED"`.
Позднейший финальный результат подтверждается отдельными квитанциями
материализации и финальной фазы, а не приписывается этому checker. [1, 2]

## 7. Независимый аудит и воспроизведение

Собранный архив содержит **112 элементов**: 111 файлов и собственный
`PACKAGE_FILES.json`. В нём находятся все исходные потоки и квитанции,
первый отказ и диагностика, версии подготовки/checker, локальные и
удалённые планы, полный инвентарь исходников, шесть закреплённых входов,
новый baseline, точные удалённые блоки и финальный скрипт материализации.
Полной копии базы и архивных передач в base64 нет. [1]

Все шесть исходных транспортных ZIP были прочитаны заново; их точные
байты, состав и каждый из 72 переданных файлов сверены с собранными
данными. В частности, проверены оба последних архива:

- `a3-pruned-architecture.zip`: 8096 байт,
  SHA-256 `054346413d0d3e2dc9cda40711b8e18ee808a95d7db15ce9d56bf575f2cdb2ba`;
- `a3-prune-inputs.zip`: 183276 байт,
  SHA-256 `88fad0852131f0735593b42f4703ea6be5d8695862a3cb023a5505af5efa27bd`.

Исходные транспортные ZIP не перезаписывались. Их сведения и хеши каждого
элемента сохранены в `TRANSFER_ARCHIVES.json`. Для всех десяти
квалификационных команд независимо проверены хеши stdout/stderr,
буквальные argv/cwd, связь PID с квитанцией запуска, завершение без
таймаута и код выхода. Две тестовые команды проверены по точным событиям
и причинам отказа; архитектурные — по полным отчётам и всем шести
самостоятельно пересчитанным счётчикам. [1–3]

`audit.py` не импортирует и не исполняет архивные Python-скрипты.
Он использует стандартную библиотеку Python, локальное чтение
`git rev-parse`, `git ls-tree`, `git cat-file`, разбор данных и проверку
хешей. Единственная запись — новый итоговый JSON без перезаписи
существующего файла. Локальная неизменяемая база должна уже находиться
в Git; сетевой загрузки и Go-исполнения в аудите нет. [3]

Из каталога публикационного отчёта основной аудит воспроизводится так:

```sh
python audit.py \
  --archive raw-evidence.zip \
  --git-repo ../../../.. \
  --output audit-recheck.json
```

Для дополнительного повторного хеширования самих шести исходных
транспортных ZIP следует добавить `--transfer-dir /path/to/original-zips`.
Сохранённый [audit.json](audit.json) получен именно с этим дополнительным
входом. Без него скрипт по-прежнему проверяет закреплённые сведения всех
передач и каждый их содержательный файл внутри итогового архива, но
выдаёт `original_zip_bytes_rehashed_in_this_replay:false`.
Для полного совпадения сохранённого результата нужны те же шесть ZIP;
они не требуются для проверки исходников, планов, событий и счётчиков.
При другой раскладке каталогов следует передать фактический путь к
локальному репозиторию с той же базой. [2, 3]

## 8. Собственное ревью и ограничения

Собственное ревью охватило владельца зависимости, единственное
связывание с `s.api`, существующие пути создания сервера, HTTP-контракт,
повторное чтение POST, семантику контрольной мутации, фактические тестовые
события, полные составы исходников, все архитектурные изменения и
точное удаление четырёх блоков baseline. Утверждения README сверены с сырыми результатами
и машинным аудитом; неуспешные попытки из §6 сохранены. [1–3]

Пределы результата остаются конкретными:

- Общий архитектурный барьер **FAILED**. Существующие 387 `new`,
  42 `grown`, 128 `stale` и 72 проблемы работников требуют собственной
  работы; A3 их не закрывает.
- Независимость двух подставных зависимостей не доказывает раздельность
  производственных файлов предпочтений. Реальное сохранение на диске
  этим направленным набором не квалифицирована.
- Полная совокупность тестов Go, установленный Product, нативный
  планировщик и системная квалификация не запускались. Обычные файловые
  операции и примитивы Windows в тестовой инфраструктуре выполняются;
  утверждения об отсутствии любого нативного кода нет.
- Квитанции подтверждают завершение непосредственных команд. В них
  `whole_process_tree_deadline_enforced:false`; независимое доказательство
  завершения всего дерева порождённых процессов отсутствует.
- Финальная сборка и `vet` относятся к точному дереву таблицы 1.
  Документы добавлены позднее; опубликованный commit и внешнее ревью
  данным архивом не установлены. [1, 2]
