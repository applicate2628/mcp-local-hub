## RX-04/read — отдельный read-only пилот из #623

**Не production reader и не замена Go API.** Семь новых файлов только в `experiments/rust-anchored-read/`; никаких изменений установки, состояния, vault, транзакций или зависимостей продукта. Это отдельная ответственность от process-owner #625 и relay #626.

[README и воспроизведение](https://github.com/applicate2628/mcp-local-hub/blob/57f69575bbe2276f14e330ecd80249872d690f9a/experiments/rust-anchored-read/README.md)

### Реализованная граница

`read_verified(root, components, cap, expected_digest, canceled)` держит исходные native handles: root → относительный компонент → final file. Нет позднего pathname reopen. NT open с no-reparse, проверка атрибутов, bounded чтение и SHA-256 тех же возвращаемых байтов.

Один владелец каждого handle, не более двух удерживаемых одновременно; cleanup отдельно от primary failure. Один close-attempt, без повторного закрытия потенциально переиспользованного численного handle. Закрытие с ошибкой не возвращает успешные данные. Реальная инъекция ошибки CloseHandle ещё не квалифицирована.

Размер проверяется не только при stat: один sentinel-байт поверх оставшегося лимита обнаруживает рост. Буфер/чанк используют upstream zeroize; это не обещание стирания всех прежних копий или allocator history.

### Native evidence

Windows 11 build 26100 / x64, Rust 1.99.1, только уже кешированные `windows-sys=0.61.2`, `sha2=0.10.9`, `zeroize=1.9.0`; `--offline --locked`, без скачивания/установки.

**15 native tests прошли без пропусков:** Unicode/empty/exact bytes, invalid inputs, cancellation до open и между чтениями, wrong hash/oversize, directory/missing native error, reparse в root/его ancestor/промежуточном/конечном компоненте, замена пути до и после приобретения handle, рост после stat, exact-cap EOF, сохранение инъецированной phase-error и отсутствие роста handles на повторных success/failure.

Отрицательный stub обнаружен первоначальными тестами. Временное удаление sentinel-байта выявлено тестом роста; исходные байты восстановлены, все проверки повторены. **`clippy --all-targets -- -D warnings` и `fmt --check` прошли.** Пользовательские файлы/секреты не читались. Symlink tests использовали уже доступную способность ОС, без elevation/настроек.

### Почему пока НЕ интегрируем

- Только drive-absolute Windows local paths; UNC/verbatim/device/network namespace не квалифицированы.
- Лимит 1 МиБ, ожидаемый digest уже разобран в 32 байта. Backup-specific cap и optional empty digest существующего Go API не реализованы: это **не drop-in parity**.
- Cancellation не прерывает уже заблокированный синхронный ReadFile; проверки выполняются между операциями.
- Нет Go/Python FFI, writer/lock/transaction engine, atomic content snapshot или нового полномочия на чтение.
- Не Windows возвращает Unsupported до эффекта; Linux/macOS native implementation/tests ещё нет.
- Нужны exact Go-contract comparison, native failure/close injection, дополнительная версия/FS qualification, независимое security/lifecycle review и применимые repo-gates.
- Нет измеренного speedup, memory improvement или преимущества над обновлённым Go-владельцем.

Исходный Go reader сверён на #616 `53645ec7170c9d56073ab5140dec865b23ce7c21`; затронутые reader-файлы без дельты относительно ранее просмотренного `92bc059c`. Новый commit основной ветки при интеграции перепроверяется.
