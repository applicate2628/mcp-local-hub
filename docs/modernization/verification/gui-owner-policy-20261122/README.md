## 1. Контракт и исправление

Публикация обычного GUI-владельца происходит после получения блокировки единственного экземпляра и до создания `Server`. Поэтому служба политики должна принадлежать этому владельцу уже при публикации; обращение к будущему `Server.api` не задаёт правильный срок её жизни.

`GUIOwnerLifecycle` теперь удерживает `GUIOwnerPolicy` с двумя существующими операциями API (программного интерфейса): чтением правил запуска и условным возобновлением. `SingleInstanceAcquireOptions.OwnerPolicy` передаёт зависимость через обычный и учитывающий резервирование пути приобретения блокировки. После успешной публикации тот же объект идёт вместе с lease — владением блокировкой — через запуск, передачу полномочий при перезапуске и завершение.

Сначала возвращается операция возобновления, затем проверка политики; обе должны завершить освобождение блокировки настроек. Ошибка, в том числе ошибка освобождения после уже применённого изменения настроек, запрещает публикацию. Только успешная запись привязывает исходное поколение процесса к объекту жизненного цикла; нового чтения файла после публикации не добавлено. `BeginHandoff` проверяет прежнюю идентичность владельца и запрашивает ту же зависимость до изменения записи.

Значения политики читаются заново при переходе, а её объект сохраняется. В рабочем приложении сохраняются общие глобальные настройки. Публичные функции, формат записи, алгоритм поколения и существующие владельцы освобождения блокировок сохранены. Новых глобальных фабрик, фоновых исполнителей или зависимостей нет.

**Совместимость оставляет архитектурный остаток:** при отсутствии явно переданной политики `newGUIOwnerLifecycle` один раз создаёт `api.NewAPI()` вне `internal/app`. Этот конструктор не скрыт исключением. Изменение устанавливает владение зависимостью; утечка ресурсов у прежних временных API-объектов здесь не доказывается.

## 4. Отрицательный контроль

Контроль сохраняет новую структуру кандидата и тесты, но одним Go overlay — подменой файла при компиляции — возвращает точные исходные тела `writeCurrentGUIOwnerRecord` и `GUIOwnerLifecycle.BeginHandoff` из родителя. Подмена содержит только `internal/gui/gui_owner_lifecycle.go`; оба тела побайтно сопоставлены с родителем. Это **возврат исходного поведения в совместимой структуре**, а не выполнение целиком неизменённой старой головы.

Оба `resume_conflict` сохраняют PASS. В сценариях независимых владельцев исходное тело возвращает `GUI_CONTROL_CONFLICT` уже при возобновлении; позднейшие утверждения этих двух случаев контроль не достигает. В обеих ветвях `resume_release` также возникает ранний `GUI_CONTROL_CONFLICT`: lease не возвращается, а моделируемая ошибка освобождения не достигается. В случаях `policy_read`, `stopped` и `policy_release` возвращаются lease и успех вопреки подменённой политике; handoff игнорирует ошибку и меняет активную запись. Сырые диагностические сообщения сохранены и сверены с терминальными событиями; ожидаемый FAIL не переименован в успех реализации.

Даже контроль с каноническим API направлен в собственное состояние через `LOCALAPPDATA` и изолированную инициализацию пакета тестов (`TestMain`). Ошибочные результаты остаются в архиве. Счётчик 17 FAIL включает родительские события; он не означает 17 независимых конечных отказов.

## 7. Ревью и оставшиеся границы

Выполнены собственное и независимое внутреннее чтение требований, порядка владения, ошибок, совместимости и сложности; блокирующего дефекта в закреплённом кандидате не найдено. Сверены все сырые события завершения тестов и их точные множества. **Внешнее ревью новой точной публикационной головы — PENDING**, ожидается; данный отчёт не объявляет PR готовым к включению.

Инъецируемый `GUIOwnerPolicy` остаётся доверенной зависимостью: он должен соблюдать синхронный вызов переданного обработчика (callback) и возврат ошибок освобождения. Канонический API проверяет управление перед callback; произвольная некорректная реализация зависимости здесь не квалифицирована. Привязан объект зависимости; действующее разрешение пути файла настроек при вызове сохранено.

Новые сценарии резервирования проходят соответствующую ветвь с пустым маркером. Они не квалифицируют настоящий дочерний перезапуск, чужое поколение процесса, аутентификацию активного резервирования, нативный отказ освобождения блокировки, аварийное завершение, завершение всех GUI-работников или установленный продукт. Реальные отказы записи с уже применённым эффектом остаются контрактом существующего владельца файлового состояния; модель ошибки политики не заменяет такие проверки.

Открыты общий архитектурный барьер и совместимый конструктор вне `internal/app`, полные Go-наборы, нативный жизненный цикл и поставочный комплект Product. Прежний перенос `gui → mcproute`, проверенные владельцы LSP (Language Server Protocol, протокол языковых серверов) и manifest-операции сохраняются в своих областях; этот инкремент не закрывает прочие находки, Serena/Product, производительность, Rust или очередь PR.
