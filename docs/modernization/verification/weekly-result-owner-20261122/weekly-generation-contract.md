## Что действительно обеспечивает текущий код

Восстановление через `CreateXMLIfAbsent` использует создание только при свободном имени. В Windows ветвь COM (Component Object Model, компонентная объектная модель Windows) вызывает `RegisterTask` с флагами создания и подавления регистрационных триггеров; принудительного обновления существующей задачи в этой ветви нет. Если конкурент занял имя после наблюдения отсутствия, отказ создания сохраняется вместе с исходной ошибкой и материалом восстановления. Это свойство относится к **созданию**, а не к предшествующему удалению [1–3].

В weekly-refresh больше не используется заменяющий `ImportXML`. Сам общий метод `ImportXML` по-прежнему реализует `/F` для других потребителей; утверждение об устранении `/F` во всём проекте было бы неверным. Предварительный снимок и сравнение текущего XML позволяют отказаться при **наблюдаемом изменении определения** [2–4].

**Таблица 1. Проверенное действие и предел его вывода.**

| Действие | Подтверждаемое свойство | Неподтверждённое свойство |
|---|---|---|
| Сохранение предыдущего XML | Есть материал для последующего восстановления | Владение текущим объектом Scheduler |
| Повторный `ExportXML` и сравнение | Определение совпало в момент наблюдения | Отсутствие замены после наблюдения или замены на идентичный XML |
| Кооперативная блокировка weekly-refresh | Согласованные участники используют общий порядок блокировок | Исключение другого процесса с самостоятельным правом изменения Scheduler |
| `CreateXMLIfAbsent` | Существующая задача не заменяется этим восстановлением | Условное удаление ранее наблюдавшегося поколения |
| Подтверждение успешного применения | Подтверждён результат объявленного сценария до ошибки освобождения блокировки | Вечное владение именем или запрет последующих внешних изменений |

## Почему промежуток перед удалением остаётся открытым

`windowsScheduler.Delete(name)` передаёт имя в существующий COM-адаптер. Адаптер находит задачу, затем вызывает `$f.DeleteTask($t.Name, 0)`. Это удаление **по имени**. Публичная сигнатура `ITaskFolder::DeleteTask` содержит имя и неподдерживаемый параметр flags; параметра ожидаемого поколения, версии или контрольной суммы в ней нет. В опубликованном интерфейсе `IRegisteredTask` метода условного удаления также нет [4–6].

Отсюда следует ограничение текущей реализации: между последним сравнением XML и `DeleteTask` другой допущенный писатель может заменить задачу под тем же именем. Удержание ранее полученного объекта COM, дополнительный повторный экспорт или совпадение XML не превращают удаление по имени в атомарную операцию «удалить только это поколение». Это вывод из приведённого контракта и последовательности вызовов, а не результат нового нативного эксперимента.

Тот же предел прямо отмечен в `verifyInstallTaskDefinitionBeforeDelete` и `installTaskRollback.rollback`: наблюдение определения не является квитанцией поколения [3]. Нельзя переносить свойство создания без замены на удаление, восстановление предшествующего состояния или `RunOwned`.

## Что требуется для завершения

Следующий самостоятельный проектный шаг должен определить исполнимый контракт записи:

1. Либо подтвердить и обеспечить исключительное право изменения соответствующего пространства задач у одного владельца, включая все реальные способы изменения извне.
2. Либо явно отказывать в разрушительной замене, когда такое право не обеспечено, сохраняя прежнюю задачу и материал восстановления.

Выбранный вариант должен согласовать обновление, восстановление и настоящих потребителей стабильного имени. Затем нужны проверки внешней замены после последнего наблюдения, идентичного XML другого поколения, занятого имени и неопределённого результата нативного действия. Изменение политики доступа и такие системные сценарии требуют отдельно допущенного окружения. Этот документ не добавляет полномочий и не изменяет производственную политику.
