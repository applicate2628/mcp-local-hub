# Weekly schedule: подтверждённое применение и аудит порядка блокировок

**22 ноября 2026 года; время исполнения ниже — UTC.** Проверки A2 подтверждают
правильную классификацию уже применённого недельного расписания при отказе
освобождения блокировки, включая настоящий маршрут HTTP → API → владелец
транзакции. Результат относится к точно описанной композиции исходников.
**Реальная проверка порядка блокировок A1 остаётся FAILED:** анализатор
останавливается на динамическом вызове локального `Unwrap` из `errnoIs`.
Успех направленных фикстур, сборки и `vet` не закрывает этот барьер.
Полная квалификация и готовность запроса на включение изменений (PR) этим
отчётом не утверждаются. [1, 2]

Это продолжение существующей области #660 после опубликованного
`203c7bacef98c0445549512a2b6cab61eca6dcd1`, а не свидетельство нового
опубликованного коммита. Предыдущий отчёт описывает родителя
`63ba3e771cb5a165e276bf7c481e10a3d3a19837`; фактическая база исполнения и
дополнительные входы приведены отдельно в [§2](#2-точный-состав-исходников).
Документы и независимый локальный аудит добавлены после квалификации и не
входят в компилировавшийся состав. [1–4]

API (Application Programming Interface) означает программный интерфейс,
HTTP (Hypertext Transfer Protocol) — протокол обмена запросами и ответами.
UTC (Coordinated Universal Time) — всемирное координированное время.
SHA-256 (Secure Hash Algorithm, 256 бит) используется как криптографическая
контрольная сумма точных байтов артефакта.

## 1. Изменённый контракт A2

До исправления владелец недельной транзакции сохранял требуемое состояние
задачи, а `ApplyWeeklyRefreshSchedule` — требуемые настройки, если создание
задачи было подтверждено и её определение прочитано обратно. При последующем
отказе освобождения блокировки результат уже имел состояние
`applied-release-unconfirmed`, но ошибка не содержала существующего признака
`ErrAppliedLockReleaseUnconfirmed`. Обработчик графического интерфейса (GUI)
проверяет именно `IsAppliedLockReleaseUnconfirmed`; поэтому подтверждённое
изменение выдавалось клиенту как HTTP 500 с `updated:false`. Направленный
отрицательный контроль API и исправленный контроль маршрута воспроизводят
этот разрыв на прежнем владельце результата. [1, 2]

Правка находится в двух существующих владельцах результата в
`internal/api/weekly_refresh.go`. `runWeeklyRefreshTaskTransaction` сначала
объединяет первоначальную ошибку с ошибкой освобождения, затем добавляет
существующий признак применённого изменения только для подтверждённого
`weeklyRefreshTaskCommitted`. `ApplyWeeklyRefreshSchedule` устанавливает
собственный флаг `applied` после подтверждённого совместного результата и
классифицирует ошибку после возврата `withWeeklyScheduleSettings`, когда уже
известен исход освобождения внешней блокировки настроек. Повторный признак
не добавляется, если внутренний владелец уже классифицировал ошибку. [1]

Успешная предварительная запись настроек сама по себе не подтверждает
применение. Общий помощник в `settings.go` не изменён; произвольный callback,
вернувший `nil`, не получает нового права объявлять совместный результат
применённым. Через `errors.Is` сохраняются исходная ошибка создания и причины
обоих отказов освобождения, в том числе при их одновременном возникновении.
Производственный обработчик GUI не изменён. [1, 2]

**Таблица 1. Различаемые результаты A2.**

| Наблюдённый исход операции | Настройки и задача | Классификация и ответ маршрута |
|---|---|---|
| `Create` подтверждён, обратное чтение соответствует запросу; weekly/settings/both release вернул ошибку | Требуемая пара сохраняется | Признак applied; HTTP 200, `updated:true`, `warning:"lock_release_unconfirmed"` |
| `Create` вернул ошибку без записи, прежней задачи нет | Точные прежние байты настроек восстановлены; задача отсутствует | Признака applied нет; HTTP 500, `updated:false`, `restore_status:"n/a"` |

Наличие требуемого XML после ошибочного `Create` не превращает
неподтверждённую операцию в успех. XML (Extensible Markup Language,
расширяемый язык разметки) здесь хранит сериализованное определение задачи
планировщика. [1, 2]

## 3. Среда, изоляция и границы проверки

Квалификацию исполнил основной исполнитель на Comet, Windows/amd64, в
`D:\dev\ChatGPT\mcp-residual-next-20261122-dcb40fba`. Использованы ранее
имеющиеся инструменты и кэши. Их проверяемые хеши, буквальные команды,
рабочие каталоги, идентификаторы непосредственных процессов (PID) и сроки
ожидания сохранены в квитанциях. Исполняемый `qualify_go.py` закреплён
SHA-256 `a483536d689df8c5713fddbdfd221b85953cf0ce4f9d578a31c4cdbfc6b9a26e`.
Локальный независимый аудит использовал только Python и чтение Git-объектов;
повторного Go-исполнения или удалённого запуска в ходе аудита не было. [1–3]

Во всех шести фазах подтверждены `GOOS=windows`, `GOARCH=amd64`,
`GOTOOLCHAIN=local`, `GOPROXY=off`, `GOSUMDB=off`, `GOVCS=*:off`,
`GOFLAGS=-mod=readonly`, `GOTELEMETRY=off` и
`MCPHUB_E2E_SCHEDULER=none`. Фазы не разрешают операции нативного планировщика.
Рабочие, временные и пользовательские каталоги квалификации размещены в
разрешённой области `D:\dev\ChatGPT`; пути уже установленных исполняемых
инструментов могут находиться на другом диске. [1, 2]

Маршрутные тесты используют зарегистрированный производственный маршрут
и его штатного владельца `ApplyWeeklyRefreshSchedule`. Подставное
хранилище заменяет scheduler; HTTP-запрос обрабатывается внутри процесса
через `httptest`, без запуска слушающего сервера и рассылки событий.
Сохранение настроек, получение и освобождение блокировок, обратная проверка
определения, восстановление, классификация ошибки и формирование ответа
остаются реальными. Готовая ошибка applied в обработчик не подставляется. [1]

Узкий `SetWeeklyScheduleUnlockFailuresForTest` разрешён только при
`testing.Testing()`, требует одного точного приватного корня для настроек
и состояния демонов и затрагивает только два заранее известных пути
блокировок. До установки общего hook регистрируется очистка: прежний hook
восстанавливается точно, реальные удерживаемые дескрипторы освобождаются,
а запись о неподтверждённом освобождении удаляется только после успешного
фактического `Unlock`. Сценарии не используют `t.Parallel`. Проверка
сохранённых настроек после отказа освобождения не повторяет получение
отравленной файловой блокировки: `SettingsGet` использует `settingsMu`. [1]

Это проверка поведения с подставным планировщиком и приватным состоянием.
Она не является проверкой установленного Product, реальных системных задач,
Windows Task Scheduler или общей готовности системы. Обычные файловые
операции и примитивы платформы в тестах выполнялись; утверждения об отсутствии
любого нативного кода здесь нет. Квитанции подтверждают завершение
непосредственных команд без таймаута. Независимого доказательства завершения
всего дерева порождённых процессов архив не даёт. [1, 2]

## 5. Разбор отрицательных контролей и отказов

### A1: прежняя граница и новый реальный отказ

В `a1-old-analyzer` сырые события содержат ровно четыре неразрешённых
вызова из `secureCreateClientConfigIfMissingImpl` в
`secure_create_client_config_windows.go` на строках 129, 134, 138 и 146.
Это наблюдение соответствует прежней границе определения происхождения
локального замыкания. Но план дополнительно требует текст `cleanup`,
которого в сыром журнале нет. Поэтому `oracle_pass:false` и
`completed:false` сохранены как неуспех; этот запуск не переименован
задним числом в успешно пройденный отрицательный контроль. [1, 2]

Новые направленные фикстуры проходят, затем настоящий
`TestWeeklyRefreshLockOrderInventory` завершается с диагностикой:

```text
unresolved typed boundary from errnoIs at secure_create_client_config_windows.go:315:10
(func() error: local function or method has no indexed body)
```

В этом месте `errnoIs` вызывает `Unwrap()` через локальный интерфейс
`interface { Unwrap() error }`. Неопределённая динамическая граница остаётся
закрывающим отказом анализа. Этот результат не доказывает реальное обратное
взятие блокировок, но также не позволяет заявить доказанное отсутствие
такого пути. [1, 2]

### A2: валидный контроль API

При возврате прежнего `weekly_refresh.go` четыре конечных сценария
подтверждённого применения завершаются точным утверждением
`applied disposition = false, want true`: прямой владелец транзакции и
`Apply` с отказом weekly, settings и обеих блокировок. Родительские тесты
и пакет добавляют остальные события FAIL из таблицы 4. Сценарии
неподтверждённого создания и восстановления проходят. С кандидатом все
14 конечных случаев проходят; контроль выделяет именно отсутствующий
признак применённого результата. [1, 2]

### A2: первая GUI-фикстура не подтверждала нужную ветвь

Первая `weeklyScheduleRouteTaskXML` не записывала `Enabled` у
`CalendarTrigger` и обязательные логические поля `Settings`.
`weeklyTaskXMLMatchesSpec` проверяет их через `xmlBool`, где требуется
явный текст `true` или `false`; отсутствие поля не считается значением
`false`. Поэтому все три сценария, названные `committed-*`, на старом и
новом владельце давали сообщение `does not match the requested definition`
до подтверждения совместного изменения. Ответ был HTTP 500,
`updated:false`, `restore_status:"degraded"`. [1, 2]

Изначальный runner принял старый GUI-контроль по более слабому условию
ошибки статуса, однако одинаковый отказ кандидата обнаружил ошибку
фикстуры. Этот первоначальный красный результат оставлен в архиве и
исключён из поведенческого доказательства A2. Исправлены только две
строки XML-помощника: добавлены явные логические поля, соответствующие
производственному `buildCreateXML`. Утверждения теста, отрицательные случаи
и производственная логика не ослаблены. [1, 2]

После исправления старый владелец всё ещё даёт HTTP 500 и `updated:false`
для трёх подтверждённых сценариев, но уже с `restore_status:"n/a"` и без
диагностики несоответствия определения. Кандидат проходит все шесть
сценариев. Именно эта исправленная пара служит отрицательным контролем
настоящего маршрута HTTP → API. [1, 2]

### Список владельцев: разные физические составы

Первая смежная проверка остановилась на точном несоответствии
`appendHubMcpLogLine calls=0, reviewed=1`: прямое создание блокировки
находится в замыкании `hubMcpLogProductionEffects/func-lit#2`. Исправленный
список также учитывает два уже существующих владельца:
`(*secretsInitRecoveryOwner).locked` и `acquireStateFileObservedLease`.
Получается 28 владельцев для рассматриваемой правки. [1, 2]

На более широком физическом квалификационном составе следующая проверка
обнаружила `AcquireSupervisorLockQuietObserved calls=1, reviewed=0`.
Добавление ровно двух владельцев из [§2](#2-точный-состав-исходников)
в отдельный квалификационный вход даёт 30 и позволяет финальной выборке
пройти. Это уточнение состава теста, а не исправление освобождения
блокировок у перечисленных владельцев. Подтверждённого отсутствия любых
ошибок у этих владельцев одна инвентаризация не устанавливает. [1, 2]

## 6. Что проверяют успешные выборки

A1 запускает четыре точных корня:
`TestWeeklyTypedLocalLiteralOrigins`, `TestWeeklyTypedContextOrigins`,
`TestWeeklyTypedCallGraphResolution`, `TestWeeklyTypedExportXMLBoundary`.
Их 68 конечных фикстур проверяют сохранение локального тела при разрешении
прямого замыкания, прямые и транзитивные пути к settings, ограничения
при записи и передаче функции, захват переменных, передачу доказанного
`nil`-контекста, именованные функции и закрывающий отказ при неизвестном
происхождении либо превышении бюджета контекстов. Отдельно различаются
типизированный nil-указатель внутри интерфейса и nil-интерфейс. Эти
результаты ограничены точными фикстурами и не заменяют неуспешный
производственный барьер из §5. [1, 2]

API A2 проверяет `TestWeeklyRefreshTransaction_AppliedReleaseDisposition`
и `TestApplyWeeklyRefreshSchedule_AppliedReleaseDisposition`: два исхода
прямой транзакции и четыре исхода совместного изменения, каждый при
трёх вариантах отказа освобождения. Проверяются `errors.Is` для исходных
причин, значение applied-признака, статус восстановления, точные байты
возвращённых настроек и итоговое определение задачи. В частности,
одновременный отказ обеих блокировок не теряет ни одну причину. [1, 2]

`TestWeeklyScheduleHandler_RealApplyReleaseSettlement` проверяет
нормализацию расписания, точное определение и единственный вызов создания,
число удалений/восстановлений, итоговые настройки и задачу, точные пять
полей JSON-ответа, предупреждение и подсказку восстановления. Исходные
тексты частных ошибок не должны попадать в HTTP-ответ. JSON здесь —
формат клиентского ответа, отдельно от JSON-событий `go test`. [1]

Шесть корней финальной смежной выборки:

- `TestSupervisorIntentLockOwnershipProductionInventory`;
- `TestSupervisorIntentLockOwnershipFixtureMatrix`;
- `TestAppliedReleaseClassifierFixtureRejectsSibling`;
- `TestWeeklyRefreshReleaseSettlementMatrix`;
- `TestWeeklyScheduleSettingsReleaseSettlementMatrix`;
- `TestReleaseAndJoinAppliedSettlementMatrix`.

Они проверяют фактический список владельцев, его направленные фикстуры,
запрет классификации в соседнем неуполномоченном владельце и существующие
матрицы исходов освобождения. Признак applied разрешён только трём
проверяемым владельцам: `releaseAndJoinApplied`,
`runWeeklyRefreshTaskTransaction` и `(*API).ApplyWeeklyRefreshSchedule`.
Точные имена всех родителей, подтестов и событий пакета, включая
единственное выполнение каждого, находятся в [audit.json](audit.json).
[1, 2]

## 7. Независимая сверка и воспроизведение аудита

Архив заново проверен по размеру и SHA-256, уникальности безопасных имён
и полному списку: **178 элементов**, из них **177 содержательных файлов**
и сам `PACKAGE_FILES.json`. Размер и хеш каждого содержательного файла
совпадают с манифестом. Предыдущий архив отдельно проверен по точному
хешу и размерам его перечисленных файлов; план прежней материализации
побайтно совпадает между архивами. [1–3]

Для **19 пар stdout/stderr** проверены отдельные хеши квитанций: 14
квалификационных команд и 5 последующих проверок `gofmt -l`. Все исходные
JSON-события тестов разобраны заново; для каждой команды проверено точное
мультимножество PASS/FAIL/SKIP и единственное событие запуска каждого
именованного теста. Имена сверяются с разобранными таблицами исходных
фикстур и отдельно просмотренными динамически образованными случаями.
Сохранённый `oracle_pass` не принимается на веру: он пересчитывается по
реальному коду выхода, обязательным строкам и событиям. [2, 3]

У пяти записывающих запусков `gofmt -w` исходные квитанции не содержат
отдельных хешей потоков. Их пустые stdout/stderr проверены по хешам
`PACKAGE_FILES.json`; точные входные/выходные байты форматирования,
аргументы, успешный код и завершение сверены отдельно. Это ограничение
формата квитанций явно сохранено в `audit.json`, без вымышленной
покомандной контрольной суммы. [1–3]

Проверочный скрипт читает архивы и Git-объекты; единственная запись —
новый результирующий JSON, создаваемый без перезаписи существующего файла.
Пример повторения из каталога публикационного отчёта:

```sh
python audit_evidence.py \
  --archive raw-evidence.zip \
  --previous-archive ../scheduler-upgrade-recovery-20261122/raw-evidence.zip \
  --git-repo ../../../.. \
  --output audit-recheck.json
```

Требуется локальный Git-репозиторий с указанной неизменяемой базой;
скрипт ничего не загружает и не исполняет проект. Он использует только
`git rev-parse`, `git ls-tree` и `git cat-file`. Идентичность результата
проверяется по содержимому JSON и закреплённым хешам. При иной раскладке
каталогов следует явно передать фактические пути к тем же архивам и базе.
[3]

## 8. Ревью и оставшиеся условия

Собственное ревью проверило соответствие результата владельцу совместной
операции, сохранение причин ошибок, различие подтверждения и возможного
эффекта записи, восстановление точных настроек, ограничение тестового
hook и подлинный маршрут до API. Затем выполнен независимый разбор всех
сырых результатов, в том числе неудачных попыток из таблицы 4. [1–3]

Остаются следующие конкретные ограничения:

- **A1 не закрыт.** `errnoIs` в
  `internal/api/secure_create_client_config_windows.go:315` вызывает
  динамический `Unwrap`; текущий анализатор не устанавливает его локальные
  цели. Следствие — производственный барьер порядка блокировок FAIL,
  несмотря на успешные 68 фикстур.
- **Квалификационный состав шире самостоятельной правки #660.** Успех
  списка 30 владельцев, `build ./...` и `vet ./...` относится к указанным
  3309 физическим файлам и точным подменам. Публикуемый список 28 владельцев
  не прошёл этот более широкий состав; подмена цифры или перенесение
  результата на другую голову недопустимы.
- **Отдельный существующий дефект secrets остаётся.** В
  `internal/api/secrets_init_recovery.go`,
  `(*secretsInitRecoveryOwner).locked`, строка 535 содержит
  `defer func() { _ = lock.Unlock() }()`. Если освобождение возвращает
  ошибку после `fn`, она отбрасывается, а вызывающему коду возвращается
  результат `fn` без причины отказа освобождения. Физический файл имеет
  SHA-256 `e585d5fc9c3b6a82f66b557b7fa50937fddfa2b94d7d473870d2cd1ae8971544`.
  Включение владельца в список учитывает конструктор блокировки; этот
  дефект не исправлен и его поведение здесь не квалифицировано.
- **Границы исполнения сохранены.** Полная Go test suite, установленный
  Product, нативный планировщик и системная квалификация не выполнялись.
  Новая опубликованная голова, внешнее ревью и общее завершение дерева
  процессов данным архивом не установлены. [1, 2]
