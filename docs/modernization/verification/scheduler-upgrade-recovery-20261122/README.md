восстановление weekly-refresh в существующей области #660. Проверки поведения

источник четырёх вызовов локального замыкания в существующем защищённом writer.

## 1. Изменённый контракт

`SchedulerUpgrade` для серверной задачи и `upgradeLazyProxyTask` теперь
делегируют замену одному `replaceTaskForSchedulerUpgrade`. Прежде оба пути
отбрасывали ошибку `ImportXML` после неудачного `Create`; импорт мог принудительно
заменить задачу, занявшую то же имя. Сохраняется ранее введённый строгий допуск
снимка: ошибка чтения, пустой успешный результат и одновременно возвращённые
XML и `ErrTaskNotFound` не разрешают удаление [1].

**Таблица 1. Порядок замены и результат отказа.**

| Состояние | Действие | Сохраняемое свидетельство |
|---|---|---|
| Подтверждено отсутствие | Только `Create`; `Delete` не вызывается | Конфликт нового владельца имени остаётся ошибкой |
| Есть прежнее определение | Требуется исходная возможность `scheduler.XMLCreator`; сохраняется защищённый снимок | Путь, исходные XML-байты, время захвата и SHA-256 |
| Повторное чтение перед удалением изменилось, пусто либо ошибочно | Замена запрещена | Ошибка и уже сохранённый снимок |
| `Delete` вернул ошибку | Существующий классификатор наблюдает состояние | Первоначальная причина; при неподтверждённом состоянии — признак неполного восстановления |
| `Create` вернул ошибку | Один вызов `CreateXMLIfAbsent` через исходный scheduler | `InstallTaskRecoveryError` хранит обе причины и путь снимка |
| Имя занято перед восстановлением | Создание прежнего определения отклоняется | Текущая задача не удаляется и не заменяется |
| Восстановление применилось, но ответ ошибочный | Ошибка остаётся ошибкой | Не выводится ложное подтверждение регистрации |

Повторно использованы `retainInstallTaskSnapshot`,
`verifyInstallTaskDefinitionBeforeDelete`, `installTaskMutationFailure` и
`InstallTaskRecoveryError`. Параллельного хранилища восстановления или
дополнительного владельца транзакции нет. Снимок остаётся в защищённой области
состояния; его XML не подставляется в диагностическое сообщение.

Сравнение определений до `Delete` обнаруживает только уже наблюдаемое изменение.
Оно **не устанавливает владение поколением** между чтением и удалением по имени;
тождественные XML у двух разных поколений также неразличимы. Это ограничение
прямо отражено в комментариях. Создание только при свободном имени защищает
восстановление, но не закрывает этот отдельный промежуток.

## 2. Weekly-refresh и сохранение настроек

`runWeeklyRefreshTaskTransaction` остаётся единственным владельцем недельной
транзакции для Ensure, Apply, swap и workspace-upgrade. Теперь он использует
тот же строгий допуск снимка, сохраняет материал до удаления и требует
create-only возможности для существующей задачи. После подтверждённого
отсутствия удаление не производится.

Общий `restoreWeeklyRefreshTaskAfterFailure` не удаляет и не импортирует
принудительно текущее определение. Уже наблюдаемое прежнее определение даёт
`restoreStatus="ok"` при сохранённой ошибке исходной операции. Подтверждённое
отсутствие позволяет существующему `installTaskRollback.restore` создать
прежнее определение и прочитать его обратно. Иное или нечитаемое состояние
сохраняется с `"degraded"`; первоначальная и восстановительная/наблюдательная
ошибки объединяются. Неудачный ответ восстановления не превращается в успех
после возможного применённого эффекта.

Ошибочный `Create` больше не становится успешным только потому, что последующий
XML совпал с желаемым. При отказе проверки после успешного `Create` текущая
задача тоже сохраняется: её наблюдение ещё не даёт права удалить её или
заменить прежним определением.

`ApplyWeeklyRefreshSchedule` сохраняет прежние правила возврата настроек при
неуспехе задачи. Ошибка самой отмены настроек остаётся видимой. Требуемые
настройки сохраняются после подтверждённого `Create` и проверки определения,
включая существующее состояние неподтверждённого освобождения блокировки.
Порядок settings → weekly lock и журнал отказа повторного входа в неосвобождённую
блокировку сохранены.

Удалены два узких forwarding-wrapper: `realSchedulerAdapter` и
`testSchedulerShim`. Возврат исходного динамического scheduler сохраняет его
необязательную реализацию `XMLCreator`; прежние оболочки скрывали её за своим
сокращённым набором методов. Направленная проверка проходит через
`InstallTestHooks` и `schedulerNewForRegister`, включая отказ второго
create-only вызова при занятом имени.

## 3. Точный состав и допуск исполнения

Источник исполнения отличается от самостоятельной старой головы #660.
Физическая исходная копия — commit
`858812988833a84368c60fba1540ae601155fa71`, tree
`dba685c090952a93a80a1e82403c4646ad8aaed1`:
**3281 файл, 50583217 байт**, инвентарь SHA-256
`63d39033d88621b5152435fca89a96ec817d5973728a565d857bb235ab169bf7`.
Она полностью сверена при копировании с сохранённым составом [1].

Сначала на неё наложены 42 точных входа предыдущей квалификации #660, включая
безопасную композицию API TestMain из #665. Три новых upgrade-файла проверены
отдельными red/green overlay. Затем для weekly материализован полный физический
состав с 52 заменами/добавлениями относительно исходной копии; в эти 52 входят
предыдущие входы и 12 файлов текущей правки с перекрытием путей.
Итог: **3305 файлов, 50813638 байт**, инвентарь SHA-256
`ecc139439ca1c3b1185cdd0c6fea9861c9ed3e989d89c09421a2584156645715`.

Материализация важна для проверок исходников: их `os.ReadFile` и `go list`
читают физические файлы, а не подмены компилятора. Перед каждой фазой и после
неё подтверждены полный состав, размеры и SHA-256 исходников и перечисленных
входов. `source_head/source_tree` квитанции обозначают **базу**, не новый
коммит всей квалифицированной композиции. Точные пути и байты находятся в
`plans/materialize-weekly.json`, остальных `plans/` и `inputs/` архива.

Среда — Comet, Windows/amd64, ранее допущенный Go 1.27.4, имеющиеся `gofmt`,
GCC и кэши. Хеши исполняемых файлов проверены до и после фаз. Загрузка модулей
и toolchain запрещена: `GOTOOLCHAIN=local`, `GOPROXY=off`, `GOSUMDB=off`,
`GOVCS=*:off`, `GOFLAGS=-mod=readonly`. Рабочие, профильные и временные пути,
включая результат нативного разрешения temp, находятся в `D:\dev\ChatGPT`.
Установок и запуска Product не было.

Выбранные тесты заменяют scheduler, используют приватные файлы/блокировки и
последовательную настройку пакетных test hooks. Фикстуры получают явный
канонический дескриптор через уже существующий seam; производственный допуск
Product не ослаблен. Восемь горутин четырёх сценариев сериализации получают
завершение через исходные каналы до восстановления общих hooks; ожидания
ограничены пятью секундами. Такой таймаут означал бы FAIL, а не доказанную
остановку. В сохранённом исполнении этих таймаутов нет.

Именованные события включают родительские тесты и подтесты; событие пакета

обычный набор vet-проверок, выполняемые выбранными `go test`, не заменяют

отдельные команды не выполнялись. Прежние результаты относятся только к
своим исходникам [1].

## 5. Разбор отрицательных контролей и FAIL

**Upgrade.** Возвращён исходный `scheduler_mgmt.go` родителя при новых
фикстурах. Отсутствующая задача остаётся успешным случаем. Остальные отказы
показывают отсутствие удержанного снимка, потерю восстановительной ошибки,
принудительную замену занятого имени либо продолжение после изменившегося
второго чтения. Это исполнение старого владельца в квалифицированной
композиции, не всей старой ветки.

**Weekly.** Возвращены точные четыре производственных файла родителя:
`weekly_refresh.go`, `scheduler_swap.go`, `register.go`, `testhooks.go`.
Отдельный red-only тестовый shim возвращает `ImportXML` только фикстуре
`fakeSwapScheduler`, чтобы старый интерфейс компилировался; выбранные
отрицательные случаи этот shim не вызывают. Новый upgrade-helper и остальные
фикстуры сохраняются. Отказы подтверждают скрытую create-only возможность,
ошибочный допуск снимка, старые Import/Delete-компенсации и ложный успех
неудачного `Create` по совпавшему XML. Все 21 именованный FAIL сохранены.

**Неожидаемый успехом gate не объявлен.** `TestWeeklyRefreshLockOrderInventory`
реально завершился FAIL: в `secureCreateClientConfigIfMissingImpl` анализатор
не разрешает источник `cleanup := func() { ... }` и его четыре прямых вызова
в `secure_create_client_config_windows.go:129,134,138,146`. Квитанция имеет
`oracle_pass=false`, фаза — `completed=false`; её источник и входы после
отказа остались неизменны. Это ограничение доказательства порядка блокировок,
а не установленный взаимный захват блокировок при выполнении.

Новый точный допуск четырёх параметров `ExportXML` не превращает хранилище
в непрозрачную границу: тела помощников продолжают анализироваться. Пять
направленных фикстур этого допуска прошли и сохраняют обнаружение неизвестного
интерфейса, подмены параметра и локальной блокировки настроек. Следующее
расширение анализа должно сохранить ребро к телу локального cleanup, доказать
передачу `nil` по цепочке callback reader, исходный `sidString` для форматирования
SID и происхождение операций наблюдаемых ресурсов. Последние границы найдены
чтением исходника; фактическая текущая диагностика остановилась на cleanup.
Общих исключений для них не добавлено, повторный запуск без исправления
предпосылок не выполнялся.

## 6. Ревью и открытые условия

Собственное ревью проверило требования, ошибки, порядок действий, защищённое
хранение, совместимость динамического интерфейса и сложность. Независимое
внутреннее чтение не нашло нового производственного дефекта в ограниченной
правке. До финальной квалификации добавлены проверка второго чтения, корректные
Windows-сопоставления экранированных путей и изоляция canonical Product во
всех затронутых фикстурах. Получение исходных горутин при раннем отказе теста
также исправлено. Чужое чтение не заменяло собственного и не объявлялось
внешним ревью новой головы.

Остаются открыты:

- Барьер порядка блокировок из §5 и полные стандартные/tagged Go-наборы.
- Нативное владение поколением перед удалением, реальный конкурент, Run/Stop,
  права задачи, отмена и подтверждение завершения всего дерева процессов.
  XML не содержит отдельно сохранённые credentials и разрешения объекта.
- Неизменённая несогласованность projection: после подтверждённой пары
  settings/task ошибка освобождения может сохранять желаемое состояние,
  но не получать `ErrAppliedLockReleaseUnconfirmed`; GUI-потребитель тогда
  отвечает `updated:false`. Это подтверждено на `858812…` и всех 42 входах
  предшественника, не введено текущим recovery-изменением. Его нужно исправлять
  у владельца результата с проверкой настоящего API/GUI-перехода.
- Квалификация самостоятельной новой головы #660: здесь проверены точные
  изменённые байты на явно заданной композиции с допущенным TestMain.
- Внешнее ревью точного публикационного коммита — **PENDING**. Полные
  установочные и продуктовые сценарии — **NOT_RUN**, требуют отдельно
  допущенного окружения.
