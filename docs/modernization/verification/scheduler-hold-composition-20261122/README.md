# Квалификация композиции Scheduler и BackendRunHold

Дата: 22 ноября 2026 года. Результат относится к **точной композиции** исходников из таблицы 1. Он не является проверкой отдельно опубликованной ветки #660 и не закрывает её нативные критерии приёмки.

Сохранён `BackendRunHold` — записанный запрет запуска backend после незавершённой остановки. Два новых теста проверяют перенос этого запрета при подготовке установки и безопасную пробную запись. Адресные проверки восстановления устаревших задач, сборка и статический анализ прошли на Windows. Отрицательный контроль сохранил два настоящих `FAIL`, подтверждающих чувствительность новых тестов.

## 1. Точные входы и отличие от самостоятельной ветки

**Таблица 1. Исходники квалифицированной композиции.** PR означает запрос на включение изменений; SHA — идентификатор содержимого Git.

| Часть | Точный источник | Применение |
| --- | --- | --- |
| `master` | `75dbc6406123e22468f168b861d5e0622c9d5769`, tree `cb3eec77c23f9400be962d91c9f23834b84f7643` | Физические 3270 файлов существующей копии, без изменений |
| #660 | `1cffaab021686a7ae27a5ffc038f280160f96a60` | Все 27 изменённых Go-файлов относительно `a7d92d2852c4f6eb8afb0569ef76a545e38aacf7` |
| Изоляция API TestMain из #665 | `b5cd530969b7089e7d7cbaf5308543be8c443f8c` | Пять файлов точной разницы относительно `858812988833a84368c60fba1540ae601155fa71` |
| Новая проверка композиции | `internal/api/install_backend_hold_composition_windows_test.go` | Два теста в сохранённом overlay, без самостоятельной правки продуктового кода |

Overlay — заданная компилятору Go подмена отдельных исходных файлов без записи в исходную рабочую копию. Всего использовано 33 подмены. Их точные байты, Git blob и SHA256 перечислены в `manifest.json` внутри архива свидетельств. SHA256 — контрольная сумма алгоритма Secure Hash Algorithm с результатом 256 бит.

Единственное пересечение Go-файлов #660 с изменениями `master` после старой базы — [`internal/api/install_parsed_manifest.go`](https://github.com/applicate2628/mcp-local-hub/blob/75dbc6406123e22468f168b861d5e0622c9d5769/internal/api/install_parsed_manifest.go). В этом файле #660 добавляет единственную проверку `len(installSchedulerRecoveryTasks(err)) == 0`. Композиция добавляет именно эту строку к текущему файлу `master`, сохраняя оба его изменения:

- клонирование `prior.BackendRunHold` в новом желаемом состоянии;
- очистку hold только в отдельной копии для временной пробной записи.

Остальные 26 файлов #660 взяты побайтово из указанного коммита. Пять файлов #665 изменяют только тестовую инфраструктуру API: раннюю диспетчеризацию вспомогательных процессов и точные селекторы тестов. Здесь API — программный интерфейс приложения.

Отрицательный контроль заменяет составной `install_parsed_manifest.go` его историческим целым файлом из #660. Совпадение байтов доказано: Git blob `bd8b5f2e965db5ac7664aa8a5231101c96384893`, SHA256 `8f04d1117f44afd7e57743b78414e76f7e7f1a10d1439ed4857bb627c5540a0b`. Такая подмена на новом `master` теряет оба изменения hold. Это модель **неверного переноса целого старого файла**; обычное объединение непересекающихся изменений Git этим опытом не обвиняется в потере hold. Самостоятельная историческая ветка #660 с новым тестовым файлом не запускалась.

До исполнения проверены доступные сохранённые результаты в каталогах `mcphub-p0`, `prune-verification` и `mcphub-audit-20261121`, а также старая область evidence на Comet. Квитанция именно этой композиции с двумя новыми тестами не найдена. Старые результаты адресного prune recovery сохранены; их прежний `PASS` не был переименован в результат композиции.

## 2. Результаты выполнения

Среда: существующий Go `go1.27.4 windows/amd64` и существующий GCC. Точные контрольные суммы `go.exe`, `gofmt.exe`, `gcc.exe`, `git.exe` проверены до и после команд. Профили, временные файлы и runtime-каталоги каждой фазы созданы внутри собственной области на `D:\dev\ChatGPT`. Уже существующие кэши компилятора и модулей на D использовались повторно. Загрузка модулей отключена: `GOPROXY=off`, `GOSUMDB=off`, `GOTOOLCHAIN=local`, `GOVCS=*:off`, `-mod=readonly`.

**Таблица 2. Реальные результаты команд.** Время включает компиляцию тестового пакета, когда она требовалась; это не измерение производительности продукта.

| Фаза | Код возврата | Наблюдение | Время |
| --- | ---: | --- | ---: |
| Версия Go и `gofmt -l` всех 33 подмен | 0 / 0 | Версия совпала; неформатированных файлов нет | 0,02 / 0,04 с |
| Отрицательный контроль, `-race` | **1** | **Два верхнеуровневых теста FAIL, пакет FAIL; 0 PASS, 0 Skip** | 50,78 с |
| Кандидат, десять выбранных тестов, `-race` | **0** | **10 верхнеуровневых тестов + 16 подтестов PASS, пакет PASS; 0 FAIL, 0 Skip** | 53,26 с |
| `go build -overlay … -mod=readonly -p=4 ./...` | 0 | Сборка всех пакетов; stdout и stderr пусты | 18,79 с |

Тестовая команда использовала `-race -json -count=1 -timeout=90s -parallel=1 -p=4`, пакет `./internal/api/` и один селектор `^(имя1|имя2|…)$` с точными именами из `required_roots` в `qualification.json`. Флаг `-race` включает динамическую проверку гонок данных только на выполненных путях. Полный набор тестов не запускался.

Отрицательный контроль квалифицирован как `EXPECTED_FAIL`; его настоящие события `fail` не заменены на `pass`. Сохранены точные сообщения:

```text
HOLD-MERGE: install merge lost the original backend run hold
HOLD-PREFLIGHT: temporary write probe failed: invalid supervisor backend stop record
```

В каждой из пяти фаз совпали контрольные суммы всех 3270 исходных файлов до и после команды. Дополнительная полная инвентаризация после тестов перед сборкой и после `vet` обнаружила ровно 3270 файлов: посторонних, отсутствующих, изменённых файлов и reparse-переходов нет; служебный каталог Git исключён явно. Собственный `TMP` каждой фазы после завершения был пуст. Содержимое остальных runtime-каталогов не объявляется отсутствующим.

Remote Desktop Commander перестал находить сессии двух тестовых launcher-процессов. Повторного неопределённого запуска не было: итог получен по сохранённым `receipt.json`, `test.result.json` и журналам. Все удерживаемые runner-ом прямые дочерние процессы завершились без timeout. Это не доказательство завершения всего дерева процессов; такое ограничение записано в квитанциях.

## 3. Проверяемые инварианты и изоляция

`TestInstallMergePreservesBackendRunHold` непосредственно вызывает `buildMergedSupervisorIntentFromPriorWithProjection`. Он требует сохранения запрета запуска, исходного наблюдения, признака существования и нового описателя daemon. Исходный объект не должен изменяться. Затем тест меняет `Work[0].PendingPhase` только у результата и проверяет, что старый hold не разделяет с ним изменяемый срез.

`TestInstallPreflightPreservesBackendRunHold` непосредственно вызывает `preflightSupervisorIntentWrite` с реальным hold в собственном временном состоянии. Он требует успешной пробной записи, неизменности желаемого состояния и сохранения запрета запуска. Исходный файл intent сравнивается по полным байтам. Файлы `.preflight` и `.preflight.lock` после проверки отсутствуют. Исходные fixtures взяты из [`supervisor_backend_hold_passive_windows_test.go`](https://github.com/applicate2628/mcp-local-hub/blob/75dbc6406123e22468f168b861d5e0622c9d5769/internal/api/supervisor_backend_hold_passive_windows_test.go).

Остальные восемь верхнеуровневых тестов проверяют композицию с уже опубликованным восстановлением #660: снимок до удаления, запрет удаления без возможности восстановления, неизвестный исход удаления, наблюдение при откате, сохранение внешней подмены, происхождение ошибки при adopt, текущие и более ранние имена восстановления и классификацию ошибок. Точные имена и все реальные терминальные события сохранены в архиве.

Просмотрены пути исполнения:

- `installRecoveryPlan` из `install_task_recovery_test.go` заменяет `schedulerFactoryFn` на заданный mock и восстанавливает его через `t.Cleanup`. `newRollbackFixtureScheduler` из `install_task_rollback_test.go` хранит задачи в памяти. Выбранные Create/Delete/Export/Restore не обращаются к настоящему Windows Task Scheduler.
- `fixturePassiveBackendIntent`, `hardenedTempDir` и выбранные install/adopt fixtures используют собственные каталоги. Настройка списка контроля доступа касается только новых тестовых каталогов.
- `TestExecuteAdoptPruneRecoveryPreservesProvenance` использует собственную временную привязку loopback-порта. [`nextBindableAdoptPortForTest`](https://github.com/applicate2628/mcp-local-hub/blob/75dbc6406123e22468f168b861d5e0622c9d5769/internal/api/adopt_test.go) вызывает `listener.Close()` до возврата порта. Внешней сетевой операции в этом пути нет.
- [`TestMain` из #665](https://github.com/applicate2628/mcp-local-hub/blob/b5cd530969b7089e7d7cbaf5308543be8c443f8c/internal/api/main_test.go) сначала проверяет допустимость вспомогательной роли. Выбранные десять тестов не являются такими ролями. Обычный пакетный путь создаёт собственное состояние, изолирует клиентские файлы и межпроцессное взаимодействие, подменяет системные process/autostart/kill точки и явно очищает пакетную временную область после `m.Run()`.
- Просмотренные Windows-активные `init` пакета API регистрируют callbacks и указатели функций. Самостоятельного запуска установленного продукта до `TestMain` в них не обнаружено.

## 4. Собственное ревью

Ревью проведено до заключения о готовности ограниченного результата. Новых обязательных замечаний к двум тестам и точной композиции не осталось. Родительский агент также прочитал оба теста, merge/preflight, используемые hold fixtures и основную часть runner; это дополнение к собственному ревью.

**Таблица 3. Область собственного ревью.**

| Критерий | Проверка и вывод |
| --- | --- |
| Требования | Оба master-инварианта проверяются напрямую. Новая область исполнения ограничена двумя hold-тестами и затронутым prune/recovery потребителем |
| Корректность | Отрицательный контроль падает по двум разным заданным причинам; кандидат проходит. Сравниваются исходные байты, состояние объектов и независимость среза |
| Безопасность | Проверен путь к mock scheduler и временному состоянию; внешний продукт не запускается; helper-роли и системные точки изолированы |
| Совместимость | Сохранён единственный пересекающийся файл master; все остальные подмены привязаны к точным коммитам. Сборка и `vet` композиции выполнены |
| Сложность | Продуктовый код не расширялся. Добавлены два направленных теста без зависимостей и новых слоёв |
| Надёжность свидетельств | Входы, инструменты, исходное дерево и журнал команд привязаны контрольными суммами; настоящий отрицательный результат и отсутствие Skip сохранены |

В runner ограничивается ожидание непосредственного дочернего процесса. В случае timeout он записывает нерешённое состояние дерева **до** обращения к сохранённому `Popen` handle, а результат записывает в `finally`. На выполненном пути timeout не возникал. Возможность принудительного завершения всего дерева этим runner не заявляется и не проверялась.

## 5. Открытые критерии

Реальные `Run`, `RunOwned`, `Stop`, `Delete` Windows Task Scheduler, права и учётные данные, отмена и срок жизни дерева процессов, внешняя замена, сквозное восстановление и хранение снимков остаются открытыми. Установленные Hub/Product/Serena не исполнялись. Полные обычные и дополнительно размеченные наборы Go-тестов не запускались. Внешнее ревью точного будущего опубликованного коммита ещё требуется.

Отдельный остаток по идентичности владельца подтверждён статически в #660: [`newPlatformScheduler`](https://github.com/applicate2628/mcp-local-hub/blob/1cffaab021686a7ae27a5ffc038f280160f96a60/internal/scheduler/scheduler_windows.go) убирает доменную часть текущего имени, `ListContext` использует `sameWindowsUser`, а [`WindowsUsersEquivalent`](https://github.com/applicate2628/mcp-local-hub/blob/1cffaab021686a7ae27a5ffc038f280160f96a60/internal/scheduler/scheduler.go) допускает совпадение короткого имени. При текущем `DOMAIN_A\alice` значение владельца `DOMAIN_B\alice` также проходит эту проверку. Это неоднозначность фильтра владельца, результаты которого поступают в prune и миграцию entrypoint; фактическая чужая задача или её изменение в этой среде не наблюдались. Отдельный будущий шаг должен использовать SID — системный идентификатор безопасности Windows — и учитывать представление principal в Task Scheduler. В данном инкременте этот механизм не изменялся.

Новые hold-тесты сохранены как неактивный overlay в архиве. Их нельзя объявлять самостоятельным PASS ветки #660 или без проверки переносить в её старую активную тестовую сборку: они используют hold fixtures текущего `master`.

## 6. Сохранённые свидетельства

[qualification.json](qualification.json) содержит компактные результаты, точные источники, список десяти тестов и ограничения. [qualification-evidence.zip](qualification-evidence.zip) содержит 75 файлов: все 33 Go overlay, отрицательный контроль, полное дерево исходных blob, manifest, точный runner, exporter, пять фаз сырых журналов и квитанций, а также две полные инвентаризации source. [export-receipt.json](export-receipt.json) перечисляет размер и SHA256 каждого члена архива.

Архив: **416 775 байт**, SHA256 **`52c1c863b1438c380d0c8c808a18a0f136c37765127bd48de6cc43f84a240728`**. После переноса проверены все 12 частей, весь архив, все 75 членов и совпадение его входов с подготовленными локальными файлами. Исходные журнал и квитанции не отредактированы. Временные исходные рабочие области остаются активными до публикации и обратной проверки родительским агентом; общий source и общие кэши не перемещались.

Подготовительные ошибки команд не смешиваются с тестовыми результатами: локальный `gofmt` отсутствовал; первоначальный remote вызов через PowerShell сообщил об отклонённой загрузке пользовательского профиля; первоначальный cmd-вызов с неверным quoting первого Python token не запустил Python. Последующее исполнение использовало существующие инструменты и `cmd`. Отказа автоматического approval review не наблюдалось.
