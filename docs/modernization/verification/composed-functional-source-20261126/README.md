### Scheduler и recovery

Взята функциональная дельта #660 на `e6f1ce535db0e2b2d626fba87ae62d83fe49c2a2`. Девять конфликтных блоков в трёх файлах разрешены по действующим контрактам P02: сохраняются захваченные исходные владельцы удаляемых процессов, завершение после успешного reconcile, отказ неподготовленного Serena и нулевые побочные эффекты такого отказа. Числовое наблюдение PID или порта само по себе не заменяет исходного владельца. Предварительный просмотр описывает условие будущей остановки; Windows не получает общего запрета, который противоречил бы существующему пути подтверждённого владельца. [2]

Из комбинации #660/#669 удалена устаревшая строка сырого recovery `flock` в реестре: P02 уже использует ledgered acquisition и release/join. Регрессионный файл #669 совпал с текущим владельцем. Классификаторы применённого освобождения `WeeklyRefreshSet` сохранены отдельно. [2]

Функциональная область включает наблюдение старых scheduler tasks при установке supervisor, зависимость остановки от reconcile и исходного владельца, dry-run без изменений, setup/watchdog, autostart со strict/recovery, явное удаление и сохранённый выбор autorun OFF. Реальный Create → Export → Ready → повторный Enable автозапуска уже выполнен в #660 на точных байтах своей области; здесь он не запускался заново. Факт Ready не является доказательством фактического входа пользователя в систему или запуска установленного приложения. [3]

### Тестовые предпосылки B

После чтения всех hunks применены только 49 отсутствовавших изменений в 12 файлах; шесть уже существовавших или эквивалентных изменений оставлены в P02. Сохранены более сильные namespace/Serena-отказы и #659 save/seal/restore. Целиком заменять пересекающиеся файлы старыми версиями не потребовалось. [4]

### CMake и полный реестр владельцев

Четыре файла CMake взяты побайтно из текущего #624 `beff0af24862a552a3e54360166728181c2ee00e`: ограниченное чтение строк, корректный размер JSON-представления, соответствующие регрессии. Перед переносом проверено равенство каждого исходного blob прежней проверенной версии P02. Это перенос опубликованного изменения, без нового повторяющего PR. [5]

Первый census обнаружил старое имя `acquireStateFileObservedLease`; адресный повтор после его исправления обнаружил `tryAcquireLedgeredObservedLeaf`. Проверка возвращала только первое различие. После чтения полного scanner и всех raw `flock.New` в производственном API сверены ещё три существующих владельца: `AcquireSupervisorLockQuietObserved`, `ReadOccupiedSupervisorLockOwner/func-lit#1`, `ObserveOccupiedSupervisorLockOwner`. Они добавлены после просмотра действительных acquisition/release путей; выполняемый производственный код блокировок не изменён. Диагностика теперь возвращает все различия в стабильном порядке, сохраняя отказ при любом несовпадении. [6]

## 3. Исходные владельцы и сохранённые отказы

Кампания v3 заняла 244,141 с. Все шесть исходных command owners, включая проверку HEAD, подтвердили завершение direct process, пустой исходный Windows Job и закрытие native handles. Все двенадцать исходных stdout/stderr readers присоединены; EOF, закрытие pipe и capture подтверждены. Превышений срока и принудительного завершения Job не было. Родитель отдельно получил исходный controller и закрыл свои captures. SHA-256 исходной квитанции: `a4582d8c5028fbd2546eeb650ed7f569e94d9413c01b7428b042c992a2f27045`. [7]

Последняя отдельная проверка `git diff --exit-code` подтвердила соответствие tracked source итоговому commit после тестов. Она также измерила hashes точных исходных `receipt.json` и `root-receiving.json` одиннадцати уже закрытых фаз. Ранний текстовый транспорт нормализовал окончания строк: при публикации восстановлены только те CRLF-байты, чьи размеры и SHA-256 точно совпали с этой нативной описью. Исходные числа времени и результаты не переписывались. Последний root record сохранён без заявления о независимом последующем измерении его собственного native hash. [8]

Сохранён также отдельный preparation FAIL: в первой подготовке v3 после `git add` не был записан tree object, поэтому `commit-tree` получил exit 128. Форматирование и точные postimages уже прошли. После получения закрытия всех исходных owners выполнены только недостающий `write-tree` и `commit-tree`; успешный commit не заменил квитанцию прежнего отказа. [6]

Обычный coordinator и его exact hash сохранены в [execution](execution/run_wave_commands.py.txt). Он не включает опубликованный внешний adapter B. Настоящий поздний debug-owner receiving остаётся отдельной незавершённой квалификацией; старые full11, held UNKNOWN и V1 этим Source не переоцениваются.

## 4. Восстановление Source

Капсула P02 содержит два Git pack суммарно 1 131 423 байта. Явно перечислены 43 публичных снимка: они дают 3 974 из 4 107 объектов основы; два pack дают остальные 133. В новой пустой базе проверены все содержимые объекты и их Git hashes. Неявных branch heads, alternates, сетевого fetch или восстановленной задним числом истории нет. [1]

Сначала выполните [инструкцию восстановления основы](p02-capsule/README.md) в новой собственной временной папке. Затем примените три последовательных патча через отдельный индекс к восстановленной bare DB. В примере `repo` — полученная `snapshot.git`, `bundle` — этот каталог, `index` — новый абсолютный путь вне входного репозитория. Команды не создают Product или новую системную среду.

```sh
export GIT_INDEX_FILE="$index"
git -C "$repo" read-tree 645ddcd88647b8c628ec966f037762886bd56b31
git -C "$repo" apply --cached --whitespace=error "$bundle/source/p02-pr660-composed.patch"
git -C "$repo" write-tree
git -C "$repo" hash-object -w -t commit --stdin < "$bundle/source/v1.commit"
git -C "$repo" apply --cached --whitespace=error "$bundle/source/source-v2-delta.patch"
git -C "$repo" write-tree
git -C "$repo" hash-object -w -t commit --stdin < "$bundle/source/v2.commit"
git -C "$repo" apply --cached --whitespace=error "$bundle/source/source-v3-delta.patch"
git -C "$repo" write-tree
git -C "$repo" hash-object -w -t commit --stdin < "$bundle/source/v3.commit"
unset GIT_INDEX_FILE
```

Каждая пара tree/commit должна точно совпасть с таблицей 1. Такое восстановление реально выполнено: [проверка цепочки](source/composed-source-verification.json) фиксирует все hashes патчей, исходные commit bytes, 43 изменённых пути и итоговый Source. Новые объекты добавлялись в проверочную bare DB; исходные объекты капсулы не заменялись. Восстановление Source само по себе не является новым запуском тестов.

## 5. Применимость и полный остаток

Это один согласованный Source для следующих проверок. Обычный Product, специальный command-test Product #657 и publisher Serena должны быть выданы из согласованного производственного состава с отдельными ролями и закреплёнными test inputs. Прежний Serena PASS на private `3ebe335a` не переносится на изменившийся Source. Готовность к установке и слиянию не заявлена.

- **A — пользовательские сценарии.** Адресные сценарии scheduler/setup/autostart/strict/recovery/удаления/OFF и отдельный `WeeklyRefreshSet` прошли в указанной области. Остаются реальные API/workspace/install/upgrade/lifecycle потребители и расширенная квалификация поколений; сохранённый OFF и явное удаление должны оставаться согласованными. Текущие причины, владельцы и состав находятся в общем плане #664 и отдельном плане #660.
- **B — квалификация.** Кандидат внешнего original-owner receiving опубликован в #664, но runtime отключён: нужны реальные late return/reader, отказ чтения после физического закрытия, frozen outer HOLD и одноразовое закрытие. Затем — полный стандартный и тегированный наборы на допустимом PowerShell/namespace, Product/Serena install/update/cancel/recovery в разрешённой среде, реальные journal/backend/abort/prune/provider/client consumers #643/#648/#652/#659/#671 и отдельный `mcproute`. Сохранить общие сроки и прежние FAIL/UNKNOWN/V1. Linux/amd64 POSIX #668 уже исполнен в своей области; Unix/ARM64 и runtimeC остаются открытыми.
- **C — измерения и Rust.** Выполненные реальные Relay/CMake consumer profiles #626 и POST-resume #629 сохраняют свои exact input scopes; новые parser tests не являются новым performance результатом. #631 требует настоящего Go-потребителя на собственном private Source `3ebe335a…`, fresh admission и предназначенной DLL, без подмены P02. #627 `1d927f5e…` уже содержит 21 native PASS, но genuine metadata/close failures и Go-контракт остаются открытыми. Нужны основание для Rust, дальнейшее ревью a217/64 файла и проверка затронутых измерений при изменении соответствующей границы.
- **D — самостоятельные PR и сохранность.** Обновлять существующих владельцев без повторяющих PR, проверять собственные изменения и точные heads, после обязательных проверок получить внешнее ревью. Платный/квотный запуск требует имеющегося отдельного разрешения. Публикации читать обратно; хранить конфликты и область применимости доказательств. Закрывать доноров после сохранения всего уникального; переносить в trash только подтверждённо ненужные закрытые дубликаты, сохраняя результаты и восстановление вне него.

Общий маршрут обновлён в `.plans/2026-11/open-pr-integration-20261117.md`, §3, и `.plans/2026-11/audit-remediation-20261125.md`. Их исторические состояния сохранены. Слияний, force push, закрытия доноров или новых постоянных сред эта публикация не выполняет.
