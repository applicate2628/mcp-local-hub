## 1. Причина и пределы наблюдения

Корневой агент сообщил два отказа `TestReconcileIPC_HandlerTimeoutCancelsSchedulerList` на проверке отсутствующего наблюдения scheduler и два PASS соседнего `TestReconcileIPC_HandlerTimeout`. Тот же симптом повторён им на чистом исходном `f5fb003...` без scheduler-исправления. Это внешний для данного обзора журнал: значения и повторный прогон не выдаются за собственное исполнение.

В старом тесте 25-миллисекундный срок обработчика начинается в `handleReconcile` до настоящих preview/read/lock-операций. До вызова scheduler имеются как минимум два ранних выхода с кадром `RECONCILE_TIMEOUT`: после `readSupervisorIntentForReconcile` и после `ReadDaemonIntentFile`/проверки `ctx.Err()` [1]. Поэтому корректный timeout-кадр ещё не доказывает, что целевой `ListContext` был вызван.

В штатной выбранной ветви вызов `ListContext` синхронен, а единственный sender записывает `ctx.Err()` в буферизированный канал **до** своего return. Следовательно, отсутствие сообщения после возвращения обработчика и проверки timeout-кадра устанавливает недостижение этой целевой точки наблюдения. Конкретный из ранних выходов и время отдельных файловых операций без дополнительной трассы не установлены; причины вроде медленного диска или блокировки не объявляются измеренными.

Свежий снимок #658 не содержит уже выполненного исправления: весь файл `supervise_reconcile_ipc_test.go` на `4f3513d...` побайтно равен версии #660 на `f5fb003...`. В проверенных списках changed files ни #658, ни #660 пока не меняли этот CLI-файл. По согласованному разделению текущая тестовая коррекция принадлежит #658, а исправление scheduler-причин остаётся в отдельном #660; перенос его кода в #658 отсутствует.

## 2. Новый точный критерий

Тест переименован в `TestReconcileIPC_ParentCancellationReachesSchedulerList`, поскольку теперь проверяет **родительскую отмену после достижения ListContext**, а не реальное истечение срока обработчика.

Последовательность кандидата:

1. Существующая fixture создаётся без изменений. От её `fx.ctrl.ctx` выводится стандартный `context.WithCancel`; производственный `baseReconcileContext` получает этот новый контекст через уже существующее поле контроллера.
2. Штатный `reconcileHandlerTimeout` не меняется. Удалена тестовая запись `25*time.Millisecond` и восстановление глобальной переменной.
3. Подменённый scheduler проверяет, что полученный `ctx.Err()` ещё равен nil; только после этого вызывает `cancelParent()`.
4. Fake ждёт **собственный полученный** `ctx.Done()`; прежний односекундный аварийный предел перенесён к этому ожиданию, а не увеличен. Дальше он отправляет в канал и возвращает фактическую `ctx.Err()`. Константа `context.Canceled` как фиктивный результат вместо измеренной ошибки не возвращается.
5. После синхронного `handleReconcile` тест требует `RECONCILE_TIMEOUT` и обязательное сообщение из канала с `errors.Is(err, context.Canceled)=true`. Отсутствие сообщения даёт немедленный FAIL через `default`: предварительный выход уже не может засчитаться за целевой сценарий.

**Таблица 1 — сохранённые и изменённые утверждения.**

| Утверждение | Статус |
|---|---|
| Префикс scheduler `mcp-local-hub-` | Сохранено |
| Настоящий `handleReconcile` → `reconcileSchedulerListFnDefault` → `ContextLister` | Сохранено; подменяется фабрика scheduler |
| Scheduler получает живой контекст до события отмены | Новая явная проверка |
| Полученный scheduler-контекст реагирует на отмену своего родителя | Прямой критерий нового теста |
| Кадр `RECONCILE_TIMEOUT` | Сохранено |
| Причина наблюдения — `context.Canceled` | Новый честный критерий вместо `DeadlineExceeded` |
| Штатный handler deadline 25 секунд, наблюдаемый остаток `(24s,25s]` | Отдельный `TestReconcileIPC_HandlerTimeout` сохранён побайтно |
| Реальное истечение handler deadline внутри уже выполняющегося ListContext | **Не доказано этим кандидатом** |
| Настоящие PowerShell/COM-отмена и завершение дерева процессов | **Не проверяются** |

Новый тест не даёт ложного PASS при замене передаваемого scheduler-контекста на `context.Background()`: родительская отмена не закроет его `Done`, и сработает аварийная проверка. Пропуск fake также остаётся FAIL благодаря обязательному канальному свидетельству. Это анализ различающей способности; такие мутации здесь не исполнялись.

`testing/synctest` не добавлен: окружение использует настоящие файловые операции и уже запущенную fixture. Требуемый порядок непосредственно обеспечивается событием внутри целевой операции; виртуализация времени не нужна.

## 3. Ревью владения и конкурентного доступа

Отдельно рассмотрена запись `fx.ctrl.ctx = parentCtx` после запуска fixture EventLoop. Обоснование для **этих точных сценариев**, а не общий вывод о безопасности произвольной замены поля:

- Fixture запускает `loop.Run(ctx)` с локальной переменной `ctx` в замыкании (`supervise_reconcile_ipc_test.go:259–264`). Новая запись поля `fx.ctrl.ctx` не изменяет эту переменную и не меняет контекст уже запущенного цикла [2].
- `NewEventLoop` создаёт пустые каналы; `Run` вызывает обработчики только после получения события из них. Стартовых событий, таймерного producer или чтения контроллерного `ctx` внутри `Run` нет (`supervisor_event_loop.go:77–89, 259–283`) [3].
- Fixture регистрирует обработчик до запуска, но не отправляет событий. Её `ctrl.intentCache.Refresh(intent)` только строит и атомарно публикует снимок; в loop ничего не отправляет (`supervisor_controller.go:1015–1034`) [4].
- В проверяемом запросе `apply=false`. До scheduler производственный путь выполняет preview и чтения файлов; cache-refresh/apply-публикации не выполняются. После фактической отмены scheduler обработчик выходит через `writeTimeout` на строках 367–368. К `applyReconcileDrift` и другим событиям ниже по коду этот сценарий не доходит [1].
- Чтение `fx.ctrl.ctx` функцией `baseReconcileContext` происходит в том же тестовом потоке после присваивания (строки 617–623 производственного файла). Для этого чтения порядок задаёт последовательное исполнение. У исходного фонового loop в данном сценарии нет конкурентного читателя изменяемого поля.

Таким образом, конкретного пути гонки на новом присваивании в прослеженной ветви не найдено. Это вывод по доступам и источникам событий; запуск `-race` остаётся отдельным необходимым свидетельством над выполненными путями и не заменяет этот разбор. Если fixture позднее получит фоновый источник событий, данное обоснование требуется пересмотреть.

`cancelParent` отменяет только дочерний контекст запроса, не исходный контекст EventLoop. Он регистрируется в `t.Cleanup`; прежняя очистка fixture позднее отменяет исходный контекст и ожидает завершения loop. Повторная отмена идемпотентна. Новых горутин, отправителей в event loop, внешних процессов или владельцев ресурсов кандидат не создаёт. При аварийном `t.Fatal` отрабатывают существующие defer/cleanup.

Побочные эффекты остаются прежними: реальные временные state/audit-файлы, файловые блокировки и DACL (списки управления доступом Windows) внутри собственных roots; подменён scheduler, сообщение IPC (межпроцессного взаимодействия) записывается в тестовое соединение. Условия изоляции `TestMain` из первоначального CONTRACT-REVIEW сохраняются.

## 4. Привязка и проверка

Базовый Git blob `623e9b74fd5b23c0ce53d2982e6621b0f4c3c0e7` совпал с метаданными GitHub точного #658. Кандидат: `4fbe28e28679c5a48b4731057683ac6f19607137`. Все байты до и после единственного изменённого теста и его комментария сопоставлены и совпали; отдельный `TestReconcileIPC_HandlerTimeout` не изменён. Контрольные суммы и оба селектора записаны в `MANIFEST.json`; патч — `candidate.patch`.

Селектор кандидата для последующей проверки владельцем:

```text
^(TestReconcileIPC_ParentCancellationReachesSchedulerList|TestReconcileIPC_HandlerTimeout)$
```

Старый селектор должен использоваться только для исходного контроля. Подмена названия в селекторе без проверки точного числа запущенных тестов недопустима: старое имя отсутствует в кандидате. Для `-count=2` ожидаются четыре тестовых события PASS и одно пакетное, без SKIP; это ожидание, не уже полученный результат.

Фактически исполнены только чтение, сравнение байтов, вычисление хешей и создание файлов кандидата/патча/манифеста. Go test/build/vet/race/gofmt не запускались; удалённого исполнения, публикации и интеграции веток нет. Прошлый FAIL сохраняется как исторический результат. Успех новой проверки будет подтверждать устойчивую постановку и новый прямой критерий, а не исчезновение старого FAIL за счёт увеличения срока.
