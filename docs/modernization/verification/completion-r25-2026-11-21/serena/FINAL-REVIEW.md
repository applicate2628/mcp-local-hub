## 1. Вывод и граница обзора

**Доступные исходные события и квитанции поддерживают ограниченные результаты R25, перечисленные ниже. Завышения до полной квалификации Go, установленного Product или отдельно выполненного опубликованного commit не требуется и не подтверждено.** Исторический compile failure V2 остаётся отказом; функционально успешный direct-seed candidate остаётся отклонённой оптимизацией.

Обзор включает чтение точных исходников, повторный подсчёт событий, сверку хешей stdout, прочтение квитанций, сравнение опубликованного GitHub commit и проверку трактовки отчётов. После завершённой упаковки root отдельно поручил этому рецензенту побайтовый перенос четырёх публичных файлов с D: и локальную независимую проверку ZIP. Для переноса один раз выполнен ограниченный Python helper; Go, CMake и установленный Product этим рецензентом не запускались. Ранее отдельно выполнены 12 синтетических проверок verifier и пять синтетических проверок устойчивого чтения; они не входят в счётчики Go.

**Вторая упаковка завершена, а перенесённый публичный архив прошёл независимую локальную проверку по внешним хешам ZIP и окончательного индекса.** Результат — integrity/consistency PASS с квалификационным статусом `BOUNDED_RESULTS_ONLY`; независимое удостоверение факта выполнения на конкретной машине этим архивом не устанавливается. Первый запуск root с `ValueError: Input changed while opening` сохранён как отдельный отказ до публикации. Наблюдаемое различие `ctime` двух Windows Python API исправлено сохранением строгих проверок внутри каждого API; история отказа не заменена успешным вторым результатом.

Тем самым корректна формулировка: **точная чистая база плюс побайтно совпадающий опубликованный overlay прошли выбранные проверки**. Отдельный запуск нового head `184104c186108b150d1183318c3f6791f2a4ba5f` не наблюдался и не заявляется.

Native-тесты подтверждают конкретные finish/close ветви на реальных тестовых дескрипторах, исходном no-child receipt и реальном отказе `CloseHandle`. Начальное частное состояние владельца остаётся синтетическим. Полная acquisition/begin-use admission, namespace/publisher authority, успешный дочерний процесс, установка и установленный Product здесь не квалифицированы. V1 с неверным внешним error assertion отклонён до выполнения; V2 с отсутствующей экспортированной константой сохранил реальный compile FAIL; их результаты не заменены V3 PASS.

## 4. Фикстуры: отклонённая оптимизация и сохранённый oracle

## 5. CMake и диагностическое измерение Go

Прочитаны готовые [CMake RUNTIME.md](../cmake/RUNTIME.md), [retention-result.json](../cmake/retention-result.json), reducer и обе исходные пары stdout/receipt. Длинные `Output` были независимо соединены по имени Test; получено по 18 строк на вариант. Это сравнение двух overlays **на одной базе** `81dcf67db013ba2879878c2ee6fe07aa0bb4aec3`: прежний production-файл без clear и текущий файл с clear, при одинаковом helper `c73994c1e23f1ebdc00f56abae36a1f987ac88e6f8f711e753c889940ff4c13f`. Сравнением двух полных исторических checkout это не называется.

Независимый пересчёт подтвердил приведённые в отчёте медианы удерживаемой памяти. Например, для `selected-32` один работник даёт **11 695 968 → 1 753 352 байта**, четыре — **46 782 072 → 7 012 784 байта**. Во всех 36 строках capacity остаётся 17 578; диапазон released-minus-baseline — −1008…6648 байт; каждая из трёх спокойных межфазных разностей `gc_cycles` равна двум. Все 18 четырёхпоточных наблюдений имеют положительное общее пересечение интервалов, 57.1936–83.7904 мс. Body SHA-256, длина, количество внутренних/публичных записей и capacity совпадают по соответствующему сценарию во всех строках обоих вариантов.

Трактовка отчёта соответствует источникам: heap allocation/retention всего Go-процесса с намеренно живыми владельцами и принудительной сборкой мусора. Ни точный размер `Result`, ни пиковая или физически резидентная память, ни обычная задержка production-запроса, ни статистическая значимость не установлены. Ноль публичных записей у `selected-1000` — проверенная исходным oracle проекция четырёх коллекций; внутренние 1000 записей сохранены. Передача первоначальных wire-байтов reducer не утверждается: он сравнивает записанные хеши/размеры, а полную семантику проверяет выполненный helper.

Перед фиксацией этого обзора прочитана текущая уточнённая редакция CMake RUNTIME SHA-256 `7c11fd86cfa11d976d79fa74938fb9a84928fb0e80850ed79fb00219d699e085`. Она явно отделяет происхождение трассы настоящего CMake от синтетического fixture-проекта R22 и не выдаёт этот вход за репрезентативную клиентскую или production-нагрузку. Ранее проверенные числовые результаты не изменены.

[Go-budget RUNTIME.md](../go-budget/RUNTIME.md) также правильно отделяет 94.159 с внешней команды, 5.054 с пакета и 4.78 с root. В raw stdout подтверждены 190 фазовых записей. 89.15% относится к сумме инструментированных фаз одного образца, не ко всему пакету и не к отдельному `FlushFileBuffers`. Нулевые короткие интервалы не объявлены нулевой вычислительной стоимостью. Эти данные #658 не подменяют контроль master для более позднего candidate.

## 7. Точность текущих и исторических формулировок

1. В [ROOT-REVIEW.md](ROOT-REVIEW.md) будущая формулировка о publication readback относится к моменту до публикации. Сейчас readback нового commit выполнен, как описано в §3. Старый текст не является доказательством отдельного published-head run.

4. Авторские source-only отчёты, в которых сказано «не запускалось этим рецензентом», остаются корректными описаниями роли. Они не отменяют новые квитанции root. Аналогично сам guard report не является remote/native qualification.

Эти различия требуют аккуратной финальной формулировки, а не новых установок, полного CI или повторных Product-запусков.
