## 1. Результат и следующий шаг

**Текущий владелец Serena, PR #637 на `1ebe00c5dbac448488d980072e689b1126875dde`, уже устраняет старую ошибку положительной фикстуры.** Исторический `SERENA_BUILD_SOURCE_INVALID` нельзя представлять как неисправленный дефект этой версии. В этой работе их наличие и пригодность на удалённой машине не проверялись; это точный недостающий вход в доказательство выполнения, а не утверждение об отсутствии файлов.

Второй результат — готовый диагностический патч только к тесту `TestMCPFrontV3_SerenaConflictClassifierMutationTable`. Он разделяет измерение создания защищённой директории, полной надёжной записи файла, чтения с валидацией и отказа отката. Следующий полезный шаг для владельца удалённого запуска — один запуск точной выборки с этим патчем после независимого просмотра исходников и входов. Повтор общего набора ради свежести не нужен.

Патч является временным измерительным дополнением. Он не предлагает исправление production-кода, не меняет `FlushFileBuffers`, не увеличивает обязательный пятиминутный таймаут и не доказывает причину таймаутов всего набора.

## 3. Serena: исправленная фикстура и необходимые входы

### 3.1. Причинная цепочка

На старой ветке положительная проверка `TestMigrateSerena_CallsInstallParsedManifest_NotDiskWrite` использовала `legacy2DaemonManifestYAML`: команда `go`, источник `git+https://example/serena` без закрепления ревизии. Реальная подготовка передаёт источник в `serenaBuildSource` из `internal/api/serena_build_environment_source.go`; эта граница требует корректный адрес HTTPS и суффикс `@` с 40 шестнадцатеричными символами в нижнем регистре. Такой вход не мог пройти контракт реальной подготовки. Это объясняет конкретный исторический `SERENA_BUILD_SOURCE_INVALID`.

В текущем #637 та же проверка вызывает `migrateSerenaPreparedTestEnv` и `seedPreparedSerenaManifestForTest`. Второй помощник сохраняет форму исходного YAML и берёт команду с базовыми аргументами из встроенного каталога Serena. Для просмотренной версии закреплён источник `git+https://github.com/oraios/serena@949a27ef1e5fda1a6e7b561e777bcece345c6ffd`, команда `uvx`. Отдельная проверка `TestPreparedSerenaManifestKeepsNativeShape` сравнивает остальные объявления фикстуры с исходной формой. Источник: [подготовленная фикстура #637](https://github.com/applicate2628/mcp-local-hub/blob/1ebe00c5dbac448488d980072e689b1126875dde/internal/cli/migrate_serena_prepared_fixture_test.go), [положительный сценарий #637](https://github.com/applicate2628/mcp-local-hub/blob/1ebe00c5dbac448488d980072e689b1126875dde/internal/cli/migrate_serena_test.go), [проверка формата источника](https://github.com/applicate2628/mcp-local-hub/blob/1ebe00c5dbac448488d980072e689b1126875dde/internal/api/serena_build_environment_source.go).

### 3.2. Почему не заменена интеграционная проверка

Существующий test-owned seam уже позволяет проверить передачу разобранного manifest без новой инъекции в production-код: `migrateSerenaRunDeps.newInstallOperation`, `runMigrateSerenaDynamicPoolWithDeps`, `callerMigrateSerenaInstallOperationForTest` и `stubInstall`. Узкая проверка вызывающей стороны могла бы записать полученный manifest, вернуть управляемую ошибку и проверить неизменность дискового файла. Такой результат доказывал бы только передачу данных и реакцию вызывающей стороны.

Однако действующая положительная проверка имеет дополнительные существенные утверждения: реальная установка создаёт строку `runtime_spec`, manifest на диске не меняется, reap происходит до записи intent, запуск преемника вызывается после записи. Подмена успешной подготовки пустой функцией и возврат искусственного результата убрали бы доказательство реальной подготовки и установки. Поскольку #637 уже исправляет исходную фикстуру, такого изменения не подготовлено. Потребность в ещё одной узкой проверке следует оценивать отдельно по отсутствующему контракту; она не снимает требование нативной квалификации.

## 4. Один диагностический запуск

Исследуемый вопрос узок: **какую долю измеренного времени конкретной mutation table занимают её файловые фикстуры по сравнению с классификатором и проверкой отказов?** Одна выборка не даёт ответа о всём пакете или всех исторических таймаутах.

Патч [phase-instrumentation.patch](phase-instrumentation.patch) относится только к `internal/cli/install_reconcile_mcp_front_v3_test.go`. Добавлены стандартные `time.Now`, `time.Since` и `t.Logf`; существующие проверки сохранены. Каждая длительность считается до вывода сообщения. Перед следующей фазой устанавливается новое начало измерения, поэтому запись предыдущего сообщения в следующую фазу не входит.

**Таблица 3. Ожидаемые фазовые записи при полном успешном выполнении.**

| Маркер | Число записей | Что включает |
|---|---:|---|
| `journal-fixture` | 1 | Общая настройка тестовой среды и создание исходного журнала |
| `initial-attempt` | 1 | Обновление общей записи попытки и её сохранение |
| `case-setup` | 34 | Клонирование данных и мутация конкретного подслучая |
| `classifier` | 34 | Вызов классификатора |
| `fixture-directory` | 30 | Создание защищённой временной директории и сборка пути |
| `fixture-write` | 30 | Полный `api.WriteStateFileAtomic`, включая маршалинг JSON, блокировку, проверки пути/прав, запись, сброс, замену и проверки результата |
| `read-validation` | 30 | Чтение и ожидаемый отказ проверки невалидного журнала |
| `rollback-refusal` | 30 | Вызов отката, который обязан отказать до вызова подставленного reader |
| **Всего** | **190** | Одна корневая проверка и 34 подслучая |

В четырёх допустимых подслучаях отдельная файловая фикстура не создаётся; они возвращаются после проверки классификатора. Общие журнал и исходная попытка являются файловыми операциями для всего root. Поэтому число 30 относится именно к индивидуальным durable-фикстурам, а не ко всем записям root и тем более не к числу системных сбросов.

Команда, **подготовлена, не выполнена**:

```text
go test -json -count=1 -p=1 -timeout=5m -run '^TestMCPFrontV3_SerenaConflictClassifierMutationTable$' ./internal/cli
```

JSON обеспечивает события начала, завершения и фазовый вывод; `-count=1` исключает повторное использование сохранённого результата теста; `-p=1` задаёт один процесс сборки одновременно. Дополнительных профилировщиков, race-режима, изменения тегов и нового общего таймаута здесь нет.

Точный вход: база #658 `2d12d9b63e60387591d27515aef3487c0e3ea560` и один указанный overlay. Целевой файл, `install_reconcile_mcp_front.go`, помощник `install_reconcile_mcp_front_pr588_test.go`, CLI TestMain и `secure_write_windows.go` также побайтно совпадают с #637; это не делает разные полные ветки взаимозаменяемыми для свидетельства запуска. Основу фактически выполненного запуска нужно записать буквально.

Имеющийся индекс на совпадающих Go-исходниках уже содержит выбранный root. Нельзя запускать широкую группу из 80 корней только потому, что этот root входит в неё: тела остальных проверок не входят в данный обзор. `tools/testshards` требует чистый checkout и не предоставляет входа для такого overlay, поэтому диагностический запуск должен быть отдельно обозначен как точная база плюс проверенный патч, а не выдан за чистый shard.

## 5. Побочные эффекты выбранного пути и TestMain

Прочитаны тело выбранного root, его прямые помощники, ранняя ветка отказа отката, реализация надёжной записи и обычный путь CLI `TestMain`. В root нет `t.Parallel`. Проверка создаёт временные директории, меняет тестовые настройки окружения через восстановимые помощники, сохраняет общий журнал и индивидуальные файлы, читает и валидирует их. После классификации невалидной формы откат обязан отказать до reader: это проверяется счётчиком `readerCalls == 0`. Фабрика rollback-операций только создаёт замыкания; внешняя работа из неё на этом пути не запускается. Источники: [тест](https://github.com/applicate2628/mcp-local-hub/blob/2d12d9b63e60387591d27515aef3487c0e3ea560/internal/cli/install_reconcile_mcp_front_v3_test.go), [помощники](https://github.com/applicate2628/mcp-local-hub/blob/2d12d9b63e60387591d27515aef3487c0e3ea560/internal/cli/install_reconcile_mcp_front_pr588_test.go), [ветка отката](https://github.com/applicate2628/mcp-local-hub/blob/2d12d9b63e60387591d27515aef3487c0e3ea560/internal/cli/install_reconcile_mcp_front.go), [запись состояния](https://github.com/applicate2628/mcp-local-hub/blob/2d12d9b63e60387591d27515aef3487c0e3ea560/internal/api/state_file_helper.go).

Даже при `-run` одного root пакетный `TestMain` выполняется. В обычной ветке он подставляет безопасные тестовые зависимости запуска и supervisor IPC, создаёт/защищает собственный временный корень, назначает тестовый корень API и окружение клиентских конфигураций, включает аудит путей и подавление браузера, затем вызывает `m.Run`. После него восстанавливает окружение и зависимости, проверяет аудит и убирает свой корень; ошибка аудита или уборки меняет итоговый код возврата. Источники: [CLI TestMain](https://github.com/applicate2628/mcp-local-hub/blob/2d12d9b63e60387591d27515aef3487c0e3ea560/internal/cli/settings_registry_test.go), [окружение клиентских настроек](https://github.com/applicate2628/mcp-local-hub/blob/2d12d9b63e60387591d27515aef3487c0e3ea560/internal/cli/client_config_env_isolation_test.go), [уборка собственного корня](https://github.com/applicate2628/mcp-local-hub/blob/2d12d9b63e60387591d27515aef3487c0e3ea560/internal/api/apitest/testmain_cleanup.go).

Поэтому окружение runner должно исключать режимы helper-dispatch и opt-in запуск внешних приложений; временные, домашние и клиентские каталоги назначаются в разрешённую собственную область до создания процесса. Исходная копия и кэши тоже принадлежат runner. Входы сборки ограничиваются уже имеющимися зависимостями: `GOENV=off`, `GOTOOLCHAIN=local`, `GOWORK=off`, `GOPROXY=off`, `GOSUMDB=off`, `GOVCS=*:off`, пустой `GOFLAGS`, собственные `GOCACHE` и `GOTMPDIR`. Эти настройки должны быть записаны в исходное свидетельство запуска вместе с фактическими путями и завершением процесса; одни строки команды не доказывают изоляцию.

Обычный Product и Serena-издатель для выбранной mutation table не требуются. Создание и удаление тестовых файлов остаются реальными операциями. Измерители фаз не охватывают весь `TestMain`, cleanup тестов, журналирование, проверки утверждений и промежутки между фазами.

## 6. Сбор событий и интерпретация

Следует сохранить исходный поток `go test -json`, отдельный stderr, точную команду/окружение/исходную базу/патч, фактический код возврата и свидетельство завершения принадлежащего runner процесса. Перед запуском проверяются базовый и итоговый SHA-256 целевого файла. После завершения используются данные из [diagnostic-selection.json](diagnostic-selection.json) и [summarize_diagnostic.py](summarize_diagnostic.py):

```text
python summarize_diagnostic.py --events <go-test.jsonl> --selection diagnostic-selection.json --exit-code <actual-exit-code> --output <new-result.json>
```

Reducer принимает только ожидаемые 35 имён (root и 34 подслучая), ровно одно начало и одно успешное завершение каждого, ровно одно успешное завершение пакета и все 190 фаз без дублей. Отказ, пропуск, неверный пакет, лишний тест, неполная фаза или ненулевой код возврата делают результат неполным. Отсутствующая длительность не превращается в ноль. Новый результат создаётся с отказом от перезаписи существующего файла. Исходные события получают контрольную сумму, но reducer **не доказывает**, что процесс действительно выполнил указанные исходники: это отдельная обязанность сборщика свидетельств.

Агрегация показывает число, сумму, минимум, медиану и максимум фаз в наносекундах с сохранением всех исходных фазовых записей. Наносекундная единица `time.Duration` не утверждает такую физическую точность часов. При первичном разборе сравниваются времена `fixture-directory`, `fixture-write`, `read-validation`, `rollback-refusal` и `classifier` именно для этой выборки. Если файловые фазы окажутся существенными, дальнейшее измерение назначается по этому факту и с отдельной проверкой причин; одного снимка в `FlushFileBuffers` для изменения production-контракта недостаточно.

`fixture-write` включает весь публичный путь записи, поэтому не является отдельным замером `FlushFileBuffers`. Нельзя вычитать сумму фаз из округлённого Go `Elapsed` и называть остаток временем процессора или простоя. Один инструментированный образец не устанавливает устойчивый бюджет, ускорение либо весь исторический таймаут. **Нет экстраполяции этих 34 случаев / 30 файловых фикстур на 3437 корневых API-тестов или 1960 корневых CLI-тестов. Полные Go-gates остаются отдельным вопросом.**

## 8. Файлы и термины

Основной комплект: [измерительный патч](phase-instrumentation.patch), [точная выборка](diagnostic-selection.json), [reducer](summarize_diagnostic.py), [итоговый файл для просмотра](../archive/README.md), два манифеста источников и два свидетельства проверок из раздела 7. [artifact-manifest.json](artifact-manifest.json) связывает точные байты комплекта. Ни один файл не является заявлением о выполнении Go.

CLI — command-line interface, интерфейс командной строки. API — application programming interface, программный интерфейс. MCP — Model Context Protocol. JSON — JavaScript Object Notation, текстовый формат структурированных данных. DACL — discretionary access control list, список управления доступом Windows. IPC — inter-process communication, межпроцессное взаимодействие. Product в этом репозитории — отдельно допускаемый обычный runtime-образ программы, а не тестовая сборка. SHA-256 — криптографическая контрольная сумма; она связывает точные байты, но сама по себе не доказывает их исполнение. Durable-файловая фикстура здесь означает тестовый файл, записываемый существующим production-путём с его контрактом надёжной записи. Overlay — один явно учтённый временный патч поверх точной базовой версии.
