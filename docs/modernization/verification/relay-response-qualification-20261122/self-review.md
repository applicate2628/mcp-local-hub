## 1. Прочитанный предмет

Прочитаны полный production diff к #629 `b3646f19706d795a8b0c0dafb2193d7dc6f4c584`, затронутые цепочки `Run` → вход → POST/GET → parser → output, все 25 новых корневых тестов и вызываемые ими helpers, соседние контрактные тесты и ранний `TestMain`. Сопоставлены закреплённые `readAllWithLimit`, конечный qualification receiver, предыдущие собственные и независимые замечания. Это собственный просмотр исходников; прежнее независимое ревью использовано как дополнительная проверка истории.

## 2. Корректность и совместимость

Отдельная блокировка ошибок POST имеет конкретную причину: чужой заблокированный `Stdout` не должен препятствовать отмене context-aware HTTP-работы. Нового владельца процесса, framework, неограниченной очереди или зависимости не добавлено. Существующее ограничение параллельных POST равно 64; новый предел относится к данным одного ответа/события, а не к общему пику памяти.

Проверено разделение `lastID` и `pendingID`: ID становится доступным следующему GET только после завершённого блока и успешного receiver. Callback failure сохраняет предыдущий ID вместе с уже наблюдавшейся scanner error. Пустое событие MCP может передать cursor без JSON. Named control остаётся ограниченным по размеру до выбора сообщения.

Значения клиента по умолчанию локальны для метода: POST 60 секунд, GET в контексте `Run`, DELETE 2 секунды. Объект клиента вызывающей стороны остаётся тем же; повторный `Run` не получает записанный ранее default timeout. Переданные читатели, писатели и transport не становятся собственностью Relay. Существующий явно предоставленный callback прерывания входа сохраняется и присоединяется.

Меняется наблюдаемое поведение для невалидных ответов: parser/output failure возвращается вызывающей стороне; повреждённый поток не продолжается; неоднозначный эффект POST не повторяется из-за redirect. Эти изменения соответствуют заявленному контракту и различаются отрицательными контролями. Строгая проверка схемы JSON-RPC не добавлена: `json.Compact` проверяет синтаксис одного JSON-значения.

## 3. Проверки и допуск

Проверены реальные завершённые журналы, а не одна отметка PASS: 25 корневых тестов проходят по два раза, 204 test/subtest PASS плюс один package PASS, 0 FAIL/SKIP. В пяти отрицательных контролях исходные тела завершаются ожидаемым кодом 1 с конкретными assertion failures. Они остались FAIL в [результатах](qualification-results.json). Старые команды не повторялись.

Довыполнены только отсутствовавшие 17 соседних корневых тестов под `-race`, `build` и `vet`. Соседний набор дал 36 test/subtest PASS плюс package PASS. Все три новые команды завершились кодом 0; состав из 3 293 файлов неизменен. Полные тесты всего дерева не выполнялись.

Прочитаны новый runner и точные phase argv. Он запускает только закреплённые команды с отключёнными загрузками и собственными D-путями, сохраняет исходный объект `Popen`, ожидает прямого ребёнка и не ищет процесс по имени/повторно найденному PID. Тайм-аут остаётся неуспехом с неопределённым состоянием потомков. Во всех выполненных фазах тайм-аут не наступил.

Тесты ответа используют конечные объекты в памяти. Изменения `http.DefaultTransport` ограничены непараллельными `synctest`-сценариями и восстанавливаются после завершения `Run`; реальные 60-секундные ожидания отсутствуют. Этот набор не измеряет поведение реального SDK-потребителя.

## 4. Подтверждённые ограничения

Следующие пункты — известные границы инкремента, а не закрытые свойства:

- `readRelaySSE`, ветвь unknown fields, и `sseListener` с паузой 1 секунда пока не соблюдают объявленный сервером `retry`. Отдельный реальный профиль должен различать это поведение.
- POST/GET/DELETE пока не несут согласованный `MCP-Protocol-Version`. Permissive сервер не является доказательством выполнения negotiation-контракта.
- Принудительное завершение всего дерева процессов и общий deadline не доказаны. Проверены завершение прямых процессов и отсутствие timeout в выполненных фазах.
- `Body.Close` и best-effort DELETE, произвольно блокирующие чужие I/O/callback, BOM/CR-only SSE, общая память, задержки и потери при реальном reconnect требуют отдельных результатов.
- Реальный consumer/SDK profile, нативные CLI tests, установленные продуктовые входы и полный Go gate остаются невыполненными. Результаты композиции не переносятся автоматически на standalone ветку либо новый `master`.

Собственный просмотр не заменяет внешнее ревью точного опубликованного SHA. По этому результату нельзя закрыть весь Relay/CMake пакет или объявить полную приёмку продукта.
