## 1. Дефект и граница исправления

В исходном [`internal/api/install.go`](https://github.com/applicate2628/mcp-local-hub/blob/b7831aabdb7162b3a39c78e73c3ab67558236d1d/internal/api/install.go#L4222-L4292) помощник `pruneObsoleteServerTasks` подавлял ошибку `ExportXML`, затем вызывал `Delete`. Возвращённый обработчик отката при отсутствии снимка мог только вывести предупреждение. При последующей ошибке установки удалённую задачу уже нельзя было восстановить из сохранённого определения.

Комментарий контракта в той же функции предписывал предупреждение и пропуск при ошибке экспорта. Кандидат реализует эту границу: задача удаляется только после успешного непустого снимка. Непустые байты вместе с ошибкой не считаются успешным экспортом. `nil` и пустой срез без ошибки также приводят к предупреждению и пропуску.

Полученный массив байтов остаётся непрозрачным для потребителя. XML — расширяемый язык разметки определения задачи; пригодность платформенного формата не доказывается одной ненулевой длиной и остаётся ответственностью адаптера. Самостоятельный разбор или нормализация XML здесь не добавлены.

## 2. Кандидат и критерии тестов

Окончательная дельта Go: **три файла, +84/−47**. Производственный файл `install.go`: **+12/−14**, только помощник очистки и его комментарий. Остальные изменения — два существующих тестовых файла.

Новая проверка `TestPruneObsoleteServerTasks_SkipsUnavailableSnapshot` охватывает ошибку без байтов, частичные байты вместе с ошибкой, `ErrTaskNotFound` после перечисления, `nil` без ошибки и пустой срез без ошибки. Для каждого случая проверяются:

- отсутствие удаления и отката отклонённой задачи;
- предупреждение с именем задачи и причиной отказа;
- обработка следующей независимо экспортируемой задачи;
- единственный ожидаемый вызов удаления и восстановления;
- сохранение исходных байтов отклонённой задачи и точное восстановление разрешённой задачи.

Тестовый `List` сортируется стандартным `sort.Slice`. Имя `…-unavailable` предшествует `…-zobsolete`; ошибочный выход из всего цикла вместо `continue` должен обнаруживаться детерминированно.

В проверке принадлежности `TestPruneObsoleteServerTasks_KeepsSiblingPrunesOwnObsolete` непустые снимки добавлены всем трём перечисленным задачам. Исходный поддельный планировщик экспортировал только содержимое `f.xml`, тогда как фикстура заполняла лишь `listSeed`. Теперь сохранение запланированной и соседней задачи проверяет именно фильтры, а не случайное отсутствие снимка.

## 3. Собственное и независимое ревью

Собственное статическое ревью проверило требования, причинную цепочку дефекта, порядок побочных эффектов, совместимость интерфейса, безопасность отказа и сложность изменения:

- проверка снимка стоит после фильтров области и принадлежности, перед первым удалением;
- любая ошибка экспорта сохраняется в предупреждении и исключает удаление;
- ошибки отдельной задачи остаются предупреждениями; первоначальная ошибка `List` сохраняет прежний возврат ошибки;
- успешная последовательность снимок → удаление → обработчик отката сохраняется;
- недостижимая ветвь обработчика «снимка нет» убрана;
- сигнатуры, область перечисления, команды платформенного адаптера и `ImportXML` не изменены.

**Замечание независимого ревью принято.** Добавленная сортировка ставила здоровую `mcp-local-hub-s-stale-debug` раньше ошибочной `mcp-local-hub-s-weekly-refresh` в существующем `TestPruneObsoleteServerTasks_DeleteFailureContinuesWithOthers`. В таком порядке замена продолжения после ошибки на выход из цикла могла остаться незамеченной. Первое собственное ревью этот эффект на существующую проверку не обнаружило.

Минимальное исправление: переименована только здоровая задача в `mcp-local-hub-s-z-stale-debug`, в её исходной записи и проверке отсутствия после удаления. Производственный код и поведение поддельного удаления не менялись. Теперь ошибочная задача гарантированно предшествует здоровой.

Повторное собственное статическое ревью подтвердило совпадение имени в исходной записи и проверке, нужный порядок сортировки и неизменность двух остальных Go-файлов.

## 5. Остаток и предлагаемый контроль

`negative-control.patch` содержит только изменения тестов. Его применение к исходному производственному коду должно обнаружить дефект: старый помощник удалит обе задачи вместо одной во всех пяти новых случаях. **Это ожидаемый результат, не выполненный запуск.**

Предлагаемая адресная выборка для родительского агента:

```text
go test -tags=test_state_path_env -race -count=2 ./internal/api -run '^TestPruneObsoleteServerTasks_'
```

Просмотренные `internal/api/main_test.go` и относящиеся к выборке фикстуры перенаправляют состояние и конфигурации и передают поддельные планировщики. На Windows временные каталоги и кеши Go должны оставаться внутри разрешённого `<WORK_ROOT>`. Этот анализ не квалифицирует общую команду `go test ./...` и не требует интеграции ограждений отдельного #658.

Кандидат не делает очистку транзакцией и не устраняет замену внешним автором между успешным экспортом и удалением. Остаются возможное частичное удаление с ошибкой, ошибки восстановления и принудительное замещение внешнего определения при `ImportXML` с `/F`.

Отдельно остаются потребители замены: исходные `install.go:3822–3839`, `register.go:2295–2333`, `scheduler_mgmt.go:143–147` и `303–305`. Общая машина транзакций, новая операция восстановления только при отсутствии задачи и изменение контракта `ImportXML` не включены: это потребовало бы согласованных правил владения несколькими поколениями задач и изменений нескольких потребителей. Дополнительное чтение перед `/F` само по себе не устраняет гонку между проверкой и записью.
