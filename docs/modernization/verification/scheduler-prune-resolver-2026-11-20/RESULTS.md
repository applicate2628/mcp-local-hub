# R17: сохранение задачи без снимка и форма ошибки CIM-поиска

**Дата:** 20 ноября 2026 года, время в тексте — московское. **Код:** существующий [PR #660](https://github.com/applicate2628/mcp-local-hub/pull/660), коммит [`f5fb00370a833255eacb992a7cd32f2e68da7399`](https://github.com/applicate2628/mcp-local-hub/commit/f5fb00370a833255eacb992a7cd32f2e68da7399), единственный родитель `b7831aabdb7162b3a39c78e73c3ab67558236d1d`, дерево `91ea0a635cbeeae0849b328c2b6064d48f95bdfc`.

**Результат:** очистка устаревших задач пропускает задачу, если её определение не удалось сохранить. Новый различающий тест сначала обнаружил прежнее удаление без снимка, затем прошёл с исправлением. Отдельное нативное чтение установило форму ошибки `Get-ScheduledTask` для одного отсутствующего имени. Производственный экспорт через COM сохранён; полная приёмка R17 и общие Go-критерии не заявляются.

## 1. Дефект и исправление

В исходном `internal/api/install.go`, `pruneObsoleteServerTasks`, ошибка `ExportXML` подавлялась. Следующий `Delete` мог удалить задачу, после чего обработчик отката без определения мог лишь сообщить о невозможности восстановления. Это противоречило комментарию функции, обещавшему предупредить и пропустить ошибку экспорта. Один существующий тест требовал такого удаления.

Исправление ограничено этим помощником. После фильтров префикса, запланированных задач и принадлежности серверу он требует успешный непустой снимок. При любой ошибке, включая байты вместе с ошибкой, либо нулевой длине успешного ответа выводится предупреждение и продолжается обработка следующей задачи. Для пропущенной задачи нет вызова `Delete` и нет обработчика отката. Успешная последовательность сохранения, удаления и восстановления остаётся прежней. Недостижимая проверка отсутствующего снимка внутри отката удалена.

**Таблица 1 — размер опубликованной дельты.**

| Файл | Изменение | Строки |
|---|---|---|
| `internal/api/install.go` | Проверка снимка перед удалением, соответствующий комментарий | +12/−14 |
| `internal/api/prune_tasks_test.go` | Новый различающий тест, управляемые ответы экспорта и детерминированный порядок | +69/−33 |
| `internal/api/install_hyphen_family_ownership_test.go` | Непустые снимки всех трёх задач в существующей проверке принадлежности | +3/−0 |
| **Всего** | **Три файла** | **+84/−47** |

Байты снимка остаются непрозрачными для этого потребителя: он не разбирает и не нормализует XML. Непустая длина не доказывает пригодность определения или возможность его успешного восстановления. Изменение не делает последовательность атомарной и не защищает от внешней замены между чтением и удалением.

## 2. Различающие проверки

**Таблица 2 — случаи нового теста `TestPruneObsoleteServerTasks_SkipsUnavailableSnapshot`.**

| Ответ экспорта первой задачи | Требуемый результат |
|---|---|
| Ошибка без байтов | Сохранить задачу, предупредить, обработать следующую |
| Частичные байты вместе с ошибкой | Не считать снимок успешным; сохранить задачу |
| `ErrTaskNotFound` после перечисления | Не выполнять последующее удаление по этому имени |
| `nil` без ошибки | Пропустить задачу как не имеющую снимка |
| Пустой срез без ошибки | Пропустить задачу как не имеющую снимка |

В каждом случае поддельный список ставит ошибочную задачу перед независимой пригодной задачей. Проверяются единственный ожидаемый `Delete`, единственный обработчик отката и `ImportXML`, точное восстановление второй задачи и сохранение исходных байтов первой. Переход к следующему кандидату проверяется по эффектам, а не только по тексту журнала.

Независимое ревью обнаружило побочное ослабление старого теста продолжения после ошибки `Delete`: сортировка ставила здоровую задачу первой. Её имя минимально изменено так, чтобы ошибка гарантированно предшествовала успеху. В проверке принадлежности снимки добавлены всем трём задачам, поэтому сохранение запланированной и соседней задачи по-прежнему проверяет фильтры, а не случайное отсутствие снимка. Оба замечания и итоговые суммы сохранены в [независимом ревью](INDEPENDENT-REVIEW.md).

Сначала к точному родителю применялись только тестовые изменения. Производственная функция оставалась исходной. После подтверждения причины отрицательного контроля применён производственный патч. Форматирование `gofmt`, проверка состава изменений и SHA-256 выполнялись до допуска кандидата. Затем опубликованное дерево получено из GitHub и выбрано в чистом detached checkout, без слияния веток.

## 3. Новое наблюдение CIM

Один отдельный наблюдатель выполнялся **20.11.2026 в 18:07:51–18:07:52 МСК**, Windows PowerShell `5.1.22621.6133`, ScheduledTasks `1.0.0.0`. В памяти сгенерировано буквальное корневое имя с GUID, без символов маски. Последовательность: контрольное `COM.GetTask` → один `Get-ScheduledTask -TaskName ... -TaskPath '\' -ErrorAction Stop` → контрольное `COM.GetTask` того же имени. Продуктовый Go-код не выполнялся.

**Таблица 4 — наблюдённый ответ.**

| Шаг | Исключение | HRESULT | Категория PowerShell |
|---|---|---|---|
| COM до | `System.IO.FileNotFoundException` | `0x80070002` | 14, `OperationStopped` |
| `Get-ScheduledTask` | `Microsoft.PowerShell.Cmdletization.Cim.CimJobException` | `0x80131501` | 13, `ObjectNotFound` |
| COM после | `System.IO.FileNotFoundException` | `0x80070002` | 14, `OperationStopped` |

Во всех трёх цепочках один элемент и `chain_truncated=false`. Результат — **`completed=true`, `classification=ERROR_OBSERVED`**, 1,481794 с; непосредственный процесс завершён с кодом 0, stderr пуст. Ошибка команды перехвачена и сохранена как разрешённые метаданные. Поэтому код 0 наблюдателя не означает успешный возврат задачи.

Это новый результат именно для этапа получения объекта. Успешного пустого массива не наблюдалось; число объектов, которые могли поступить до исключения, не измерялось. Прежний прямой экспорт отсутствующего имени давал `CimException`, `NativeErrorCode=1` и `0x80070002` в расширенных числовых данных. Новый ответ содержит другой тип и общий код `0x80131501`; прежняя схема обработки ошибки экспорта не покрывает его автоматически.

Категория 13 соответствует `ObjectNotFound`, но это общая диагностическая категория. `0x80131501` — общий код `SystemException`, а не код отсутствующей задачи. Из одного наблюдения нельзя выводить универсальное сопоставление типа, категории или HRESULT с `ErrTaskNotFound`. Первичные источники и объяснение возможного механизма приведены в [разборе результата](RESOLVER-INTERPRETATION.md); совпадение открытого исходного кода PowerShell с установленным бинарным PowerShell 5.1 не установлено.

Наблюдатель не вызывал экспорт, регистрацию, запуск, остановку или удаление задач, не читал XML/Definition, не менял списки управления доступом. Имя задачи, значения полей и тексты исключений не сохранялись. `semantic_absence_verdict=null`, атомарность интервала не заявляется. Перед выполнением встроенный PowerShell прошёл отдельный синтаксический разбор: **0 ошибок, 936 токенов**, без исполнения строки.

В первой попытке доставки команды RDC вернул ошибку соединения. Перед новой доставкой проверены отсутствие receipt и runtime, отсутствие её активной сессии и отсутствие фонового ожидающего вызова. Отдельное создание runtime с `exist_ok=False` предшествует нативному процессу и исключает повторный запуск этого наблюдателя в том же корне. Сохранена одна завершённая нативная квитанция; новая доставка не была повтором уже полученного результата.

| Полная установка и её откат | **Не квалифицированы**; правка затрагивает только очистку устаревших задач |
| Универсальный CIM-классификатор отсутствия | **Не квалифицирован**: один буквальный корневой случай; скрытые задачи, права и отказ поставщика остаются |

Это прежние результаты точных исходников, не свежие результаты `f5fb0037`. Никакие ограждения, Product или Rust-изменения из других веток сюда не переносились.

Перестановка одного обработчика отката или дополнительный экспорт перед `/F` сами по себе не устраняют гонку между проверкой и записью. Общая транзакционная машина не добавлялась.

## 6. Целостность свидетельств

Архив `evidence-redacted.zip`: **69079 байт, 86 элементов, 85 файлов в манифесте**; SHA-256 **`a75ef70ddf339b07bb36f423d01caf7df28631c9c7f5d43d9b2aec7886d17ad2`**.

На исходном хосте все **46 исходных потоков команд** сверены с квитанциями; события Go повторно рассчитаны из JSON-журналов. После переноса проверены ZIP CRC, все 85 файловых хешей и 32 JSON-документа. Архив получен обратно из GitHub в Base64, совпал побайтно; CRC и все 85 хешей повторно проверены. Результат — в [archive-verification.json](archive-verification.json).

Исходные и сохранённые после маскирования суммы разделены в [MANIFEST.json](MANIFEST.json). Нативные потоки не сохранены: их длины/хеши — квитанция наблюдателя, а не возможность повторно проверить отсутствующие исходные байты. Сценарии с заменёнными путями являются аудиторскими копиями, а не готовыми неизменёнными входами исполнения.

## 8. Обозначения

PR — запрос на включение изменений; Draft — черновик. COM — компонентная объектная модель Windows; CIM — общая модель управленческих данных; XML — формат определения задачи. API — программный интерфейс; CLI — интерфейс командной строки; GUID — глобально уникальный идентификатор; HRESULT — 32-разрядный код результата Windows. SHA-256 — криптографический хеш содержимого; CRC — контроль целостности ZIP; UTF-8 — кодировка Unicode; JSON — формат структурированных данных. RDC — Remote Desktop Commander; runner — управляющий сценарий; receipt — квитанция выполнения; intent — сохранённый желаемый набор задач. PASS/FAIL/SKIP/NOT_RUN — успешная проверка, отказ, пропуск, отсутствие запуска. Число PASS-событий включает повторные исполнения и отдельно обозначенные подтесты.
