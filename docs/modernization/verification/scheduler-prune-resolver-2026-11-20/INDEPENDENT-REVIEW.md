# R17: независимое ревью prune-исправления и observer отсутствия

**Дата:** 20.11.2026. **Роль:** встроенное независимое чтение исходников `queue_checkpoint`. **Основа кандидата:** #660, `b7831aabdb7162b3a39c78e73c3ab67558236d1d`.

**Вывод:** в окончательном узком исправлении `pruneObsoleteServerTasks` производственных дефектов по прочитанному исходнику не обнаружено. Выявленное ухудшение различающей способности теста исправлено. В окончательном observer после устранения предсуществующего `runtime` и с учётом предоставленного root подтверждения свежего рабочего каталога оставшихся блокирующих дефектов для описанного одного наблюдения не обнаружено.

Это исходниковое ревью, не результат исполнения Go, PowerShell или нативных задач, не формальное внешнее одобрение и не свидетельство полной готовности PR.

## 2. Prune: замечание и исправление

### 2.1. Проверенный производственный контракт

В `pruneObsoleteServerTasks` проверка снимка расположена после фильтров префикса, запланированных задач и принадлежности серверу, но до `Delete`.

- Любая ошибка `ExportXML` запрещает удаление этой задачи, в том числе когда вместе с ошибкой возвращены непустые байты.
- Успешный вызов с `nil` либо пустым массивом байтов также запрещает удаление.
- Для пропущенной задачи выводится предупреждение с её именем и причиной; цикл продолжает обработку независимых задач.
- Для успешно удалённой задачи сохраняется прежний rollback — действие восстановления — с исходными байтами снимка.
- Старые сообщения об успешном удалении, ошибке Delete и исходе ImportXML сохранены. Новая ветвь не печатает сообщение об успешном удалении пропущенной задачи.
- Возвращаемый тип, вызывающий install-путь и прежняя политика продолжения после отдельной ошибки не меняются. Первичная ошибка List по-прежнему возвращается вызывающему коду; частичные ошибки описываются предупреждениями.

Непустые байты не разбираются повторно в этом helper: формат снимка остаётся ответственностью backend. Это не проверка семантической эквивалентности XML и не новый общий механизм транзакций.

### 2.2. Найденное тестовое замечание

**Место:** `fakeListScheduler.List` и `TestPruneObsoleteServerTasks_DeleteFailureContinuesWithOthers` в `prune_tasks_test.go`.

Новая сортировка List первоначально всегда ставила здоровую задачу `mcp-local-hub-s-stale-debug` перед задачей `mcp-local-hub-s-weekly-refresh`, для которой задан отказ Delete. Поэтому существующий тест продолжения после ошибки переставал различать регрессию `return rollbacks, nil` вместо `continue`: успешное удаление и регистрация rollback уже были выполнены до отказа.

Это было конкретное ухудшение тестового покрытия, а не обнаруженный дефект производственной ветви Delete.

**Исправление:** здоровая задача переименована в `mcp-local-hub-s-z-stale-debug` в seed и assertion. При возрастающей сортировке ошибка теперь гарантированно предшествует независимой успешной задаче.

Окончательный файл содержит ровно два употребления нового имени. Обратная замена этих двух имён и восстановление выравнивания литерала в seed возвращают исходный хеш первого кандидата:

`a9a126e73c350f1b764812ede191597717700a275364733b15469caa02f76091`.

Следовательно, повторный проход проверил ограниченное исправление замечания, без других изменений этого тестового файла. Проверка различения раннего return здесь выполнена чтением условий и утверждений теста; запуск такого мутанта этим рецензентом не выполнялся.

### 2.3. Различающая способность остальных затронутых тестов

Новый табличный тест включает пять входов: ошибка экспорта; непустые байты вместе с ошибкой; `ErrTaskNotFound` после List; `nil` без ошибки; пустой массив без ошибки. Детерминированный порядок ставит проблемную задачу перед независимой экспортируемой задачей.

Утверждения проверяют единственный Delete для независимой задачи, единственный rollback, единственный ImportXML, сохранность пропущенной задачи и точные восстановленные байты. Отдельно проверяется предупреждение с именем и причиной.

В ownership fixture все три задачи — planned, собственная obsolete и sibling — получили непустые снимки. Поэтому новый snapshot guard не маскирует ошибочное удаление planned/sibling задачи при снятии прежних фильтров: соответствующие вызовы Delete остаются наблюдаемыми через `deleteNames`. Это исходниковый вывод о тесте, не заявление о выполненных мутационных контролях.

<a id="observer"></a>
## 3. Observer: замечание и исправление

### 3.1. Найденный путь записи через предсуществующий runtime

В первой версии observer с SHA-256

`f1baf760d1d8842b4141d09724b7654b9b82923c9018f0e3add93ce1590dad6e`

проверялись ROOT и его предки, но не существующий `ROOT/runtime`. Отсутствие `receipt.json` не доказывало пустоту рабочего каталога. Последующий `mkdir(parents=True)` для `runtime/temp` мог следовать уже существующему junction и создавать каталоги вне разрешённой области.

**Условие замечания:** наличие предсуществующего `runtime`, перенаправляющего путь. Root отдельно сообщил, что фактический ROOT был проверен как отсутствующий, затем создан и содержал только observer и parser; рецензент не повторял этот удалённый предконтроль.

**Исправление в самом observer:** до вложенных каталогов добавлено

`(ROOT / "runtime").mkdir(exist_ok=False)`.

Предсуществующий каталог, файл или junction теперь приводит к отказу до дальнейшего создания runtime-путей. Самостоятельно подтверждён окончательный SHA-256 из таблицы 1. Удаление ровно этой добавленной строки возвращает исходный хеш первой версии, поэтому других изменений observer между двумя проходами не было.

### 3.2. Данные и операции

Исходник сохраняет только проверенные метаданные, числовые коды, типы, версии, размеры и хеши потоков. Сгенерированное имя задачи остаётся внутри PowerShell-процесса. Определения XML, свойства задач, пути из исключений и тексты ошибок не переносятся в receipt. stdout/stderr временно находятся в памяти; на диск пишется проверенный receipt.

В прочитанном сценарии нет команд создания, экспорта, изменения, запуска, остановки или удаления задач. Нет команд изменения ACL. Используются импорт установленного модуля, получение команды, подключение COM, корневая папка, два вызова `GetTask` и один `Get-ScheduledTask` с буквальным сгенерированным именем. Файловые записи предусмотрены в собственном ROOT.

Этот вывод относится к явным операциям данного исходника. Он не подменяет квалификацию установленного PowerShell/модуля и не заявляет об отсутствии внутренних действий системных служб.

### 3.3. Отсутствие и протокол результата

Завершённое наблюдение допускается только при наблюдении HRESULT `0x80070002` в контрольных цепочках COM до и после запроса. При этом:

- `semantic_absence_verdict` остаётся `null`;
- `atomicity_claim` остаётся `false`;
- классифицируется только полученный ответ resolver: ошибка, пустой успех или непустой успех.

Это не доказательство атомарного отсутствия, видимости скрытых задач, правильной классификации отказа доступа или всей матрицы нативного поведения.

Для принятия результата требуются код завершения процесса 0, пустой stderr, отсутствие timeout, допустимая длина stdout, строгий UTF-8 и успешная проверка схемы. Ошибки процесса или протокола не становятся завершённым наблюдением.

## 5. Границы выводов

### 5.1. Prune и общая транзакция

Узкое исправление предотвращает удаление при неполученном непустом снимке. Оно не гарантирует успешный ImportXML, не меняет general install replacement и не защищает rollback от внешней замены определения между наблюдениями и действиями. Нативная сохранность определений, полный install/upgrade/register/weekly-путь, общий набор Go-критериев и формальные внешние отзывы этим ревью не закрыты.

### 5.2. Сроки и ресурсы observer

45 секунд — бюджет ожидания непосредственного дочернего процесса. Затем предусмотрены kill, дополнительное чтение потоков и ожидание завершения. Это не строгий общий срок всего runner и не срок завершения дерева потомков. Незавершённые потоки и неподтверждённое завершение непосредственного процесса отмечаются в receipt отдельно.

Порог stdout в 65 536 байт проверяется после `communicate`. Он ограничивает принятие протокола, но не задаёт жёсткий предел оперативной памяти при сборе stdout/stderr. Для фиксированного прочитанного сценария это не выявленный блокирующий дефект; утверждение об ограниченном по памяти чтении было бы шире кода.

Создание свежего runtime закрывает найденный путь через предсуществующий junction. Оно не заявляет атомарного удержания файловой системы против внешнего автора, меняющего пути во время исполнения.

### 5.3. Статус независимого чтения

Отсутствие оставшихся блокирующих замечаний в этом срезе не является разрешением на нативные действия, слияние, интеграцию веток или расход внешних квот. Требуемые права и допуски остаются отдельными от данного документа. Самостоятельное чтение root также не заменяется этим ревью.

**Обозначения:** PR — pull request, запрос на включение изменений; SHA-256 — алгоритм криптографического хеширования для сверки байтов; XML — формат определения задачи; COM — компонентная модель Windows; CIM — общая модель управленческих данных; ACL — список управления доступом; HRESULT — числовой код результата Windows; UTF-8 — кодировка Unicode; stdout/stderr — стандартные потоки вывода и ошибок процесса; junction — точка перенаправления каталога Windows.
