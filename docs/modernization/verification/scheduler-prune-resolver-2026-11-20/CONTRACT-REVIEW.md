## 1. Решение

Сохранить производственный экспорт через COM — компонентную объектную модель Windows. Следующее отдельное наблюдение касается только отсутствующего объекта на этапе **`Get-ScheduledTask`**. Оно не вызывает `Export-ScheduledTask`, не читает свойство XML — определения в расширяемом языке разметки — и не повторяет ранее завершённое сравнение вариантов экспорта.

Проверяемая гипотеза: отсутствие буквального корневого имени в CIM — общей модели управленческих данных — может представляться пустым успешным результатом, ошибкой слоя команд PowerShell либо ошибкой поставщика CIM. Эти исходы нельзя заранее свести к одному `ErrTaskNotFound`. Наблюдатель фиксирует форму ответа и типизированные числовые сведения; он не внедряет классификатор в продукт.

Оператор PowerShell `-ceq` чувствителен к регистру, но его не следует называть сравнением `StringComparison.Ordinal`: документация описывает для строк `InvariantCulture` [3]. Для текущего ASCII-префикса это различие не меняет описанный обычный путь, однако произвольный Unicode требует отдельного контракта.

`Get-ScheduledTask` поддерживает запросы с маской в `TaskName` и `TaskPath`; документация для Windows Server 2016 явно отмечает это в свойствах параметров [4]. В современной странице встречается противоречие между описанием маски и таблицей `Supports wildcards`; это не основание считать параметр буквальным. Будущий поиск должен явно проверять число выбранных объектов, их корневой путь и соответствие имени принятой политике регистра. Передача первого найденного объекта недопустима. `Export-ScheduledTask -InputObject` и экспорт по каноническим имени/пути — разные наборы параметров [5]; имеющееся наблюдение уже показало различающиеся представления, поэтому они не взаимозаменяемы по умолчанию.

Протокол перечисления задач предусматривает пропуск объектов, на которые у вызывающего нет доступа на чтение или запись [6]. Следовательно, отсутствие имени в результате перечисления не доказывает физическое отсутствие задачи вообще. Это вывод из документации и текущей конструкции поиска, а не новое нативное воспроизведение отказа доступа. Настоящее получение определения отдельно описывает отсутствие и отказ в доступе [7]; конкретный мост и вложенные исключения всё равно требуют квалификации.

Значение `NativeErrorCode=1` означает общий `Failed`, а `NotFound` в перечислении CIM имеет значение 6 [8]. Поэтому прежнюю запись нельзя корректно описать как «CIM вернул NativeErrorCode NotFound». Наличие `0x80070002` именно в расширенных числовых данных существенно; исходное сообщение ошибки для этого не требуется.

<a id="probe"></a>
## 4. Новый узкий наблюдатель

Файл: [probe_cim_resolver_absence.py в архиве](evidence-redacted.zip), раздел `resolver/`. Фиксированная рабочая область: `<WORK_ROOT>\mcp-r17-cim-resolver-20261120`. Начальный каталог должен существовать; файл квитанции и каталоги времени выполнения должны быть новыми. Все собственные записи направлены в эту область; список управления доступом не изменяется.

Последовательность:

1. Проверить Windows PowerShell 5.1, модуль ScheduledTasks 1.0.0.0 и единственную команду `Get-ScheduledTask` из него.
2. Создать в памяти корневое буквальное имя с GUID — глобально уникальным идентификатором — без символов маски и разделителей пути. Имя не сохраняется и не печатается.
3. Вызвать `GetTask` COM для этого имени. Продолжать только при наличии `0x80070002` в цепочке исключений; неожиданный объект, `null` или иная ошибка не допускают случай к измерению.
4. Один раз вызвать `Get-ScheduledTask -TaskName $leaf -TaskPath '\' -ErrorAction Stop`. При успехе сохранить число результатов и только имена типов; при исключении — типы, HRESULT, числовую категорию и доступные числовые поля ошибки CIM. После исключения число ранее поступивших объектов не объявляется известным.
5. Повторить только контрольный COM `GetTask` того же имени. Второй `0x80070002` допускает наблюдение к интерпретации; атомарность между контрольными чтениями не заявляется.
6. Сохранить проверенную по разрешённой схеме квитанцию. Для исходных потоков сохраняются лишь длины и SHA-256 — 256-разрядные криптографические хеши. Имена задач, XML, значения полей задач, сообщения исключений и сами исходные потоки не записываются.

`completed=true` и код завершения 0 означают только завершённое наблюдение с обоими допущенными контролями. Поле `classification` различает `EMPTY_SUCCESS`, `NONEMPTY_SUCCESS`, `ERROR_OBSERVED`; `semantic_absence_verdict` остаётся `null`. Это не PASS миграции на CIM. `source_executed=false` и `actual_product_consumer_exercised=false` сохраняются явно.

Ограничитель непосредственно созданного процесса — 45 секунд; после принудительного завершения предусмотрено до 5 секунд сбора потоков. Полное дерево потомков не квалифицируется. При незавершённом сборе потоков сценарий не пытается синхронно закрывать буфер, блокировка которого может удерживаться потоком чтения Windows; завершение отдельного процесса наблюдателя освобождает его дескрипторы.

Перед нативным запуском нужен отдельный синтаксический разбор встроенного PowerShell через `System.Management.Automation.Language.Parser.ParseInput`. Строку `SCRIPT` можно извлечь Python `ast.parse`/`ast.literal_eval`, не исполняя файл. Эта статическая записка не утверждает, что разбор PowerShell или нативный запуск уже выполнены.

<a id="review"></a>
## 5. Собственное ревью

Проверено локально: синтаксис Python; принятие допустимой синтетической квитанции; отказ при лишнем имени задачи, вложенном сообщении исключения, несогласованном коде контрольного отсутствия и несогласованной классификации — четыре отрицательных случая. Проверено отсутствие в исполняемой строке PowerShell вызовов экспорта, регистрации, удаления и запуска задач, свойств `Xml`/`Definition` и операций изменения прав. Это статические проверки конкретного сценария; они не доказывают все возможные побочные действия модуля Windows.

Исправлены до передачи: неожиданные исключения подготовки/сохранения выдаются только как имя класса; на ошибке завершается собственный дочерний процесс; неполный сбор потоков не приводит к потенциально бесконечному ожиданию блокировки буфера. После независимого замечания основной исполнитель потребовал отдельное создание `runtime` с `exist_ok=False`: любой существующий каталог или ссылка отклоняется до вложенных записей. Продуктовый код не менялся. Установок, запусков внешних агентов, публикаций GitHub и обращений к удалённой машине этим рецензентом не было.

Текущий SHA-256 файла наблюдателя: `c1eb1a4172bf89a308e06c65c0134aed404ae66e54d2b61907676917da4b7cce`. SHA-256 строки PowerShell: `fbf2f3cb65e40ab64115f815397ff64e786fde43aed961ae26027a965628c128`. Результаты нативного запуска должны храниться отдельно от этой записи подготовки.
