## 1. Метод

Проверялось только состояние, реально достижимое из текущего `master`. Название ветки, открытый Pull Request (PR; запрос на включение изменений) и заявленный результат тестов сами по себе не меняют текущий продукт.

Классификация:

- commit в `master` — текущий контракт, подлежащий повторному сканированию;
- открытый PR — ожидающее доказательство;
- закрытая без merge ветка — историческое evidence;
- прежний audit finding не закрывается без проверки актуального дерева.

## 2. Масштаб изменения

Между снимками находится 61 commit. Изменения затрагивают supervisor lifecycle, install/adopt, Serena routing, readiness, upgrade, scheduler handling, tool runtimes, release metadata, документацию и архитектурный анализатор.

Поэтому A2 не использует старые:

- fingerprints;
- file-size counts;
- package owners;
- worker locations;
- результаты сканирования `83b49f4`.

Единственная допустимая база — exact `master@f6df9f6` либо более новый exact SHA, если до генерации baseline в `master` будут слиты дополнительные изменения.

## 3. Слитые архитектурно значимые изменения

### 3.1. Supervisor и process lifecycle

В `master` появились либо существенно изменились:

- durable stop-batch settlement;
- generation-bound readiness и process identity;
- supervisor-owned Serena activity;
- route-front readiness и stop handling;
- transaction fencing upgrade/liveness;
- typed termination outcomes;
- process-tree и port-fence проверки.

Это усиливает будущие `WP-11C` и `WP-08`, но не отменяет characterization: A3/A5 должны фиксировать именно текущее post-hotfix поведение.

### 3.2. Install, adopt и upgrade

Текущий код содержит:

- durable receiver settlement;
- adopt profile-update transaction;
- lease namespace migration;
- upgrade transaction с проверкой retained prior;
- удаление старых неподдерживаемых mutation paths;
- rollback/readback contracts.

Следствие: `WP-11D` должен извлекать чистые planning/execution owners из уже существующих транзакционных механизмов, а не проектировать параллельную систему.

### 3.3. MCP, routing и совместимость

Слиты:

- profile-scoped legacy protocol compatibility;
- stdio bridge admission до публикации;
- текущий route daemon;
- Serena default-workspace resolution;
- protocol/readiness distinctions.

Следствие: `DELTA-001` и `DELTA-006` остаются обязательными объектами revalidation. Наличие новых механизмов не считается доказательством полного закрытия исходных требований.

### 3.4. Tool runtimes

Появился durable VTune run owner; сохранены отдельные oneAPI, vcpkg и другие tool-runtime процессы. A2 учитывает их Go goroutine в общем scan, а межъязыковые и native process trees остаются отдельным inventory `DELTA-004`.

### 3.5. Каноническая документация и A1

Слиты:

- PR №605 — канонический пакет модернизации;
- PR №602 — `internal/archguard` и `tools/archcheck`.

A2 теперь может хранить policy/owners/baseline/workers в репозитории и использовать локальный ratchet без GitHub-hosted Continuous Integration (CI; непрерывной интеграции).

<a id="a2"></a>
## 6. Следствия для A2

1. Policy сканирует `cmd`, `internal` и `tools`.
2. Подтверждённые custom test-only build tags: `af1_counters` и `test_state_path_env`.
3. `api.NewAPI`, `cli.NewRootCmd` и `gui.NewServer` становятся exact constructor rules.
4. Существующие production-вызовы и mutable globals фиксируются exact fingerprints, а не path-wide исключениями.
5. File budgets являются начальной policy и утверждаются только после просмотра распределения текущего scan.
6. Owners применяются specific-first; временный catch-all имеет короткий срок и не допускается в финальном baseline.
7. `workers.yaml` начинает с пустого реестра; worker violations остаются baseline debt до A5/A6.
8. Baseline создаётся локально командой `archcheck baseline` из exact clean checkout.
9. Один repository contract test проверяет policy/owners/workers и каноническую трассировку; отдельный `doccheck`, генератор Markdown и JSON Schema не создаются.
10. GitHub остаётся владельцем live-status; YAML не дублирует текущие assignee или mutable dashboard state.
