## 1. Дефект и граница исправления

В исходном #660 `verifyInstallTaskDefinitionBeforeDelete` повторно читал
описание задачи и сравнивал его с сохранёнными байтами. Следующий вызов
`Delete(name)` удалял текущего владельца имени. Между чтением и удалением
другой писатель мог заменить регистрацию; новое поколение могло иметь точно
такое же XML-представление (Extensible Markup Language, расширяемый язык
разметки). Локальная блокировка manifest не исключала такого писателя.

Та же граница находилась в компенсации ранее созданной задачи и в
`pruneObsoleteServerTasks`. Кроме того, `installTaskMutationFailure` принимал
совпадение с прежним XML после ошибочного ответа за подтверждение прежнего
состояния, хотя идентичность поколения оставалась неизвестной.

Исправлены именно эти три владельца: замена задачи в install, компенсация
создания и автоматическое удаление устаревших задач при полном install.
Прочие операции удаления перечислены в разделе 7 и не объявлены исправленными.

## 2. Контракт и последствия

**Таблица 1 — поведение после исправления.**

| Ситуация | Результат |
|---|---|
| До создания наблюдается существующая задача | Замена отклоняется с `ErrSchedulerReplacementUnowned`; сохраняется доступное наблюдаемое описание. Нет `Delete`, `Create`, `ImportXML` или восстанавливающей регистрации. |
| Наблюдается отсутствие задачи | Допускается единственный `Create`, который сам обязан отклонить занятое имя. Ошибка ответа не вызывает повтор или удаление занятого имени. |
| После ошибочного `Create` подтверждено отсутствие | Сохраняется первоначальная ошибка; дополнительная неполная компенсация не создаётся. |
| После ошибочного действия результат неизвестен | Возвращается `InstallSchedulerRollbackIncompleteError`; сохраняются первоначальная ошибка и ошибка наблюдения. Совпадающее XML не превращает ошибку в успех или подтверждение прежнего поколения. |
| После подтверждённого создания падает следующий шаг | Компенсация подтверждает наблюдаемое отсутствие либо удерживает задачу и сообщает неполное восстановление. При доступном описании сохраняет снимок. |
| Prune находит устаревшую задачу | Сохраняет наблюдаемое описание и выдаёт именованное предупреждение об отказе. При недоступном описании или хранилище сохраняет причину предупреждения. Удалений и последующих компенсаций нет. |

У prune интерфейс содержит только `List` и `ExportXML`. Удалены прежние
компенсации prune, а также сравнение XML, за которым следовал `Delete`.
Порядок остальных компенсаций остаётся обратным порядку выполненных шагов.
Первоначальные, Scheduler- и клиентские причины не смешиваются в один тип:
неполное восстановление Scheduler продолжает удерживать provenance adopt,
то есть исходные сведения, необходимые для восстановления принятой конфигурации.

Практическое ограничение сознательное: обычная повторная установка не может
разрушительно заменить существующую задачу без исключительного права на её
поколение. Необязательный prune может оставить старую задачу действующей и
обязан сообщить об этом. Полноценная замена требует отдельного подтверждённого
контракта исключительного писателя либо условной операции в самом Scheduler.

## 5. Каждый FAIL и SKIP

Первая фаза `install-generation-v1-20261123-57604a3a` дала 121 PASS, 5 FAIL и
1 SKIP. Три конечных FAIL относятся к `TestExecuteInstallToPruneRetainsObservedDefinition`:
`install_succeeds`, `later_failure`, `external_absence_before_later_failure`.
Ещё два — их родитель и пакет. Проверка сообщения искала неэкранированный
Windows-путь, тогда как ошибка намеренно печатает его через `%q`.
Исправлено сравнение с `strconv.Quote(path)`; проверка сохранённых байтов и
отсутствия мутаций осталась прежней. Финальный повтор прошёл. Сырые события
первого отказа сохранены; остановившиеся последующие команды первой фазы
исполнены уже на финальном составе.

В отрицательном контроле код `install.go` и `install_task_rollback.go` взят
побайтно из родителя. Ещё два прежних файла тестов используются только для
совместимости изменившейся сигнатуры prune; они не входят в выбранные контрольные
сценарии. Это настоящий прежний производственный код, а не искусственно
сломанная реализация. Все 18 FAIL ожидаемы: 14 конечных случаев, три родителя и
пакет. Часть случаев различает новый тип отказа; четыре обязательных случая
отдельно закреплены в плане:

- `replacement_external_same_xml`: прежний install возвращает успех;
- `prune_external_same_xml`: прежний prune сообщает удаление задачи;
- `external_same_xml` в компенсации: прежний владелец возвращает только исходную
  ошибку вместо неполного восстановления;
- `same_xml` в классификаторе: совпадение с прежним описанием ошибочно снимает
  неопределённость поколения.

Единственный вид SKIP, повторённый в двух финальных выборках:
`TestExecuteInstallToRollbackBackendCompatibility/unsupported_platform`.
Он проверяет неподдерживаемый нативный backend Linux/macOS и пропущен на Windows,
где backend поддерживается. Это объяснённая неприменимость данного случая к
хосту; исполнение POSIX — интерфейсов Unix-подобных систем — остаётся отдельным
обязательным пунктом, не закрытым этим пропуском.

## 6. Собственное ревью

Проверены требования, источник полномочий, конкурентная замена, неизвестный
эффект, сохранение ошибок, совместимость клиентов, порядок компенсаций,
сохранность снимков и отсутствие неявного повторения операции. Исправление не
вводит фиктивный токен поколения, новую блокировку или неиспользуемый интерфейс
исключительного владельца. Существующий тип отказа переиспользован; предупреждения
prune не объявляют удаление выполненным. Удалены недостижимые разрушительные
ветви и обновлены тесты соответствующего поведения.

В проверенном изменении открытых предметных замечаний собственного ревью не
осталось. Внешнее ревью нового коммита отсутствует; собственное ревью его не
заменяет. Полная готовность PR и продукта не заявляется.

## 7. Ограничения и остаточный план

Этот инкремент не даёт backend исключительных прав записи. Не квалифицированы
реальные системные задачи, дерево процессов при тайм-ауте, установка и обновление
продукта. В остальных владельцах остаются операции по имени, в частности
`Uninstall`/`uninstallWithoutManifest`, legacy enable/disable, liveness,
авторегистрация LSP (Language Server Protocol, протокол языковых серверов) и
регистрация supervisor. Их назначение, полномочия и жизненный цикл требуют
отдельного адресного разбора; локальный mutex или XML-сравнение не заменяют его.

Полные обязательные команды `go test -count=1 -timeout 5m ./...` и
`go test -tags=test_state_path_env -count=1 -timeout 5m ./internal/api/ ./internal/cli/`
имеют статус NOT_RUN: полный состав ещё требует допустимых нативных фикстур и
согласованных Source/Product/Serena-входов. API — программный интерфейс; CLI —
интерфейс командной строки. Наблюдённое препятствие нативной namespace-фикстуры
сохранено в [предыдущем отчёте](https://github.com/applicate2628/mcp-local-hub/tree/b884b1ea90edd041204bc15ac6c9f0f3fb8b6da0/docs/modernization/verification/publisher-roles-20261123):
нельзя удержать требуемый доступ к предку установленного PowerShell в WindowsApps.
Фикстура требует PowerShell 7.2+, поэтому системный PowerShell 5.1 не является
совместимой заменой. Установка другого runtime или изменение прав не выполнялись.

Ближайшие шаги: закончить остальные адресные границы удаления; согласовать новый
Source с текущими владельцами, включая новые #664/#665/#666 и Serena-ветви;
заново выдать отдельные Product, тестовый Product #657 и издатель Serena; затем
допустить полные наборы и сквозные нативные сценарии. Полный остаточный план A–D
поддерживается у владельца #664; измерения Relay/CMake, возобновление POST-потока,
обоснование Rust, reader #627 и компонент a217 этим изменением не закрыты.
