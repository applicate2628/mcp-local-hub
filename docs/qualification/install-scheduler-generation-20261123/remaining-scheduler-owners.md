## 1. Граница контракта

Task Scheduler, планировщик задач Windows, выполняет `Delete(name)` и
принудительный импорт по имени. Выгрузка XML (расширяемого языка разметки)
описывает содержимое регистрации. После чтения внешний писатель может занять то
же имя с изменённым или побайтово идентичным определением. Для привязки мутации
к прочитанному поколению нужна условная операция в планировщике или подтверждённая
исключительность записи. Снимок и блокировки между сотрудничающими процессами
эту привязку не обеспечивают. [Интерфейс планировщика](/internal/scheduler/scheduler.go#L120) · [Принудительный импорт Windows](/internal/scheduler/scheduler_windows.go#L261)

не превращает неизвестный эффект в успех. Отпечаток StrictMode по-прежнему
служит для сравнения наблюдений при откате intent.

## 4. Явное удаление и сохранённый OFF

- `uninstall` и `unregister` удаляют задачи целевого сервера или workspace по
  имени. Общие задачи watchdog и liveness удаляются при явном uninstall после
  проверки, что других управляемых серверов не осталось. Команда
  `scheduler weekly-refresh --disable` удаляет общую задачу расписания.
  [Uninstall](/internal/api/install.go#L1910) · [Uninstall без manifest](/internal/api/install.go#L2153) · [Unregister](/internal/api/register.go#L2780) · [Общие задачи](/internal/cli/setup.go#L789) · [WeeklyRefreshDisable](/internal/api/scheduler_mgmt.go#L336)
- `autostart disable` записывает OFF и удаляет каноническую задачу по имени.
  Сохранённый выбор OFF применяется install, StrictMode и завершением upgrade
  под блокировкой настроек. При такой проекции выполняется независимое чтение
  после удаления, включая случай ошибки удаления. Только типизированное
  отсутствие подтверждает OFF. Эти действия реализуют выбранную политику для
  имени задачи. [Явный OFF](/internal/cli/autostart_owner_mode_windows.go#L60) · [Проекция и чтение](/internal/autostart/autostart.go#L241) · [Типизированное отсутствие](/internal/autostart/windows.go#L214) · [Проекция при upgrade](/internal/cli/install_migration_wiring_windows.go#L1647)

## 5. Композиция с #669

При наложении #669 на отдельную ветку #660 требуется одна правка описи.
Из `reviewedRawFlockOwners` удаляется строка с ключом
`internal/api/secrets_init_recovery.go:method:*secretsInitRecoveryOwner.locked`
и счётчиком `1`. В #660 строка соответствует прямому `flock.New`. #669
переводит вызов на `lockLeafLedgered` и передаёт ошибку освобождения через
`ReleaseAndJoin`. Проверка синтаксического дерева считает только `New`,
привязанный к `github.com/gofrs/flock`, поэтому в таком сочетании счётчик
становится нулём. Проверка композиции — `TestSupervisorIntentLockOwnershipProductionInventory`.
[Строка перечня](/internal/api/supervisor_intent_lock_ownership_test.go#L42) · [Проверка вызовов](/internal/api/supervisor_intent_lock_ownership_test.go#L234) · [Условие композиции](/docs/qualification/scheduler-generation-error-origins-20261123/README.md#6-dependencies-and-readiness)

В Product B `3ebe335a` и Test Source B `001648f4` уже применены
`lockLeafLedgered` и `ReleaseAndJoin`, а исходная строка Secrets Recovery
уже отсутствует. Из #669 остаются объединение двух причин в `Unwrap` и
тестовый файл. Для композиции с B сперва нужна кодовая база #660, включая
транзакционный weekly refresh и две соответствующие записи описи

последующая autostart-правка `c0b0cc22` на девять путей, native-коррекция
`36651526` на четыре пути и остаток #669.
В том же составе сохраняются актуальные #637
`123858ef8292aceb86d8ca7ef71d4e4dea1fec91`, #659
`6f59746beae329d9f3f6e4f5af4d503d822d2e4f` и #671

Тринадцать blob B в исторической таблице сохраняют исходный тестовый слой,

## 7. Итоги проверки правки

Результаты прежней правки на 22 пути сохраняют свои исходные границы.
Последующие адресные результаты приведены отдельной контрольной точкой ниже.

- Исправлено пересечение legacy handoff с прямым остановом удалённой
  supervisor-цели. Ранее общий путь install мог остановить процесс по
  прежнему порту после отказа удалить legacy-задачу. Теперь автоматический
  Windows install завершает эту ветку до вызовов принудительного останова по PID
  (идентификатору процесса) и порту. Reconcile у supervisor продолжает обрабатывать
  его собственные процессы. [Граница останова](/internal/api/install_parsed_manifest.go#L1684)
- Исправлена устаревшая запись `actual_intent_state` при успешной записи
  intent и отказе autostart. Тот же учёт применяется к `actual_intent_owner_mode`.
  В исходном срезе на 22 пути существующая задача при включённом autorun
  требовала явного решения для продолжения проекции; новый no-op описан в §2. [Учёт результата](/internal/cli/strict_mode.go#L900)
- Исправлена подсказка при отказе применить сохранённый autorun OFF:
  `autostart enable` записывает противоположный выбор ON. Теперь диагностика
  предлагает `autostart status --details` и проверку сохранённой политики.
  Существующий тест запрещает совет enable для OFF и требует один Enable без
  Disable для ON. Адресная квалификация этой поздней правки теперь получена
  в обоих режимах в составе с 26 точными входами; см. текущую контрольную точку. [Диагностика](/internal/api/install_parsed_manifest.go#L1395) ·
  [Проверки выбора](/internal/api/phase_f_lifecycle_test.go#L675)
- Эти выводы основаны на чтении обеих точек входа install и ветвей
  StrictMode. Подтверждённый CLI-прогон относится к своим 21 закреплённым файлам;
  его результат не переносится на другие составы. Новая workspace-фикстура,
  поздние lifecycle-проверки и смежные install/port-stop сценарии теперь
