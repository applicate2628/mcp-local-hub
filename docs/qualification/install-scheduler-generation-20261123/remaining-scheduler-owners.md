## 1. Граница контракта

Task Scheduler, планировщик задач Windows, выполняет `Delete(name)` и
принудительный импорт по имени. Выгрузка XML (расширяемого языка разметки)
описывает содержимое регистрации. После чтения внешний писатель может занять то
же имя с изменённым или побайтово идентичным определением. Для привязки мутации
к прочитанному поколению нужна условная операция в планировщике или подтверждённая
исключительность записи. Снимок и блокировки между сотрудничающими процессами
эту привязку не обеспечивают. [Интерфейс планировщика](/internal/scheduler/scheduler.go#L120) · [Принудительный импорт Windows](/internal/scheduler/scheduler_windows.go#L261)

Prune сохраняет доступное описание и предупреждает. Компенсация подтверждает отсутствие либо удерживает текущую регистрацию и сообщает о неполном восстановлении. При подтверждённом отсутствии задачу создаёт `Create`, который отклоняет занятое имя. Ошибка создания не разрешает удаление или повторную регистрацию. Dry-run перечисляет видимые задачи, отобранные по текущему пользователю. Setup проверяет legacy watchdog после обязательного шага liveness и продолжает регистрацию EventLog при отказе или ошибке наблюдения watchdog. [Переход legacy](/internal/api/install_parsed_manifest.go#L1733) · [Dry-run](/internal/api/install_parsed_manifest.go#L1253) · [Setup](/internal/cli/setup.go#L734) |

Доступные байты сохраняются через защищённый снимок. После ошибки создания выполняется диагностическое чтение без повторной мутации. StrictMode сохраняет первичную ошибку и сопоставляет полную выгрузку XML и признак Disabled с исходным наблюдением. Install продолжает межпроцессное обращение к работающему supervisor и проверку его блокировки. При недоступности такого обращения Windows-ветка пропускает запуск задачи по имени. После reconcile обе ветви отказываются от прямого принудительного останова удалённых целей по PID или порту. Dry-run явно показывает отказ в глобальной ветке. POSIX использует прежний путь останова. Явные stop и uninstall используют свои пути. [Вызов для workspace](/internal/api/install_parsed_manifest.go#L687) · [Глобальный вызов](/internal/api/install_parsed_manifest.go#L1151) · [Отказ](/internal/api/install_parsed_manifest.go#L1684) · [Dry-run](/internal/api/install_parsed_manifest.go#L1265) |
| Учёт записи intent в StrictMode `--recover` | После успешной записи либо ошибки с подтверждённым применением intent обновлённая запись восстановления отражает выбранные strict mode и owner mode. Обычная ошибка записи не подтверждает это применение. Проекция может отказать при наличии Windows-задачи. Применённый intent остаётся в силе, ошибка проекции и возможная ошибка обновления записи выводятся с кодом выхода 10. [Проекция](/internal/cli/strict_mode.go#L937) · [Запись восстановления](/internal/cli/strict_mode.go#L900) |

с нормализацией Windows и подтверждения на воспроизводимой фикстуре. Отпечаток

## 3. Открытые владельцы

| `EnsureLivenessTask` и `RestoreLivenessTask` | Setup принудительно импортирует liveness-задачу при отсутствии или расхождении определения. При ошибке или расхождении контрольного чтения откат удаляет созданную задачу по имени либо принудительно импортирует старую. Публичный Restore, вызываемый сейчас только тестами, проверяет равенство XML перед тем же откатом. Между чтением и мутацией может появиться другой владелец имени. Ошибка liveness завершает Windows setup с кодом 12 до наблюдения watchdog и регистрации EventLog. Минимальный следующий контракт — `XMLCreator.CreateXMLIfAbsent` после подтверждённого отсутствия, сохранение наблюдаемого определения при drift и отказ от разрушительного отката. Текущая проверка совпадения охватывает часть полей, например, пропускает начало и признак включения календарного триггера. [Ensure и Restore](/internal/api/liveness_task.go#L197) · [Разбор определения](/internal/api/liveness_task.go#L469) · [CreateXMLIfAbsent](/internal/scheduler/scheduler_xml_create_windows.go#L13) |
| Windows Product, `OwnedEntrypointTaskTxn` | Транзакция работает с задачами текущего пользователя по префиксу, включая подходящую liveness-задачу. Исключение задач, перевод команды на новый Product, финальное включение и восстановление вызывают принудительный импорт. Компенсация проверяет байты перед импортом, а при неизвестном результате мутации возвращает ошибку незавершённого перехода без повторного импорта. Требуется отдельно установить полномочия на последующий импорт при внешнем писателе. [Исключение](/internal/scheduler/entrypoint_migration_windows.go#L296) · [Финальный импорт и компенсация](/internal/scheduler/entrypoint_migration_windows.go#L392) · [Перенос команды](/internal/scheduler/entrypoint_migration_windows.go#L809) · [Restore](/internal/scheduler/entrypoint_migration_windows.go#L887) |
| Runtime `supervise --ensure-alive` | После проверок режима и доступности supervisor ветка повторного запуска всё ещё вызывает `Run` по каноническому имени autostart. Идентификатор процесса и путь исполняемого файла подтверждают свойства процесса. Они не привязывают `Run` к поколению регистрации, которая может измениться между наблюдением и запуском. Это отдельный путь от холодного старта из install. [Решение runtime](/internal/cli/supervise_ensure_alive.go#L1737) · [Запуск по имени](/internal/cli/supervise_ensure_alive.go#L580) |

Перенос существующего прокси LSP (Language Server Protocol, протокол языковых серверов) и регистрация в режиме supervisor также сохраняют именованные удаления и принудительное восстановление. ## 4. Явное удаление и сохранённый OFF

- `uninstall` и `unregister` удаляют задачи целевого сервера или workspace по
  имени. Общие задачи watchdog и liveness удаляются при явном uninstall после
  проверки, что других управляемых серверов не осталось. Команда
  `scheduler weekly-refresh --disable` удаляет общую задачу расписания.
  [Uninstall](/internal/api/install.go#L1910) · [Uninstall без manifest](/internal/api/install.go#L2153) · [Unregister](/internal/api/register.go#L2780) · [Общие задачи](/internal/cli/setup.go#L789) · [WeeklyRefreshDisable](/internal/api/scheduler_mgmt.go#L336)
- `autostart disable` записывает OFF и удаляет каноническую задачу по имени.
  Сохранённый выбор OFF применяется install, StrictMode и завершением upgrade
  под блокировкой настроек. При такой проекции выполняется независимое чтение
  после удаления, включая случай ошибки удаления. Только типизированное
  отсутствие подтверждает OFF. Эти действия реализуют выбранную политику для
  имени задачи. [Явный OFF](/internal/cli/autostart_owner_mode_windows.go#L60) · [Проекция и чтение](/internal/autostart/autostart.go#L241) · [Типизированное отсутствие](/internal/autostart/windows.go#L214) · [Проекция при upgrade](/internal/cli/install_migration_wiring_windows.go#L1647)

## 5. Композиция с #669

При наложении #669 на отдельную ветку #660 требуется одна правка описи.
Из `reviewedRawFlockOwners` удаляется строка с ключом
`internal/api/secrets_init_recovery.go:method:*secretsInitRecoveryOwner.locked`
и счётчиком `1`. В #660 строка соответствует прямому `flock.New`. #669
переводит вызов на `lockLeafLedgered` и передаёт ошибку освобождения через
`ReleaseAndJoin`. Проверка синтаксического дерева считает только `New`,
привязанный к `github.com/gofrs/flock`, поэтому в таком сочетании счётчик
становится нулём. Проверка композиции — `TestSupervisorIntentLockOwnershipProductionInventory`.
[Строка перечня](/internal/api/supervisor_intent_lock_ownership_test.go#L42) · [Проверка вызовов](/internal/api/supervisor_intent_lock_ownership_test.go#L234) · [Условие композиции](/docs/qualification/scheduler-generation-error-origins-20261123/README.md#6-dependencies-and-readiness)

В Product B `3ebe335a` и Test Source B `001648f4` уже применены
`lockLeafLedgered` и `ReleaseAndJoin`, а исходная строка Secrets Recovery
уже отсутствует. Из #669 остаются объединение двух причин в `Unwrap` и
тестовый файл. Для композиции с B сперва нужна кодовая база #660, включая
транзакционный weekly refresh и две соответствующие записи описи
классификаторов. После неё применяются локальная правка на 22 пути и
остаток #669. [Матрица путей и порядок композиции](scheduler-source-composition-20261126.md)

## 6. Открытая квалификация

Остаются сквозные проверки точного состава с реальным Windows Task Scheduler
для установки, обновления, отмены и восстановления, включая одновременного
писателя, неизвестный результат создания и проверку уже работающего владельца.
Отдельно нужны квалификация актуальных Source и Product и полные стандартный
и tagged наборы Go с допущенными входами. Результаты тестов с фикстурами
Scheduler, предыдущие отчёты и снимки XML применимы в границах указанных в них
составов. [Пределы квалификации install](/docs/qualification/install-scheduler-generation-20261123/README.md#7-ограничения-и-остаточный-план) · [Пределы квалификации Scheduler](/docs/qualification/scheduler-generation-error-origins-20261123/README.md#6-dependencies-and-readiness)

## 7. Итоги проверки правки

- Исправлено пересечение legacy handoff с прямым остановом удалённой
  supervisor-цели. Ранее общий путь install мог остановить процесс по
  прежнему порту после отказа удалить legacy-задачу. Теперь автоматический
  Windows install завершает эту ветку до вызовов принудительного останова по PID
  (идентификатору процесса) и порту. Reconcile у supervisor продолжает обрабатывать
  его собственные процессы. [Граница останова](/internal/api/install_parsed_manifest.go#L1684)
- Исправлена устаревшая запись `actual_intent_state` при успешной записи
  intent и отказе autostart. Тот же учёт применяется к `actual_intent_owner_mode`.
  При включённом autorun существующая задача по-прежнему требует явного решения
  для продолжения проекции. [Учёт результата](/internal/cli/strict_mode.go#L900)
- Исправлена подсказка при отказе применить сохранённый autorun OFF:
  `autostart enable` записывает противоположный выбор ON. Теперь диагностика
  предлагает `autostart status --details` и проверку сохранённой политики.
  Существующий тест запрещает совет enable для OFF и требует один Enable без
  Disable для ON. Последняя правка и эти проверки имеют статус исполнения
  NOT_RUN. [Диагностика](/internal/api/install_parsed_manifest.go#L1395) ·
  [Проверки выбора](/internal/api/phase_f_lifecycle_test.go#L675)
- Эти выводы основаны на чтении обеих точек входа install и ветвей
  StrictMode. Подтверждённый CLI-прогон относится к своим 21 закреплённым файлам;
  финальная API-квалификация остаётся открытой. Новая workspace-фикстура и
  обновлённая lifecycle-проверка сохранения legacy-задач не исполнены.
  [Точные области проверок](scheduler-owner-contracts-20261126.md#3-проверки-и-точные-исходники).
  Владение поколением задачи для runtime-запуска и остальных операций из таблицы 2
  остаётся открытым.
