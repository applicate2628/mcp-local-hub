# Автоматические владельцы Scheduler: продолжение A от 26 ноября 2026 года

**Изменённые в этом продолжении автоматические операции сохраняют наблюдаемое определение существующей задачи и отказываются от замены без владения её конкретным поколением.** Создание разрешено после типизированного подтверждения отсутствия. На Windows install также отказывается от самостоятельного принудительного останова удалённых supervisor-целей по PID или порту. Уведомление supervisor о новых настройках сохраняется. Остальные владельцы, включая отдельную liveness-ветку setup, перечислены как открытые в разделе 5.

Это продолжение существующего PR #660. Исходная база — `8d4f2606c9af7e20181e4ad290b29be0e0a2dd0f`. Изменения install replacement, rollback и prune из этой базы повторно не реализуются. Общая композиция с исходниками B и #669 и выпуск нового Product остаются открытыми.

Имя задачи, совпадение её XML, PID и путь процесса сами по себе не подтверждают владение исходным поколением регистрации. Ошибка `ErrTaskReplacementUnowned` общая для Scheduler и autostart. Обёртка наблюдённых байтов клонирует данные при входе и выдаче; строки ошибок не раскрывают XML. API использует существующее защищённое сохранение, без нового хранилища или зависимости.

Сохранённый autorun OFF продолжает означать явное удаление проекции с независимым подтверждением отсутствия. Английский текст ошибки вроде «does not exist» больше не считается таким подтверждением. Полный отпечаток наблюдения StrictMode учитывает исходное определение и отключённое runtime-состояние задачи. Равенство отпечатков не предоставляет права заменить задачу.

Холодный Windows install сохраняет IPC-уведомление и проверку блокировки supervisor, но не запускает задачу по имени. При отсутствии подтверждённого работающего supervisor печатает подсказку о запуске владельца через `mcphub gui` или `mcphub supervise`.

## 2. Замечания собственного чтения

Проверка зависимостей и контрактов выявила три дополнительных дефекта. Они исправлены в этой же области PR и перечислены в [описи владельцев, раздел 7](remaining-scheduler-owners.md#7-итоги-проверки-правки).

Первый относился к recovery. Успешная запись intent с последующим отказом autostart оставляла прежние `ActualIntentState` и `ActualIntentOwnerMode` в записи восстановления. Теперь результат самой записи передаётся в `strictModeSettlement.intentApplied`. Этот факт обновляет запись без повторного чтения или захвата блокировки. Обычная ошибка записи не утверждает применение. Причина отказа и ошибка сохранения записи выводятся в stderr, поскольку общий обработчик завершения с кодом 10 не печатает присоединённые причины.

Второй находился после legacy cleanup. Автоматический install мог сохранить Scheduler-задачу, затем остановить её процесс через отдельный путь удалённых supervisor-строк. Даже видимая выдача без совпадений оставляла скрытые регистрации, позднее появление и повторное использование PID/порта. Windows-обёртка install теперь отказывается от прямого принудительного останова независимо от этой выдачи. Supervisor продолжает самостоятельно обрабатывать reconcile через собственный механизм владения процессами. Отказ относится к прямой ветке install и не обещает, что supervisor не остановит своего ребёнка.

Третий найден независимым внутренним статическим чтением. При ошибке проекции сохранённого autorun OFF прежняя подсказка предлагала `mcphub autostart enable`. Эта команда записывает ON до своей попытки регистрации, поэтому следование совету меняло бы выбранную политику. Общая диагностика теперь предлагает `mcphub autostart status --details` и проверку сохранённой политики. Существующий тест дополнен проверкой этой подсказки и запретом совета `enable` для OFF. Его ветви ON также требуют ровно один вызов `Enable` и ни одного `Disable`. Эти последние изменения перепроверены чтением, но нативно не исполнены.

Проверка сообщений также обнаружила прежнюю подсказку `stop --force`, хотя текущий CLI не объявляет этот флаг. Новое Windows-предупреждение требует ручной проверки регистрации и процесса, не предлагает несуществующий флаг и не обещает исправление повторным install. Прежняя POSIX-подсказка остаётся отдельным вопросом документации интерфейса.

## 4. История неуспешных попыток

Исторические результаты не переименовываются после исправлений:

- `focused-v1`: подготовка API остановилась до тестов из-за недоступного `go-winio` в первоначальном локальном кэше. Следующий профиль использовал существующий файловый прокси.
- `focused-v2`: широкий селектор захватил прежнюю матрицу Stop. Go завершил пакет по пределу 120 с; исходная внешняя команда закрылась без принудительного завершения Job. Последующий scoped-набор не заменяет этот результат.
- `format-autostart-v1`: исходный процесс остановлен до возобновления по пределу подготовительного этапа. Читатели ещё не запускались. Следующий `autostart-v1` по ошибке выполнился на предшествующих исходниках; его PASS исключён из свидетельств новой правки.
- `autostart-v2`: тегированный CLI достиг 120-секундного предела Go в прежней матрице recovery; стек содержал `FlushFileBuffers`. Внешняя команда также достигла 240 с и завершила исходный Job. Процесс, Job и читатели получены закрытыми. Причина задержки файловой операции не установлена.
- `negative-v1`: контрольная подмена не содержала зависимых функций. Это ошибка компиляции до тестов, не отрицательный контроль поведения.
- `negative-v2`: две legacy-корневые проверки и четыре autostart-корневые проверки действительно упали на прежнем поведении; также упали 9 и 6 вложенных случаев соответственно. Контроллер сохранил FAIL из-за несовпадения ожидаемого текста `fingerprint omitted` с фактическим `runtime disabled state did not change the fingerprint`. Семантическое обнаружение прежних ошибок и исходный FAIL контроллера представлены раздельно.
- `api-final-v1`: первая новая группа прошла, соседняя остановилась на `SERENA_PREPARATION_ASSEMBLY_UNAVAILABLE`. Исправление её подготовки не переклассифицирует этот FAIL.
- `api-final-v2`: оригинальный Job закрыт, но stdout не присоединён в исходное окно завершения. Поздние поля EOF и закрытия не превращены в своевременный PASS. Последующие проверки не запускались; захваты, исходная рабочая копия и незавершённый родитель сохранены.

Контроль legacy возвращал старые cleanup/preview и четыре удалённых зависимых функции из `8d4f2606`, сохраняя остальные API-изменения промежуточного коммита. Autostart-контроль подменял только `windows.go` его исходной версией. Оба использовали fake операции. Старый `WeeklyRefreshSet`, который напрямую выбирал системный Scheduler, в отрицательный контроль не включался.

[Отдельный разбор координатора](retained-owner-coordinator-20261126.md) устанавливает отсутствие вызова уже существующего приёмщика позднего физического закрытия в живом A-контроллере. [Сохранённая база](run_wave_commands.py) и [патч будущего координатора](retained-owner-coordinator-20261126.patch) позволяют проверить предлагаемую правку. Применимость патча и синтаксис Python проверены статически; нативное исполнение — **NOT_RUN**. Правка не применялась к работающему процессу. Она не расширяет исходный срок квалификации и не допускает старые захваты после отказа.

## 5. Композиция и оставшиеся владельцы

[Матрица композиции](scheduler-source-composition-20261126.md) проверяет 71 кодовый путь прежнего #660, 22 пути этого продолжения и 13 тестовых файлов B. Test Source `001648f4` не содержит полную основу #660. В B уже перенесена часть #669, поэтому полная композиция требует проверки пересечений, а не простого наложения текущих 22 файлов.

Для самостоятельной композиции #660 + #669 удаляется только устаревшая строка прямого захвата recovery-блокировки из census. В B этой строки уже нет; там нужно сохранить его владельцев, перенести остаток #669 и добавить соответствующие классификаторы результата weekly refresh. Точный новый Product, дочерний Test Source и их квалификация ещё не выданы. Повторный install с существующей autostart-задачей сейчас сохраняет новый снимок при каждом отказе; дедупликация и очистка этих защитных снимков не реализованы.

[Опись оставшихся владельцев](remaining-scheduler-owners.md) сохраняет открытыми Ensure/Restore liveness, Product migration, регистрацию/перерегистрацию и runtime-запуск задачи по имени. Полные стандартный и тегированный API/CLI-наборы, текущий жизненный цикл Product, Unix/ARM64 и внешнее ревью точной вершины остаются открытыми. Результаты B и C не расширяют область этих проверок.

**Scheduler** — планировщик задач. **Поколение задачи** — конкретная регистрация, которую может сменить другая под тем же именем. **Intent** — сохранённая желаемая политика. **Reconcile** — приведение состояния supervisor к этой политике. **Dry-run** — предварительный просмотр без изменений. **PID** — числовой идентификатор процесса. **IPC** — взаимодействие процессов. **Job** — объект Windows, которому принадлежат контролируемые процессы. **SHA-256** — контрольная сумма байтов. **API/CLI** — программный интерфейс / интерфейс командной строки. **Default/tagged** — стандартный режим и режим с `test_state_path_env`.
