## Инвариант и сценарий

Проверяется следующее: настоящий backend создаёт отсутствующую liveness-задачу
из производственного XML; обратное чтение принимается реализованным
производственным сравнением; повторный вызов принимает то же определение без
повторного создания. Здесь XML — Extensible Markup Language, формат определения
задачи, который принимает и возвращает Планировщик.

Таблица 1. Входы и независимые источники ожидаемых значений.

| Вход | Источник |
| --- | --- |
| Имя Windows-задачи | Случайное собственное имя `\mcp-local-hub-qa-scheduler-liveness-<time>-<random>` |
| Команда действия | Абсолютный путь к отсутствующему `absent-mcphub.exe` в изолированной временной папке |
| Рабочая папка | Производственный `livenessWorkingDir(command)` |
| SID принципала | Производственный `livenessPrincipalSID()`; SID — Windows security identifier, идентификатор безопасности |
| Пользователь logon trigger | Производственный `defaultCurrentWindowsUser()` |
| Ожидаемое XML | Производственный `scheduler.BuildLivenessXML` внутри Ensure и matcher |

Адаптер принимает от производственного кода только `LivenessTaskName`, а в
Windows передаёт только отдельное QA-имя. XML передаётся без исправлений.
Операции `CreateXMLIfAbsent` и `ExportXML` разрешены в адаптере; остальные
операции через его незаполненный встроенный интерфейс приводят к ошибке теста,
не доходя до Windows. Глобальные фабрики и resolvers не заменяются.

Планируемая последовательность:

1. Первый Ensure: типизированное отсутствие, один настоящий
   `CreateXMLIfAbsent`, настоящий Export, результат `created-from-absent`.
2. Наблюдение ровно своей задачи в состоянии `Ready`.
3. Повторный Ensure: `unchanged`, общее число созданий один, XML первого и
   повторного readback совпадает побайтно.
4. Диагностика фактических Calendar StartBoundary/Enabled, повторения,
   дневного интервала, Logon Enabled и Settings Enabled.
5. Отдельная разрешённая очистка своего QA-имени с подтверждением
   `ErrTaskNotFound` и нулевых XML-байтов.

## Разрешение и очистка

Корневой `AGENTS.md`, раздел Scope and safety, требует точного разрешения на
изменения Scheduler. Сохранённая приёмка autostart проверяла другой writer,
`Create(TaskSpec)`, и не является разрешением на новую XML-регистрацию.

Для будущего запуска предлагаются две адресные команды — обычная и с
`test_state_path_env` — на Windows/amd64, последовательно, с `-count=1`,
`-parallel=1`, `-timeout 5m`, под существующим владельцем исходных процессов и
читателей. В каждом режиме создаётся не более одной отдельной QA-задачи.
TEMP/TMP и все тестовые файлы размещаются в разрешённой рабочей области.

Производственный XML содержит включённые Calendar и Logon triggers. Windows
может попытаться обработать триггер; его действие указывает на отсутствующий
файл. Тест не вызывает Run и не устанавливает исполняемый файл по этому пути.

После подтверждённого собственного Create cleanup повторно читает QA-имя.
При типизированном отсутствии ничего не удаляет. При ошибке, отсутствии первого
readback или изменившемся определении сохраняет задачу и завершает тест ошибкой.
При подтверждённом неизменившемся определении выполняет разрешённый QA Delete и
затем независимо проверяет отсутствие. Ошибка Create, включая неизвестный исход,
не включает удаление наблюдаемой регистрации.

Совпадение XML не доказывает владение поколением задачи и не устраняет окно
между Export и Delete. Разрешение на удаление здесь относится только к
собственному QA-имени; этот порядок не расширяет полномочия product rollback.

## Почему getter не заменяет этот сценарий

Наблюдение установленного liveness от 28 ноября подтвердило фактические
календарные значения и эффективный Enabled, но не вызывало полный matcher.
Сценарий выше проверяет другую границу: Windows CreateXMLIfAbsent, его реальный
readback и resolved Ensure с независимыми входами из таблицы 1.

Полный matcher установленной задачи нельзя честно принять, подставив ожидаемую
команду из её же XML. На этой голове `canonicalMcphubPath()` вызывает
`RuntimeMcphubExecutable()`: он выбирает образ аутентифицированного supervisor
с допуском роли Product и повторной проверкой owner либо собственный образ
вызывающего процесса при отсутствии supervisor. Отдельный Go test поэтому
сам по себе не задаёт установленный Product. Для такого read-only сравнения
нужен независимый подтверждённый Product-вход или подходящий runtime-контекст.
В этом этапе такое сравнение не выполнялось.

## Оставшаяся приёмка

Будущий PASS предлагаемого сценария будет относиться только к resolved
transaction на собственной QA-регистрации. Он не подтвердит публичный
`EnsureLivenessTask()` с установленным именем, Product identity, выполнение
`supervise --ensure-alive`, logon, внешнего писателя, все неизвестные XML-поля
или сквозной install/upgrade/cancel/recovery. Единственное наблюдение Ready не
доказывает выполнение действия или непрерывность этого состояния.

Прежние 464 адресных PASS Source52, отдельные setup/liveness и autostart
результаты сохраняют свои привязки. Подготовка нового opt-in не закрывает
полный блок A и не меняет статусы B/C/D. Обязательные полные команды репозитория
и внешнее ревью актуальной головы остаются отдельными критериями готовности.
