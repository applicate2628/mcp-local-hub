## 1. Обнаруженный дефект и исправление

Подставной Scheduler в предыдущем срезе не воспроизводил две особенности
настоящей выгрузки Task Scheduler. Поэтому успешно созданная задача в состоянии
`Ready` отклонялась при первом повторном `Enable`.

**Таблица 1. Фактические различия между writer и native export**

| Поле | Writer | Полученная выгрузка | Исправление сравнения |
| --- | --- | --- | --- |
| `Settings/UseUnifiedSchedulingEngine` | Поле отсутствует | `true` | При отсутствии явного требования writer принимается единственное простое boolean-значение. Явные expected `true` и `false` остаются значимыми. |
| `Triggers/LogonTrigger/UserId` | SID текущего пользователя | Полное имя `DOMAIN\name` того же пользователя | Допускаются только SID и полное имя из доверенного снимка `os/user.Current()`. |

SID — системный идентификатор учётной записи. XML — расширяемый язык разметки.
Документированное значение engine по умолчанию в схеме Microsoft остаётся
`false` [1]. Полученное `true` — наблюдение этой native-регистрации; оно не
объявляется новым общим значением по умолчанию Windows. Изменение относится
к сопоставлению наблюдения с требованиями writer и не переписывает задачу.

Сравнение направлено от observed к expected. Обратное сопоставление с явным
expected `true` не разрешает его отсутствие. Неизвестные поля, атрибуты,
дочерние элементы, чужие пространства имён и повторённые элементы сохраняют
значимость. Свойства действий, триггеров и runtime проверяются прежним путём.

Нормализация имени применяется только к `Principal/UserId` и
`LogonTrigger/UserId` наблюдаемого определения. Произвольного поиска учётной
записи из XML нет; совпадения короткого имени недостаточно. `OTHER\name`,
другой пользователь и другой SID дают отказ. `Current()` кеширует полученные
данные [2]; дополнительный вызов переиспользует тот же снимок пользователя,
который применяется существующим `currentWindowsTaskOwner`.

## 2. Полученные результаты

**Таблица 2. Кампании и точные границы результатов**

| Кампания | Получено | Итог |
| --- | --- | --- |
| Native v1, прежний matcher | Реальный Create, export и Ready; первый повторный Enable отказал | **FAIL / CLOSED** |
| Native v2, только диагностика | Тот же отказ; получена выгрузка, установлены оба различия из таблицы 1 | **FAIL / CLOSED** |
| v3, matcher default | 7 корневых тестов, 59 подтестов, 2 пакета PASS | **PASS** |
| v3, matcher `test_state_path_env` | 7 корневых тестов, 59 подтестов, 2 пакета PASS | **PASS** |
| v3, настоящий Task Scheduler | 1 корневой тест, 1 пакет PASS; пакет 4,259 с | **PASS** |
| Непересекающийся остаток Enable, default | 9 корневых тестов, 21 подтест, 1 пакет PASS | **PASS** |
| Тот же остаток Enable, `test_state_path_env` | 9 корневых тестов, 21 подтест, 1 пакет PASS | **PASS** |

В совокупности адресные unit-проверки дают по **16 корней и 80 подтестов PASS**
в каждом режиме, без FAIL/SKIP. Первый фильтр включал XML matcher и один
runtime-контракт Enable. Остальные девять корней приняты отдельным фильтром;
уже полученные корни не повторялись. Фильтры и терминальные результаты корней
сохранены в [машиночитаемом свидетельстве](autostart-native-roundtrip-20261126.json).

Native-тест создаёт случайно именованную задачу с существующим QA-префиксом.
Её команда указывает на заведомо отсутствующий файл внутри временной папки
теста. Тест не запрашивает запуск приложения. Он проверяет:

1. Единственный успешный Create, непустой настоящий export и состояние Ready.
2. Два успешных повторных Enable, каждый с настоящими export и Status.
3. Один Create за весь сценарий, отсутствие Delete внутри Enable и побайтовое
   равенство определения до и после повторных включений.
4. Удаление точного QA-имени после успешного собственного Create и независимое
   типизированное подтверждение отсутствия.

Тот же cleanup выполнился без ошибок в v1 и v2. Неопределённый эффект Create
не предоставляет cleanup-права: при таком отказе фикстура сохраняет имя в
диагностике и не предпринимает автоматическое удаление.

## 3. Исходники и завершение исполнения

Нативная рабочая копия имеет Git HEAD `b14cdeba95b2a69815d1677ee3f0dc236e8f1c79`
с прежними девятью проверенными autostart-путями `c0b0cc22` и текущей правкой.
Поэтому её HEAD не выдаётся за новый кодовый коммит. Перед каждым исполнением
закреплены **десять точных файлов**; их SHA-256 совпадают с опубликованными
кодовыми байтами. Четыре изменённых файла получены после native gofmt.
Это адресное соответствие входов, а не утверждение о полной композиции Source.

**Таблица 3. Получение исходных ресурсов**

| Кампания | Команды / readers | Внешний контроллер | Интервал контроллера |
| --- | --- | --- | --- |
| v1 | 3 / 6, CLOSED | exit 1, получен, файлы закрыты | 8,4766 с |
| v2 | 3 / 6, CLOSED | exit 1, получен, файлы закрыты | 10,1519 с |
| v3 | 6 / 12, CLOSED | exit 0, получен, файлы закрыты | 49,7956 с |
| Остаток unit | 3 / 6, CLOSED | exit 0, получен, файлы закрыты | 4,9415 с |

Все **15 исходных команд и 30 потоков чтения** завершены: получен direct exit,
исходное дерево пусто, native handles закрыты, исходные readers присоединены.
Сроки работы и получения завершения приведены по каждой команде в JSON.
Смена результата v1/v2 на PASS не выполнялась.

Полученные stdout проверены по SHA-256 сырых байтов до разбора JSON-событий.
Квитанции пересекли текстовый транспорт CRLF → LF; преобразование LF → CRLF
только в памяти воспроизводит native-хеш, закреплённый исходным родителем.
Обе формы хешей помечены в JSON. Private XML, пути профиля, PID и имя учётной
записи в публикацию не включены. Зафиксированы хеш и размер успешного export.

## 4. Границы свидетельства

Получен именно Create/export/Ready/repeat-Enable/cleanup для закреплённых
исходников. Running и Queued покрыты подставными тестами; фактический logon,
запуск Product, install/upgrade/cancel/recovery, одновременный писатель и
неопределённый эффект native Create этим сценарием не квалифицированы.

Равенство определения не подтверждает владение поколением регистрации.
Явные OFF/удаление и отказ от автоматической замены сохраняют свои контракты.
Полные build/vet/default/tagged на новой общей композиции и внешнее ревью
её точных коммитов остаются открытыми. Прежние A `api-final-v2` и B full11
не затрагивались и не получили новой классификации.

Общий остаточный маршрут ведётся в [плане #664](https://github.com/applicate2628/mcp-local-hub/pull/664).
Точный рецепт состава — [scheduler-source-composition-20261126.md](scheduler-source-composition-20261126.md).
