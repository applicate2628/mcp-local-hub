# v0.5.0 mcp-local-hub supervisor architecture

**Status:** Accepted spec, v5 (revised after CLI deep-sec review rounds
1–3 + subagent review round 4 — total 9× P0 + 44× P1 + 11× P2 surfaced
across v1/v2/v3/v4 drafts). v5 incorporates Round 4 subagent findings:
PID/port resolution via `lookupProcess` (no pidport JSON), `taskkill /T`
tree-kill, `pre-os-mutating` marker AFTER first kill (resume safety),
fixed-cadence maintenance timers (no cron dep), package ownership
clarification, per-resource ACE mask separation, reconcile-prune
identity, `idle | manual_restart` transition, Windows rename-aside
upgrade, `principal.user_id` removed (no `CreateProcessAsUser`
infrastructure), XML deviation-only classification, 60s rollback
port wait with explicit exit semantic, strict-mode atomic mutation
command, transient-child tracking on graceful exit, IPC handshake
expected-PID source, distinguished migration-ready budget, cold-start
TIME_WAIT settling, rollback IPC-exit-before-lock, maintenance timer
single-run guard, LIFO lock release.

**Date:** 2026-05-16

**Goal:** Replace the N-scheduled-tasks-per-daemon architecture of
v0.4.x with one `mcphub supervise` long-lived parent process that
owns every MCP daemon as a child process under an OS-appropriate
lifecycle primitive (Windows Job Object — strong containment; Linux
`PR_SET_PDEATHSIG` direct-child or systemd-user-service with
control-group kill — beta; macOS process group + kqueue observation
or LaunchAgent-owned restart — preview).

**Motivation:**

- **Process tail compression** — operator sees one `mcphub.exe` plus
  N children instead of N scheduler-managed orphans on crash.
- **Atomic upgrade story** — old supervisor exits, new supervisor
  reconciles, ~10s blip via MCP client retry semantics.
- **Removes the v0.4.x corrupt-state self-quarantine machinery** —
  no more 5-min watchdog poll cadence; child-exit observation is
  immediate.
- **Cross-platform foundation** — by removing Windows-specific Task
  Scheduler dependency, mcphub becomes a CLI tool that runs from
  any shell. The supervisor binary IS the lifecycle primitive;
  autostart-at-logon is a separate, optional, OS-specific shim
  (Q8). On Linux/macOS the strong-containment story optionally
  couples lifecycle to the init system (Q2 managed-mode); the
  default beta/preview is a weaker direct-child guarantee.

| Q5 | Upgrade handoff | **Defer hot-upgrade. `mcphub install --upgrade` writes new binary via rename-aside, signals current supervisor for graceful exit via control IPC (Q11), waits ack with 5s timeout, falls back to force-kill on timeout. | Q6 | Migration v0.4.x → v0.5.0 | **Two-phase journaled migration with lock ordering plus PID/port daemon stop using `lookupProcess` plus tree-kill plus deviation-only XML classification plus IntentReason TTL preservation plus maintenance-timer carryover plus strict-mode atomic mutation plus quarantine→intent translation on rollback plus restart-on-rollback for restored daemons.** See "Migration journal (detail)" below. Locks always released LIFO. | Removes every v3/v4 fabricated artifact (no `/shutdown` HTTP, no pidport JSON). Aligns kill semantics with production `internal/api/install.go:2159-2188` which uses `/T` precisely because hub.exe spawns npx/uvx grandchildren. Marker-after-kill closes the resume race where v4 had marker-then-kill and resume couldn't distinguish "marked but unkilled" from "marked and killed". |
| Q7 | Supervisor invocation | **`mcphub supervise` is just a CLI subcommand.** Anyone on PATH can run it from any shell; no install / scheduler / privileges required (default modes). The optional managed modes (`--linux-managed` / `--darwin-managed`) couple supervisor lifecycle to the init system, in which case the operator should NOT invoke `mcphub supervise` from a shell — it runs via systemd-user or LaunchAgent. | Removes the v0.4.x "lifecycle = scheduler entry" mental model; aligns with `supervisord` / `pm2` / `s6` semantics. |

The `mcphub strict-mode {enable, disable}` command is the explicit mutation path; it rewrites intent + shim atomically under the same lock contract as `mcphub install`. ## State file architecture (detail)

### managed-entries.json (existing — preserved)

- Owner: `internal/api/managed_entries.go`.
- Root shape: `{"version": int, "entries": [...]}`.
- Entry shape: `{"client": string, "server": string, "installed_at": RFC3339}`.
- v0.5.0: read-only from supervisor's perspective.

### daemon-intent.json (existing — preserved exactly)

- Owner: `internal/api/daemon_intent.go`.
- Actual root shape: `{"tasks": map[string]DaemonIntent}` only (per `daemon_intent.go:231-233`). No top-level `version`. No top-level `updated_at`. `DisallowUnknownFields()` at line 577 rejects extra top-level fields → reader quarantines as corrupt.
- Per-entry `DaemonIntent` shape: `{"desired", "reason", "updated_at"}` per `daemon_intent.go:219-223`.
- Keys: canonical leading-backslash per `canonicalIntentTaskKey` at `daemon_intent.go:275-283`. Example: `\mcp-local-hub-memory-default`.
- `desired`: `running` / `stopped`.
- `reason`: `user-stop` (TTL'd via `IsActiveStop(now)` at `daemon_intent.go:289-324`), `user-disabled` (permanent), `chronic-failure` (auto-set by recovery, `recovery.go:294-298`).
- v0.5.0 supervisor reads this file unchanged via existing `ReadDaemonIntent`. No schema changes — byte-symmetric for rollback.

### supervisor-intent.json (NEW)

- Owner: `internal/api/supervisor_intent.go`.
- Schema version 1:

  ```json
  {
    "version": 1,
    "updated_at": "RFC3339Nano",
    "daemons": [
      {
        "task_name": "\\mcp-local-hub-memory-default",
        "server": "memory",
        "daemon": "default",
        "command": "node",
        "args": ["./mcp-memory-server.js"],
        "env": { "MEMORY_PATH": "..." },
        "workspace": "C:\\Users\\...\\repo",
        "port": 9128,
        "manifest_hash": "sha256:..."
      }
    ],
    "maintenance_timers": [
      {
        "name": "\\mcp-local-hub-workspace-weekly-refresh",
        "kind": "workspace-weekly-refresh",
        "command": "mcphub.exe",
        "args": ["workspace-weekly-refresh"]
      },
      {
        "name": "\\mcp-local-hub-memory-weekly-refresh",
        "kind": "server-weekly-refresh",
        "server": "memory",
        "command": "mcphub.exe",
        "args": ["restart", "--server", "memory"]
      }
    ],
    "strict_mode": false
  }
  ```

- `task_name` keys to v0.4.x `daemon-intent.json` semantics (canonical leading-backslash). Supervisor reconcile checks `daemon_intent.Tasks[task_name].IsActiveStop(now)`.
- **No `principal` field, no `settings.priority`.** v4's `principal.user_id` + `settings.priority` carry was unimplementable: supervisor is a non-elevated user process; `CreateProcessAsUser` requires a primary token from `LogonUser` (needs password) or `LogonUserExEx` (S4U — needs `SeTcbPrivilege` and domain trust); the existing codebase has zero `CreateProcessAsUser` / `SetPriorityClass` / `setpriority` references. Non-current-user `<UserId>` in legacy XML is classified as Unsupported by the migration (operator must `--discard-scheduler-customizations` or remove the custom RunAs manually). Priority customization is silently dropped on migration with a warning (default process priority on Windows is `NORMAL_PRIORITY_CLASS` which is what spawned child processes inherit; the legacy `<Priority>7</Priority>` Task Scheduler setting maps to `NORMAL_PRIORITY_CLASS` anyway, so the "drop" is a no-op on default values).
- **Fixed-cadence maintenance timers — no cron parser.** v4 referenced `github.com/robfig/cron/v3` claiming transitive dependency; verified false (zero `robfig`/`cron` in `go.mod` + `go.sum`). v5 commits to TWO fixed cadences matching v0.4.x semantics: `workspace-weekly-refresh` and `server-weekly-refresh`, both fire Sunday 03:00 local time (per `internal/api/weekly_refresh.go:31-35`). Supervisor schedules them via a domain-specific weekly-trigger evaluator (~30 lines, no external dep). If future timers need different cadences, add a new `kind` enum value and a new in-tree evaluator — do NOT introduce a generic cron parser.
- `strict_mode`: canonical truth. Mutated only via `mcphub strict-mode {enable, disable}` (see Q8).
- Write: atomic via the shared state-file helper. Read: supervisor on start + reload.

### supervisor-state.json (NEW)

- Owner: `internal/api/supervisor_state.go`.
- Schema version 1:

  ```json
  {
    "version": 1,
    "daemons": {
      "\\mcp-local-hub-memory-default": {
        "state": "running",
        "current_pid": 12345,
        "pid_generation": 7,
        "started_at": "RFC3339Nano",
        "restart_history": [
          {"at": "RFC3339Nano", "exit_code": 1, "signal": null}
        ],
        "backoff_until": "RFC3339Nano",
        "quarantine_since": "RFC3339Nano"
      }
    },
    "transient_pids": [
      {"pid": 23456, "kind": "workspace-weekly-refresh", "started_at": "RFC3339Nano"}
    ]
  }
  ```

- `daemons[*]`: Hybrid C state machine persistence (Q4). Resume across crashes.
- `pid_generation`: monotonic counter incremented on every spawn. Stale `child_exit` events with old PIDs are dropped.
- `backoff_until`: absolute UTC RFC3339Nano so supervisor restart re-arms the timer at the same wall-clock moment.
- `transient_pids[*]`: tracks maintenance-timer fire-and-forget children that are NOT Job Object members. On supervisor graceful exit (IPC `exit{graceful: true}`), supervisor sends a 5-second-grace SIGTERM-equivalent to each transient PID then force-kills surviving ones via `taskkill /F /T`. On crash, Windows Job Object only kills Job Object members; transient children survive crash → cold-start reaper sweeps them on next supervisor start (matches the daemon cold-start reaper pattern).
- Write: every state transition flushed BEFORE the side effect.
- Read: supervisor on start.

### supervisor-events.log (NEW)

- Owner: `internal/api/supervisor_events.go`. Pattern mirrors `internal/api/watchdog_log.go:25-36` and `internal/api/gui_event_log.go:19-25`.
- Schema version 1 (every entry):

  ```json
  {
    "schema": 1,
    "ts": "RFC3339Nano",
    "severity": "debug|info|warn|error",
    "source": "ipc|lifecycle|restart-policy|migration|autostart|reconcile",
    "event": "...",
    "task_name": "\\mcp-local-hub-...",
    "fields": { "..." }
  }
  ```

- `severity`: `info` = normal; `warn` = recoverable; `error` = unrecoverable per-daemon; `debug` = high-volume operational detail (env-gated).
- Per-entry size cap matches watchdog_log: 16 KB hard cap; identity fields never truncated; non-identity oversize triggers longest-non-identity-field truncation with `_truncated:true`.
- 10 MB rotation with single `.log.1`; rotation event `event: "log-rotated"` written to new file.
- Flock-protected appends for concurrent IPC / reconcile / restart-policy / migration writers.

### watchdog-state.json (existing — preserved unchanged)

- Owner: `internal/api/watchdog_state.go`. Fields per `watchdog_state.go:276-281` with DisallowUnknownFields.
- v0.5.0 supervisor does NOT extend or write this file (not even read-only — DisallowUnknownFields would reject on a v0.5.0-extended file). The standalone `mcphub watchdog status` subcommand continues to read it as a diagnostic surface.

## Migration journal (detail)

Subsection elaborating Q6.

### Journal layout

```text
<state-dir>/migration-journal-<UTC-timestamp>/
  prepared                       # marker, empty (touch)
  pre-os-mutating                # marker, AFTER first successful kill
  os-mutating-complete           # marker, AFTER all task unregisters
  committed                      # marker, AFTER supervisor verified reconcile-ready
  legacy-tasks/
    mcp-local-hub-memory-default.xml
    mcp-local-hub-time-default.xml
    mcp-local-hub-watchdog.xml
    mcp-local-hub-workspace-weekly-refresh.xml
    mcp-local-hub-memory-weekly-refresh.xml
    ...
  legacy-tasks-classification.json   # per-task: supported/unsupported XML attrs + destination
  canonical-template-snapshot.xml    # v0.4.x install template rendered for diff baseline
  pre-migration-strict-mode          # text: "1" or "0"
  derived-supervisor-intent.json     # exact bytes of new supervisor-intent.json
  killed-daemons.json                # PIDs the migration stopped (resolved at kill time)
```

### Lock ordering

Migration acquires BOTH locks in this exact order:

1. `<state-dir>/migration.lock` (flock, exclusive). New v0.5.0 lock.
2. `<state-dir>/--once.lock` (flock, exclusive). Existing v0.4.x lock per `internal/cli/watchdog.go:498-529`.

All install / uninstall / register / watchdog install / setup auto-install paths in v0.5.0 honor `migration.lock` (newly added) plus `--once.lock` or fail closed. **Locks are always released LIFO**: `--once.lock` first, then `migration.lock`. Deferred close in install / rollback / resume / error handlers makes this automatic.

### XML deviation-only classification

v4 listed only a small set of "preserved" fields and classified everything else Unsupported — which on real v0.4.x hosts triggers Unsupported for every legacy task because the v0.4.x install template renders ~15 default fields (battery policy, ExecutionTimeLimit, AllowHardTerminate, MultipleInstancesPolicy, AllowStartOnDemand, Enabled, StartWhenAvailable, etc., all visible in `scheduler_windows.go:106-153`).

v5 classifier compares each XML field against the canonical v0.4.x install template rendered for the same task identity (`canonical-template-snapshot.xml`, written to journal at step 4 below). Fields that MATCH the template default are silently preserved-by-default (re-rendered by v5 install if needed). Only DEVIATIONS are classified, into three buckets:

**Deviation preserved through supervisor + autostart shim:**

- `Settings.RunOnlyIfNetworkAvailable` (only when operator flipped from default `false`) → supervisor delays spawn until network reachability check passes (5s poll loop).
- `Settings.Priority` deviation from default `7` → silently dropped on migration with one warning line per affected task (no `SetPriorityClass` infrastructure in v0.5.0; default `NORMAL_PRIORITY_CLASS` of child process inherit covers the `7` case, which is `NORMAL` already).

**Deviation preserved through autostart shim only (not per-daemon):**

- Trigger types other than LogonTrigger on the supervisor's own shim. Per-daemon non-LogonTrigger triggers other than the weekly-refresh maintenance pattern are classified Unsupported.

**Deviation that aborts migration (unless `--discard-scheduler-customizations`):**

- `Principal.UserId` not equal to the current Windows user (non-current-user RunAs requires `CreateProcessAsUser` infrastructure that v0.5.0 does not have).
- `Principal.LogonType` other than `InteractiveToken` (same reason).
- Custom `<Actions>` other than the v0.4.x canonical single `<Exec>` shape.
- `IdleSettings` deviations, `WakeToRun=true`, `RunOnlyIfIdle=true`.

If any task lands in the abort bucket, migration aborts and prints the per-task classification table. Operator can either remove the customization manually and retry, or pass `mcphub install --discard-scheduler-customizations`.

### Pre-unregister daemon stop (lookupProcess + tree-kill)

The v3 spec called `/shutdown` over HTTP (route doesn't exist). The v4 spec called a pidport sidecar JSON (no such file in v0.4.x). v5 uses the verified production pattern from `internal/api/install.go:1846-1879`:

1. For each legacy `mcp-local-hub-*` daemon task (NOT including weekly-refresh / watchdog tasks — those have no live daemon to stop), parse the `<Exec>` argv to get the daemon's `--server` and `--daemon` names.
2. Resolve the expected port via `portForTask(normalized, manifestPortMap(""), workspaceTasksByName())` — same lookup the production `stopKillCore` uses.
3. Resolve the listening PID via `lookupProcess(port)` (`internal/api/processes.go:283-309`, shells `netstat -ano` + `wmic` for PID + creation date). If `lookupProcess` returns `ok=false`, the port is not bound — no daemon to stop; skip to step 7.
4. Ownership gate (3 conditions, all must pass before killing):
   - Process image basename = `mcphub.exe` (Windows) or `mcphub` (POSIX).
   - Process argv contains `daemon --server <server> --daemon <daemon>`.
   - Process creation date precedes the `migration.lock` acquisition time (so we don't kill an unrelated mcphub spawned by a parallel install attempt that beat us to PID assignment).
5. If gate passes, append `{pid, server, daemon, start_time, port}` to `killed-daemons.json`.
6. **`taskkill /PID <pid> /F /T`** (Windows — `/T` is critical because hub.exe spawns npx/uvx which spawn node/python grandchildren; without `/T` the grandchildren survive and keep ports bound; see `internal/api/install.go:2163-2166`). POSIX: send `SIGTERM` to the process group (`kill -- -<pgid>`) then `SIGKILL` after 5s grace; using the process group ensures forked descendants die too. The `mcphub daemon` parent is responsible for putting itself + children in one process group via `setsid` at start time.
7. Wait up to 10 seconds for the port to release via repeated `lookupProcess(port)` polling.
8. If port still bound after 10s, abort migration with the exact port + PID + retry guidance.
9. **`touch pre-os-mutating`** — AFTER first successful kill, not before. Resume rule below depends on this ordering.

### Resume / partial-state recovery

Journal markers in causal order: `prepared` → `pre-os-mutating` → `os-mutating-complete` → `committed`.

- **Journal at `prepared` only:** no daemon was killed and no task was unregistered → safe to abort and delete journal directory.
- **Journal at `pre-os-mutating` but no `os-mutating-complete`:** at least one daemon was killed. **Forward-resume MUST** enumerate ALL `mcp-local-hub-*` tasks via `EnumerateAllMcphubTasks` and probe each task's port via `lookupProcess` independent of `killed-daemons.json` membership (the kill list captures only what THIS migration attempt killed; an earlier crashed attempt may have killed others). Tasks whose ports are NOT bound resume from step 7; tasks whose ports ARE bound get the pre-unregister stop applied. Then continue from "stop and unregister each legacy task". Rollback path: re-register from XML snapshots, run restored tasks, verify ports (rollback step 9 below).
- **Journal at `os-mutating-complete` but no `committed`:** legacy tasks unregistered, supervisor maybe not running. Operator picks forward retry (`mcphub install`) or rollback (`mcphub install --rollback-to-legacy`); resume cannot decide silently.

### Forward migration steps

1. Acquire `migration.lock` (flock; refuse if held).
2. Acquire `--once.lock` (flock; refuse if held — a v0.4.x `watchdog --once` is running; wait or abort).
3. Enumerate ALL `mcp-local-hub-*` scheduler tasks via NEW `EnumerateAllMcphubTasks()` helper. The current `scheduler.List()` at `internal/scheduler/scheduler_windows.go:341-356` filters to the current Windows user; migration must look at every task in `schtasks /Query /XML`.
4. **Render the v0.4.x canonical install template** for the same identity to `canonical-template-snapshot.xml` (so deviation-only classification has a baseline for diff).
5. Export each task's raw XML to `legacy-tasks/<task>.xml`.
6. Classify XML deviations per the table above. Abort if any deviation lands in the "abort" bucket and `--discard-scheduler-customizations` was not passed.
7. Derive `supervisor-intent.json` from manifest YAML + workspace bindings + snapshotted task argv + deviation-preserved fields + maintenance_timers + `strict_mode` (read from `pre-migration-strict-mode`).
8. `touch prepared`.
9. Pre-unregister daemon stop: kill each live daemon per the section above. Each successful kill appends to `killed-daemons.json` BEFORE the marker write. **`touch pre-os-mutating` AFTER the first successful kill** (not before). For the corner case where there are no daemons to kill (all ports unbound), `touch pre-os-mutating` happens immediately before step 10.
10. Stop and unregister each legacy task via `schtasks /Delete`.
11. `touch os-mutating-complete`.
12. Install supervisor autostart shim (per Q8 — explicit per-OS backend; `--strict-mode` CLI arg if applicable).
13. **Explicitly start supervisor** per the cold-restart upgrade flow below.
14. Wait for supervisor to confirm **reconcile-ready** via IPC `status` query within 30s. Reconcile-ready means: IPC listener accepting connections AND supervisor has read both `supervisor-intent.json` + `daemon-intent.json` AND the first reconcile pass has been scheduled (NOT that all daemons are healthy — per-daemon health is observable post-commit via `mcphub status`, which has its own retry budget). On timeout: roll back automatically (run the rollback path below) with reason `forward-migration-supervisor-not-ready`.
15. `touch committed`.
16. Release `--once.lock` (LIFO).
17. Release `migration.lock` (LIFO).

### Rollback steps (`mcphub install --rollback-to-legacy`)

1. Acquire `migration.lock`.
2. **Stop supervisor BEFORE acquiring `--once.lock`** — send IPC `exit{graceful: true, timeout_ms: 5000}` immediately, with `--once.lock` not yet held. This prevents the supervisor's reconcile loop from respawning daemons into about-to-be-restored legacy task identities. Fall back to force-kill (look up PID from `supervisor.lock`).
3. Acquire `--once.lock`.
4. Find the latest `migration-journal-*/` directory with `committed` marker (or `pre-os-mutating` for partial rollback).
5. Read current `supervisor-state.json`. For each entry in `quarantined` state, write a corresponding `daemon-intent.json` entry with `reason=chronic-failure, desired=stopped` via existing `WriteDaemonIntent` (canonicalizes the key).
6. Uninstall supervisor autostart shim.
7. For each `legacy-tasks/<task>.xml`: re-register via `schtasks /Create /XML /F` (the `/F` overwrites if a same-named task somehow already exists; safer than the v4 plain `/Create`).
8. **Run each restored daemon task** via `schtasks /Run /TN <task>`.
9. **Verify ports bind. Wait up to 60s** per task (was 10s in v4; 60s matches npx cold-start budget on AV-instrumented Windows hosts — sequential-thinking, paper-search, wolfram all routinely 15-30s cold). For each task whose port is NOT bound after 60s, append `{task, port, reason}` to `rollback-warnings.json`. **Rollback exits 0 (success-with-warnings) even with warnings present**; the operator inspects the warnings file and decides whether to retry per-task `schtasks /Run`. Non-zero exit is reserved for "rollback itself failed" (e.g., XML re-register error, journal corrupted).
10. Delete `supervisor-intent.json` + `supervisor-state.json` + `supervisor-events.log`.
11. Release `--once.lock` (LIFO).
12. Release `migration.lock` (LIFO).

## Fresh install flow (detail)

The "no v0.4.x state to migrate, no prior supervisor" case. `mcphub install` on a clean machine writes intent and EXPLICITLY starts the supervisor; the autostart shim is opt-in and never the canonical first-start trigger.

### When this applies

- No `<state-dir>` exists, OR
- `<state-dir>` exists but contains no `mcp-local-hub-*` Task Scheduler tasks, no `supervisor-intent.json`, and no migration journal directories.

### Fresh install sequence

1. Acquire `<state-dir>/migration.lock` (flock; refuse if held). Even a fresh install acquires this lock so a concurrent second install cannot race autostart shim setup + supervisor start.
2. Acquire `<state-dir>/--once.lock` only if a v0.4.x watchdog task exists on disk (defensive).
3. Write `supervisor-intent.json` from manifest YAML + workspace bindings + (optional) operator-passed `--strict-mode`.
4. (Optional) If `--autostart` flag passed, install the autostart shim per Q8.
5. **Explicitly start supervisor.** Same per-OS commands as the cold-restart upgrade flow step 6 below, but with no prior supervisor to exit. Errors here cleanup the autostart shim (if installed in step 4), leave `supervisor-intent.json` on disk for retry, release locks LIFO, exit non-zero with the failed syscall + retry command.
6. Wait for supervisor reconcile-ready via IPC `status` within 30s (reconcile-ready, NOT all-daemons-healthy; same distinction as migration step 14).
7. Release `--once.lock` (LIFO) if acquired.
8. Release `migration.lock` (LIFO).

### `--no-start` contract

`mcphub install --no-start` writes intent and optionally installs the autostart shim but does NOT start supervisor. Intended for CI / fleet-provisioning. Prints a reminder line ending with the exact command the operator must run. Default for fresh install is `--start` (implicit).

## Cold-restart upgrade flow (detail)

`mcphub install --upgrade` is the explicit restart trigger across all OSes (autostart shim is a LogonTrigger, not an exit-trigger).

### Windows binary replacement (rename-aside)

`MoveFileEx REPLACE_EXISTING` over a running .exe can return `ERROR_ACCESS_DENIED` because the loader holds the image with `FILE_SHARE_DELETE` only (no `FILE_SHARE_WRITE`). The Chocolatey / Squirrel / auto-updater idiom is rename-aside:

1. Write new binary to `<install-dir>/mcphub.exe.new`.
2. `MoveFileExW(target, target + ".old-<ts>", REPLACE_EXISTING)` — rename the running binary out of the way (Windows allows rename of an executing image because the loader uses `FILE_SHARE_DELETE`).
3. `MoveFileExW(target + ".new", target, 0)` — atomic rename of new binary into place.
4. Schedule cleanup of `target.old-<ts>` for the next upgrade or supervisor restart (Windows can't delete a still-mapped image; the old binary stays on disk until the running process exits).

POSIX path is simpler: atomic `rename(2)` over the existing binary works because `unlink(2)` decrements the inode link count and the kernel keeps the inode alive until all references close.

### Upgrade sequence

1. Replace binary atomically (rename-aside on Windows; `rename(2)` on POSIX).
2. Connect to supervisor IPC pipe / socket via Q11 trust boundary. Client reads `supervisor.lock` for expected `{pid, start_time}` FIRST.
3. Send `exit{graceful: true, timeout_ms: 5000}`.
4. Supervisor stops accepting new IPC requests, sends 5-second-grace termination to transient maintenance-timer children (tracked in `supervisor-state.transient_pids`), then gracefully terminates daemon children (Windows: terminate Job Object members — kill descends; POSIX default: SIGTERM children, SIGKILL after grace).
5. Supervisor exits with code 0.
6. **`mcphub install` explicitly starts the new supervisor.** Per-OS:
   - Windows: if autostart shim is installed, run `schtasks /Run /TN \mcp-local-hub-supervisor`. Otherwise launch `mcphub.exe supervise [--strict-mode]` as a detached child via `CreateProcess` with `DETACHED_PROCESS | CREATE_NEW_PROCESS_GROUP`.
   - Linux managed: `systemctl --user restart mcphub-supervisor.service`.
   - Linux unmanaged: `mcphub supervise [--strict-mode] &` (detached).
   - macOS managed: `launchctl kickstart -k gui/<uid>/com.applicate2628.mcphub-supervisor`.
   - macOS unmanaged: `mcphub supervise [--strict-mode] &` (detached).
7. New supervisor starts → reads intent + daemon-intent → reconcile → respawns daemons.
8. Operator sees ~10s blip in MCP clients via existing retry semantics.

### Fallback if step 3 IPC fails

- Force-kill the prior supervisor PID (look up `supervisor.lock` for `{pid, start_time}`; terminate via `taskkill /F /T /PID` if PID alive with matching start_time).
- Run cold-start stale-child reaper (Linux/macOS default modes only; Windows Job Object already killed). Reaper waits 2-3 seconds after each kill to let TCP TIME_WAIT settle before the new supervisor's first reconcile spawn attempts to bind the same ports.
- Proceed to step 6.

## Restart policy state machine (detail)

Supervisor runs a **single-threaded FIFO event loop**: events from IPC, child_exit, timers, and intent-file watchers all serialize through one channel. The transition table is sufficient — no concurrent-event tie-breakers needed.

### States

- `idle` — entry exists in intent but not yet spawned.
- `spawning` — supervisor issued OS create-process; child not yet confirmed running.
- `running` — child PID alive + first health check OK.
- `exiting` — graceful or forced termination in progress.
- `backoff-waiting` — child exited recently; backoff timer armed.
- `quarantined` — failure count exceeded the 30-min window budget; auto-restart disabled.

### Events

- `child_exit{pid, exit_code, signal}` — OS-level child termination.
- `timer_due{kind}` — backoff timer fired.
- `intent_update{task_name, new_intent}` — `supervisor-intent.json` or `daemon-intent.json` updated.
- `manual_restart{task_name}` — IPC `restart` command from operator.
- `supervisor_restart` — supervisor process is starting.

### Transition table

`failures` = count of `child_exit` events in trailing 30-min sliding window per `(task_name)`. `gen_match` = `child_exit.pid` matches `supervisor-state.daemons[task_name].current_pid`.

| From | Event | Guard | To | Side effect | Persist when |
| --- | --- | --- | --- | --- | --- |
| idle | (start) | intent.desired=running AND NOT IsActiveStop(now) | spawning | bump pid_generation, OS create-process | BEFORE create-process |
| idle | intent_update | new.desired=stopped | idle | none | n/a |
| idle | intent_update | new.desired=running (TTL refreshed) | spawning | bump pid_generation, OS create-process | BEFORE create-process |
| idle | manual_restart | intent.desired=running AND NOT IsActiveStop(now) | spawning | bump pid_generation, OS create-process | BEFORE create-process |
| idle | manual_restart | intent.desired=stopped OR IsActiveStop(now) | idle | reject IPC with `RESTART_REFUSED_INTENT_STOPPED` | n/a |
| spawning | (health check OK) | first probe success | running | none | AFTER probe OK |
| spawning | child_exit | gen_match | backoff-waiting | arm timer at backoff(failures) | BEFORE timer arm |
| spawning | child_exit | NOT gen_match | spawning | drop event (stale PID) | n/a (log only) |
| running | child_exit | gen_match | backoff-waiting | arm timer | BEFORE timer arm |
| running | child_exit | NOT gen_match | running | drop event (stale PID) | n/a (log only) |
| running | intent_update | new.desired=stopped | exiting | issue terminate | BEFORE terminate |
| running | manual_restart | always | exiting | issue terminate, queue spawn | BEFORE terminate |
| exiting | child_exit | always | depends on queued action | spawn or idle | per next state |
| backoff-waiting | timer_due | failures < 10 | spawning | bump pid_generation, OS create-process | BEFORE create-process |
| backoff-waiting | timer_due | failures >= 10 | quarantined | clear timer | BEFORE clear |
| backoff-waiting | intent_update | new.desired=stopped | idle | cancel timer | BEFORE cancel |
| backoff-waiting | intent_update | new.desired=running (TTL refreshed) | spawning | cancel timer, bump pid_generation, OS create-process | BEFORE create-process |
| backoff-waiting | manual_restart | always | spawning | cancel timer, bump pid_generation, OS create-process | BEFORE create-process |
| quarantined | intent_update | new.desired=stopped | idle | none | n/a |
| quarantined | intent_update | new.desired=running (TTL refreshed) | spawning | reset failures, bump pid_generation, OS create-process | BEFORE create-process |
| quarantined | manual_restart | always | spawning | reset failures, bump pid_generation, OS create-process | BEFORE create-process |
| (any) | supervisor_restart | persisted state=quarantined | quarantined | none | done via load |
| (any) | supervisor_restart | persisted backoff_until > now AND failures < 10 | backoff-waiting | re-arm timer at absolute backoff_until | done via load |
| (any) | supervisor_restart | persisted backoff_until <= now AND intent.desired=running AND NOT IsActiveStop(now) | spawning | bump pid_generation, OS create-process | BEFORE create-process |
| (any) | supervisor_restart | persisted intent.desired=stopped | idle | none | done via load |

Backoff schedule: 0s, 0s, 0s (immediate first 3 retries) then 5s, 15s, 60s, 5min, 30min capped.

## Maintenance timer scheduler (detail)

Supervisor schedules `supervisor-intent.maintenance_timers` entries via an in-process fixed-cadence evaluator. Two cadence kinds in v0.5.0:

- `workspace-weekly-refresh`: Sunday 03:00 local time. Fires `mcphub.exe workspace-weekly-refresh`.
- `server-weekly-refresh`: Sunday 03:00 local time. Fires `mcphub.exe restart --server <server>`.

No cron parser. If future cadences are needed, add a new `kind` enum value with its own in-tree evaluator.

### Single-run guard

Per-timer in-process mutex prevents overlap: if a timer fires while the previous fire's transient child is still running, the new fire is skipped with one warning line. Operator can also tighten by setting a per-timer `max_duration` (deferred to plan phase if needed).

### Transient child tracking

Every timer fire spawns a child detached from the supervisor's Job Object (so a slow `mcphub restart` doesn't block supervisor exit). The PID is recorded in `supervisor-state.transient_pids` at spawn time (BEFORE the syscall, so resume sees it). On supervisor graceful exit (IPC `exit{graceful: true}`):

1. Supervisor sends termination to each transient PID (Windows: `taskkill /F /T /PID`; POSIX: SIGTERM to process group, then SIGKILL after 5s).
2. Supervisor waits up to 5s for transient PIDs to disappear.
3. Supervisor exits.

On supervisor crash, transient children outside Job Object survive. Cold-start reaper on next supervisor start checks each `transient_pids` entry: if the PID is still alive AND owned by the operator (same 3-gate ownership check as migration), kill it; in any case remove the entry from `transient_pids` (clean slate).

### Concurrent IPC during reconcile / timer fire

The FIFO event loop (Q4) serializes everything. An IPC `manual_restart{server: memory}` arriving while a `server-weekly-refresh` for `memory` is running is queued behind the timer's spawn child (which the event loop already returned from). The `manual_restart` then runs against the now-restarted daemon — operator sees consistent ordering.

## Control IPC trust boundary (detail)

### Wire format

Newline-delimited JSON, one object per line.

Request:

```json
{"id": 42, "cmd": "status"}
{"id": 43, "cmd": "exit", "args": {"graceful": true, "timeout_ms": 5000}}
{"id": 44, "cmd": "restart", "args": {"server": "memory", "daemon": "default"}}
{"id": 45, "cmd": "reload"}
```

Response:

```json
{"id": 42, "ok": true, "result": { "daemons": [] }}
{"id": 43, "ok": true, "result": "exit-acked"}
{"id": 43, "error": {"code": "TIMEOUT", "message": "exit took >5s; forced kill"}}
{"id": 44, "error": {"code": "RESTART_REFUSED_INTENT_STOPPED", "message": "..."}}
```

### Handshake

**Before opening the connection**, the client reads `<state-dir>/supervisor.lock` for `{expected_pid, expected_start_time}`. This is the canonical pre-read source of "which supervisor should I be talking to". Then:

1. Client opens the pipe / socket.
2. Supervisor immediately sends a `hello` frame:

   ```json
   {"hello": {"version": 1, "pid": 12345, "started_at": "RFC3339Nano"}}
   ```

3. Client validates `pid + started_at` against the pre-read expectation. Mismatch → connection closed with reason `stale-supervisor-instance`.
4. Only after validation does the client send commands.

### Trust boundary

- Windows: pipe DACL constructed via the **shared SECURITY_DESCRIPTOR builder** extracted from `internal/api/secure_write_windows.go:498-535`. The SD-builder is shared; the per-resource ACE access mask is set by the call site:
  - File ACE: `GENERIC_ALL` (matches existing `SecureWriteClientConfig` behavior).
  - Named pipe ACE: `GENERIC_READ | GENERIC_WRITE` (NOT `GENERIC_ALL` — granting take-ownership rights on a command pipe is over-broad).
- POSIX: unix socket mode 0600 + owner-uid match.
- Allowlist SIDs: current-user SID + LocalSystem + BuiltinAdministrators (matches existing).
- No token. The OS-level access control is the boundary.

### Audit

Every command write-through to `supervisor-events.log` (JSONL) as `source: "ipc"`:

```json
{"schema": 1, "ts": "...", "severity": "info", "source": "ipc",
 "event": "ipc-command", "fields": {"cmd": "exit", "args": {},
 "caller": {"pid": 99}, "result": "ok"}}
```

## Open plan-phase questions

- **Reconcile trigger on each OS.** Linux inotify can be invalidated by atomic rename and queues can overflow; Windows `ReadDirectoryChangesW` behaves similarly; macOS kqueue EVFILT_VNODE is fd-based. Plan phase: parent-dir watch + re-arm + overflow → full-rescan + IPC reload as authoritative + periodic 60s poll for safety.
- **Autostart `status` richer enum.** Per-backend probe semantics for `absent` / `enabled-running` / `enabled-stopped` / `drifted` / `stale-residue`.
- **`supervisor.lock` stale-PID detection.** Lock file carries `{pid, start_time}`; if PID is not running OR matches a different start_time, the lock is stale.
- **Concurrent `mcphub status` query fan-out.** Plan picks: per-connection goroutine reading a snapshot of in-memory child registry, OR serialized.
- **Linux non-systemd host fallback.** On Alpine/musl without systemd-user, `--linux-managed` is unavailable; default `PR_SET_PDEATHSIG` is the only option.
- **macOS containment posture.** No kernel containment primitive equivalent to Job Object / cgroup is available; both default and managed modes are observation + restart. v0.6 reevaluates.
- **Swappable-var idiom for new supervisor state.** Plan decides whether the new supervisor read/write functions need the test-time redirection that `clients.WriteConfigFile` ↔ `api.SecureWriteClientConfig` uses.
- **Per-timer max_duration**. If overlap is observed in practice for any maintenance kind, plan phase adds a per-timer `max_duration` field that triggers force-kill of the previous fire.

## Terms and Abbreviations

- `canonical task name`: leading-backslash form of a Task Scheduler task name (e.g. `\mcp-local-hub-memory-default`), per `internal/api/daemon_intent.go:275-283`.
- `canonical template snapshot`: per-migration artifact `canonical-template-snapshot.xml` rendered for the same task identity as the v0.4.x install template emits; used as the diff baseline for XML deviation-only classification.
- `cgroup scope`: Linux systemd transient unit type. NOT a kill-on-parent-exit primitive — scope outlives any one process.
- `cold-start reaper`: supervisor's startup procedure on Linux/macOS default modes that scans PID files + ports for orphaned daemons from a prior crash and kills them before the new spawn loop runs.
- `daemon-intent.json`: existing v0.4.x state file. Top-level shape is `{tasks: ...}` only. Preserved verbatim by v0.5.0.
- `deviation-only classification`: v5 migration classifier compares each Task Scheduler XML field against the v0.4.x canonical install template; matching values are silently preserved, only deviations are routed to "preserved through supervisor", "preserved through shim", or "abort" buckets.
- `direct-child containment` (Linux default): supervisor's `PR_SET_PDEATHSIG`-only mode. Double-fork descendants escape; the cold-start reaper sweeps them.
- `EnumerateAllMcphubTasks`: new helper in `internal/scheduler` that lists every `mcp-local-hub-*` Task Scheduler task regardless of Run As — closes the v0.4.x `List()` current-user filter gap.
- `FIFO event loop`: supervisor's single-threaded event channel that serializes child_exit, timer_due, intent_update, manual_restart, and supervisor_restart events. Removes the need for concurrent-event tie-breakers in the state machine.
- `IntentReason TTL`: per `IsActiveStop(now)`, the time-window during which a `user-stop` reason suppresses reconcile spawn.
- `IPC`: inter-process communication; in this spec, supervisor's control surface via Windows named pipe / POSIX unix socket.
- `Job Object`: Windows kernel primitive grouping processes for shared lifecycle, resource limits, and termination control.
- `JSON line protocol`: newline-delimited JSON; IPC wire format and supervisor-events.log format.
- `KILL_ON_JOB_CLOSE`: Job Object flag that kills all member processes when the last open handle to the job is closed.
- `killed-daemons.json`: migration journal artifact recording every PID the migration stopped, populated AT KILL TIME from runtime `lookupProcess` resolution (NOT from a pidport sidecar — no such file exists in v0.4.x).
- `kqueue`: BSD/macOS kernel event-notification facility. Observation only, NOT containment.
- `LaunchAgent`: macOS plist-defined background job. `KeepAlive` provides restart-after-exit semantics, NOT cgroup-style descendant containment.
- `lookupProcess(port)`: production v0.4.x PID resolver at `internal/api/processes.go:283-309`. Shells `netstat -ano` then `wmic` to resolve PID + creation date for a TCP loopback port. v5 migration uses this in place of v4's fabricated pidport file.
- `maintenance_timers`: section of supervisor-intent.json carrying weekly-refresh schedules from v0.4.x. v5 commits to two fixed cadences (workspace + per-server) firing Sunday 03:00 local; no cron parser.
- `managed-entries.json`: existing v0.4.x state file recording `(client, server)` ownership. Root shape: `{version, entries}`.
- `managed mode` (Linux/macOS optional): supervisor's init-system-owned mode. Linux: systemd-user-service with `KillMode=control-group` (strong containment). macOS: LaunchAgent (restart-after-exit only — NOT containment).
- `MCP`: Model Context Protocol.
- `mcphub.exe supervise`: new subcommand introduced in v0.5.0 that runs as the long-lived parent process. Lives in `internal/cli/supervise.go`.
- `mcphub strict-mode {enable, disable}`: NEW v0.5.0 command. Canonical mutation path for `supervisor-intent.strict_mode`. Atomically rewrites supervisor-intent.json AND the autostart shim's CLI args under the same lock contract as `mcphub install`.
- `migration.lock`: NEW exclusive flock at `<state-dir>/migration.lock` serializing v0.5.0 install / uninstall / migration runs.
- `migration journal`: per-install directory holding raw scheduler-task XML snapshots + state markers + classification + derived intent + strict-mode marker + killed-daemons list + canonical-template-snapshot.
- `--once.lock`: existing v0.4.x watchdog exclusive flock at `<state-dir>/--once.lock`. v0.5.0 migration acquires this lock too.
- `PID generation`: monotonic counter incremented on every spawn; guards against stale `child_exit` events.
- `PR_SET_PDEATHSIG`: Linux prctl option. Per-process and cleared on fork.
- `pre-os-mutating`: migration journal marker written AFTER the first successful daemon kill (v5 ordering correction — v4 placed it BEFORE, which created a resume-corruption window where the marker existed but no kills had landed yet).
- `quarantine`: terminal state after exceeding the Hybrid C restart-failure budget. On rollback, translated to `daemon-intent.json` `chronic-failure` so legacy watchdog respects it.
- `reconcile loop`: supervisor's core algorithm — diff intent against running children and bring them into alignment.
- `reconcile-prune identity`: the key used to diff `Plan.SupervisorIntent` entries against existing supervisor children during install reconcile — canonical task_name (leading-backslash form), identical to daemon-intent.json keying.
- `rename-aside`: Windows binary replacement pattern. `MoveFileExW` to a side path first (with `REPLACE_EXISTING`), then `MoveFileExW` of the new binary into place. Proven by Chocolatey / Squirrel; avoids `ERROR_ACCESS_DENIED` from `REPLACE_EXISTING` over a running .exe.
- `rollback-warnings.json`: rollback journal artifact listing tasks whose ports did not bind within the 60s budget. Rollback exits 0 (success-with-warnings) regardless; operator inspects the file and retries `schtasks /Run` per task as needed.
- `state-file helper`: NEW shared utility under `internal/api` combining flock + atomic temp+rename + `SecureWriteClientConfig` used by all new supervisor-* state files.
- `strict mode`: operator opt-in via `MCPHUB_REQUIRE_SINGLE_USER_HOME=1` historically, or `--strict-mode` CLI arg, or supervisor-intent.json field. v5 makes `supervisor-intent.strict_mode` the canonical source-of-truth; `--strict-mode` CLI is a transport that the supervisor reconciles into intent on start.
- `supervisor-events.log`: NEW JSONL audit log. Schema version, severity, source, flock, 10 MB rotation, 16 KB per-entry cap with identity-field protection.
- `supervisor-intent.json`: NEW state file holding full daemon descriptors keyed by canonical task name + maintenance_timers + strict_mode bool. Supervisor reconcile source-of-truth.
- `supervisor-state.json`: NEW state file holding Hybrid C state machine state + transient_pids for maintenance-timer fire-and-forget children.
- `systemd-user`: per-user systemd instance; manages user units like `mcphub-supervisor.service`.
- `Task Scheduler`: Windows service. v0.4.x used N entries; v0.5.0 uses one entry (autostart shim for supervisor).
- `transient_pids`: array in supervisor-state.json tracking maintenance-timer fire-and-forget children that are NOT Job Object members. Used by graceful exit (terminate transients before exiting) and cold-start reaper (sweep crash-orphaned transients).
- `tree-kill`: `taskkill /F /T /PID <pid>` — `/T` kills the process tree, critical because hub.exe spawns npx/uvx which spawn node/python grandchildren that survive a non-tree kill and keep ports bound. Verified at `internal/api/install.go:2163-2174`.
- `watchdog-state.json`: existing v0.4.x state file. Preserved unchanged in v0.5.0 for rollback byte-compatibility.
