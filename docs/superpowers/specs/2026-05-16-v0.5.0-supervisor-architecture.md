# v0.5.0 mcp-local-hub supervisor architecture

**Status:** Accepted spec, v4 (revised after CLI deep-sec review rounds
1–3 — total 6× P0 + 34× P1 + 5× P2 surfaced across v1/v2/v3 drafts).
v4 incorporates Round 3 findings: daemon-intent.json byte-shape and
canonical-key correction, maintenance-timer ownership, fresh-install
lifecycle owner, explicit per-OS cold-restart trigger, strict-mode
persistence via CLI arg (Task Scheduler XML has no env support),
macOS containment honesty, full restart-policy transition table,
cross-lock ordering between migration and watchdog `--once`, custom
XML attribute destination fields, pre-unregister daemon stop via
PID/port (no nonexistent `/shutdown` HTTP), pre-os-mutating journal
marker, rollback that actually restarts restored daemons, and
`supervisor-events.log` ownership with schema/severity/rotation.

**Date:** 2026-05-16

**Goal:** Replace the N-scheduled-tasks-per-daemon architecture of
v0.4.x with one `mcphub supervise` long-lived parent process that
owns every MCP daemon as a child process under an OS-appropriate
lifecycle primitive (Windows Job Object — strong containment; Linux
`PR_SET_PDEATHSIG` direct-child or systemd-user-service with
control-group kill — beta; macOS process group + kqueue observation
or LaunchAgent-owned restart — preview).

**Motivation:**

- **Process tail compression** — operator sees one `mcphub.exe` plus
  N children instead of N scheduler-managed orphans on crash.
- **Atomic upgrade story** — old supervisor exits, new supervisor
  reconciles, ~10s blip via MCP client retry semantics.
- **Removes the v0.4.x corrupt-state self-quarantine machinery** —
  no more 5-min watchdog poll cadence; child-exit observation is
  immediate.
- **Cross-platform foundation** — by removing Windows-specific Task
  Scheduler dependency, mcphub becomes a CLI tool that runs from
  any shell. The supervisor binary IS the lifecycle primitive;
  autostart-at-logon is a separate, optional, OS-specific shim
  (Q8). On Linux/macOS the strong-containment story optionally
  couples lifecycle to the init system (Q2 managed-mode); the
  default beta/preview is a weaker direct-child guarantee.

## Brainstorm decisions

out of these decisions and is resolvable during plan phase without
re-opening the decision is listed in "Open plan-phase questions".

| ID | Topic | Decision | Rationale (short) |
| --- | --- | --- | --- |
| Q1 | Lifecycle owner | **One** long-lived `mcphub supervise` process per user, OS-agnostic Go binary. Replaces v0.4.x's N-per-daemon Task Scheduler entries. The Task Scheduler entry that remains is the autostart shim for Windows (Q8), not the lifecycle primitive. | Single recovery point; one log channel; OS-portable from day one. |
| Q2 | Process lifecycle binding | **OS-appropriate kill-on-parent-exit with explicit per-OS strength.** Windows = Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` plus `PROC_THREAD_ATTRIBUTE_JOB_LIST` (assign at create-time — closes the start-then-assign race at `internal/process/jobobject_windows.go:65-71`); strong-containment GA. Linux default = `PR_SET_PDEATHSIG` direct-child containment, with double-fork/setsid daemons documented OUT OF SCOPE (beta); optional `--linux-managed` registers supervisor as a systemd user service with `KillMode=control-group` for strong containment. macOS default = process group plus kqueue `EVFILT_PROC NOTE_EXIT` for death observation plus cold-start orphan reaper (preview — observation and restart, NOT crash-safe containment); optional `--darwin-managed` registers supervisor as a LaunchAgent so launchd owns restart (still observation plus best-effort process-group cleanup of escapees, NOT cgroup-equivalent containment). Linux default mode is honest beta: `PR_SET_PDEATHSIG` is per-process and cleared on fork per man7 prctl(2). macOS even in managed mode is preview honesty: no kernel containment primitive equivalent to Job Object or cgroup is available — kqueue NOTE_EXIT is exit notification only, LaunchAgent `KeepAlive` is restart-after-exit not descendant containment. Cold-start reaping handles the residual "supervisor crashed and left orphans" case without requiring strong containment. |
| Q3 | Supervisor intent source | **New `supervisor-intent.json` state file** with versioned schema carrying full daemon descriptors keyed by canonical task name (the canonical leading-backslash form per `internal/api/daemon_intent.go:275-283`, e.g. `\mcp-local-hub-memory-default`). Written by `mcphub install` from manifest YAML plus workspace bindings; read by supervisor on start plus reload. The canonical task-name key matches `daemon-intent.json` keying 1:1, so user-stop / chronic-failure / user-disabled state correlates without re-keying. `managed-entries.json` stays as the existing client-server ownership index. | v1 draft's "reconcile from managed-entries.json" was wrong: that file records `(client, server, installed_at)` only. v2's per-(server, daemon) keying for daemon-intent was wrong: the file is keyed by canonical task name. v3 used bare task names; v4 corrects to leading-backslash form, which is the canonical storage shape. |
| Q4 | Restart policy on child crash | **Hybrid C with persisted state machine.** States: `idle`, `spawning`, `running`, `exiting`, `backoff-waiting`, `quarantined`. Events: `child_exit`, `timer_due`, `intent_update`, `manual_restart`, `supervisor_restart`. First 3 attempts: immediate restart. Then exponential backoff 5s / 15s / 60s / 5min / 30min. After 10 failures in a 30-min sliding window: `quarantined` — supervisor refuses further auto-restart until an `intent_update` or `manual_restart` event clears it. All state transitions persisted to NEW `supervisor-state.json` BEFORE side effect (spawn / terminate / arm timer) so supervisor crash mid-backoff resumes correctly. PID generation counter on every spawn so stale `child_exit` events from old PIDs are dropped via guard check. **Full transition table in "Restart policy state machine (detail)" section below** — no longer deferred. | Reuses the sliding-window primitive *idea* from `internal/api/watchdog_state.go:159-162` but writes to a separate file (`supervisor-state.json`) so v0.4.x rollback doesn't hit `DisallowUnknownFields` corruption. Hybrid C splits cleanly into transient port-collision recovery (fast) and deterministic-fail crash-loop containment (slow). |
| Q5 | Upgrade handoff | **Defer hot-upgrade. `mcphub install --upgrade` writes new binary, signals current supervisor for graceful exit via control IPC (Q11), waits ack with 5s timeout, falls back to force-kill on timeout. Old supervisor exits and children die per Q2 containment, then `mcphub install` itself EXPLICITLY starts the new supervisor.** The autostart shim (Q8) is a logon trigger, not a supervisor-exit trigger — on Windows `LogonTrigger` only fires at user logon, never on supervisor exit. So `mcphub install` is responsible for the cold start across all per-OS paths (detailed in "Cold-restart upgrade flow (detail)" below). | Named handle handoff (Windows Job Object cross-process inheritance; POSIX detached pgrp re-parenting) is fragile and contradicts kill-on-parent-exit as the safety invariant. v3 said "autostart shim cold-starts new supervisor", but Windows `LogonTrigger` does not fire on supervisor exit; that mechanism only fires on user logon. v4 makes the install CLI the explicit restart trigger across all OSes, with per-OS commands. |
| Q6 | Migration v0.4.x → v0.5.0 | **Two-phase journaled migration with cross-lock ordering plus pre-unregister PID/port daemon stop plus XML-customization classification with destination fields plus IntentReason TTL preservation plus global watchdog plus maintenance-timer carryover plus strict-mode persistence via CLI arg plus quarantine→intent translation on rollback plus restart-on-rollback for restored daemons.** See "Migration journal (detail)" below for the full step list. Briefly: acquire `migration.lock` and the v0.4.x `--once.lock` together (so concurrent `mcphub watchdog --once` cannot mutate state); classify each legacy scheduler task's raw XML; map preserved customizations (`Principal.UserId`, `LogonType`, `RunLevel`, `Priority`, `RunOnlyIfNetworkAvailable`) into supervisor-intent destination fields; snapshot every legacy `mcp-local-hub-*` task XML including global watchdog and per-server + workspace weekly-refresh; pre-unregister daemon stop by PID/port + ownership check (NO `/shutdown` HTTP — route does not exist in v0.4.x); journal `pre-os-mutating` marker BEFORE first kill (so partial-crash resume knows OS state was touched); derive supervisor-intent.json keyed by canonical task name; carry v0.4.x daemon-intent.json over without rewriting (supervisor reads it via existing `ReadDaemonIntent`); persist strict-mode into supervisor-intent.json AND into the autostart shim's CLI args (Task Scheduler XML has no env support); stop and unregister legacy tasks; start supervisor explicitly via per-OS command; verify reconcile; commit. **Rollback** translates quarantined supervisor entries to daemon-intent.json chronic-failure, restores raw XML, RUNS the restored daemon tasks (not just registers them), and verifies their ports. | Lossless rollback requires the raw-XML journal — operator-customized tasks cannot be reconstructed from manifest defaults alone. Cross-lock ordering prevents `watchdog --once` (scheduled every 5 min on v0.4.x) from racing the unregister phase. PID/port handoff is necessary because `schtasks /End` does not kill the spawned daemon (per `internal/api/install.go:1816-1820` evidence), the `/shutdown` HTTP route in v3 does not exist in v0.4.x daemons, and without explicit kill plus port-release-wait, live daemons keep ports bound while the new supervisor records backoff/quarantine. Pre-os-mutating marker keeps resume correct after a crash between the first kill and `os-mutating-complete`. Rollback-runs-tasks ensures services restore immediately, not at next logon. |
| Q7 | Supervisor invocation | **`mcphub supervise` is just a CLI subcommand.** Anyone on PATH can run it from any shell; no install / scheduler / privileges required (in default Linux/macOS mode and on Windows). The binary IS the lifecycle primitive. Idempotent: refuses to start if another supervisor instance holds `<state-dir>/supervisor.lock`. The optional managed modes (`--linux-managed` / `--darwin-managed`) couple supervisor lifecycle to the init system, in which case the operator should NOT invoke `mcphub supervise` from a shell — it runs via systemd-user or LaunchAgent. | Removes the v0.4.x "lifecycle = scheduler entry" mental model; aligns with `supervisord` / `pm2` / `s6` semantics. The lock file prevents multi-supervisor concurrency (would create duplicate children). |
| Q8 | Autostart-at-logon | **Three independent per-OS backend contracts under one CLI surface: `mcphub autostart {enable, disable, status}`.** Windows backend: Task Scheduler logon-trigger task (reuses `internal/scheduler/scheduler_windows.go` primitives, but registers ONE task). Strict-mode persists as `<Arguments>--strict-mode</Arguments>` because Task Scheduler `execType` schema does NOT define `<Environment><Variable>` (per `scheduler_windows.go:106-153` evidence — only Command, Arguments, WorkingDirectory). Linux backend: systemd user unit (`~/.config/systemd/user/mcphub-supervisor.service`); strict-mode persists as `ExecStart=mcphub supervise --strict-mode`; `--linux-managed` elevates to `KillMode=control-group`. macOS backend: LaunchAgent plist (`~/Library/LaunchAgents/com.applicate2628.mcphub-supervisor.plist`); strict-mode persists in `ProgramArguments` array; `--darwin-managed` ties supervisor lifecycle to launchd (restart-after-exit only, not cgroup containment). Status output is a per-backend richer enum (deferred to plan phase): `absent`, `enabled-running`, `enabled-stopped`, `drifted`, `stale-residue`. **Strict-mode persistence channel is the CLI arg, NOT env. Supervisor parses `--strict-mode` first, then `supervisor-intent.json.strict_mode`, then env as last resort.** | v3 promised `<Environment><Variable>` in Task Scheduler XML; Microsoft `execType` schema does NOT define env tags, and `schtasks /Create /XML` rejects them. CLI arg works across all three backends without per-OS divergence. Richer status enum is needed because a boolean cannot distinguish healthy vs absent vs stale-pointing-at-old-binary. |
| Q9 | v0.5.0 OS release scope | **Windows GA + Linux beta + macOS preview**, with each platform's containment guarantee explicitly documented. Windows: production gate (Job Object strong containment, existing test infrastructure). Linux: behind `mcphub install --linux-beta` flag; default mode = `PR_SET_PDEATHSIG` direct-child containment, double-fork/setsid daemons OUT OF SCOPE; optional `--linux-managed` upgrades to systemd-user-service strong containment; cold-start reaper covers supervisor-crash residue. macOS: build-only preview (Go cross-compile, no automated tests); default mode = process group + kqueue observation + cold-start reaper; optional `--darwin-managed` upgrades to LaunchAgent-owned restart-after-exit (still observation, NOT containment). v0.5.x stabilizes Linux to GA + adds macOS CI lane; v0.6 promotes macOS to GA only if a real containment primitive becomes available. | Avoids over-committing on OSes the test infrastructure doesn't yet cover. Macros is explicit about the residual containment gap rather than overpromising. |
| Q10 | State file architecture | **Five files under `<state-dir>`** with distinct ownership and rollback compatibility. v4 schemas (corrected from v3 to match the actual v0.4.x on-disk shapes): managed-entries.json = `{"version": int, "entries": [{client, server, installed_at}]}` per `internal/api/managed_entries.go:21-29`; daemon-intent.json = `{"tasks": {<canonical leading-backslash key>: {"desired", "reason", "updated_at"}}}` per `internal/api/daemon_intent.go:231-233` — **TOP-LEVEL HAS ONLY `tasks`. ## State file architecture (detail)

Subsection elaborating Q10 for plan phase. Schemas reflect the
ACTUAL on-disk shapes verified against the v0.4.x codebase.

### managed-entries.json (existing — preserved)

- Owner: `internal/api/managed_entries.go`.
- Actual root shape: `{"version": int, "entries": [...]}`.
- Entry shape: `{"client": string, "server": string, "installed_at": RFC3339}`.
- Purpose: client-server ownership index for safe demigration.
- v0.5.0: read-only from supervisor's perspective. `mcphub install`
  continues to maintain it unchanged.

### daemon-intent.json (existing — preserved exactly)

- Owner: `internal/api/daemon_intent.go`.
- **Actual root shape: `{"tasks": map[string]DaemonIntent}` only.**
  Confirmed at `internal/api/daemon_intent.go:231-233`:

  ```go
  type DaemonIntentFile struct {
      Tasks map[string]DaemonIntent `json:"tasks"`
  }
  ```

  No top-level `version`. No top-level `updated_at`. The
  `DisallowUnknownFields()` parser at line 577 rejects any file
  with extra top-level fields → reader quarantines as corrupt.
  v0.4.x rollback compatibility depends on this exact shape.
- Per-entry `DaemonIntent` shape: `{"desired", "reason", "updated_at"}`
  per `daemon_intent.go:219-223`. `updated_at` is PER TASK, not
  top-level.
- Keys: canonical leading-backslash task names per
  `canonicalIntentTaskKey` at `daemon_intent.go:275-283`. Example:
  `\mcp-local-hub-memory-default`. Writers normalize through this
  helper; readers index by the canonical form. Bare-name lookups
  (without leading backslash) silently miss → that was the v3 bug.
- `desired` values: `running` / `stopped` per `daemon_intent.go:80-123`.
- `reason` values: `user-stop` (TTL'd per `IsActiveStop(now)` at
  `daemon_intent.go:289-324`), `user-disabled` (permanent),
  `chronic-failure` (auto-set by recovery, `recovery.go:294-298`).
- Purpose: quarantine + user-disabled intent. Honored by supervisor
  reconcile to suppress spawn for daemons whose intent
  `IsActiveStop(now)` evaluates to true.
- v0.5.0 supervisor reads this file unchanged via the existing
  `ReadDaemonIntent` API. **No schema changes** so v0.4.x → v0.5.0 →
  rollback is byte-symmetric.

### supervisor-intent.json (NEW)

- Owner: `internal/api/supervisor_intent.go` (new file).
- Schema version 1:

  ```json
  {
    "version": 1,
    "updated_at": "RFC3339Nano",
    "daemons": [
      {
        "task_name": "\\mcp-local-hub-memory-default",
        "server": "memory",
        "daemon": "default",
        "command": "node",
        "args": ["./mcp-memory-server.js"],
        "env": { "MEMORY_PATH": "..." },
        "workspace": "C:\\Users\\...\\repo",
        "port": 9128,
        "manifest_hash": "sha256:...",
        "principal": {
          "user_id": "DESKTOP-XYZ\\Dmitry",
          "logon_type": "InteractiveToken",
          "run_level": "LeastPrivilege"
        },
        "settings": {
          "priority": 7,
          "run_only_if_network_available": false
        }
      }
    ],
    "maintenance_timers": [
      {
        "name": "\\mcp-local-hub-workspace-weekly-refresh",
        "kind": "workspace-weekly-refresh",
        "cron": "0 0 3 * * 0",
        "command": "mcphub.exe",
        "args": ["workspace-weekly-refresh"]
      },
      {
        "name": "\\mcp-local-hub-memory-weekly-refresh",
        "kind": "server-weekly-refresh",
        "server": "memory",
        "cron": "0 0 3 * * 0",
        "command": "mcphub.exe",
        "args": ["restart", "--server", "memory"]
      }
    ],
    "strict_mode": false
  }
  ```

- `task_name` keys the entry to v0.4.x `daemon-intent.json`
  semantics (canonical leading-backslash form). Supervisor
  reconcile checks `daemon_intent.Tasks[task_name].IsActiveStop(now)`.
- `principal.user_id` / `logon_type` / `run_level` carry the
  preserved Task Scheduler XML customizations from migration (see
  "XML customization classification" below). The supervisor honors
  them by spawning under matching credentials (Windows: `CreateProcessAsUser`
  with the operator's token; Linux: setuid/setgid; macOS: `posix_spawn`
  with attributes). Non-current-user `user_id` is permitted on
  Windows but requires elevation — `mcphub install` surfaces this
  as an explicit warning.
- `settings.priority` carries to child process creation flags
  (Windows: `CREATE_NEW_PROCESS_GROUP` plus `SetPriorityClass`;
  POSIX: `setpriority`).
- `settings.run_only_if_network_available`: supervisor delays spawn
  until network reachability check passes (poll loop at 5s).
- `maintenance_timers` carries the per-server weekly-refresh and
  shared workspace-weekly-refresh tasks that v0.4.x ran via
  scheduler. Supervisor's reconcile loop schedules these via
  in-process timer (`time.Ticker` + cron parser); on fire, supervisor
  invokes the recorded command + args as a transient child (NOT
  managed by Job Object — fire-and-forget). Fires in operator's
  local time zone (matches v0.4.x scheduler "Weekly Sun 03:00 local").
- `strict_mode` persists the strict-mode posture so a supervisor
  spawned by autostart inherits the operator's choice even when
  `MCPHUB_REQUIRE_SINGLE_USER_HOME` is not in the shim's environment.
  The autostart shim ALSO passes `--strict-mode` on the CLI (see Q8);
  CLI arg takes precedence over file when both are present.
- Write: atomic via the shared state-file helper (flock plus
  temp-then-rename plus `SecureWriteClientConfig`) from `mcphub install`.
- Read: supervisor on start + on reload signal.

### supervisor-state.json (NEW)

- Owner: `internal/api/supervisor_state.go` (new file).
- Schema version 1:

  ```json
  {
    "version": 1,
    "daemons": {
      "\\mcp-local-hub-memory-default": {
        "state": "running",
        "current_pid": 12345,
        "pid_generation": 7,
        "started_at": "RFC3339Nano",
        "restart_history": [
          {"at": "RFC3339Nano", "exit_code": 1, "signal": null}
        ],
        "backoff_until": "RFC3339Nano",
        "quarantine_since": "RFC3339Nano"
      }
    }
  }
  ```

- Purpose: Hybrid C state machine persistence (Q4). Resume across
  supervisor crashes.
- `pid_generation` increments on every spawn; child-exit events
  carry the PID that exited, supervisor matches against current
  PID + generation, drops stale events.
- `backoff_until` is absolute UTC RFC3339Nano so supervisor restart
  re-arms the timer at the same wall-clock moment regardless of
  uptime.
- Write: every state transition flushed BEFORE the side effect (per
  Q4 "persist when" column in the transition table below).
- Read: supervisor on start (resume mid-backoff correctly).

### supervisor-events.log (NEW)

- Owner: `internal/api/supervisor_events.go` (new file). Owner
  pattern mirrors `internal/api/watchdog_log.go:25-36` (JSONL,
  per-entry size cap, oversize-truncation policy) and
  `internal/api/gui_event_log.go:19-25` (severity enum, source
  enum, atomic append).
- Schema version 1 (every entry):

  ```json
  {
    "schema": 1,
    "ts": "RFC3339Nano",
    "severity": "debug|info|warn|error",
    "source": "ipc|lifecycle|restart-policy|migration|autostart|reconcile",
    "event": "ipc-command|child-spawn|child-exit|state-transition|migration-step|autostart-action|...",
    "task_name": "\\mcp-local-hub-...",
    "fields": { "..." }
  }
  ```

- `severity` semantics: `info` = normal lifecycle; `warn` =
  recoverable anomaly (backoff arming, stale event dropped);
  `error` = unrecoverable per-daemon (quarantine entered, intent
  parse failure); `debug` = high-volume operational detail (gated
  by env or flag).
- Per-entry size cap matches the watchdog_log policy: 16 KB hard
  cap; identity fields (`task_name`, `event`, `source`) are NEVER
  truncated; non-identity oversize triggers longest-non-identity
  field truncation with `_truncated:true` marker.
- 10 MB rotation with single `.log.1` retention. Rotation event
  written to new file as `event: "log-rotated"` for forensics.
- Flock-protected appends to handle concurrent IPC + reconcile +
  restart-policy + migration writers.
- Caller-pluggable: a future `mcphub supervisor events --tail`
  CLI can stream this file via the same logging helper that powers
  `internal/api/watchdog_log.go`.

### watchdog-state.json (existing — preserved unchanged)

- Owner: `internal/api/watchdog_state.go`.
- Actual fields: `cooldowns`, `last_wall_clock_seen`, three strike
  windows per `watchdog_state.go:276-281` with DisallowUnknownFields.
- v0.5.0 supervisor does NOT extend or write this file.
- Preserved for `--rollback-to-legacy` byte-compatibility.
- The standalone `mcphub watchdog status` subcommand
  (`internal/cli/watchdog.go`) continues to read this file as a
  diagnostic surface.

### Journal layout

```text
<state-dir>/migration-journal-<UTC-timestamp>/
  prepared                       # marker, empty (touch)
  pre-os-mutating                # marker, written BEFORE first kill
  os-mutating-complete           # marker, written after task unregister
  committed                      # marker, written after supervisor verified
  legacy-tasks/
    mcp-local-hub-memory-default.xml
    mcp-local-hub-time-default.xml
    mcp-local-hub-watchdog.xml
    mcp-local-hub-workspace-weekly-refresh.xml
    mcp-local-hub-memory-weekly-refresh.xml
    ...
  legacy-tasks-classification.json   # per-task: supported/unsupported XML attrs + destination
  pre-migration-strict-mode          # text: "1" or "0"
  derived-supervisor-intent.json     # exact bytes of new supervisor-intent.json
  killed-daemons.json                # PIDs the migration stopped
```

### Lock ordering

Migration acquires BOTH locks in this exact order to prevent
concurrent v0.4.x `watchdog --once` mutations and concurrent
installs:

1. `<state-dir>/migration.lock` (flock, exclusive). New v0.5.0 lock.
2. `<state-dir>/--once.lock` (flock, exclusive). Existing v0.4.x
   watchdog lock at `internal/cli/watchdog.go:498-529`. Acquiring
   this lock blocks any concurrent `mcphub watchdog --once` from
   running, AND any v0.4.x install path that already honored it.

**All install / uninstall / register / watchdog install / setup
auto-install paths in v0.5.0 honor `migration.lock` (newly added)
plus `--once.lock` (already honored on v0.4.x paths) or fail
closed.** If `migration.lock` is held when a concurrent install
attempts to run, the concurrent install exits with a clear
"another mcphub install / migration is in progress; retry in 30s"
message. This closes the v3 gap where a scheduled-task install
plus an operator install could race the journal.

### XML customization classification

For each legacy `mcp-local-hub-*` scheduler task enumerated via a
NEW `EnumerateAllMcphubTasks()` helper (`internal/scheduler` —
expands beyond `List()`'s current-user filter at
`scheduler_windows.go:341-356`, so custom-Run-As tasks are not
silently dropped), parse the raw XML and classify each customization:

**Preserved through supervisor-intent.json destination fields:**

- `Principal.UserId` → `principal.user_id`
- `Principal.LogonType` → `principal.logon_type`
- `Principal.RunLevel` → `principal.run_level`
- `Settings.RunOnlyIfNetworkAvailable` → `settings.run_only_if_network_available`
- `Settings.Priority` → `settings.priority`
- `Settings.RestartOnFailure` → becomes Q4 Hybrid C restart policy
  semantic via supervisor state machine (no XML field; the spec
  state machine is the equivalent).

**Preserved through supervisor maintenance_timers:**

- Per-server weekly-refresh CalendarTrigger (`mcp-local-hub-<server>-weekly-refresh`)
- Workspace weekly-refresh CalendarTrigger (`mcp-local-hub-workspace-weekly-refresh`)

**Preserved through autostart shim only (not per daemon):**

- Trigger types other than LogonTrigger on the supervisor's own
  shim (e.g., daily, on-event). The supervisor itself is autostarted
  via the shim. Per-daemon triggers other than logon are reflected
  in `maintenance_timers` if they are a weekly-refresh pattern; any
  other custom trigger is classified as Unsupported.

**Unsupported, abort with explicit list:**

- Custom `Actions` (more than one `<Exec>` per task)
- Conditions that can't be represented (`IdleSettings`, `WakeToRun`,
  `RunOnlyIfIdle`)
- Custom XML attributes outside the v0.4.x install code's canonical
  generation (anything not in the preserved/maintenance lists above)

If any task has unsupported customizations, migration aborts and
prints the per-task classification table. Operator can either
remove the customization manually and retry, or pass
`mcphub install --discard-scheduler-customizations` to proceed
with explicit acknowledgment.

### Pre-unregister daemon stop (no /shutdown — PID/port)

The v3 spec called `/shutdown` over HTTP. **That route does not
exist in v0.4.x daemons** (verified — no `/shutdown` handler in
`internal/cli/daemon.go`). v4 replaces with PID/port stop modelled
on the verified pattern at `internal/api/install.go:1816-1879`:

1. Parse legacy task XML `<Exec>` argv to get the daemon's
   `--server` and `--daemon` names.
2. Read the pidport file
   `<state-dir>/pidport-<server>-<daemon>.json` to get the
   running daemon's PID and port.
3. **Ownership gate before kill.** Same 3-gate test as
   `mcphub gui --force --kill`:
   - Image basename = `mcphub.exe` / `mcphub`
   - argv contains `daemon --server <server> --daemon <daemon>`
   - Process start time precedes pidport mtime
4. Append `{pid, server, daemon, start_time, port}` to
   `killed-daemons.json` (for resume and rollback inspection).
5. **`touch pre-os-mutating`** — journal mutation marker. Once this
   file exists, OS state IS being changed; resume must reconcile.
6. `taskkill /F /PID <pid>` (Windows) or `kill -TERM <pid>` then
   `kill -KILL <pid>` after 5s grace (POSIX).
7. Wait up to 10s for the port to release via repeated port-probe
   (`net.Listen("tcp", ":<port>")` succeeds = port free).
8. If port still bound after 10s, abort migration with the exact
   port and the offending PID; operator investigates manually.

### IntentReason TTL preservation

When migrating across to v0.5.0, **do NOT rewrite
`daemon-intent.json` in any way.** Supervisor reads the existing
file directly via the existing `ReadDaemonIntent` API. The canonical
leading-backslash key normalization at `canonicalIntentTaskKey`
handles bare-vs-canonical conversion on writes by existing v0.4.x
callers; reads index by the canonical key form which is what
supervisor uses.

For each entry, supervisor calls `IsActiveStop(now)` at spawn
decision time:

- `user-disabled`: permanent stop intent → supervisor suppresses spawn.
- `chronic-failure`: permanent stop intent → supervisor suppresses spawn.
- `user-stop`: TTL'd; suppress spawn until TTL expires.
- Clock-skew-future timestamps: per existing `daemon_intent.go`
  semantics, fail closed (do not revive a future-dated stop intent).

### Strict-mode persistence (via CLI arg, not env)

The v3 spec wrote env into Task Scheduler XML. **Microsoft
`execType` schema does not define `<Environment><Variable>`** (per
the existing scheduler XML at `scheduler_windows.go:106-153` — only
Command, Arguments, WorkingDirectory). v4 persists strict-mode via
CLI arg on the autostart shim:

If `MCPHUB_REQUIRE_SINGLE_USER_HOME=1` is set in the install
process's environment:

1. Write `"strict_mode": true` into `supervisor-intent.json`.
2. Pass `--strict-mode` on the autostart shim command line:
   - Windows Task Scheduler XML: `<Arguments>supervise --strict-mode</Arguments>`.
   - Linux systemd user unit: `ExecStart=/usr/local/bin/mcphub supervise --strict-mode`.
   - macOS LaunchAgent plist: `ProgramArguments` array containing
     `["/usr/local/bin/mcphub", "supervise", "--strict-mode"]`.
3. The supervisor at start resolves strict-mode in this priority:
   - `--strict-mode` CLI arg (highest priority — set by autostart shim)
   - `supervisor-intent.json.strict_mode == true`
   - `MCPHUB_REQUIRE_SINGLE_USER_HOME=1` env (lowest — for ad-hoc CLI runs)
4. Once resolved, all state writes from the supervisor go through
   the strict-mode pipeline.

### Forward migration steps

1. Acquire `<state-dir>/migration.lock` (flock; refuse if held).
2. Acquire `<state-dir>/--once.lock` (flock; refuse if held — that
   means a v0.4.x `watchdog --once` is running; wait or abort).
3. Probe `MCPHUB_REQUIRE_SINGLE_USER_HOME` env. If set: verify the
   target autostart shim can pass `--strict-mode` on its CLI on
   this OS (always true for Windows / Linux / macOS).
4. Enumerate ALL `mcp-local-hub-*` scheduler tasks via
   `EnumerateAllMcphubTasks()` (independent of current-user filter)
   — including global `\mcp-local-hub-watchdog`, all per-daemon
   tasks, per-server weekly-refresh, and workspace weekly-refresh.
5. Export each task's raw XML to `legacy-tasks/<task>.xml`.
6. Classify XML customizations per the table above; write
   `legacy-tasks-classification.json`. Abort if unsupported
   customizations found and `--discard-scheduler-customizations`
   was not passed.
7. Derive `supervisor-intent.json` from manifest YAML + workspace
   bindings + snapshotted task argv + classified preserved-customization
   fields + maintenance_timers from weekly-refresh tasks. Include
   `strict_mode` per step 3.
8. `touch prepared`.
9. **`touch pre-os-mutating`** — IMPORTANT: BEFORE first kill, not
   after. Crash between this marker and `os-mutating-complete`
   means OS state IS partially mutated → resume MUST reconcile.
10. Pre-unregister daemon stop: kill each live daemon + wait port
    release per the handoff section above. Append every killed PID
    to `killed-daemons.json`.
11. Stop and unregister each legacy task via `schtasks /Delete`
    (Windows) or equivalent (POSIX — N/A for v0.5.0 since legacy
    v0.4.x is Windows-only).
12. `touch os-mutating-complete`.
13. Install supervisor autostart shim (per Q8 — explicit per-OS
    backend; `--strict-mode` CLI arg if applicable).
14. **Explicitly start supervisor** (NEW; v3 relied on autostart
    trigger which only fires on logon):
    - Windows: `schtasks /Run /TN \mcp-local-hub-supervisor` if
      autostart shim installed, else launch `mcphub.exe supervise
      [--strict-mode]` as detached child of install process.
    - Linux managed: `systemctl --user start mcphub-supervisor.service`.
    - Linux unmanaged: launch `mcphub supervise [--strict-mode]` as
      detached child.
    - macOS managed: `launchctl bootstrap gui/<uid> <plist-path>;
      launchctl kickstart gui/<uid>/com.applicate2628.mcphub-supervisor`.
    - macOS unmanaged: launch detached child.
15. Wait for supervisor to confirm reconcile-success via IPC `status`
    query within 30s. If timeout: roll back automatically by running
    the rollback step list with explicit reason
    `forward-migration-supervisor-start-timeout`.
16. `touch committed`.
17. Release `--once.lock`.
18. Release `migration.lock`.

### Rollback steps (`mcphub install --rollback-to-legacy`)

1. Acquire `migration.lock`.
2. Acquire `--once.lock`.
3. Find latest `migration-journal-*/` directory with `committed`
   marker (or `pre-os-mutating` for partial rollback).
4. Read current `supervisor-state.json`. For each entry in
   `quarantined` state, write a corresponding `daemon-intent.json`
   entry with `reason=chronic-failure, desired=stopped` via
   existing `WriteDaemonIntent` (which canonicalizes the key).
5. Stop supervisor via IPC `exit{graceful: true, timeout_ms: 5000}`,
   fall back to force-kill (look up PID from `supervisor.lock`).
6. Uninstall supervisor autostart shim.
7. For each `legacy-tasks/<task>.xml`: re-register via
   `schtasks /Create /XML` (preserves operator's raw XML including
   global watchdog and weekly-refresh).
8. **Run each restored daemon task** via `schtasks /Run /TN <task>`
   (NEW; v3 just registered them and waited for next logon).
9. **Verify ports bind.** For each daemon task, wait up to 10s for
   its expected port (from the manifest) to be bound by any
   process. If not bound, append `{task, port, reason}` to a
   `rollback-warnings.json` so the operator sees what needs manual
   investigation.
10. Delete `supervisor-intent.json` + `supervisor-state.json` +
    `supervisor-events.log`.
11. Release `--once.lock`.
12. Release `migration.lock`.

### Resume / partial-state recovery

The journal markers progress in order:
`prepared` → `pre-os-mutating` → `os-mutating-complete` → `committed`.

- **Journal at `prepared` only (no `pre-os-mutating`):** no OS state
  touched → safe to abort and delete journal directory.
- **Journal at `pre-os-mutating` but no `os-mutating-complete`:**
  process-stop has begun but legacy tasks may still be registered.
  Read `killed-daemons.json`. Options:
  - **Forward resume** (`mcphub install`): re-acquire locks, scan
    ports for the killed-daemons entries, restart any whose port
    is free via `schtasks /Run`, then continue from step 11.
  - **Rollback** (`mcphub install --rollback-to-legacy`): same but
    rollback-style; legacy tasks are already registered.
- **Journal at `os-mutating-complete` but no `committed`:** legacy
  tasks unregistered, supervisor maybe not running. Operator MUST
  pick forward retry (`mcphub install`) or rollback
  (`mcphub install --rollback-to-legacy`); resume cannot decide
  silently.

## Fresh install flow (detail)

Subsection covering the "no v0.4.x state to migrate, no prior
supervisor" case (the L1-P1 #3 finding from Round 3). `mcphub install`
on a clean machine writes intent and EXPLICITLY starts the
supervisor; the autostart shim is opt-in and never the canonical
first-start trigger.

### When this applies

- No `<state-dir>` exists, OR
- `<state-dir>` exists but contains no `mcp-local-hub-*` Task
  Scheduler tasks, no `supervisor-intent.json`, and no migration
  journal directories.

### Fresh install sequence

1. Acquire `<state-dir>/migration.lock` (flock; refuse if held).
   Even a fresh install acquires this lock so a concurrent second
   install attempt cannot race the autostart shim setup and the
   supervisor start. The same lock contract from Q6 applies here
   so `install`, `uninstall`, `register`, and `watchdog install`
   are mutually exclusive across the lifetime of the operation.
2. Acquire `<state-dir>/--once.lock` only if a v0.4.x watchdog
   task exists on disk (defensive: a clean machine should not have
   it, but honor the lock if state was manually copied or
   migration was incomplete).
3. Write `supervisor-intent.json` from manifest YAML + workspace
   bindings + (optional) operator-passed `--strict-mode` flag.
   `principal` defaults to current user with `InteractiveToken` +
   `LeastPrivilege`; `settings.priority` defaults to 7;
   `maintenance_timers` populated from manifest `weekly_refresh:
   true` entries.
4. (Optional) If `--autostart` flag passed, install the autostart
   shim per Q8.
5. **Explicitly start supervisor.** Same per-OS commands as the
   upgrade flow step 6, but with no prior supervisor to exit:
   - Windows: if autostart shim was just installed, run
     `schtasks /Run /TN \mcp-local-hub-supervisor`. Otherwise,
     launch `mcphub.exe supervise [--strict-mode]` as a detached
     child via `CreateProcess` with `DETACHED_PROCESS |
     CREATE_NEW_PROCESS_GROUP`.
   - Linux managed: `systemctl --user start
     mcphub-supervisor.service` (if shim installed) or
     `mcphub supervise [--strict-mode] &`.
   - Linux unmanaged: `mcphub supervise [--strict-mode] &`.
   - macOS managed: `launchctl bootstrap gui/<uid> <plist-path>;
     launchctl kickstart gui/<uid>/com.applicate2628.mcphub-supervisor`
     (if shim installed).
   - macOS unmanaged: `mcphub supervise [--strict-mode] &`.
6. Wait for supervisor reconcile-success via IPC `status` within
   30s. On timeout: report error with the exact supervisor command
   the operator can run manually; do NOT silently leave a
   half-installed state.
7. Release `--once.lock` if acquired.
8. Release `migration.lock`.

### `--no-start` contract

`mcphub install --no-start` writes `supervisor-intent.json` and
optionally installs the autostart shim but does NOT start the
supervisor. Intended for CI / fleet-provisioning flows where the
caller starts supervisor on its own schedule (next reboot,
explicit launchctl bootstrap, etc.). Prints an explicit reminder
line ending with the exact command the operator must run to
activate the install. Default for fresh install is `--start`
(implicit).

### Error path on supervisor start failure

If step 5's supervisor start syscall fails (binary missing,
permission denied, port collision), the install:

1. Removes the autostart shim if it was installed in step 4.
2. Leaves `supervisor-intent.json` on disk so a retry does not
   re-derive it from manifest unnecessarily.
3. Releases locks.
4. Exits non-zero with a structured error message naming the
   failed syscall plus the exact retry command.

## Cold-restart upgrade flow (detail)

Subsection elaborating Q5 for plan phase. The v3 spec leaned on the
autostart shim to cold-start the new supervisor, but on Windows
`LogonTrigger` only fires at user logon, never on supervisor exit.
v4 makes the install CLI the explicit restart trigger.

### Sequence

1. `mcphub install --upgrade` writes new binary atomically:
   - Windows: write to `<install-dir>/mcphub.exe.new`,
     `MoveFileEx` with `REPLACE_EXISTING`. If the current binary is
     locked, `MOVEFILE_DELAY_UNTIL_REBOOT` is rejected as user-hostile
     and install aborts with instructions to stop supervisor first.
   - POSIX: atomic `rename(2)` over the existing binary.
2. Connect to supervisor IPC pipe / socket via Q11 trust boundary.
3. Send `exit{graceful: true, timeout_ms: 5000}`.
4. Supervisor stops accepting new IPC requests, gracefully terminates
   children (Windows: terminate Job Object members — kill descends;
   POSIX default: SIGTERM children then SIGKILL after grace).
5. Supervisor exits with code 0.
6. **`mcphub install` explicitly starts the new supervisor.** Per-OS:
   - Windows: `schtasks /Run /TN \mcp-local-hub-supervisor` if the
     autostart shim is installed (passes any `--strict-mode` arg
     baked into the shim). If shim not installed, launch directly
     as detached child of install process.
   - Linux managed: `systemctl --user restart mcphub-supervisor.service`.
   - Linux unmanaged: `mcphub supervise [--strict-mode] &` (detached).
   - macOS managed: `launchctl kickstart -k gui/<uid>/com.applicate2628.mcphub-supervisor`.
   - macOS unmanaged: `mcphub supervise [--strict-mode] &` (detached).
7. New supervisor starts → reads `supervisor-intent.json` and
   `daemon-intent.json` → reconcile → respawns daemons.
8. Operator sees ~10s blip in MCP clients via their existing retry
   semantics.

### Fallback if step 3 IPC fails

- Force-kill the prior supervisor PID (look up `supervisor.lock`
  for `{pid, start_time}`; if PID alive with matching start_time,
  terminate).
- Run cold-start stale-child reaper (Linux/macOS default modes
  only; Windows Job Object already killed).
- Proceed to step 6.

## Restart policy state machine (detail)

Subsection elaborating Q4 for plan phase. v3 deferred the
transition table; v4 commits it now.

### States

- `idle` — daemon entry exists in intent but not yet spawned.
- `spawning` — supervisor has issued OS create-process; child not
  yet confirmed running.
- `running` — child PID alive + first health check OK.
- `exiting` — graceful or forced termination in progress.
- `backoff-waiting` — child exited recently; supervisor armed an
  exponential-backoff timer.
- `quarantined` — failure count exceeded the 30-min window budget;
  auto-restart disabled until intent_update or manual_restart.

### Events

- `child_exit{pid, exit_code, signal}` — OS-level child termination.
- `timer_due{kind}` — backoff timer fired.
- `intent_update{task_name, new_intent}` — `supervisor-intent.json`
  or `daemon-intent.json` updated; supervisor reloads.
- `manual_restart{task_name}` — IPC `restart` command from operator.
- `supervisor_restart` — supervisor process is starting (fresh boot
  or recovery from crash).

### Transition table

`failures` = count of `child_exit` events in trailing 30-min
sliding window per `(task_name)`. `gen_match` = `child_exit.pid`
matches `supervisor-state.daemons[task_name].current_pid` AND the
generation counter was not incremented since.

| From | Event | Guard | To | Side effect | Persist when |
| --- | --- | --- | --- | --- | --- |
| idle | (start) | intent.desired=running AND NOT IsActiveStop(now) | spawning | bump pid_generation, OS create-process | BEFORE create-process |
| idle | intent_update | new.desired=stopped | idle | none | n/a |
| spawning | (health check OK) | first probe success | running | none | AFTER probe OK |
| spawning | child_exit | gen_match | backoff-waiting | arm timer at backoff(failures) | BEFORE timer arm |
| spawning | child_exit | NOT gen_match | spawning | drop event (stale PID) | n/a (log only) |
| running | child_exit | gen_match | backoff-waiting | arm timer | BEFORE timer arm |
| running | child_exit | NOT gen_match | running | drop event (stale PID) | n/a (log only) |
| running | intent_update | new.desired=stopped | exiting | issue terminate | BEFORE terminate |
| running | manual_restart | always | exiting | issue terminate, queue spawn | BEFORE terminate |
| exiting | child_exit | always | depends on queued action | spawn or idle | per next state |
| backoff-waiting | timer_due | failures < 10 | spawning | bump pid_generation, OS create-process | BEFORE create-process |
| backoff-waiting | timer_due | failures >= 10 | quarantined | clear timer | BEFORE clear |
| backoff-waiting | intent_update | new.desired=stopped | idle | cancel timer | BEFORE cancel |
| backoff-waiting | intent_update | new.desired=running (TTL refreshed) | spawning | cancel timer, bump pid_generation, OS create-process | BEFORE create-process |
| backoff-waiting | manual_restart | always | spawning | cancel timer, bump pid_generation, OS create-process | BEFORE create-process |
| quarantined | intent_update | new.desired=stopped | idle | none | n/a |
| quarantined | intent_update | new.desired=running (TTL refreshed) | spawning | reset failures, bump pid_generation, OS create-process | BEFORE create-process |
| quarantined | manual_restart | always | spawning | reset failures, bump pid_generation, OS create-process | BEFORE create-process |
| (any) | supervisor_restart | persisted state=quarantined | quarantined | none | done via load |
| (any) | supervisor_restart | persisted backoff_until > now AND failures < 10 | backoff-waiting | re-arm timer at absolute backoff_until | done via load |
| (any) | supervisor_restart | persisted backoff_until <= now AND intent.desired=running AND NOT IsActiveStop(now) | spawning | bump pid_generation, OS create-process | BEFORE create-process |
| (any) | supervisor_restart | persisted intent.desired=stopped | idle | none | done via load |

Backoff schedule: 0s, 0s, 0s (immediate first 3 retries), then 5s,
15s, 60s, 5min, 30min capped. The "first 3 immediate" handles
transient port-collision recovery; the exponential phase handles
deterministic-fail crash loops.

`pid_generation` is the monotonic counter at
`supervisor-state.daemons[task_name].pid_generation`. Every spawn
increments it. The gen_match check drops stale child_exit events
whose PID has been recycled to a different supervisor child.

`failures` window: 30 minutes sliding. After the 30-min window, old
exit entries fall off and the daemon can leave quarantine via
`manual_restart` or `intent_update`.

## Control IPC trust boundary (detail)

Subsection elaborating Q11 for plan phase.

### Wire format

Newline-delimited JSON, one object per line.

Request:

```json
{"id": 42, "cmd": "status"}
{"id": 43, "cmd": "exit", "args": {"graceful": true, "timeout_ms": 5000}}
{"id": 44, "cmd": "restart", "args": {"server": "memory", "daemon": "default"}}
{"id": 45, "cmd": "reload"}
```

Response:

```json
{"id": 42, "ok": true, "result": { "daemons": [] }}
{"id": 43, "ok": true, "result": "exit-acked"}
{"id": 43, "error": {"code": "TIMEOUT", "message": "exit took >5s; forced kill"}}
```

### Handshake

On connection, supervisor sends a hello frame:

```json
{"hello": {"version": 1, "pid": 12345, "started_at": "RFC3339Nano"}}
```

Client must ACK with its own hello echoing the PID + start_time it
expects. Mismatch = stale-instance detection → connection closed.

### Trust boundary

- Windows: pipe DACL constructed via a NEW `internal/api`-owned
  helper (`internal/api.BuildOwnerOnlyDACL()` or equivalent) that
  the existing `SecureWriteClientConfig` is refactored to also use.
  Allowlist: current-user SID + LocalSystem + BuiltinAdministrators
  (same as `internal/api/secure_write_windows.go:474` today).
- POSIX: unix socket mode 0600 + owner-uid match.
- No token. The OS-level access control is the boundary.

### Audit

Every command write-through to `supervisor-events.log` (JSONL) as
`source: "ipc"`:

```json
{"schema": 1, "ts": "...", "severity": "info", "source": "ipc",
 "event": "ipc-command", "fields": {"cmd": "exit", "args": {},
 "caller": {"pid": 99}, "result": "ok"}}
```

## Open plan-phase questions

These are detail items the spec defers to plan phase. Plan phase
will encode each as a concrete table / contract / sequence; the
spec's role is to commit to the architectural intent.

- **Reconcile trigger on each OS.** Linux inotify can be invalidated
  by atomic-rename and queues can overflow; Windows
  ReadDirectoryChangesW + atomic rename behaves similarly; macOS
  kqueue EVFILT_VNODE is fd-based. Plan phase: parent-dir watch +
  re-arm + overflow → full-rescan + IPC reload as authoritative +
  periodic 60s poll for safety.
- **Autostart `status` richer enum.** Per-backend probe semantics
  for `absent` / `enabled-running` / `enabled-stopped` / `drifted`
  / `stale-residue`. Each backend (Task Scheduler, systemd-user,
  launchd) needs an OS-specific status query plus classification.
- **`supervisor.lock` stale-PID detection.** Lock file carries
  `{pid, start_time}`; if PID is not running OR the matching
  process has a different start_time, the lock is stale and can
  be reclaimed.
- **Concurrent `mcphub status` query fan-out.** Plan phase picks:
  per-connection goroutine reading a snapshot of in-memory child
  registry, OR serialized.
- **Linux non-systemd host fallback.** On Alpine/musl without
  systemd-user, `--linux-managed` is unavailable; default
  PR_SET_PDEATHSIG mode is the only option. Plan phase: explicit
  warning on `mcphub install --linux-beta` if cgroup-scope
  unavailable.
- **macOS containment posture.** No kernel containment primitive
  equivalent to Job Object or cgroup is available; both default
  and managed modes are observation plus restart. Plan phase
  documents this as v0.5.0 known limitation; v0.6 reevaluates if
  new primitives become available.

## Terms and Abbreviations

- `canonical task name`: leading-backslash form of a Task Scheduler
  task name (e.g. `\mcp-local-hub-memory-default`), the storage
  key form per `internal/api/daemon_intent.go:275-283`.
- `cgroup scope`: Linux systemd transient unit type that groups
  processes for lifecycle and resource control. NOT a
  kill-on-parent-exit primitive — scope outlives any one process.
- `cold-start reaper`: supervisor's startup procedure on
  Linux/macOS default modes that scans PID files + ports for
  orphaned daemons from a prior supervisor crash and kills them
  before the new spawn loop runs.
- `daemon-intent.json`: existing v0.4.x state file recording
  per-canonical-task-name `{desired, reason, updated_at}`. Top-level
  shape is `{tasks: ...}` only — no other fields. Preserved verbatim
  by v0.5.0.
- `direct-child containment` (Linux default): supervisor's
  PR_SET_PDEATHSIG-only mode — covers daemons that don't `setsid`
  or double-fork. Double-fork descendants escape; the cold-start
  reaper cleans them up.
- `EnumerateAllMcphubTasks`: new helper in `internal/scheduler` that
  lists every `mcp-local-hub-*` Task Scheduler task regardless of
  Run As — closes the gap where the existing `List()` filters to
  the current Windows user and would silently miss custom-Run-As
  legacy tasks during migration enumeration.
- `IntentReason TTL`: per `IsActiveStop(now)`, the time-window
  during which a `user-stop` reason suppresses reconcile spawn.
  v0.5.0 supervisor honors this verbatim by reading the existing
  daemon-intent.json file via existing API.
- `IPC`: inter-process communication; in this spec, the
  supervisor's control surface via Windows named pipe / POSIX unix
  socket.
- `Job Object`: Windows kernel primitive grouping processes for
  shared lifecycle, resource limits, and termination control.
- `JSON line protocol`: newline-delimited JSON, one object per
  line; the IPC wire format and the supervisor-events.log format.
- `KILL_ON_JOB_CLOSE`: Job Object flag that kills all member
  processes when the last open handle to the job is closed.
- `killed-daemons.json`: migration journal artifact recording
  every PID the migration stopped, for resume and rollback
  inspection.
- `kqueue`: BSD/macOS kernel event-notification facility; used here
  to observe child-process exit via `EVFILT_PROC NOTE_EXIT`.
  Observation only, NOT a containment primitive.
- `LaunchAgent`: macOS plist-defined background job run by launchd
  in the user's login session. `KeepAlive` provides restart-after-exit
  semantics, NOT cgroup-style descendant containment.
- `maintenance_timers`: section of supervisor-intent.json carrying
  per-server and workspace weekly-refresh schedules that v0.4.x
  ran via scheduler. Supervisor schedules them in-process via cron
  parser; fires `mcphub.exe <command>` as transient (NOT Job Object
  managed) children.
- `managed-entries.json`: existing v0.4.x state file recording
  `(client, server)` ownership. Root shape: `{version, entries}`.
- `managed mode` (Linux/macOS optional): supervisor's init-system-owned
  mode. Linux: systemd-user-service with KillMode=control-group
  (strong containment via cgroup). macOS: LaunchAgent (restart-after-exit
  only — still NOT cgroup containment).
- `MCP`: Model Context Protocol — wire protocol between agents and
  MCP servers.
- `mcphub.exe supervise`: new subcommand introduced in v0.5.0 that
  runs as the long-lived parent process.
- `migration.lock`: NEW exclusive flock at `<state-dir>/migration.lock`
  serializing v0.5.0 install/uninstall/migration runs.
- `migration journal`: per-install directory holding raw
  scheduler-task XML snapshots plus state markers
  (`prepared`/`pre-os-mutating`/`os-mutating-complete`/`committed`)
  plus classification plus derived supervisor-intent plus
  strict-mode marker plus killed-daemons list, used for forward
  and rollback paths in Q6.
- `--once.lock`: existing v0.4.x watchdog exclusive flock at
  `<state-dir>/--once.lock` per
  `internal/cli/watchdog.go:498-529`. v0.5.0 migration acquires
  this lock too so concurrent `watchdog --once` cannot mutate state.
- `PID generation`: monotonic counter incremented on every spawn;
  guards against stale `child_exit` events from old PIDs.
- `PR_SET_PDEATHSIG`: Linux prctl option that requests delivery of
  a signal to the calling process when its parent dies. Per-process
  and cleared on fork.
- `pre-os-mutating`: NEW migration journal marker written BEFORE
  any OS mutation (BEFORE the first daemon kill, BEFORE any
  schtasks /Delete). Resume reads this to know OS state was
  touched.
- `quarantine`: terminal state for a daemon after exceeding the
  Hybrid C restart-failure budget; supervisor refuses further
  auto-restart until intent_update or manual_restart. On rollback,
  translated to `daemon-intent.json` `chronic-failure` so legacy
  watchdog respects it.
- `reconcile loop`: supervisor's core algorithm — diff intent
  against running children and bring them into alignment.
- `state-file helper`: NEW shared utility under `internal/api`
  combining flock + atomic temp+rename + `SecureWriteClientConfig`
  used by all new supervisor-* state files.
- `strict mode`: operator opt-in via
  `MCPHUB_REQUIRE_SINGLE_USER_HOME=1`. v0.5.0 persists this
  through THREE channels resolved in priority order: (1) CLI arg
  `--strict-mode` on the autostart shim's command (canonical;
  Windows Task Scheduler XML has no env support so this is the
  only path on Windows); (2) `supervisor-intent.json.strict_mode`;
  (3) env var for ad-hoc CLI runs.
- `supervisor-events.log`: NEW JSONL audit log of supervisor
  lifecycle events. Schema version, severity (debug/info/warn/error),
  source (ipc/lifecycle/restart-policy/migration/autostart/reconcile),
  flock-protected appends, 10 MB rotation with `.log.1`, per-entry
  16 KB cap with identity-field protection.
- `supervisor-intent.json`: NEW state file holding full daemon
  descriptors keyed by canonical task name, plus principal /
  settings destination fields for preserved Task Scheduler
  customizations, plus maintenance_timers, plus strict_mode bool.
  Supervisor reconcile source-of-truth.
- `supervisor-state.json`: NEW state file holding Hybrid C state
  machine state (restart counts, backoff timers absolute
  timestamps, quarantine windows, PID + generation).
- `systemd-user`: per-user systemd instance; manages user units
  like `mcphub-supervisor.service`.
- `Task Scheduler`: Windows service that runs scheduled tasks;
  v0.4.x used N entries (one per daemon plus weekly-refresh plus
  global watchdog), v0.5.0 uses one entry (autostart shim for
  supervisor).
- `watchdog-state.json`: existing v0.4.x state file with sliding
  strike windows; preserved unchanged in v0.5.0 for rollback
  byte-compatibility.
