### P2.1 Vault DACL-refusal mislabeled "corrupt", steering operator to data-destroying recovery
- **loc:** internal/api/secrets.go:307-332 (classifyVault), consumed by internal/gui/frontend/src/screens/Secrets.tsx:455-459 (BrokenView)
- **problem:** classifyVault distinguishes vault failure modes by substring-matching OpenVault's err.Error() against "parse identity"/"no identity"/"not X25519"/"unmarshal vault"/"age decrypt". The documented and common corp/sandbox failure вЂ” a broadened DACL on .age-key or secrets.age that the fail-closed read-hardening refuses вЂ” produces the error string "file <path> not single-user safe: ..." (internal/api/hub_mcp_state_read_inode_windows.go:191/198/201) wrapped as "read vault: %w" / "read identity: %w". That string matches NONE of the discriminators, so classifyVault falls through to `default: return "corrupt"` (secrets.go:329-330). The files exist and decrypt fine, so keyExists/vaultExists are both true and the "missing" branch is not taken either. The GUI then renders BrokenView, whose recovery text tells the operator: "remove the vault files and re-initialize. Removing the vault destroys all stored secrets." вЂ” i.e. it actively pushes the operator toward irreversible data loss when the actual problem is a one-command icacls fix (per the CLAUDE.md "secret daemons exit 1 on a sandbox-broadened %LOCALAPPDATA%" runbook). The runtime daemon-launch path correctly surfaces this as a remediable DACL error (cli/daemon.go:407), so only the GUI Secrets screen mis-classifies it. Verified by reading both the discriminator switch and the error-wording producer.
- **fix:** Add a discriminator branch in classifyVault BEFORE the default: when the captured err string contains "not single-user safe" or "DACL" (or, better, when errors.As/errors.Is matches the DACL-violation type, e.g. *api.DACLAllowlistViolation / ErrDaclOutsideAllowlist), return a new vault_state value such as "access_denied" (add it to the VaultState union in lib/secrets-api.ts and render a remediation banner that points at the icacls/chmod fix and explicitly does NOT suggest deleting the vault). Until the new state ships, at minimum stop returning "corrupt" for a permission refusal вЂ” "decrypt_failed" is still wrong but its banner is less destructive; the access-denied state is the correct fix.

### P2.2 Supervisor IPC connections have no read deadline вЂ” a same-user client that connects but never sends a complete frame leaks a goroutine + kernel pipe/socket handle indefinitely
- **loc:** internal/cli/supervise.go:1534-1577 (handleIPCConn); listener config internal/cli/supervise_ipc_windows.go:67-89 and internal/cli/supervise_ipc_posix.go:68-92; accept loop internal/cli/supervise.go:1455-1517
- **problem:** handleIPCConn does `reader.ReadString('\n')` in an unbounded loop with NO read deadline ever set on the accepted net.Conn, and the listeners (winio.ListenPipe / net.Listen("unix")) impose none either. There is no http.Server wrapping these conns, so the spec's documented IdleTimeout/ReadTimeout (which apply only to the HTTP hub listener, hub_listener.go:59-63) do NOT cover the supervisor IPC channel. acceptIPCConnections spawns `go handleIPCConn(conn, deps)` per connection (supervise.go:1515) with no per-connection lifetime bound. A client that opens the pipe and sends a partial line without a trailing newline (or nothing at all) parks the goroutine forever in ReadString; the 4KiB+4KiB kernel pipe buffers (set at supervise_ipc_windows.go:75-76) and the goroutine accumulate with no cap. The pipe DACL admits the current user + LocalSystem, so any same-user process вЂ” including a buggy/crashing `mcphub restart`/`status` client that dies mid-frame after connect, or a hostile co-resident same-user process вЂ” can hold these open. Because mcphub's own status/restart commands are frequent IPC clients in long-lived supervisor sessions, accumulation is realistic, degrading the supervisor toward goroutine/handle exhaustion with no recovery short of a supervisor restart.
- **fix:** In handleIPCConn, set an idle read deadline before each ReadString and reset it per successfully-read frame, e.g. at the top of the for-loop: `_ = conn.SetReadDeadline(time.Now().Add(ipcConnIdleTimeout))` (pick a value comfortably above the longest legitimate inter-frame gap вЂ” IPC frames are short JSON lines, so 60s is generous; the long-running drain on `quiesce-timers`/`exit` is supervisor-side, not client-read-side). A deadline error then returns from handleIPCConn, the deferred conn.Close() (already present at supervise.go:1535) reclaims the handle, and the goroutine exits. No protocol change вЂ” legitimate clients that send frames within the window are unaffected; the existing per-stop/per-command behavior is preserved.
- closable=True conf=verified

### P2.3 Global multi-client scan aborts entirely on ONE malformed client config file вЂ” no per-client error isolation, untested branch fails GUI matrix, `mcphub scan`, AND hub bind
- **loc:** internal/api/scan.go:762-764 (ScanFrom per-client loop); reached via internal/gui/scan.go:20-21 (HTTP 500 SCAN_FAILED), internal/cli/scan.go:99-114, internal/gui/hub_listener.go:841-844 (hub-bind pre-gate)
- **problem:** In ScanFrom the per-client scan loop does `if err := sc.scan(entries, path); err != nil { return nil, fmt.Errorf(...) }` вЂ” a single client whose config scanner returns an error aborts the ENTIRE scan. The scanners (e.g. scanGemini scan.go:1078, scanQwen :1114, scanAntigravity :1150, scanZed, scanVSCode, etc.) do a strict `json.Unmarshal` and return that error verbatim. Add a regression test in internal/api/scan_test.go: seed two client config paths (one valid, one with malformed JSON e.g. `{"mcpServers":{` truncated), call ScanFrom, assert (a) ScanFrom returns no error, (b) the valid client's entries are present, (c) the malformed client is surfaced as a presence/scan error rather than silently dropped. Mirror the projects_aggregate isolation contract so both scan paths behave identically.

### P2.4 Secret vault rotation and deletion commit credential-material changes with ZERO audit trail
- **loc:** internal/api/secrets.go:385 (SecretsRotate), internal/api/secrets.go:528 (SecretsDelete)
- **problem:** SecretsRotate re-encrypts a credential into the vault (v.Set at secrets.go:415) and then triggers daemon restarts (restartServersForKey at :431); SecretsDelete destroys a vault entry. Neither emits ANY event to any of the four JSONL logs вЂ” verified by grep: secrets.go contains no .Emit / AppendGUIEventLog / LogHubMcpEvent / AppendIntentAudit call (the only audit-adjacent symbol is SecretsDeleteError.Error). A secret rotate/delete is the most security-sensitive operator action in the system (it mutates credential material and can restart every daemon that references the key), yet it leaves no forensic record of who rotated/deleted which key and when. Every other state-mutating path in the codebase (daemon spawn/exit/quarantine, IPC commands, intent writes, client-config writes, even runtime-state-persist failures) emits a structured event; the vault mutation is the conspicuous exception. The state-file write-hardening fallback IS audited, but the higher-level 'a secret was rotated/deleted' fact is not.
- **fix:** Emit a supervisor-events.log entry (or gui-events.log via AppendGUIEventLog) at the end of the successful vault-write phase in both SecretsRotate (after secrets.go:423 vaultMutex.Unlock, before the restart phase) and SecretsDelete (after the delete commits). Event e.g. {source:'lifecycle', severity:'warn', event:'secret-rotated'|'secret-deleted', body:{key:name, restart_requested:restart, caller_user:currentOSUser()}}. CRITICAL: log only the key NAME, never the value (per the sensitive-data redaction rule). The vaultMutex section is already the natural single owner.

### P2.5 9 baseline marketplace catalog rows install UNPINNED npx/uvx packages вЂ” re-resolve to registry-latest at every cold spawn, contradicting the project's own pin policy
- **loc:** marketplace/v2/catalog.json:12-17 (filesystem), :33-35 (git), :53 (fetch), :71-75 (sqlite), :91-93 (playwright), :141-143 (excalidraw), :161-163 (everything), :181-183 (memory), plus paper-search-mcp uvx --from paper-search-mcp
- **problem:** These rows draft manifests whose command/base_args are `npx -y @modelcontextprotocol/server-filesystem` / `uvx mcp-server-git` / `uvx mcp-server-fetch` / `npx -y @modelcontextprotocol/server-memory` etc. with NO version qualifier. npx/uvx resolve the package to whatever the public registry serves at that moment, and re-resolve on a clean cache at every cold spawn. A compromised npm/PyPI account, a malicious version push, or a registry MITM therefore executes attacker code on the operator's host on the NEXT daemon restart вЂ” with no operator action and no diff. This directly contradicts the project's own supply-chain posture: the Tier-1 rows are all version-pinned (grafana `mcp-grafana==0.17.0`, tableau `@tableau/mcp-server@2.18.1`, time `@mcpcentral/mcp-time@0.0.5`, ansys `==0.2.1`), the serena row pins a 40-hex git SHA, and marketplace_tier1_catalog_test.go:215/588 hard-fails any fork row missing a pin. The decision doc (work-items/decisions/2026-06-23-d2-vendored-source.md) names exactly this risk ("the fork content can change underneath the pin between admission and install, defeating any vetting") yet only enforces it for vendored forks via vendored_source вЂ” official-package rows have no equivalent gate, so the 9 baseline rows ship unpinned.
- **fix:** Pin each baseline row to a known-good version in args (the same shape Tier-1 rows already use): `@modelcontextprotocol/server-filesystem@<ver>`, `mcp-server-git==<ver>` (uvx accepts `pkg==ver`), `mcp-server-fetch==<ver>`, `@modelcontextprotocol/server-memory@<ver>`, etc., and `paper-search-mcp==<ver>`. Then add a guard in marketplace_tier1_catalog_test.go that asserts EVERY stdio entry whose command is `npx` or `uvx` carries a version qualifier (`@<ver>`, `==<ver>`, or a `git+...@<40-hex-sha>` --from), mirroring the existing fork-pin assertion, so an unpinned official row is rejected at author/test time. Also pin servers/fetch/manifest.yaml, servers/memory/manifest.yaml, servers/sequential-thinking/manifest.yaml, servers/time/manifest.yaml, servers/paper-search-mcp/manifest.yaml the same way (the in-repo shipped manifests carry the identical unpinned base_args).
