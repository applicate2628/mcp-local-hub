# LSP lazy-proxy: two pre-existing lifecycle/refcount edges (backlog)

- **status:** fixed
- **severity:** low
- **filed:** 2026-07-02
- **fixed:** 2026-07-03 (branch `fix/lsp-preexisting-lifecycle-edges`, both edges)
- **context:** surfaced by the P2c-unified commission (fable+opus) as PRE-EXISTING (present on master before the unified refactor); deliberately NOT fixed in PR #489 to avoid scope creep.

## Edge 1 — transient Configured-stomp during the reserve→shadow-reset window

`internal/daemon/lazy_proxy.go` reapIdleBackend's post-unlock `PutLifecycle(Configured)` can land after a concurrent cold-path reserve's flock `Starting` write (reserve passed the `reaping` spin before the reap began). The row reads `Configured` for the ~30-45s materialize window → other proxies' cold-start gate / hard cap undercount by one. Self-heals at publish-time reconcile. Master had the same ordering. Fix direction: reset/reconcile the row under the flock inside reserve rather than after return, or gen-guard the idle-reap Configured write.

**Fixed 2026-07-03 (NARROWED, disclosed residual — post-review corrected attribution).** `reapIdleBackend` now routes its terminal Configured write through the single-owner `reconcileRegistryLifecycleLocked(gen)` under `p.mu` instead of the out-of-band `PutLifecycle(Configured)`. Two DISTINCT protections (a fable xhigh pre-bot review corrected the initial misattribution):

- **The gen guard's real production trigger is a concurrent proxy `Stop()` mid-reap** — every other generation bumper (publish, wedge-reap, send-failure) refuses while `p.reaping` is held, so "a materialize republished over the teardown" cannot actually race this call site; a concurrent `Stop()` can, and the stale reap's write then no-ops.
- **The documented reserve race** (a cold-path reserve's flock `Starting` write landing before this reconcile — the original stomp) is mitigated by the reconcile DERIVING `Starting` from `startingSince`: once `markStartingReserved` has run, the reap's write preserves Starting. **RESIDUAL:** a reserve that has written its flock Starting but not yet returned to `markStartingReserved` leaves a microseconds-wide gap where the reconcile still derives Configured — narrowed from the old ~`Stop()`-duration window, NOT fully closed; reachability needs the reserve to stall ≥ IdleBackendTTL between its `reaping`-spin break and its flock write (same exotic class as the original bug); self-heals at publish-time reconcile.

This removes the last non-reconcile RUNNING-lifecycle Configured writer (the pre-concurrency startup seeds remain, gen-0 before Serve) and keeps the `lastWrittenLifecycle` shadow consistent with the registry. `Stop()` still precedes the Configured write. Regression: `TestLazyProxy_IdleReap_StaleConfiguredWriteNoStompsNewerStarting` (constructs the superseded-gen state directly; fails on master with `lifecycle=configured`).

**Follow-up 2026-07-03 (bot PR #492 r1 P2 — phantom-Starting inverse of the stomp).** The reconcile-at-reap created a NEW exposure the old bare Configured write accidentally masked: a flight that RESERVED (flock `Starting` write + `markStartingReserved`) and then died at the publish-rejection gate (`errLazyProxyUnpublishable`, mid-reap) left `startingSince` armed with no endpoint and no active flight, so the reap's final reconcile derived and PERSISTED a phantom `Starting` row — counting against every proxy's cold-start gate / hard cap until Branch B's ≤5m probation timer. Fixed at the flight's terminal moment: `publishMaterializedEndpoint`'s rejection branch now zeroes `startingSince` under the same `p.mu` hold that observes closed/reaping (flight-scoped by that atomicity — while `reaping` is held the `ensureMaterialized` spin blocks every new caller before reserve/mark, and a closed proxy refuses callers outright, so no post-rejection flight can have re-armed the marker; the fn is the flight's guaranteed terminal executor even when every bounded waiter abandoned the join, which is why the clear lives there and not in `ensureMaterialized`'s error branch). No new reconcile call — the reap's own final reconcile settles the row (Configured), preserving the Stop()-before-Configured ordering; for the closed case `LazyProxy.Stop` owns final state and clears the marker itself. The other post-mark error paths deliberately KEEP the marker armed (triage in the `markStartingReserved` doc): in-flight/ctx-cancel = flight still running (marker is the truthful Starting-derivation input); genuine materialize error / throttle-cached error = the armed marker is Branch B's only handle on the swallowed-Failed-write double fault (clearing would orphan a stuck-Starting row forever). Regression: `TestLazyProxy_RejectedPublish_ClearsStaleStartingSince_ReapSettlesConfigured` (fails pre-fix with `lifecycle after reap = "starting"`).

## Edge 2 — warm-path didOpen/didClose rollback-after-delivery (refcount desync)

`handleDocLifecycle`: with `warmed=true` the forward runs under the raw client ctx; a delivered `didOpen` that stalls past the client deadline hits `isClientCancelErr` → `rollbackDocRef` even though the bytes were written to stdin → refcount desync (the next `didOpen` duplicates the upstream open). The delivered⇒keep-refcount logic (round-1 P2c fix) exists ONLY in the `!warmed` probation branch, not the warm path. Fix direction: apply the same delivered⇒keep-refcount classification to the warm notification path.

**Fixed 2026-07-03.** The SendRequest-error block in `handleDocLifecycle` now classifies BOTH delivered shapes as 202 + keep-refcount: `isProbationDeadline` (cold budget, `!warmed`) OR `isClientCancelErr` (client ctx canceled/deadlined after delivery — the warm path). This is sound because SendRPC writes stdin BEFORE awaiting and the endpoint's only context-error surface is that post-write select, so any context cancel/deadline error means the notification was already delivered. The pre-delivery failure path (a non-context send error while the client ctx is live) still rolls back the refcount and tears down. Residual (CLOSED by the r3 root fix below): a client-cancel racing a broken-pipe write failure kept a phantom refcount — the r3 identity-keyed classification now sends that shape down the failure path. Regressions: `TestLazyProxy_DocLifecycle_WarmDeliveredThenClientCancel_KeepsRefcount` (fails on master with code 200/-32603, passes now) and `TestLazyProxy_DocLifecycle_WarmPreDeliveryFailure_RollsBackAndTearsDown` (guards the still-rolls-back failure path).

**Follow-up 2026-07-03 (bot PR #492 r2 P2 — keep-on-dead-backend select race).** A ctx-shaped SendRPC error does NOT prove the backend outlived the call: Go's select picks pseudo-randomly among READY cases, so when the client cancel/deadline and the subprocess death (`done`/`childExited`) are simultaneously ready, SendRPC can return its ctx arm. The delivered⇒keep classification then cached a DEAD endpoint (`onSendFailure` skipped) and retained a refcount the dead backend no longer honors — the next didOpen for that uri was absorbed (never forwarded) and the dead endpoint lingered until some unrelated forward tripped teardown. Guarded now: on a delivered-shaped error (BOTH arms — the probation-budget deadline races `childExited` identically), the handler probes the backend's own death arms before keeping — `stdioHostEndpoint.BackendAlive()` does a non-blocking select-default read of the `done`/`childExited` close-only broadcast channels SendRPC selects on (race-free per the Go memory model). The r2 decision to exclude `procExited` ("match SendRPC's arms") was REVERSED in r3 — see the r3 follow-up below for the delivered-to-nowhere rationale. Alive → 202 + keep, exactly as before. Dead → the failure path: rollback + `onSendFailure` teardown + error response (the refcount bookkeeping is moot — teardown's `resetDocRefs` clears it — and teardown-now beats a lingering cached dead endpoint). The probe is an OPTIONAL endpoint facet (`backendAliveProber`); an endpoint without it keeps the prior contract (assumed alive). Point-in-time residual: a backend dying a microsecond AFTER the probe reads alive is indistinguishable from a pure cancel and is caught by the next forwarded request's send failure — the systematic misclassification is what is closed here. Regressions: `TestLazyProxy_DocLifecycle_CancelWithDeadBackend_TearsDownNotKeep` (fails pre-guard with a 202 delivered⇒keep) and the live-backend twin `TestLazyProxy_DocLifecycle_WarmDeliveredThenClientCancel_KeepsRefcount` (now exercises the probe-positive side).

**Follow-up 2026-07-03 (bot PR #492 r3 P2 — ROOT fix: delivered classification keys on ERROR IDENTITY, not ctx state).** `isClientCancelErr` returned true for ANY error whenever the request ctx happened to be already canceled — classification by ctx STATE, not by the error's identity. A broken-pipe/EOF/host-stopped send failure (the notification was NEVER written) under a canceled client ctx therefore classified as delivered⇒keep; composed with an alive-reading probe (the `procExited` drain window), the doc path kept a refcount for an undelivered notification PERMANENTLY (the retained count absorbs the retry, so no later send ever fires `onSendFailure`/`resetDocRefs`), and the request paths skipped the teardown of a genuinely dead backend. ROOT fix at the single predicate owner serving all three call sites (`handleToolsCall`/`handleForward`/`handleDocLifecycle`): `isClientCancelErr` now requires BOTH the error identity (`errors.Is(err, context.Canceled/DeadlineExceeded)`) AND client attribution (`ctx.Err() != nil` on the client's own ctx — a context-shaped error with the client live belongs to the ceiling/probation predicates). The SendRPC invariant this rests on (verified in `backend_lifecycle.go`): SendRPC returns a BARE `ctx.Err()` ONLY from its post-write select — i.e. only after `writeStdin` returned nil, and per the io.Writer contract a nil write error means the FULL line was accepted by the backend stdin — while every pre-/mid-write failure wraps a NON-context io/marshal error (`write stdin: %w`; `writeStdin` takes no ctx, so a context error can never hide inside it). So context-shaped ⇔ delivered; io-shaped ⇔ not delivered, regardless of ambient ctx state. (The old comment's fear — "SendRequest wraps context.Canceled where errors.Is would miss it" — was false for the actual error surface.) `procExited` decision (point 3): INCLUDED in `BackendAlive`, reversing r2 — with identity fixed, the remaining composed case is a GENUINE post-write ctx error during the drain window (child OS-dead, pipes draining for ≤ `pipeDrainTimeout`): delivered-to-nowhere. The probe serves the KEEP decision, and an OS-dead child can never honor the notification, so the probe now answers "is the process OS-alive"; `procExited` is the same close-only, closed-exactly-once watcher channel (Phase 1), identical race-correctness. Request-path audit (point 4): `isColdHoldCeilingDeadline` and `isProbationDeadline` were ALREADY identity-anchored (both require `errors.Is(err, DeadlineExceeded)`), so the non-retryable "delivered" 500 was never reachable by an io error; the only confused predicate was `isClientCancelErr`, fixed once — the request-path behavior delta is that a non-context send failure under a canceled client ctx now tears down (evicting the dead endpoint immediately) instead of skipping teardown. Regressions: `TestLazyProxy_DocLifecycle_BrokenPipeUnderCanceledCtx_RollsBackAndTearsDown` (the bot's exact scenario; fails pre-fix with a 202 for an undelivered notification) and `TestLazyProxy_ToolsCall_BrokenPipeUnderCanceledCtx_TearsDownGenericError` (fails pre-fix with stopCount=0); `TestLazyProxy_ClientCancelDoesNotTearDownBackend` (genuine `context.Canceled` identity → still no teardown) and the r2 pair pass unchanged.

Both were low-severity, self-healing/bounded, and pre-dated the P2c work.
