## g9-architecture

**Verdict:** Architecture is largely healthy with strong single-owner discipline in the load-bearing seams (stop-intent write path, port bands, process-identity, client registry, restart dispatch, GUI-always-through-API); the residual debt is concentrated in daemon-state-string classification, which is fanned across four hand-maintained mappers with a confirmed silent passthrough dependency, plus a client config-path that is encoded twice per adapter with no reconcile test.


### [P1 — ✅ FIXED 4133dd1] Daemon-state classification is fanned across 4 hand-maintained mappers; the IPC client's normalizer silently relies on default-passthrough for the terminal 'Quarantined' state
- **File:** `internal/api/supervisor_ipc_status_client.go:301-312 (normalizeSupervisorIPCStatusState); internal/cli/supervise_status.go:204-219 (supervisorStatusGUIState); internal/api/health.go:1056-1075 (normalizeDaemonState); internal/cli/supervisor_runtime_tracker.go:519-544`
- **Detail:** One conceptual decision вЂ” 'what health group is this daemon in' вЂ” has four independent owners, each a separate switch statement kept aligned by hand: (1) tracker constants idle/running/backoff/quarantine; (2) supervisorStatusGUIState (producer) maps those to Running/Stopped/Restarting/Quarantined onto the IPC wire; (3) normalizeSupervisorIPCStatusState (IPC client, the PRODUCTION /api/status path) re-normalizes the already-normalized producer output; (4) normalizeDaemonState (health.go, the /api/health DaemonRow path). Verified data flow: tracker emits 'quarantine' -> supervisorStatusGUIState returns 'Quarantined' -> normalizeSupervisorIPCStatusState('Quarantined') has NO quarantine case so it hits `default: return state` and passes 'Quarantined' through verbatim -> frontend stateShape('Quarantined') (internal/gui/frontend/src/lib/status.ts:43-45) maps it to the failure cross. It works ONLY because the verbatim default-passthrough happens to preserve the exact casing the frontend expects. normalizeSupervisorIPCStatusState claims to be the wire-state normalizer but silently depends on passthrough for a KNOWN terminal-failure state it does not enumerate. If anyone later tightens that normalizer to a closed enum (the exact change normalizeDaemonState already received вЂ” see the PR #281 P2 note at health.go:1037-1055 that had to RE-ADD Quarantined->failed after an unknown->failed/unknown collapse), Quarantined daemons would silently render as benign-idle in the Dashboard вЂ” a fail-loud->fail-quiet regression on the operator's single most important failure signal. The IPC-client normalizer is the unfixed sibling of a trap already fixed once in normalizeDaemonState.
- **Fix:** Establish ONE canonical state vocabulary + ONE classifier in internal/api (the package both cli producer and gui consumer import). Define typed DaemonState constants and a single classifier that both the supervisor producer (supervise_status.go) and the IPC decode (supervisor_ipc_status_client.go) call, replacing the three Go switch statements. At minimum, immediately close the latent bug: add explicit `case "quarantine", "quarantined": return "Quarantined"` to normalizeSupervisorIPCStatusState so the terminal state is enumerated, not passthrough-dependent, plus a table-driven test asserting every tracker constant round-trips through producer->IPC-client->frontend-expected casing. Consolidation target: a new internal/api/daemon_state.go owning the enum + the one classifier.

### [P2] Client config path is encoded twice per client (registry descriptor vs adapter ConfigPath()); COPILOT_HOME env logic is re-implemented inline and no test reconciles descriptor-vs-adapter
- **File:** `internal/clients/clients.go:632-853 (clientDescriptor.configPath field + ConfigPathForName); internal/clients/copilot_cli.go:50-76 (defaultCopilotCLIConfigPath); internal/api/scan_registry_drift_test.go:117-135`
- **Detail:** clientRegistry() carries a per-client `configPath func(home string) string` field whose own doc-comments repeatedly say 'Mirrors the adapter's own ConfigPath() derivation' (clients.go:641-642, 680-681, 690-728) вЂ” the path for all 46 clients is declared TWICE: once in the registry descriptor (scan/install-target resolution via ConfigPathForName) and once inside each adapter's ConfigPath() (the actual write surface during install). For copilot-cli the COPILOT_HOME-vs-~/.copilot env decision is fully re-implemented inline at clients.go:714-719, duplicating defaultCopilotCLIConfigPath at copilot_cli.go:57-76 вЂ” two copies of the same env-resolution logic, additionally sourcing `home` differently (descriptor receives os.UserHomeDir() from ConfigPathForName; adapter calls os.UserHomeDir() itself). The existing guard TestDefaultScanConfigPaths_CoversEverySupportedClient (scan_registry_drift_test.go:117) asserts DefaultScanConfigPaths == ConfigPathForName, but BOTH derive from the SAME registry configPath field, so it cannot catch a descriptor-vs-adapter divergence. If a future adapter ConfigPath() change is not mirrored into the descriptor, SCAN reads a different file than INSTALL writes (a registration that looks successful but is invisible to scan/re-migrate) вЂ” exactly the В§9.2 drift class the registry was created to eliminate, moved one layer down.
- **Fix:** Make the adapter the single owner: have clientDescriptor drop the configPath closure and have ConfigPathForName resolve through the constructed adapter's ConfigPath() (build via the descriptor factory, call c.ConfigPath()), mirroring how IsRelayStdio already delegates to the adapter (clients.go:901-907). Where a factory needs ConfigPathForName at construction (the init-cycle note at clients.go:657-661), keep a single shared path helper that BOTH the adapter and the resolver call, never two literals. Add a reconcile test iterating AllClients() asserting ConfigPathForName(name) == adapter.ConfigPath() for every client. Consolidation target: adapter ConfigPath() as the sole path owner.

### [P2] /api/status and /api/health report the same cached daemon rows through two different state-enum normalizers with no consistency guard
- **File:** `internal/api/health.go:472-487 (DaemonRow projection via normalizeDaemonState) and internal/api/health.go:290-311 (DaemonStatusSnapshot returns rows with State from normalizeSupervisorIPCStatusState); internal/api/supervisor_ipc_status_client.go:249`
- **Detail:** Both endpoints are projections of the SAME healthCache.daemonStatuses rows (the G2 'one fetch, two surfaces' design at health.go:488-499) вЂ” which is good. But the two surfaces apply DIFFERENT classifiers to those rows: /api/status (DaemonStatusSnapshot вЂ” the Dashboard's primary feed, confirmed via internal/gui/server.go:59-89) carries the rich Title-case State from normalizeSupervisorIPCStatusState ('Quarantined','Restarting'), while /api/health daemons.items applies normalizeDaemonState to the SAME row, yielding the lowercase wire enum where Quarantined->'failed', Restarting->'starting'. For one identical daemon the two endpoints emit different state vocabularies (e.g. 'Quarantined' vs 'failed'). The two wire shapes are intentional, but there is no single classifier asserting the two enums are consistent mappings of each other, so a change to one normalizer can silently desynchronize the two operator-facing surfaces (a monitor on /api/health state=='failed' and a GUI on /api/status state=='Quarantined' can disagree). This compounds finding #1.
- **Fix:** Drive BOTH wire enums from the single canonical classifier proposed in finding #1: define the lowercase /api/health enum as a pure projection of the canonical DaemonState (one function CanonicalState->HealthWireState) and the Title-case /api/status enum as another projection of the same canonical state, so the two are provably consistent and a vocabulary change updates one owner. Add a test asserting that for every canonical state, the health-wire and status-wire projections agree on the health GROUP. Consolidation target: the same internal/api/daemon_state.go owner.

### [P3] Hardened state-file write pipeline (WriteStateFileAtomic) exists but several hand-rolled atomic-temp+rename writers in the same package bypass it
- **File:** `internal/api/state_file_helper.go:70-114 (canonical WriteStateFileAtomic); bypassed by internal/api/workspace_registry.go:159-189, internal/api/settings.go:143-163, internal/api/dismiss.go:140, internal/api/client_install_prefs.go:165-185, internal/api/daemon_intent.go:981-1030 (writeIntentLocked, retired/test-only)`
- **Detail:** WriteStateFileAtomic / WriteStateFileBytesAtomic is the documented single owner for hardened state-file writes (per-file flock + handle-bound DACL + parent-dir relax-gate + audit event); its docstring (state_file_helper.go:27-35) names the FILE_DELETE_CHILD TOCTOU swap on supervisor-intent.json as the threat it closes. Yet several state-file writers in the same package hand-roll their own os.OpenFile(0600)+Chmod+os.Rename without that pipeline (workspaces.yaml via workspace_registry.go, gui-preferences via settings.go, dismissed.json via dismiss.go, client-install-prefs). The daemon_intent.go writer is the most security-relevant bypass but is fine in practice: WriteDaemonIntent has ZERO production write callers post-Phase-E2 (verified вЂ” live stops route through stop_intent_subblock.go::WriteStopIntent; daemon_intent.go:760-776 documents it as test/migration-boundary-only), so daemon-intent.json is the known retired dual-store correctly out of the live write path. The residual smell: the remaining lower-sensitivity state files each re-implement the atomic-write mechanism, so any future hardening (symlink-refusal, parent-gate) must be applied N times instead of once.
- **Fix:** Route the remaining state-file writers (workspace_registry.go, settings.go, dismiss.go, client_install_prefs.go) through WriteStateFileBytesAtomic / WriteStateFileAtomic so the atomic-write + DACL + parent-gate mechanism has one maintained implementation; leave manifest.go (operator-edited YAML with its own external-mutation detection) and the retired daemon_intent.go writer as documented exceptions. Do NOT touch daemon_intent.go writeIntentLocked вЂ” it is correctly retired per Phase E and editing it only churns the migration-fidelity test seam. Consolidation target: WriteStateFileBytesAtomic as the sole atomic state-file write mechanism.

## g16-security-surface

**Verdict:** Strong posture: every mutating/destructive GUI route is POST/PUT/DELETE-method-guarded AND wrapped in requireSameOrigin (plus the global requireAllowedHost DNS-rebind gate); no mutating route bypasses CSRF. Path-traversal is well-defended on the two filesystem-path endpoints (backups restore/delete pins source+dest to the client config dir + backup-naming prefix + Lstat regular-file refusal; logs/manifest names are regex/slash-gated; LSP auto-register is trusted-root gated). Destructive defaults are safe-polarity (cleanup Apply not DryRun; secrets used-by 409 backstop; backups -original sentinel). The only real gaps are NON-uniform error redaction вЂ” there is no central redactErrorDetail helper, so several handlers leak raw err.Error() (filesystem paths from os.PathError) into the GUI response while the manifest/marketplace handlers correctly sanitize вЂ” and a couple of read-only path-echo leaks. No P0/P1.


### [P2] No central error-redaction helper; many handlers leak raw err.Error() (os.PathError filesystem paths) to the GUI response while only manifest/marketplace sanitize
- **File:** `internal/gui/scan.go:49-56 (writeAPIError) + internal/gui/daemons.go:68-80,116-135 + internal/gui/demigrate.go:40 + internal/gui/migrate.go:43 + internal/gui/daemon_env.go:121,176,204,219,288,300 + internal/gui/supervisor_restart.go:84`
- **Detail:** The prompt's check 4 asks whether redactErrorDetail covers EVERY endpoint. It does not exist. writeAPIError (scan.go:49) unconditionally writes err.Error() into the JSON 'error' field. The manifest handlers (manifest.go:138,177,210,230,257,296) and marketplace-install (marketplace_install.go:119,151,191,204,212,217) DELIBERATELY log-server-side + return a stable opaque string precisely because their errors wrap *os.PathError that embeds the absolute manifest/home dir. But the SAME class of error reaches the client raw on other endpoints: /api/demigrate (demigrate.go:40 writeAPIError(w, err,...) where err is 'manifest load failed' carrying a path), /api/migrate (migrate.go:43), the daemon-env family (daemon_env.go:121 'read supervisor-intent.json: <path>', :176 'write overlay: <path>', :204/:219 overlay load), and the weekly-* handlers (daemons.go:71,79,119,134 surface registry_path/registry_load detail with err.Error()). On Windows these absolute paths embed the operator's home directory (C:\Users\<name>\...) and on corp hosts can reveal the AD username вЂ” exactly the leak the manifest handlers were hardened against. It is a same-origin local UI so exposure is bounded, but it is an inconsistent, regression-prone posture: a future contributor copying the demigrate pattern reintroduces the leak the manifest pattern fixes.
- **Fix:** Introduce one canonical helper (e.g. writeAPIErrorRedacted(w, err, status, code, logCtx) in scan.go next to writeAPIError) that log.Printf's the raw err server-side and emits a stable code-keyed message, mirroring the manifest.go pattern. Consolidation target: route demigrate.go:40, migrate.go:43, daemon_env.go's STATE/OVERLAY 500s, and daemons.go's registry/membership 500 details through it. Keep the deliberate client-facing strings (hash-mismatch, validation 'invalid value', generator BAD_ENTRY) as-is вЂ” those are intentional signals, not path leaks.

### [P3] /api/path/validate echoes the raw os.Stat error string (which includes the supplied path) for non-NotExist failures
- **File:** `internal/gui/path_validate.go:120`
- **Detail:** On a stat failure that is not os.IsNotExist (permission denied, name-too-long), the handler sets resp.Error = err.Error() and returns it in the 200 body. The comment acknowledges 'os.Stat already includes the path in its error string.' This is a same-origin GET driven by the operator's own typed path, so the leaked path is the operator's own input вЂ” not internal state вЂ” and the risk is genuinely low. Flagging only for completeness against check 4: it is the one read endpoint that reflects a raw OS error string back rather than a code-keyed message.
- **Fix:** Low priority. If tightened, return a stable reason token (e.g. 'permission_denied' / 'stat_failed') instead of err.Error(), keeping resp.Path (already the caller's own input) for the inline UI. Not worth a dedicated change unless the redaction helper from the P2 finding is added вЂ” then route this through it too.

### [P3] Backups restore writes the safety-snapshot path back to the client and returns it; restore SOURCE validation is correct but the response surfaces absolute paths
- **File:** `internal/gui/backups_actions.go:217-221 (restore response) and :256-259 (delete response)`
- **Detail:** Confirming the prompt's specific check 3 question: backups RESTORE *does* validate the SOURCE backup path вЂ” validateBackupTarget (backups_actions.go:132-182) pins gotDir==expectedDir (client config dir) AND filename prefix '<liveBase>.bak-mcp-local-hub-' AND Lstat-regular-file BEFORE Restore runs, so the source cannot traverse out or follow a symlink. Noting it so the redaction sweep does not over-correct and strip these legitimate operator-facing path echoes.
- **Fix:** No change required. Explicitly EXEMPT these path echoes from any redaction helper added for the P2 finding вЂ” they are intentional confirmation artifacts (the operator needs the snapshot path to undo a wrong restore), not internal-state leaks.
