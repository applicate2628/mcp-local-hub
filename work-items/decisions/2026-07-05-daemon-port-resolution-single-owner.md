# Daemon port/deadline resolution has a single lazy owner

- **status:** accepted
- **filed:** 2026-07-05
- **accepted:** 2026-07-05 — promoted `proposed → accepted` on the strength of an independent `$architecture-reviewer` verified finding (a §4a regression on the serena-proxy pool population) that this decision now incorporates; see `## Correction (2026-07-05)`.
- **context:** `work-items/active/2026-07-05-unify-port-resolution-owner/` — the supervisor answers "what port does daemon X use" via TWO owners (persisted `SupervisorDaemon.Port` + the manifest read by the status path), so a `Port=0` legacy descriptor structurally disables the liveness bind-check, P1b deadline, P2a squatter reap, and `mcphub daemon recover`. F5 (`BackfillIntentDaemonPorts`) is a write-convergence that warms the cache, now accreting special-cases (`Port>0||RuntimeSpec`, `server=="serena"`).
- **design:** `work-items/active/2026-07-05-unify-port-resolution-owner/design.md`
- **gate:** promoted `proposed → accepted` early on the `$architecture-reviewer`'s verified §4a-regression finding (`## Correction`); a further `$architecture-reviewer` gate on the implementing PR maps the design §10 claims 1:1 to findings. The seam/blast-radius is `$architect`-owned (design §6), consumed by `$planner` + implementers.

## Decision

Introduce ONE pure, stateless resolver `api.EffectiveDaemonPort(d) (port, ok)` + `api.EffectiveStartupBindDeadlineSeconds(d) int` (with a per-pass memoized `NewDaemonPortResolver` for hot loops) in `internal/api/supervisor_port_owner.go`. It resolves `descriptor.Port when >0, else the manifest-declared port for the descriptor's resolved (server,daemon) identity`; the deadline resolves `explicit field > manifest daemon-deadline > server-identity default` (server-identity default = 120s for `serena`, else 60s — see the deadline paragraph below). Every port-**protection decision** (liveness sweep, P1b deadline, squatter classifier, recover CLI, startup running-scan) calls the owner instead of reading `d.Port`/`d.StartupBindDeadlineSeconds` raw. It MUST be a pure function over `(SupervisorDaemon, embedded manifest)` — not an in-memory supervisor cache — because `mcphub daemon recover` runs outside the supervisor process and must resolve the identical answer.

`SupervisorDaemon.Port` STAYS a persisted field, authored ONLY by the authoritative writers (install fan-out, serena/LSP builders). It is NOT made derived-only: it is the spawn contract (`daemon_serena.go:255-256`), the sole source for runtime_spec rows (no manifest port), and a cache-vs-cache input to reconcile drift-detection. What changes is ownership of the DECISION, not the field.

The 120s serena first-bind deadline resolves via ONE rule keyed on **server identity**: `EffectiveStartupBindDeadlineSeconds` returns `SerenaStartupBindDeadlineSeconds` (=120) when the descriptor's **resolved** server identity (`descriptorServerDaemon(d)`) equals `api.SerenaServerName` and it carries no explicit `StartupBindDeadlineSeconds>0`, else the 60s default (precedence: explicit field > manifest daemon-deadline > server-identity default). The `120` and `60` are single-owner named constants in the owner package (`internal/api/supervisor_port_owner.go`), referenced only by the resolver; the `isSerenaProxyDescriptor` argv-shape arm is deleted from `supervisorStartupBindDeadline`. This gives 120s to **both** serena on-disk shapes — legacy-unified (`Daemon` `unified`) AND the serena-proxy dynamic-pool rows (`Daemon` = per-workspace hash) — with no code special-case, no argv-shape branch, and no manifest edit. It is the same identity predicate F5 already used for its serena skip (`intent_port_backfill.go:222 if server == SerenaServerName`).

`BackfillIntentDaemonPorts` (F5) is DELETED in full once the decision consumers are migrated — it is a cache-warmer, structurally unnecessary because every consumer (incl. the out-of-process recover CLI) can reach the pure owner. Both F5 special-cases go with it.

## Rejected alternatives

- **Persist-once (keep F5 + owner as defense-in-depth):** keeps the two-owner duplication and F5's special-cases; treats the cold-cache symptom, not the two-owner cause.
- **`Port` derived-only:** breaks the spawn contract + runtime_spec rows (no manifest source) and forces lazy-resolve into ~40 non-decision read sites + phantom-drifts reconcile; blast radius disproportionate.
- **Deadline via a manifest edit keyed on the `unified` daemon (§4a — originally chosen, now REJECTED):** declaring `startup_bind_deadline_seconds: 120` on the serena manifest's `unified` daemon covers legacy-unified serena but **misses the serena-proxy dynamic-pool rows**, whose `Daemon` field is a per-workspace hash (`supervisor_intent_build.go:247-250,:276`), so the manifest daemon lookup fails and — with the `isSerenaProxyDescriptor` arm deleted — those rows fall to 60s and re-enter the `daemon-bind-timeout` cycle 4a exists to prevent. It also re-introduces a second source of the `120` (manifest vs. code). Superseded by the server-identity rule above (the reviewer-recommended §4b). The original "§4b re-homes 120 as a second owner" objection is void once the value has a single named home in the owner package (there is no competing manifest source under §4b).

## Blast radius

New `internal/api/supervisor_port_owner.go` (hosts the port + deadline resolvers and the sole `120`/`60` deadline constants); edits to `supervise_liveness.go` (deadline delegates to the owner; drop the now-unused `supervisorSerenaStartupBindDeadline` const), `supervise_status.go`, `supervise_squatter.go`, `daemon_recover.go`, `supervise.go`, `migrate.go`; delete `internal/api/intent_port_backfill.go(+_test)`. **No manifest file is edited** (§4a dropped). No on-disk schema change; no migration; byte-symmetric rollback. Behavioral change confined to Port=0-legacy protection activation + the serena first-bind deadline (both the legacy-unified and the serena-proxy dynamic-pool rows resolve 120s). Adjacent (not admitted): `stop_force_supervisor.go` shares the Port=0 kill-by-port gap.

## Correction (2026-07-05) — §4a → §4b, and the promotion basis

The design's §4 originally chose **§4a** (declare `startup_bind_deadline_seconds: 120` on `servers/serena/manifest.yaml`'s `unified` daemon + delete the argv-keyed `isSerenaProxyDescriptor` deadline arm). An independent `$architecture-reviewer` found — and this pass re-verified against the code — that §4a is a **regression on the serena-proxy dynamic-pool population**:

- A serena-proxy pool row's `Daemon` field is `daemonKey = ws.WorkspaceKey`, a **per-workspace hash**, not `unified` (`internal/api/supervisor_intent_build.go:247-250`, stamped `:276`); its `Server` field is `serena` (`:275`).
- `servers/serena/manifest.yaml` declares only the `unified` daemon (`:60-64`), so a manifest lookup on the workspace-hash daemon name **misses** and the resolver falls to its default.
- The field contract documents `0 = ... 120s for serena-proxy descriptors` as a supported on-disk state (`internal/api/supervisor_intent.go:73`); the `isSerenaProxyDescriptor` arm that rescued those rows lives at `internal/cli/supervise_liveness.go:520`.
- Real reachable population: serena-proxy fan-out shipped #234 (2026-05-27); the explicit `StartupBindDeadlineSeconds:120` stamp (`supervisor_intent_build.go:289`) and the argv arm both shipped #488 (2026-07-02). Hosts that migrated serena to the dynamic pool in that ~5-week window carry serena-proxy rows with explicit deadline `0`; reconcile drift-compare excludes the deadline field and a plain restart does not rebuild serena rows, so the `0` persists. Under §4a with the arm deleted, those rows resolve **60s** and re-enter the `daemon-bind-timeout` restart cycle (serena `uvx`+SolidLSP cold start ~46s+).

**Correction:** adopt the reviewer-recommended **§4b** — one rule keyed on **resolved server identity** (`== api.SerenaServerName`), covering both the `unified` and the workspace-hash proxy shapes, with the `120`/`60` values homed as single named constants in the owner package (`internal/api/supervisor_port_owner.go`). The original "§4b re-homes 120 as a second owner" objection is void because there is no competing manifest source of the value under §4b. The §4a manifest edit is **dropped** so the resolver is the sole authority; no manifest file is modified. Design detail: `design.md` §4 (§4.1 regression, §4.2 chosen rule, §4.3 drop-the-manifest-edit decision).

This is the promotion basis: the acceptance above is the `$architecture-reviewer` gate call enacted — the reviewer's verified finding is the evidence that this decision (now carrying the correction) is sound.

## Commission review note (2026-07-05) — legacy-unified serena bind-check activation (fable-F4)

The fable-5 commission lane flagged a deliberate-behavior change worth recording: F5 NEVER backfilled a serena descriptor (its `server=="serena"` skip), and the old `daemon recover` hint told the operator to `mcphub migrate serena legacy-to-dynamic-pool` rather than protect it. Deleting F5 + owning the deadline by server identity means a **legacy-unified serena row with Port=0** (`server=serena, daemon=unified`, no runtime_spec) now RESOLVES the manifest port `9121` and enters the liveness bind-check with a 120s first-bind deadline (a real improvement over the old argv-arm's 60s for this shape).

**Accepted tail-risk:** on a host with a genuinely cold `uvx` cache, serena's first bind (git-fetch of the pinned serena commit + SolidLSP init) can exceed 120s → `daemon-bind-timeout` → restart; a persistently-cold host could reach the 10-fail/30-min quarantine, where master left this row untouched. This is a NARROW population (Port=0 AND daemon=unified — a legacy state that should already be on the dynamic pool) and the quarantine is a **correct signal that the row needs the dynamic-pool migration** — the same remediation the deleted recover hint named. Accepted as-is to preserve single-owner (no serena special-case in the sweep). If field reports show false quarantines of otherwise-healthy legacy serena, the follow-up is a larger legacy-serena identity deadline in the owner (not a sweep special-case).
