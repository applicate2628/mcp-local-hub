Независимый узкий PR оценивается по собственному контракту; он не обязан ждать завершения плана перехода на Rust или всей научной интеграции HFSS. Основания: замечания [§4](#findings), матрица [§5](#prs), сохранённые результаты проверок [§7](#qualification).

### 3.1. Общий контракт завершения

Нужно передавать раздельно: **исход операции**, **факт применённого эффекта**, **результат освобождения**, **сохранённые материалы восстановления**. Код выхода 0 у запускающей программы не доказывает готовность всех получателей результата; отмена наблюдения не доказывает завершение управляемого процесса; закрытый Job не исправляет функциональный FAIL; хеш не создаёт полномочия управления. Эти различия используются в критериях плана и уже представлены существующими типизированными владельцами и протоколами результатов. Новая универсальная система подтверждений для этого не нужна.

### WL-01. Устаревшая запись владельца может привести к преждевременному завершению нового Supervisor — P1

**Владелец:** lifecycle-runtime — компонент GUI, создающий Supervisor; application-services предоставляет аутентифицированный IPC и наблюдение за блокировкой.

**Контракт:** Диагностическая запись о поколении не даёт права считать новый дочерний процесс проигравшим конкуренту. Управление привязано к исходному процессу; действующего конкурента нужно подтвердить идентичностью процесса средствами ОС и через IPC.

**Условие:** После аварии остаётся старый supervisor.lock.owner.json. Новый дочерний процесс уже создан, но родитель читает вспомогательный файл раньше публикации новой записи владельца. Блокировка flock уже свободна либо захвачена новым дочерним процессом.

**Последствие:** owner != original немедленно трактуется как смена поколения; GUI сначала вызывает settleUnboundCreator (Kill и исходный Wait), лишь затем проверяет предполагаемого конкурента. Живой новый Supervisor завершается из-за устаревших данных, и запуск GUI не достигает готовности.

**Доказательство и вывод трассировки:** Порядок вызовов установлен по закреплённой версии исходников. В инциденте npm-native от 2026-10-18 с устаревшим путём присутствуют generation-changed и bind-then-exit; связь того события именно с описанным порядком исполнения не доказана.

**Область:** GitHub master; файлы supervisor_launch.go и gui_supervisor_owner.go имеют те же Git blob ID в #628/#659/#660/#671.

**Уже выполнено / состояние веток:** Ни один из проверенных текущих PR не меняет два причинных файла; это подтверждено совпадением Git blob ID. Работы #671 над готовностью и агрегированием не доказывают исправление обычного пути создания Supervisor из GUI.

**Минимальная корректировка:** Различить устаревшую или ещё не готовую запись владельца и подтверждённого живого конкурента. Пока исходный процесс жив и остаётся под своим владельцем, продолжать ограниченное ожидание. Завершать созданный процесс как проигравший только после подтверждения конкурента, выхода самого процесса либо окончательного решения его владельца.

**Приёмка:**

- Подложить устаревшую запись владельца и приостановить дочерний процесс до публикации новой: процесс должен стать готовым без преждевременного Kill.
- При живом конкуренте завершить только тот проигравший процесс, который был создан этой операцией; конкурента подтвердить средствами ОС и через IPC.
- При отмене, истечении срока и выходе процесса сохранить единственного владельца исходного Wait и все причины завершения; повторное открытие по PID не даёт права на остановку.

**Граница доказанного:** Возможный порядок исполнения установлен по исходникам; продукт и тесты в этом аудите не запускались.

### WL-04. Force-stop сохраняет разрыв между проверкой PID и остановкой процесса по тому же числу — P1

**Владелец:** application-services — получатель политики принудительной остановки; lifecycle-runtime — исходный владелец процесса и объекта Job.

**Контракт:** Снимок образа процесса, SID и PID даёт сведения о процессе, но не право действовать от имени его создателя. Операция остановки должна обращаться к исходному процессу или Job через удерживаемую владельцем ссылку.

**Условие:** После обнаружения через IPC или порт и проверки образа/SID исходный процесс завершился, а все удерживавшие его дескрипторы закрыты. Его PID переиспользован до taskkill /PID /F /T. Другой вариант: уже исходное обнаружение не содержит идентичности поколения, созданного владельцем.

**Последствие:** taskkill выбирает процесс и дерево по текущему числовому PID. Возможна остановка другого поколения или постороннего процесса; фактической такой остановки в этом аудите не наблюдалось.

**Доказательство и вывод трассировки:** Отдельные проверки не возвращают удерживаемый дескриптор с правом остановки; конечный exec.Command использует десятичный PID. Документация Microsoft PROCESS_INFORMATION допускает переиспользование идентификатора после закрытия всех дескрипторов процесса и освобождения его объекта.

**Область:** master и #659.

**Уже выполнено / состояние веток:** #659 исправляет классификацию неизвестного состояния порта и сведения после действия. Дескриптор проверки из #628 служит наблюдению и закрывается до возврата. #625/#644/#631 удерживают исходных нативных владельцев в экспериментах; их подключение как производственной замены не выполнено.

**Минимальная корректировка:** Выполнять аутентифицированную операцию Supervisor через действующего исходного владельца дочернего процесса или Job. Сохранить принудительный перезапуск и адресацию исходного поколения. Если владелец недоступен, явно сообщать о неподдерживаемой операции или неизвестном результате; обнаружение процесса само по себе не даёт права на остановку.

**Приёмка:**

- Детерминированно заменить поколение между наблюдением и действием: новый процесс остаётся жив, допустимая цель — только исходный.
- Принудительная остановка сохраняет Desired=running и возможность перезапуска наблюдателем завершения; API и Supervisor не выполняют две остановки одной цели.
- Неизвестное состояние до действия запрещает его выполнение. Неизвестный исход после действия сообщается отдельно от уже выполненного действия; выход исходного процесса и завершение потомков Job подтверждаются раздельно.

**Граница доказанного:** Порядок, допускающий гонку, установлен по исходникам; реальная остановка процессов не выполнялась.

**Источники:** [`b74b15b7d8:internal/api/install.go`](https://github.com/applicate2628/mcp-local-hub/blob/b74b15b7d85516cc75779b09484c0f7f24908f15/internal/api/install.go#L3239-L3291); [`b74b15b7d8:internal/api/install.go`](https://github.com/applicate2628/mcp-local-hub/blob/b74b15b7d85516cc75779b09484c0f7f24908f15/internal/api/install.go#L4905-L4966); [`a3568dfe34:internal/api/stop_force_supervisor.go`](https://github.com/applicate2628/mcp-local-hub/blob/a3568dfe3426afaca4176d57a2310097e5214e77/internal/api/stop_force_supervisor.go#L109-L178).

### ARA-01. Изоляция состояния Sequential Thinking не включена в производственный запуск — P1

**Владелец:** поколение защищённого listener и daemon.StdioLaunchContext/IsolatedStdioSessions. Владелец манифеста и композиции выбирает политику для сервера, сохраняющего состояние.

**Контракт:** Разные клиентские MCP-сессии не должны разделять изменяемую историю рассуждений и её ветви без явно заданной общей области. Аутентификация сессии сама по себе не создаёт изолированный сервер.

**Условие:** Два зарегистрированных клиента используют sequential-thinking через обычный daemon по умолчанию. Оба привязаны к одной команде npx и одному StdioHost.

**Последствие:** Клиент B может получить историю или ветку клиента A; также возможны взаимное изменение состояния и неверное продолжение рассуждений. Исторический инцидент 18 ноября подтверждён заявкой; в этом аудите повторный запуск не выполнялся.

**Доказательство и вывод трассировки:** На GitHub master манифест задаёт global + stdio-bridge, один daemon на порту 9124 и один вариант по умолчанию для всех клиентов. cli/daemon создаёт один NewStdioHost, запускает его и публикует его HTTPHandler. Полный git grep по производственному Go-коду показывает только объявление NewIsolatedStdioSessions, без вызовов. Существующий компонент изоляции уже отвечает за выделение ресурсов, проверку роли, срок жизни и завершение. Отсутствие подключения доказано отдельно от качества самого компонента. Дополнительно проверено отсутствие производственного вызова на трёх чистых снимках Wave, перечисленных в таблице 2 и поле `wave_readback` машинного реестра. Общий Git blob манифеста: 6e327d2a398a707a38bed1d6e049bfd962d04386.

**Уже выполнено / состояние веток:** В исследованных текущих PR исправление подключения не обнаружено. Наличие компонента изоляции, исторического двухпроцессного теста или нового агрегатора без GUI в подготовленных исходниках Wave не закрывает обычный зарегистрированный маршрут. Второй нативный владелец и перенос решения на Rust не нужны. Локальные ветки содержат полезные части: ordinary-admission c384d937, чьи проверенные вспомогательные функции уже входят в #671, и guarded-manifest fence27101472. Их нужно сохранить и переиспользовать; сами по себе они не создают изолированный сервер и не закрывают рабочий маршрут двух клиентов.

**Минимальная корректировка:** В существующей композиции единственного защищённого listener подключить IsolatedStdioSessions для серверов, которым нужна изоляция, с текущей проверкой роли и поколения и бюджетом дерева процессов. Сохранить владение, отзыв доступа, завершение каждой сессии и запрет запуска на неподдерживаемой платформе. Проверять штатный маршрут, без отдельной обходной точки входа только для теста.

**Приёмка:**

- Два настоящих зарегистрированных клиента используют штатный URL; A и B получают независимые последовательности счётчика мыслей 1→2 и не видят чужих ветвей.
- Наблюдаются два исходных дерева серверных процессов под управлением их создателей; отключение A не останавливает B.

### ARA-02. Relay блокирует ответы клиента и отмену тем же допуском, который удерживает ожидающий их запрос — P1

**Владелец:** daemon.HTTPToStdioRelay.stdinPump — состояние согласования протокола, допуск запросов и управление ограниченным числом POST.

**Контракт:** После initialize сообщения MCP должны проходить в обе стороны. Необязательный Session-Id не обозначает завершение initialize. Ответы на встречные запросы сервера и отмена должны доходить, пока исходный запрос инструмента ещё открыт.

**Условие:** Вариант A: сервер успешно завершает initialize без MCP-Session-Id, затем через SSE в ответе на POST посылает sampling/createMessage или другой встречный запрос и ждёт ответа клиента. Вариант B: идентификатор сессии есть, но 64 открытых POST заняли все разрешения семафора и ожидают ответов клиента или отмены.

**Последствие:** В A stdinPump синхронно ждёт завершения первого handlePOST и не читает ответ из stdin. В B он блокируется на postSem ещё до handlePOST для управляющего сообщения. Возникает цикл ожидания; по умолчанию он заканчивается примерно через 60 секунд по сроку HTTP-запроса и отказом транспорта, без корректной доставки ответа или отмены. При заданном пользователем timeout=0 ожидание может быть неограниченным.

**Доказательство и вывод трассировки:** В #629 protocolVersion публикуется отдельно от необязательного sid, но stdinPump по-прежнему выбирает синхронный путь по пустому sid. Для пути с сессией один семафор на 64 разрешения охватывает все JSON-RPC-сообщения без различения их класса. Встречный запрос сервера пересылается в stdout до окончательного ответа; поэтому ответ клиента необходим для завершения исходного POST. Существующий тест предела блокирует уведомления и проверяет максимальное число запросов, но не возможность обмена в обе стороны.

**Уже выполнено / состояние веток:** #629 исправляет обработку отказа stdout, ограничение ответов, согласованную версию протокола и возобновление POST SSE. Описанный цикл ожидания остаётся в точной вершине e33924ac. #626 измеряет максимум 16 активных вызовов инструментов и не доказывает поведение при заполнении всех 64 мест либо при вложенных запросах.

**Минимальная корректировка:** Разделить завершение согласования протокола и наличие токена сессии. Ограничивать допуск новых рабочих запросов так, чтобы чтение входа, ответы и отмена продолжались при занятых рабочих местах. Использовать ограниченную очередь или отказ до допуска нового вызова с эффектом. Увеличение числа 64 или неограниченное создание горутин не устраняет причину цикла.

**Приёмка:**

- Детерминированный тестовый сервер без Session-Id возвращает корректный InitializeResult, посылает встречный запрос и получает подготовленный тестом ответ клиента до завершения внешнего вызова инструмента; платный вызов модели не требуется.
- Для сервера с сессией 64 ожидающих запроса не блокируют ответ на встречный запрос и notifications/cancelled; память и число рабочих горутин остаются ограниченными.
- Каждый допущенный вызов с эффектом имеет ровно одну POST-попытку; отказ или истечение срока не запускает повтор вызова с неизвестным результатом.
- Сохраняются точные JSON-RPC ID и срок каждого запроса. Ошибка вывода по-прежнему делает вывод непригодным для дальнейшего использования; собственные рабочие горутины и потоки ввода-вывода завершаются с подтверждённым результатом.

**Граница доказанного:** Дефект установлен трассировкой исходников; ни один из этих сценариев не запускался. В исследованных relay*test.go не обнаружены сценарии без сессии, sampling или elicitation; вывод ограничен проверенным набором файлов.

**Источники:** [`e33924ac97:internal/daemon/relay.go`](https://github.com/applicate2628/mcp-local-hub/blob/e33924ac97449c7cb8f103d80a39ecbb064310d3/internal/daemon/relay.go#L283-L325); [`e33924ac97:internal/daemon/relay.go`](https://github.com/applicate2628/mcp-local-hub/blob/e33924ac97449c7cb8f103d80a39ecbb064310d3/internal/daemon/relay.go#L350-L380); [`e33924ac97:internal/daemon/relay.go`](https://github.com/applicate2628/mcp-local-hub/blob/e33924ac97449c7cb8f103d80a39ecbb064310d3/internal/daemon/relay.go#L414-L435); [`e33924ac97:internal/daemon/relay_test.go`](https://github.com/applicate2628/mcp-local-hub/blob/e33924ac97449c7cb8f103d80a39ecbb064310d3/internal/daemon/relay_test.go#L376-L420).

### CP-03. Prepare отменяет рабочий контекст до получения результатов закрытия исходных writer — P1

**Владелец:** PreparedSerenaRuntimeOwner.Prepare — завершение публикации состояния в исходном контексте.

**Контракт:** Результаты окончательного закрытия получает исходный владелец ресурса. Локальная отмена после завершения работы не должна предшествовать получению этих результатов; внешняя отмена и исходный срок продолжают действовать.

**Условие:** Prepare возвращается, когда результат окончательного завершения writer, приобретённого с исходным рабочим контекстом, ещё не получен. Условие не распространяется автоматически на отдельную запись ошибки, созданную уже с контекстом очистки.

**Последствие:** Отложенные defer исполняются в обратном порядке регистрации. Поэтому cancel, зарегистрированный позже FinishPreparation, выполняется первым. Исходный request.Context writer уже отменён; completionInBound и проверка срока не могут подтвердить закрытие в рамках исходного контракта.

### ARA-03. После HTTP 404 об утрате сессии Relay продолжает использовать эту сессию — P2

**Контракт:** После HTTP 404, сообщающего об утрате сессии, клиент транспорта MCP должен начать новый initialize без прежнего Session-Id. Вызов инструмента с неизвестным результатом не повторяется. <a id="cp-07"></a>
### CP-07. Поиск uv использует PATH текущего процесса вместо выбранного окружения выполнения — P2

**Владелец:** BuildSerenaPreparationInputs — построение входов для проверенного окружения выполнения.

**Контракт:** Источник исполняемого uv должен соответствовать уже выбранному окружению выполнения. Проверка его закреплённой идентичности и версии дополняет выбор из нужного PATH, но не заменяет его.

**Условие:** PATH проверенного окружения содержит одобренный uv, однако подсказки поиска или PATH текущего процесса выбирают другой uv либо не находят нужный.

**Последствие:** Для подготовки выбирается кандидат, не соответствующий утверждённому окружению, либо выдаётся install-needed, хотя допустимый runtime есть. Последующая проверка версии и хеша сама по себе не восстанавливает правильный выбор.

**Минимальная корректировка:** Интегрировать #632 fd2d8969392a402c9826288d3d614de9f8d4ff31 во владельца входных данных. Сохранить отдельные правки #646 для предпочтения Python и #647 для Windows PATHEXT/longpaths. Не расширять общее окружение процесса и постоянную конфигурацию Git.

**Приёмка:**

- При разных uv в PATH текущего процесса и выбранного окружения используется кандидат из выбранного окружения.
- uv, доступный только через окружение текущего процесса, не засчитывается как выбранный источник. Незавершённый или неподходящий кандидат не допускается как успешный.
- Реальная подготовка на Windows с системным Python, длинными путями Git и неизменяемым выбранным окружением проходит на точном Source; исходный порядок очистки сохраняется.

**Граница доказанного:** Для известного дефекта уже существует узкий PR. Проверка хеша и версии фактического исполняемого файла присутствует; утверждения об исполнении любого непроверенного файла нет.

**Источники:** [`b74b15b7d8:internal/api/serena_prepared_inputs.go`](https://github.com/applicate2628/mcp-local-hub/blob/b74b15b7d85516cc75779b09484c0f7f24908f15/internal/api/serena_prepared_inputs.go#L102-L110); [`b74b15b7d8:internal/api/serena_prepared_inputs.go`](https://github.com/applicate2628/mcp-local-hub/blob/b74b15b7d85516cc75779b09484c0f7f24908f15/internal/api/serena_prepared_inputs.go#L139-L159); [`09dc07e01d:internal/api/serena_prepared_inputs.go`](https://github.com/applicate2628/mcp-local-hub/blob/09dc07e01d1a3236ab5f45f384e11fe2f9dfd30d/internal/api/serena_prepared_inputs.go#L139-L159).

- Эксперименты Rust остаются отдельной возможностью; их отсутствие в продукте не блокирует минимальные исправления Go.

### 8.13. Контроль размера PR и замена устаревших веток

Не объединять 32 PR в один технический мегакоммит. Сначала принять независимые изменения по зонам ответственности, затем собрать отдельный интеграционный кандидат с явным списком исходных веток и сопоставимыми картами файлов. Закрывать старый PR можно после доказанного сохранения уникальных изменений, тестов и открытых замечаний в одном преемнике. Изменение исходной или целевой версии требует пересмотра затронутых контрактов и повторения необходимых проверок; оно не отменяет историю неудачных попыток и ревью. [§5](#prs).

### 9.1. Дополнительно проверенные защитные границы

**Вход GUI из браузера.** `httpHandler` применяет проверку `Host` к общему обработчику GUI; допустимые host и port связаны с реально выбранным портом. Это выявленное решение модели доверия, а не новый подтверждённый взлом. [Выбор прямого соединения или прокси](https://github.com/applicate2628/mcp-local-hub/blob/b74b15b7d85516cc75779b09484c0f7f24908f15/internal/api/marketplace_http.go#L118-L224), [запрос и лимит тела](https://github.com/applicate2628/mcp-local-hub/blob/b74b15b7d85516cc75779b09484c0f7f24908f15/internal/api/marketplace_http.go#L333-L391), [проверка URL](https://github.com/applicate2628/mcp-local-hub/blob/b74b15b7d85516cc75779b09484c0f7f24908f15/internal/api/marketplace_safety.go#L117-L176).

## 12. Термины и сокращения

| Термин | Значение |
|---|---|
|PR, Pull Request|Запрос на включение изменений; head — точный commit рассматриваемой ветки, base — целевая ветка/исходная основа.|
|Source / Product / consumer|Source — выбранные исходные файлы и их происхождение; Product — выданный сборкой артефакт определённой роли; consumer — настоящий получатель/пользователь результата.|
|Owner / authority / observation|Owner отвечает за действие и время жизни ресурса. Authority — действительное право выполнить действие. Observation — полученные сведения; сами по себе они полномочием не являются.|
|Custody / settlement|Custody — сохранённое владение исходными ресурсами. Settlement — полученные конечные исходы исполнения, потомков и потоков; не синоним функционального успеха.|
|PID / SID / handle / Job|PID — числовой идентификатор процесса; SID — идентификатор безопасности Windows; handle — дескриптор конкретного объекта ОС; Job — объект Windows для управления группой процессов.|
|IPC / stdio / HTTP / SSE|IPC — межпроцессный обмен; stdio — стандартные потоки; HTTP — протокол запросов; SSE — поток событий сервера поверх HTTP.|
|MCP / JSON-RPC|Model Context Protocol — протокол взаимодействия с инструментами и другими возможностями сервера; JSON-RPC — формат запросов, ответов и уведомлений. Идентификатор связывает запрос с ответом; у уведомления идентификатора нет.|
|ABI / FFI / PE|ABI — двоичный интерфейс; FFI — вызовы через границу языков; PE — формат исполняемых файлов Windows, где роль файла и подсистема важны для допуска.|
|LIFO / context / deadline|LIFO — выполнение отложенных действий в обратном порядке регистрации; context переносит отмену/срок; deadline — конечный момент, который нельзя незаметно обновлять при передаче.|
|SLO / fixture / oracle|SLO — целевое качество сервиса; fixture — управляемая тестовая среда/данные; oracle — различающий критерий правильного результата.|
|PASS / FAIL / NOT_RUN / UNKNOWN|PASS — конкретная проверка прошла; FAIL — её критерий не выполнен; NOT_RUN — проверка не исполнялась; UNKNOWN — требуемый исход не доказан. Ни один ярлык не переносится автоматически на другой Source.|
|mtime / blob / SHA-256|mtime — время изменения файла; blob — объект Git с содержимым файла, имеющий собственный идентификатор; SHA-256 — криптографический хеш для сверки байтов, а не самостоятельное полномочие выполнить действие.|
|HFSS / AEDT / source-only|HFSS — программа для решения задач электромагнетизма; AEDT — среда Ansys Electronics Desktop; source-only — получение заявленных исходных сведений без утверждения о полноте физической модели или привязке к сетке сохранённого расчёта.|
|API / SDK / CLI / GUI|Application Programming Interface — программный интерфейс; Software Development Kit — набор средств разработки; Command-Line Interface — командная строка; Graphical User Interface — графический интерфейс.|
|COM|Component Object Model — компонентные интерфейсы Windows; в этом отчёте используются, в частности, для доступа к Планировщику заданий.|
|SSRF / CSRF / DNS|Server-Side Request Forgery — принуждение сервиса к нежелательному сетевому запросу; Cross-Site Request Forgery — выполнение запроса из постороннего браузерного источника; Domain Name System — система разрешения доменных имён в адреса.|
|ACL / DACL / CVE|Access Control List — список прав доступа; Discretionary Access Control List — список разрешений объекта Windows; Common Vulnerabilities and Exposures — система идентификаторов известных уязвимостей.|
|RSS / SLO|Resident Set Size — показатель резидентной памяти, конкретная метрика зависит от платформенного контракта; Service Level Objective — заданная цель качества сервиса, например срок завершения операции.|
|ABI / FFI / PE — полные названия|Application Binary Interface; Foreign Function Interface; Portable Executable. Их смысл для данного отчёта раскрыт выше.|
|IPC / HTTP / SSE — полные названия|Inter-Process Communication; Hypertext Transfer Protocol; Server-Sent Events.|
|LIFO / PID / SID / SHA — полные названия|Last In, First Out; Process Identifier; Security Identifier; Secure Hash Algorithm.|
