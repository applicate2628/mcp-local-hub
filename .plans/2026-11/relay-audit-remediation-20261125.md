# Relay: исправления ARA-02 и ARA-03

## Область

Существующий PR #629, исходная вершина `e33924ac97449c7cb8f103d80a39ecbb064310d3`.
Рабочий маршрут: `internal/cli/relay.go:newRelayCmdReal` →
`daemon.HTTPToStdioRelay.Run` → HTTP POST / GET → протокольный stdout.
Область изменяемая; CLI-опека над stdin и квалификация Product не меняются.

## Причина и исправление

| Находка | Причина | Изменение владельца |
|---|---|---|
| ARA-02: сервер без Session-Id | `stdinPump` считал отсутствие необязательного токена незавершённой инициализацией и синхронно ожидал внешний запрос, которому нужен ответ из stdin | Отдельный факт завершённой инициализации публикуется вместе с результатом переговоров после принятия полного кадра stdout; Session-Id остаётся необязательным |
| ARA-02: заполненные 64 слота | Сам читатель stdin ожидал слот, занятый запросом, которому нужен последующий ответ или отмена | Слоты принадлежат запросам. Ответы и уведомления передаются синхронным POST читателя; HTTP-контракт требует их подтверждения 202. При заполнении слотов новый запрос получает отказ **до отправки** |
| ARA-03: истёкшая сессия | POST 404 выдавал только ошибку JSON-RPC, а GET повторял старый токен | POST / GET 404 завершают текущий Run с причиной потери сессии. Все принятые работники присоединяются, следующий Run начинает переговоры без старого токена. Уже отправленные запросы не повторяются |
| Ошибка доставки ответа клиента | Общий генератор ошибок мог ответить на response как на request | Ответ на response не генерируется; отказ доставки ответа/уведомления сохраняется как ошибка транспорта |

Предел остаётся 64 параллельных **запроса** плюс один синхронный POST
ответа/уведомления. Очередь ожидающих запросов и новые фоновые читатели не
добавлены. Изменение перегрузки намеренное: прежнее блокирование ввода
заменяется адресным отказом с сообщением `message was not forwarded`.

`setSessionID` остаётся частным входом конечного владельца квалификации,
который вызывает его после проверки InitializeResult. Его существующие
тестовые пользователи также моделируют уже установленную сессию. Обычный
stdio-путь устанавливает факт инициализации независимо от наличия токена;
`takeSessionID` сбрасывает все три поля при завершении.

## Проверки

**Целевой Windows-прогон PASS**, Go 1.27.4. На неизменённом производственном коде исходной вершины оба новых сценария `stateless` и `saturated` дали ожидаемый FAIL. Затем `go test -count=1 -timeout 5m ./internal/daemon -run '(Relay|HTTPToStdio)'` завершился с exit 0 (время пакета 2,761 с). Для компиляции отрицательного контроля только в тест добавлялся sentinel; производственный код базы не менялся. Полные gates, race detector и перезапуск внешнего клиента здесь не проверены.

Все шесть исходных команд получили завершение исходного процесса, нулевое число членов Job, закрытие handles и присоединение читателей. Отдельная первая попытка остановилась на отсутствии offline dependency `go-winio`, до тестов; после выбора существующего файлового proxy зависимости распакованы в изолированный кэш. Это не дефект Relay и не скрытый успешный повтор. [Машинная запись области проверки](relay-audit-evidence-20261125.json) содержит хеши проверенных файлов.

| Проверка | Отвергаемое неправильное поведение |
|---|---|
| `TestRelayAdmissionKeepsNestedResponsesLive/stateless` | Успешный InitializeResult без Session-Id оставляет запрос синхронным; ответ на `sampling/createMessage` не доходит |
| `TestRelayAdmissionKeepsNestedResponsesLive/saturated` | 65-й запрос блокирует reader до ответа/отмены; тест удерживает ровно 64 открытых результата, требует явного отказа 65-му до HTTP и прохождения обоих управляющих сообщений |
| `TestRelaySessionExpiryStopsGETAndClearsNextInitialization` | GET 404 повторяется или следующая инициализация наследует старые заголовки |
| `TestRelaySessionExpiryTerminatesSDKConsumerWithoutReplay` | Настоящий клиент Go SDK остаётся на старом stdio-транспорте после произвольной ошибки JSON-RPC либо повторяет эффект |
| `TestRelayDoesNotRespondToFailedClientResponse` | HTTP-отказ response порождает ответ на ответ либо теряется как ошибка |

Новый тест насыщения заменяет старый `TestRelay_StdinPumpCapsConcurrentPOSTs`,
который посылал уведомления, ждал 200 мс и проверял только верхний предел.
Используются исходные каналы и `testing/synctest`, без естественных гонок
тайминга, платного sampling или внешних MCP-серверов. Тестовый владелец
закрывает принадлежащие ему stdio-каналы и присоединяет работников даже при
отрицательном исходе.

Целевые команды:

```sh
gofmt -w internal/daemon/relay.go internal/daemon/relay_test.go internal/daemon/relay_admission_contract_test.go
go test -count=1 -timeout 5m ./internal/daemon -run 'TestRelay(Admission|SessionExpiry|DoesNotRespond)'
go test -count=1 -timeout 5m ./internal/daemon -run 'TestRelay|TestReadJSONRPCLine'
```

При доступном поддерживаемом race detector повторить изменённую область с
`-race`. Эти проверки не заменяют обязательные общие gate репозитория.

## Границы результата

Это исправление переговоров и допуска для существующего initialize-era
транспорта; миграция на другой протокольный профиль не выполнялась.
Первый initialize по-прежнему последовательный. Произвольный блокирующий
заимствованный Reader/Writer требует механизма завершения от своего
владельца; CLI уже предоставляет отдельную возможность прерывания stdin.
Существующий default HTTP deadline сохранён, как и тайм-ауты переданного
пользователем HTTPClient. Автоматический перезапуск конкретного внешнего
клиента этим изменением не доказывается: ему предъявляется окончание
транспорта, а новый транспорт требует нового initialize.

## Источники и применённые навыки

1. [MCP 2025-11-25: transports](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), просмотрено 25.11.2026: Session-Id необязателен; ответы/уведомления подтверждаются 202; 404 завершает использование старой сессии; повтор сообщения с эффектом не следует из повторного подключения.
2. [MCP 2025-11-25: lifecycle](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle), просмотрено 25.11.2026: порядок инициализации и окончание stdio-транспорта.
3. `go-concurrency-lifecycle`: владелец каждого работника, предел до создания goroutine, присоединение на всех исходах, детерминированная проверка цикла ожидания.
4. `mcp-boundary`: сопоставление протокольных сообщений с HTTP-подтверждением, эффектами и фактическим SDK-потребителем; транспортная ошибка не подменяется произвольной ошибкой отдельного вызова.
5. `ponytail`: используются текущие reader, semaphore, WaitGroup, обработчик POST и механизм ошибок; отдельный транспорт, очередь и зависимости не добавлены.
