## Исправление

Продолжение #655, база `1a5a7dd04fe732df5c539860dde813c8c703586d`.
Решение о пробуждении Serena больше не принимает совпадение размера и времени
модификации файла за совпадение исходного объекта. Использован существующий
`sameRegistryFileInfo`: идентичность объекта вместе с метаданными. На Windows
исходный идентификатор фиксируется через `os.SameFile(info, info)` до чтения,
пока путь ещё указывает на наблюдённый файл; это закрывает отложенное получение
file ID внутри Go. Такой же порядок применён к снимку registry.

Замена файла обнаруживается на следующем чтении. Изменение содержимого того же
файла с намеренно сохранёнными метаданными обнаруживается при существующей
периодической сверке байтов: не позднее 32 неизменившихся обращений. Это граница
по числу обращений, без обещания мгновенной реакции или фиксированного времени.
Обновление stop-state по-прежнему проходит через исходную блокировку и свежее
чтение; нового владельца состояния или кэша не добавлено.

Независимое ревью выявило дополнительный переход: отсутствие файла → новый
пустой файл. Для отсутствия сохранённые байты равны nil, а пустые байты могли
показаться равными и обойти декодирование. Повторное использование декодированного
значения теперь требует положительно наблюдённого исходного файла. Пустой файл
вызывает ошибку разбора, инвалидирует кэш и не разрешает Wake; повторное чтение
также не скрывает ошибку. После коррекции отдельное независимое ревью этого
перехода прошло без замечаний.

## Проверка

Go 1.27.4, Windows/amd64: целевые тесты ReadSerenaUnifiedStopForTask,
WakeIdleSerenaDaemon, WriteSerenaIdleStop, RegistrySnapshotObserver и
RegistrySnapshotView прошли, exit 0, время пакета 28,106 с. Проверяются замена
при совпадающих метаданных, периодическая сверка содержимого, отсутствие →
пустой файл и отказ пробуждения. Проверки используют изолированное состояние
существующего API test harness; установленная Serena не запускалась.

[Машинная запись входов](serena-audit-evidence-20261125.json) содержит хеши пяти
проверенных файлов. Они совпадают с локальными публикуемыми исходниками после
gofmt. Все пять исходных команд получили завершение, закрытие handles и потоков,
нулевое число членов Job и присоединение читателей.

## Границы и остаточный план

Положительный результат относится к целевым регрессиям кэшей. Полная цепь
подготовки и миграции Serena, общие build/vet/default/tagged gates и итоговая
композиция ещё требуют своих проверок. Проверка кэша не заменяет приёмку
подготовленного runtime. Сохранить исправления #632→#635→#643→#649→#637 и
соседних тематических PR; новую ветку для кэшей не создавать. Слияние запрещено.

## Источники

1. `internal/api/serena_idle_shutdown.go` и его тесты — чтение stop-state и Wake.
2. `internal/api/workspace_registry_snapshot.go` и его тесты — идентичность снимка.

4. Go data consistency, Go testing and verification, Ponytail — проверка
   идентичности и содержимого, причинные регрессии, повторное использование владельца.

идентификатор файла; Job — объект Windows, удерживающий принадлежащие запуску процессы.
