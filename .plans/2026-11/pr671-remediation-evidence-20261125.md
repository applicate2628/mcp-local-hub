## Исходники и область изменений

Этот документ относится к совмещённым изменениям существующего PR **#671** над `09dc07e01d1a3236ab5f45f384e11fe2f9dfd30d`: WL-01, WL-02, CP-05 и P04. Базовый commit сам по себе не обозначает испытанный результат. [Машиночитаемая запись](pr671-remediation-evidence-20261125.json) фиксирует SHA-256 23 исходных Go-файлов, отдельного реестра Product и 18 входных npm-файлов для каждого локального npm-запуска. Все Go-файлы совпали с входами соответствующих проверок после форматирования в Windows run 3. [1]

Здесь **Product** — распространяемая Windows-программа; **fixture** — изолированный тестовый сценарий с подготовленными входами; **receipt** — запись результата и завершения исходных ресурсов. Успех fixture не равен приёмке установленного Product.

Общий **Windows run 3 — FAIL**, хотя первые три профильные проверки прошли. **Windows run 4 — PASS** для выбранного rollback-сценария. Контроллер run 3 завершился с кодом 1 за 91.416 s, контроллер run 4 — с кодом 0 за 10.645 s; в обоих receiving records отмечены получение исходного завершения и закрытие capture handles. Эти полные времена не обозначают длительность отдельного Go-теста.

Для перечисленных Windows-команд receipts фиксируют: исходный корневой процесс получен через wait, число активных процессов его Job равно нулю, native handles закрыты, исходные читатели stdout/stderr присоединены, EOF получен, файлы вывода закрыты. Это свидетельства завершения **runner**, отдельно от проверок исходных провайдеров внутри P04 fixture. Код выхода 0 или HTTP 204 сам по себе не выдаётся за закрытие дерева процессов.

В run 4 параметр `compiledWindowsProductRegistryBase64` содержит байт-в-байт `windows-product-artifacts.json`, SHA-256 `5e979049615428188bc345c1f08e1e58a10a3d29e498d41abec98cd05b91839f`. Это тот же вход и linker variable, которые использует обычная ветка `CurrentWindowsPackage` в `build.ps1`; сам `build.ps1` и установленный Product в данном испытании не запускались. [1, 3]

Оба npm-запуска выполнены командой `npm test` из роли `repository/npm`, Node `v24.22.3`, npm `11.19.1`. Сохранены исходный stdout/stderr, exit code, длительность и hashes до/после; во время каждого запуска входные файлы не изменились. Между запусками изменён **только** `npm/postinstall.test.js`: название кейса и точный список V4-файлов. Проверки `deepStrictEqual` и отсутствия собственного `bin` у platform package сохранены. Один из 12 platform-тестов выполняет `npm pack` над fixture; это не упаковка настоящего release Product. [1, 4]

## История неуспешных запусков

Две более ранние попытки зарегистрированного маршрута использовали тестовый источник `StatusContext`, тогда как `Scan()` вызывает `Status()`. Эта история сохранена как сообщение координатора и подтверждённая цепочка вызовов; их raw receipts не входят в этот компактный набор. В run 3 fixture подставляет правильный существующий источник наблюдения и проходит. Ранним неуспешным попыткам не приписывается PASS или дефект установленного Product.

Первый rollback-запуск остановился с `compiled current Windows Product registry is missing`, до выполнения выбранного сценария. Run 4 передал реестр через обычный build input. Admission не отключался, исходный FAIL не заменён успешной записью.

Прежний checkpoint сообщал `12/12` для локальных npm-проверок без сохранённого raw stdout. Повтор полного `npm test` установил точную границу: все 12 platform-кейсов прошли, но среди 19 общих кейсов остался старый список файлов в `postinstall.test.js`. Отдельно сохранены этот FAIL, разрешённая минимальная коррекция ожидания и последующий PASS 19/19. Production-генератор и manifest ради получения PASS не менялись.

JSON содержит собственные hashes локальных копий receipts и вывода. Hash исходного Windows run-3 receipt воспроизводится при CRLF-сериализации локального JSON. Для run 4 точное байтовое совпадение с hash исходного receipt из receiving record здесь не установлено; локальная сериализованная копия указана отдельно. Hash stdout, все исходные Go-входы и встроенный registry проверены напрямую. Это ограничение происхождения байтов receipt не скрывается за общим словом «проверено».

## Проверка тестового Status

Независимое чтение `SetStatusInternalDialForTest` и текущего serial fixture **не выявило подтверждённого дефекта**. Hook требует тестовый binary и ненулевую функцию, подставляет `statusInternalDialFn`, который действительно вызывается из `Scan → Status → statusReadinessSnapshot`, и восстанавливает значение через `sync.Once`. Fixture устанавливает hook до старта listener и регистрирует восстановление в `t.Cleanup`; deferred retirement исходного listener выполняется раньше. Текущие тесты этого пакета не используют `t.Parallel`. [1, 5]

Подставляется только наблюдение Supervisor. Защищённый bind, token/binding checks, маршрутизация и исходный stdio-владелец по-прежнему исполняются. Hook не является новым источником native-полномочий. Это глобальный изменяемый test seam для последовательных fixture; произвольная конкурентная подстановка или восстановление в другом порядке данной проверкой не квалифицированы.

## Что ещё не подтверждено

- Shipped manifest Sequential Thinking не включает session-local переход. Согласованные `install/reconcile/restore` и их rollback ещё не реализованы и не квалифицированы этой работой.
- Project enrollment/rebind остаются неподключёнными. Две зарегистрированные front sessions не доказывают изоляцию или восстановление проектной регистрации.
- Точный реальный провайдер Sequential Thinking, настоящий release `npm pack` и окончательный установленный Product не прошли эту приёмку.
- Для WL-01 нет утверждения о полном установленном GUI startup, всех IPC-переходах или отсутствии пустых консолей у реального Product. Для WL-02 подтверждён названный синтетический native-сценарий, а не вся матрица upgrade/rollback.
- Более широкие Go-фильтры из документа P04 и все обязательные repository gates не объявлены выполненными на основании этих focused runs. Новая композиция исходников требует своей проверки; PASS не переносится на другой head автоматически.

Документы подготовлены без новых удалённых проверок, native-тестов Windows, запусков Product, публикации или merge. Разрешённые дополнительные действия ограничились двумя локальными `npm test` и исправлением одного тестового ожидания. Исходники Go, production npm-код и package manifests в этой редакторской задаче не менялись.
