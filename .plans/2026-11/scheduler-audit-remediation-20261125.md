### NextRun: время не преобразуется в UTC

Прочитанные Root нативные примеры имели тип `System.DateTime`, `Kind=Unspecified`. Два календарных значения: `2026-11-25T00:53:00.0000000` и `2026-11-29T03:00:00.0000000`. Отдельная задача дала `1899-12-30T00:00:00.0000000` и `ToOADate()=0`. Имена, XML, пользователи и машинные пути в эту запись не перенесены. Это наблюдение установленного производителя, не запуск изменённого кода.

Передаваемое время — локальное календарное время Task Scheduler, без выдуманного суффикса UTC или смещения. Go проверяет его синтаксис. Нулевой DATE отличается от ошибки чтения; отсутствующий или повреждённый `next_run` даёт `ErrUnavailable`, а не пустую строку. Disabled остаётся Disabled даже при наличии прогноза. По документации Microsoft [1, 2] отдельно отключённые триггеры могут влиять на прогноз NextRunTime: прогноз не является подтверждением будущего исполнения или готовности процесса.

### Срок и ограниченный захват

Исходный предел одной команды — 15 секунд — сохраняется внутри срока вызывающей операции. Повторный вызов не продлевает исходный caller deadline. Старые вызовы без контекста сохраняют совместимость и получают предел каждой команды; общего срока для произвольной legacy-последовательности они не обещают.

**Новая политика ресурсов:** не более 16 MiB stdout и 64 KiB stderr сохраняется в памяти на один worker. Эти значения приняты Root как явный бюджет ограниченного захвата для данного исправления; они не взяты из Windows XML schema и не выдаются за прежний контракт. Полные ранее допустимые ответы сверх нового бюджета теперь дают видимую ошибку. Данные не обрезаются до успешного результата: чтение возвращает unavailable; неоднозначная мутация остаётся неизвестной и не повторяется. Совместимость для XML/перечислений сверх бюджета не заявлена. Новый ввод ограничен фактической конечной длиной подготовленного запроса; стандартные потоки принадлежат одному исходному исполнителю.

Компенсация исходной Task-транзакции уже была отдельной обязанностью после отмены. Для неё теперь есть **один** общий предел 15 секунд на всю последовательность чтения/восстановления/проверки; он не возобновляется для каждой задачи. Это отдельная фаза, которую следует учитывать в суммарной длительности приёмки. При `ErrMutationOutcomeUnknown` эта автоматическая Task-компенсация вообще не начинается. Нативное завершение и исходные ограничения `RunStrictlyContained` остаются отдельными проверяемыми свойствами; исходы без положительного `SettledExit` не объявляются чистыми.

### Корректировки после независимого ревью

1. **V3 Product, P1:** `RewriteCommand` может вернуть `EntrypointTaskPartialProgressError` с `ErrMutationOutcomeUnknown`. Проверки только внутри Scheduler недостаточно: `WindowsProductTxn.Run` передавал эту ошибку в `rollback`, который восстанавливал Product ещё до `Tasks.RestoreImport`. Теперь вход `rollback` сначала сохраняет причину и возвращает `ErrWindowsProductRecoveryPending`; журнал и task recovery store остаются, ни одна связанная обратная мутация не начинается. Контекст транзакции при этом может оставаться действующим.
2. **Отказ до исполнения, P2:** отмена между публичной проверкой и входом в исполнитель теперь сохраняет доказанное «не запускалось». Закрытый тип ошибки создаётся только в двух ранних отказах `runSchedulerCommand`, до допуска исходного исполнителя. Пустой `cmd.Process` после допуска и `ErrSpawnPostCreate` таким доказательством не являются и не снимают unknown.
3. **Восстановление LSP, P2:** после подтверждённого Delete отмена reconcile не отменяет уже возникшую обязанность вернуть прежнюю задачу. Обратное действие сначала проверяет unknown, затем ровно один раз связывает тот же backend с `WithTimeout(WithoutCancel(ctx), 15 s)`. Пятисекундная очистка proxy, Import и Run входят в эту фазу; Import/Run не обновляют её общий deadline. Значения исходного контекста сохраняются. Неуспешный Import по-прежнему запрещает Run.

## Проверки и границы доказательства

Добавленные проверки:

- `TestSchedulerCOMNextRunProjection`: future/none/disabled, missing/null/malformed и ложный UTC.
- `TestSchedulerCOMNextRunScript`: полный производственный PowerShell-производитель с локальными объектами вместо единственного COM connection; русская локаль, Status/List, неизвестное поле после уже корректной строки. Windows Task Scheduler не вызывается.
- `TestSchedulerBoundOperationPreservesDeadlineAndCancellation`: виртуальное время `testing/synctest`, неизменный общий deadline между командами, запрет dispatch после отмены, отсутствие изменения общего backend.
- `TestSchedulerContainedCommandRefusesCanceledAdmission`: отменённый вызов не получает дочерний процесс.
- `TestSchedulerCOMCancellationBeforeExecutorAdmissionRemainsKnown`: настоящий публичный Delete проходит через COM-обёртку; существующий seam отменяет контекст строго после её допуска и до допуска исполнителя. Итог сохраняет причину и не получает unknown. Составление schtasks-ошибки проверяется в предыдущем тесте.
- `TestSchedulerCOMPostCreateFailureRemainsUnknown`: `ErrSpawnPostCreate` сохраняет unknown и причину; отдельная строка классификационной таблицы покрывает такой же исход schtasks.
- `TestSchedulerCommandMutationOutcomePreservesExecutionCause`: известный ненулевой выход, неизвестное завершение, overflow с одновременно сохранённой execution-причиной и отмена. Использует маленькую синтетическую запись захвата; не создаёт 16 MiB фикстуру ради классификации.
- `TestEntrypointUnknownMutationDoesNotCompensate`, `TestEntrypointTransitionObservesCreatorCancellation`: запрет inverse и сохранение причины отмены исходного создателя.
- `TestSchedulerUnknownMutationDoesNotTriggerRegistrationInverse`: существующий register harness проходит три реальных пути dispatch/rollback — legacy, supervised и automatic LSP — без настоящих задач и процессов.
- `TestInstallSchedulerFactoryBindsOriginalOperationContext`: исходный context достигает существующего factory seam.
- `TestWindowsProductTxnUnknownTaskRewritePreservesWholeRecoveryDomain`: настоящий `WindowsProductTxn.Run`, действующий контекст и типичная вложенная ошибка RewriteCommand; новый Product остаётся на месте, Tasks.RestoreImport не вызывается, журнал побайтно сохранён, recovery store не отбрасывается, публикация не происходит.
- `TestEnsureLSPRegisteredCanceledReconcileRestoresLegacyTask`: настоящий сценарий регистрации удаляет legacy task, затем отменяет исходный контекст внутри reconcile. ContextBinder-fixture проверяет восстановление XML и Run через одно независимое ограниченное представление backend с сохранением значений контекста и отменой таймера после завершения.

Существующие LastResult/SID/hidden fixture-данные дополнены наблюдённым `next_run`, чтобы их основной предмет проверки сохранился при полном новом статусном контракте. Обычное восстановление после известного отказа проверяют существующие `TestRegister_PriorTaskRestoredIfCreateFails`, `TestRegister_SupervisedLiveLegacyKillFailureRunsPrearmedRestore` и `TestEnsureLSPRegistered_KillFailureRunsPrearmedLegacyRestore`.

## Фактическая проверка Root

25.11.2026: независимое повторное статическое ревью принято после исправления трёх caller-path замечаний и дополнительного дефекта происхождения no-dispatch evidence. Проверяется только внешний закрытый тип ошибки текущего вызова: прежняя ошибка, попавшая через `context.Cause`, не снимает unknown у уже начавшегося другого вызова. Настоящий COM wrapper сохраняет это внешнее свидетельство до классификации. `TestSchedulerForeignNoDispatchCauseCannotDowngradeCurrentMutation` различает оба случая; модельные сведения о post-create/timeout не названы настоящим scheduler mutation.

Пакет Scheduler после этой тестовой правки не перезапускался: все его входные файлы и все production-файлы побайтно прежние; изменился только API regression. Эти результаты не означают выполнения общих gates или приёмки установленного Product.

## Термины и сокращения

COM — Component Object Model, нативный интерфейс Windows; DATE/OLE DATE — нативное календарное представление времени; SID — Security Identifier; XML — язык документа задачи; LSP — Language Server Protocol; PR — запрос на включение изменений; MiB/KiB — 2²⁰/2¹⁰ байт; deadline — крайний срок операции; inverse/compensation — обратное действие восстановления; unknown — отсутствие подтверждённого результата; Job — исходный объект владения группой процессов Windows.
